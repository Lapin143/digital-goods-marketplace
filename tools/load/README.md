# Нагрузка: ориентир NFT-1.0 и NFT-1.1 (k6)

| Файл | Что делает |
| --- | --- |
| `seed_catalog.sql` | Засев каталога: 5000 опубликованных товаров, 100 продавцов по 50 товаров, остатки на витрине. Запускается от суперпользователя базы (триггер переходов статуса не пускает вставку сразу опубликованного товара), повторный запуск сначала удаляет прежний засев (префикс названия `[load] `) |
| `storefront.k6.js` | NFT-1.0: карточка товара, 50 запросов в секунду, порог p95 меньше 300 мс. Обходит витрину по курсору, прогревает кэш Redis (каждая карточка один раз), затем ступени 10, 25, 50 запросов в секунду по 15 секунд и устойчивая фаза `STEADY` (2 минуты, на сервере 5) |
| `search.k6.js` | NFT-1.1: 70 % поиска по части названия и 30 % фильтров (тип, платформа, регион, диапазон цены, сочетания), тот же профиль нагрузки, порог p95 меньше 500 мс. Считает долю пустых ответов (`empty_search`, `empty_filter`): если больше половины ответов пустые, `run.py` падает, потому что быстрые пустые ответы ничего не доказывают |
| `run.py` | Запускает оба сценария, печатает сводку (p95, медиана, p99, максимум, число запросов, доля ошибок) и аннотации для GitHub Actions. Пороги на раннере это ориентир: нарушение даёт предупреждение, красный код выхода только при `LOAD_STRICT=1` |

## Запуск

```bash
DGM_LOAD_PUBLIC_PER_MINUTE=1000000 DGM_LOAD_PUBLIC_BURST=1000000 make up SET=dev-sellers DEBUG=1
make load-seed          # 5000 товаров, PRODUCTS=20000 SELLERS=200 меняют объём
make load-nft           # нужен k6 в PATH (или K6=/путь/к/k6)
```

k6 ставится по инструкции [grafana.com/docs/k6](https://grafana.com/docs/k6/latest/set-up/install-k6/) (в CI скачивается релиз 1.5.0 со сверкой контрольной суммы, задание `load`). Центр сертификации стенда берётся из `secrets/tls_ca.crt` через `SSL_CERT_FILE`.

## Почему лимит шлюза поднимается

Публичная группа лимита шлюза (ADR-021) пропускает 60 запросов в минуту с одного IP. k6 идёт с одного адреса, поэтому при 50 запросах в секунду почти все ответы были бы 429, а метод NFR замеряет время ответа карточки, а не работу лимитера. На время замера лимит поднимается переменными `DGM_LOAD_PUBLIC_PER_MINUTE` и `DGM_LOAD_PUBLIC_BURST` (compose передаёт их шлюзу как `DGM_GATEWAY_LIMITS_PUBLIC_PERMINUTE` и `DGM_GATEWAY_LIMITS_PUBLIC_BURST`); без них значения остаются из `application.yml`. Стенд с поднятым лимитом для обычной работы не годится: лимитер проверяет ST-05 и проверки шлюза.

## Ограничения ориентира (Р-28)

- Раннер GitHub Actions: 4 vCPU и 16 ГБ делятся между k6 и двадцатью контейнерами стенда, поэтому время ответа хуже, чем на выделенном сервере. Результат записывается в отчёт среза как ориентир.
- Зачёт по методике ([nfr-methodology.md](../../docs/08-testing/nfr-methodology.md), раздел 3) снимается на сервере (D-1): тот же каталог, 5 минут устойчивой нагрузки (`STEADY=5m`), сверка с гистограммой Prometheus на шлюзе.
- Если порог нарушен, по методике берётся `EXPLAIN ANALYZE` запроса к триграммному индексу; результат для каталога в 5000 строк лежит в [explain-report.md](../../docs/07-data/explain-report.md).
