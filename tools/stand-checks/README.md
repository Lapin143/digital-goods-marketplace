# tools/stand-checks

Проверки поднятого стенда. Запускаются после `make up` и в CI (задания `infra`, позднее `stand`).

| Файл | Что делает |
| --- | --- |
| `wait.py` | Ждёт готовности контейнеров набора: healthy, либо running без проверки, либо завершённое разовое задание с кодом 0. При ошибке печатает журналы проблемных контейнеров. Вызывается из `make up` |
| `lib.sh` | Общие функции проверок: `ok`, `bad`, `expect_ok`, `expect_fail`, `expect_denied`, `check`, `finish` (подключается командой `source`). В GitHub Actions `finish` пишет число проверок в аннотацию |
| `infra_security.sh` | Шифрование и права доступа PostgreSQL, Redis и Kafka. Клиенты запускаются контейнерами образов стенда в сети `data`, каталог секретов только для чтения. Каждая проверка либо «плохой» случай (должен быть отказ с нужной причиной), либо «хороший» (должен пройти) |
| `storage_checks.sh` | Объектное хранилище: TLS и отказ обычному HTTP, ограничения контейнеров, права `catalog-service` (свой бакет полностью, чужой никак), подписанные ссылки (рабочая, просроченная, с испорченной подписью), повтор `storage-init`, подмена политики и её возврат, смена пароля, данные после перезапуска, пик памяти. Клиент `aws` CLI v2 ходит на отладочный порт 19000 (`DEBUG=1`) |
| `stubs_checks.sh` | Контейнер заглушек: ограничения, секреты только файлами, разделение портов 8443 и 8444, TLS и отказ обычному HTTP, ключи интерфейсов, SMTP, доставка подписанных вебхуков получателю по HTTPS (`stubs_receiver.mjs` под именем `api-gateway`, подпись проверяет независимая реализация), дефектные режимы, перезапуск, пик памяти. Отладочные порты 18443, 18444, 11025 (`DEBUG=1`) |
| `stubs_receiver.mjs` | Получатель вебхуков для `stubs_checks.sh`: HTTPS с сертификатом `api-gateway`, проверка подписи секретом источника, свежести метки времени и клиентского сертификата заглушки, по строке JSON на запрос |
| `kc_client.py` | Клиент входа Keycloak на стандартной библиотеке Python: страницы входа, пароль, TOTP (RFC 6238), код авторизации с PKCE, refresh, Admin API, таблица маршрутов (публичный адрес `https://localhost:8443/auth` ведёт на отладочный порт). Шаги TOTP, занятые предыдущими процессами проверок, лежат в `build/totp-state.json` (переменная `DGM_TOTP_STATE`, пустая строка отключает файл): Keycloak не принимает код дважды, а два отказа подряд быстрее секунды закрывают пользователю вход на минуту. Повтор кода после отказа идёт через 1,2 секунды |
| `test_kc_client.py` | Модульные тесты клиента: векторы RFC 4226 и RFC 6238, выбор шага TOTP без повторного кода (в том числе общий файл состояния и пауза перед повтором), PKCE, JWT, разбор страниц, маршруты. `make keycloak-test`, сеть не нужна |
| `keycloak_checks.py` | Около 160 проверок настоящим входом: токены по ролям, второй фактор (в том числе настройка TOTP целиком и повторный вход с `prompt=login`, находка F4-2), разделение ролей, сроки, ротация refresh, блокировка после пяти неудач, подключение расширения `sms-otp` и ответ «временно недоступен» без платформы, нейтральные регистрация и сброс пароля без платформы (одна страница, время ответа, а письма и записи нет: режим отказа счётчика писем, ADR-010; письма и ссылки проверяет `--mail-flows`, см. ниже), claim `seller_id`, настройки realm, служебный клиент, VK ID, письма |
| `keycloak_checks.py --mail-flows` | Письма регистрации и сброса пароля на стенде с платформой (`make keycloak-mail-check`, набор `full`, `DEBUG=1`, `make keycloak-users`; TC-101, TC-102, TC-106, TC-107, TC-143): свободный и занятый адрес получают нужные письма, ссылка подтверждения возвращает покупателя в приложение, сброс пароля по ссылке, четыре попытки на один адрес за 10 минут дают три письма (F4-1). Записи одноразовые (`link-…`, `quota-…`), тестовые пользователи не меняются. Задание `e2e` |
| `stubs_admin.py` | Клиент команд управления заглушками (порт 8444) для сценариев на стенде: сброс между сценариями, режим платежа и почты на время блока `with` (на выходе умолчания возвращаются, даже если сценарий упал), платёж по идентификатору, команды `confirm`, `decline`, `expire`, `refund-complete`, повтор вебхука, ожидание письма, статус письма вебхуком. Настройка `STUBS_ADMIN_TARGET`. Модульные тесты `test_stubs_admin.py` идут в `run_all.sh` |
| `sms_login_checks.py` | Вход по SMS на настоящей платформе (`make sms-login-check`, набор `full`, `DEBUG=1`, `make keycloak-users`): покупатель подтверждает телефон через шлюз (код берётся из SMS-заглушки), входит по SMS (`amr = [sms]`, не больше 15 минут, нет refresh-токена, шлюз не пускает в разделы полного входа), клиент `dgm-web` после SMS просит пароль (F3-3), чужой номер неотличим от привязанного (страница, сообщение, время, SMS не уходит; ST-06). Номер подтверждённого покупателя запоминается в `secrets/sms_login_phone.json` для повторных прогонов. Задание `e2e` |
| `accounts_checks.py` | Учётные записи сквозь стенд (`make accounts-check`, набор `full`, `DEBUG=1`, `make keycloak-users`; TC-103, TC-104, TC-109 – TC-112, TC-115 – TC-118, TC-120, TC-124, ST-02): одноразовый покупатель входит по паролю (до подтверждения почты токенов нет, неверный пароль и неизвестный адрес неразличимы), вход через VK ID (первый и повторный вход, отказ провайдера), жизненный цикл записи сотрудника через административный API (список, смена роли с обязательным TOTP, токен без `otp` получает 403, деактивация закрывает вход и refresh, анонимизация обезличивает запись), занятый номер, внутренние операции платформы закрыты шлюзом. Все записи одноразовые, тестовые пользователи стенда не меняются. Задание `e2e` |
| `sellers_checks.py` | Заявка продавца сквозь стенд (`make sellers-check`, набор `full`, `DEBUG=1`, `make keycloak-users`; US-2.1, T-36): одноразовый покупатель создаёт черновик (ETag, `If-Match`, устаревшая версия, 428), подача без документа даёт 422, PDF загружается через шлюз, текст под видом PDF и файл больше 2 МБ отвергаются, ссылка открывается через `/files` шлюза без токена с заголовками «только скачать» (`Content-Disposition: attachment`, CSP, `no-store`), чужая подпись и запрос без подписи отвергаются, после удаления документа файла в хранилище нет, подача переводит заявку на проверку со сроком 3 суток. Границы 2 МБ, тип по содержимому, 11-й файл, пауза и срок ссылки на 301-й секунде проверяет `SellerOnboardingIT` (управляемое время). Задание `e2e` |
| `seller_approval_checks.py` | Решения модератора и роль продавца сквозь стенд (`make seller-approval-check`, набор `full`, `DEBUG=1`, `make keycloak-users`; TC-013, ST-13, US-2.2, US-2.3, INV-36, INV-37): два одноразовых покупателя подают заявки, moderator-1 (с TOTP) смотрит очередь и карточку со ссылкой на документ, отклоняет первую (без причины 422, повтор решения 409, пауза 24 часа) и возвращает на доработку вторую, после правки одобряет; платформа по `seller.approved` ставит в Keycloak роль `seller` вместо `buyer`, атрибут `seller_id` и обязательный TOTP; вход нового продавца ведёт на настройку TOTP, первый токен (`amr` = `pwd`) кабинет не открывает (403 `second-factor-required`), токен после входа с кодом открывает и несёт claim `seller_id`; admin-1 не может ни назначить, ни снять роль `seller` (409 `role-managed-by-system`). Продавца без устройства TOTP (seller-2) проверяет `keycloak_checks.py`, границы срока, откат решения и запись аудита в Outbox проверяет `SellerModerationIT`, роль и аудит на стороне платформы `PlatformServiceIT` (журнал аудита и его чтение появятся позже). Задание `e2e` |
| `purchase_checks.py` | Покупка до письма с ключом сквозь стенд (`make purchase-check`, набор `full` с `make fast-up`, `DEBUG=1`; шаг 17 Ф4, К6, TC-001): оплата на странице заглушки, выдача сама, одно письмо от выдачи с тремя разными ключами, статус «доставлено» вебхуком, письма платформы «Заказ создан» и «Заказ оплачен» без ключа, остаток ключей; по времени событий видно, где проходит время между оплатой и письмом, идентификатор запроса виден в журналах четырёх контейнеров, трасса `payment.paid` → `order.paid` и `delivery.accepted` → `order.issued` не рвётся, на очереди выдачи начинается заново; канарейка: значения ключей `DGM-ORD-…` не найдены в журналах, темах Kafka и дампах пяти баз, адресов покупателей нет в журналах выдачи и платформы. Помощники (`primary_of`, `key_letter`, `leak_scan`) использует `delivery_checks.py`, письма и выдачу `payments_checks.py` |

| `ui_smoke.py` | Дымовой сценарий интерфейса в браузере (`make ui-smoke`, набор `full` с `make fast-up`, `DEBUG=1`, `make keycloak-users`; К4, шаг 19 Ф4, покупка К8, шаг 21 Ф4). Playwright (Chromium) открывает страницу шлюза: moderator-1 входит через Keycloak с паролем и кодом TOTP (клиент `dgm-staff`), в очереди открывает заявку со ссылкой на документ и одобряет её, публикует один товар и отклоняет другой с причиной; гость без входа находит опубликованный товар по названию, видит карточку с ценой и «Нет в наличии», страницу отклонённого товара видит как «Товар не найден». Данные готовятся через API (функции `seller_approval_checks.py`), итог каждого решения сверяется по API, тексты кнопок берутся из `ru.json`. Сценарии покупателя (К8) берут продавца и товары у `orders_checks.py` и заводят нового покупателя с подтверждённым телефоном на каждый сценарий; платёжная заглушка стоит в режиме `hold`. Покупка до выдачи: количество 2, сумма 2 998 на карточке, на странице заглушки 2998.00 RUB, «Оплатить», экран заказа «Выдан» с адресом почты в тексте, ключей на экране нет, строка в «Мои заказы», письмо с двумя разными ключами в заглушке почты; сценарий повторяется `UI_PURCHASE_REPEAT` раз (в CI 3) разными покупателями. Перед каждым сценарием покупателя пауза `UI_AUTH_GAP` (30 с): шлюз пускает на входные страницы Keycloak 30 запросов в минуту с адреса, лимит не отключается (его проверяет `gateway_checks.py`), а первый запуск в CI без паузы получил 429 на странице входа.
