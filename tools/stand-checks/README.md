# tools/stand-checks

Проверки поднятого стенда. Запускаются после `make up` и в CI (задания `infra`, позднее `stand`).

| Файл | Что делает |
| --- | --- |
| `wait.py` | Ждёт готовности контейнеров набора: healthy, либо running без проверки, либо завершённое разовое задание с кодом 0. При ошибке печатает журналы проблемных контейнеров. Вызывается из `make up` |
| `lib.sh` | Общие функции проверок: `ok`, `bad`, `expect_ok`, `expect_fail`, `expect_denied`, `check`, `finish` (подключается командой `source`). В GitHub Actions `finish` пишет число проверок в аннотацию |
| `infra_security.sh` | Шифрование и права доступа PostgreSQL, Redis и Kafka. Клиенты запускаются контейнерами образов стенда в сети `data`, каталог секретов только для чтения. Каждая проверка либо «плохой» случай (должен быть отказ с нужной причиной), либо «хороший» (должен пройти) |
| `storage_checks.sh` | Объектное хранилище: TLS и отказ обычному HTTP, ограничения контейнеров, права `catalog-service` (свой бакет полностью, чужой никак), подписанные ссылки (рабочая, просроченная, с испорченной подписью), повтор `storage-init`, подмена политики и её возврат, смена пароля, данные после перезапуска, пик памяти. Клиент `aws` CLI v2 ходит на отладочный порт 19000 (`DEBUG=1`) |
| `stubs_checks.sh` | Контейнер заглушек: ограничения, секреты только файлами, разделение портов 8443 и 8444, TLS и отказ обычному HTTP, ключи интерфейсов, SMTP, доставка подписанных вебхуков получателю по HTTPS (`stubs_receiver.mjs` под именем `api-gateway`, подпись проверяет независимая реализация), дефектные режимы, перезапуск, пик памяти. Отладочные порты 18443, 18444, 11025 (`DEBUG=1`) |
| `stubs_receiver.mjs` | Получатель вебхуков для `stubs_checks.sh`: HTTPS с сертификатом `api-gateway`, проверка подписи секретом источника, свежести метки времени и клиентского сертификата заглушки, по строке JSON на запрос |
| `kc_client.py` | Клиент входа Keycloak на стандартной библиотеке Python: страницы входа, пароль, TOTP (RFC 6238), код авторизации с PKCE, refresh, Admin API, таблица маршрутов (публичный адрес `https://localhost:8443/auth` ведёт на отладочный порт) |
| `test_kc_client.py` | Модульные тесты клиента: векторы RFC 4226 и RFC 6238, выбор шага TOTP без повторного кода, PKCE, JWT, разбор страниц, маршруты. `make keycloak-test`, сеть не нужна |
| `keycloak_checks.py` | Около 100 проверок настоящим входом: токены по ролям, второй фактор, разделение ролей, сроки, ротация refresh, блокировка после пяти неудач, расширение SMS, настройки realm, служебный клиент, VK ID, письма |
| `keycloak_checks.sh` | Обёртка: ограничения контейнера, секреты не в окружении и журналах, TLS (1.1 отклоняется), издатель токенов, затем `keycloak_checks.py` и проверка таблицы `credential` (Argon2, своя соль у каждого пароля, паролей в открытом виде нет, NFT-3.1), память после проверок. Отладочный порт 18445 (`DEBUG=1`) |
| `db_migrations.sh` | Образ Flyway применяет миграции каждого сервиса с нуля под ролью-мигратором по TLS, повтор ничего не меняет, подмена применённой миграции обнаруживается, таблиц 44. Права ролей: мигратор не суперпользователь, рабочая роль видит только свою схему и базу, журнал аудита не изменить даже владельцем, предел соединений действует, `make db-roles` повторяется без ошибок |

Запуск: `make up SET=dev-min && tools/stand-checks/infra_security.sh && tools/stand-checks/db_migrations.sh` (последний также `make db-check`). Хранилище: `make up SET=dev-platform DEBUG=1 && make storage-check` (нужен `aws` CLI v2). Заглушки: `make up SET=dev-min DEBUG=1 && make stubs-check`. Keycloak: `make up SET=dev-auth DEBUG=1 && make keycloak-check` (шлюз появится на шаге 13, до этого достаточно профилей `infra,stubs,auth`). Нужны Docker с Compose и `openssl` (для чужого центра сертификации, который скрипт создаёт сам на время проверки).
