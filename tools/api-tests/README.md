# tools/api-tests

API-тесты через шлюз для Newman (шаг 4 Ф4, уровни L4 и L5 стратегии тестирования). Коллекция Postman не хранится в репозитории: она собирается из контрактов, матрицы прав и сценариев, поэтому не может разойтись с ними.

| Файл | Что делает |
| --- | --- |
| `oas.py` | Загружает операции из `docs/06-api/openapi/*-service.yaml` (сервис, метод, путь, коды ответов, роли, строки матрицы) и статусы операций из реестров сервисов `services/<сервис>/src/test/resources/dgm/operations.txt` |
| `st02_matrix.py` | Разворачивает матрицу ролей и прав (`docs/05-architecture/roles-permissions.md`, раздел 4.2) в случаи «операция × роль → ожидаемый ответ». `python3 tools/api-tests/st02_matrix.py` печатает таблицу, `--all` показывает и операции без обработчиков |
| `build.py` | Собирает коллекцию Postman 2.1 из матрицы и сценариев `scenarios/*.json`. `--check` проверяет всё без стенда, `--out файл` записывает коллекцию |
| `run.py` | Берёт токены тестовых пользователей настоящим входом через Keycloak, запускает Newman, разбирает отчёт и печатает сводку (консоль, аннотации и сводка запуска GitHub). Команда `make e2e` |
| `test_build.py` | Модульные тесты сборщика: хороший сценарий собирается, плохие отвергаются с понятной причиной |
| `scenarios/` | Сквозные сценарии (формат описан в начале `build.py`): `accounts.json` — отказы администратору в учётных записях, состояние записей не меняется (TC-111, TC-113, TC-115, TC-116); `keys.json` — пул ключей: продавец без профиля, модератор, администратор, покупатель и гость получают отказ, значение ключа из тела в ответе не повторяется (TC-408, ST-01); `moderation.json` — права на заявки, товары и решения модератора, роли без права получают отказ и ничего не меняют (TC-217, TC-303, TC-315); `storefront.json` — витрина без входа: карточка, список, поиск и фильтры, проверка границ параметров (TC-318, TC-322 – TC-324); `documents.json` — документы заявки продавца: PDF принимается, текст, HTML и SVG под видом PDF, PNG и JPEG отвергаются кодом 415, пустой файл 422, ссылка и удаление (ST-12); `orders.json` — границы оформления заказа без товара, чужие и несуществующие заказы, история (US-5.1, US-5.9); `payments.json` — вход вебхука платёжного шлюза закрыт подписью, очередь ручных возвратов закрыта ролью (US-5.5, US-5.8); `delivery.json` — вход вебхука e-mail-провайдера (`receiveKeyEmailStatus`): без подписи, с неверной подписью и с устаревшей меткой времени 401, неизвестное письмо и незнакомый статус 200, нарушения схемы тела 400 (US-6.3, шаг 17) |

## ST-02: матрица прав

Для каждой операции из контракта, доступной через шлюз (`/api/v1`), и каждой роли получается один запрос с токеном тестового пользователя роли (гость идёт без токена):

| Ячейка матрицы | Ожидание |
| --- | --- |
| «Да» | Роль допущена: ответ не 401, не 403, не 429 и не 5xx. Коды 200, 404, 422 говорят, что права пройдены |
| «Усл: U…» | Роль допущена при условии (профиль, статус, телефон): 403 возможен, 401 и 5xx нет |
| «Нет» | Отказ: 403, у гостя 401 |

В коллекцию входят только операции со статусом `done` в реестре сервиса: матрица растёт вместе с обработчиками и не краснеет заранее. Когда срез закрывается (`check_ledger.py --strict`), все его операции уже в матрице. Чужой объект (ответ 404) матрица не проверяет: для этого нужны данные двух владельцев, это дело сценариев.

## Сценарии

Файл `scenarios/<имя>.json`: цепочка шагов с ролью, операцией, параметрами, ожидаемым кодом, сохранением значений из ответа и проверками тела (формат в докстринге `build.py`). Задание `e2e` дополнительно запускает `make e2e-sabotage`: ожидание отказа 403 заменяется на 200, и Newman обязан покраснеть (если остался зелёным, матрица ничего не проверяет). Шаг может отправлять форму с одним файлом (`multipart`, содержимое только текстовое: двоичные файлы проверяют Java-тесты и стендовые проверки), проверять заголовок ответа (`{"header": ..., "contains": ...}`) и отсутствие в теле отправленной строки (`{"bodyNotContains": ...}`). Сборщик отвергает сценарий, если операции нет в OpenAPI или она ещё не `done`, код ответа не описан в контракте, не задан параметр пути или переменная не сохранена предыдущим шагом.

### Идемпотентность, подпись вебхуков, переменные между запросами (шаг 4 среза 2)

Шаг сценария может задать переменную до запроса (`"set": {"orderKey": "{{$guid}}"}`) и отправить её как ключ идемпотентности (`"headers": {"Idempotency-Key": "{{orderKey}}"}`): повтор шага уходит с тем же ключом, и сервис обязан вернуть тот же ответ (ADR-006). Значения из ответа (`save`, например идентификаторы заказа и платежа) питают следующие шаги и сценарии.

Вебхук с подписью (`receivePaymentGatewayNotification`, `receiveKeyEmailStatus`) входит в сценарий только с блоком `sign`: перед запросом скрипт Postman ставит `X-Webhook-Timestamp` и `X-Webhook-Signature` (hex HMAC-SHA-256 от «метка.тело», ADR-015). Секрет берётся из переменной окружения Newman `secret_<имя>`, которую `run.py` заполняет из `secrets/<имя>` и стирает вместе с токенами после запуска; в коллекции и в отчёте секрета нет. `sign` принимает `timestampOffsetSeconds` (устаревшее уведомление) и `badSignature` (неверная подпись); `"unsigned": true` проверяет отказ без подписи. Тест сборщика выполняет скрипт подписи в Node и сверяет результат с проверкой заглушки платёжного шлюза.

В матрицу ST-02 входят пять операций среза 2, доступных через шлюз с токеном (`createOrder`, `getOrder`, `getOrderPaymentSession`, `listManualRefunds`, `completeManualRefund`); остальные шесть внутренние или вебхуки, их проверяют сценарии и ST-04. Тест `test_slice2_operations_are_covered_by_matrix_or_marked_as_not_reachable` не даёт операции потеряться.

## Запуск

```bash
make up SET=full DEBUG=1 && make keycloak-users     # стенд и тестовые пользователи
npm install -g newman@6.2.1                          # версия закреплена в versions.md
make e2e                                             # матрица ST-02 и сценарии
make e2e-sabotage                                    # проверка проверки: испорченное ожидание обязано покраснеть
make e2e-check                                       # то же без стенда: только сборка и проверка сценариев
```

Токен живёт 5 минут: `run.py` берёт токены прямо перед Newman и стирает файл окружения после запуска. Отчёты (`collection.json`, `report.json`, `junit.xml`) лежат в `build/api-tests` и в артефакте `newman-report` задания `e2e`. Без сценариев и без готовых операций задание зелёное с пометкой «проверять нечего».
