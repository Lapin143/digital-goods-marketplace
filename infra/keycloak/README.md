# infra/keycloak

Сервер идентификации: Keycloak 26.8 с realm `dgm`, который хранится в репозитории как код, и расширение `sms-otp`: вход по коду из SMS, уровни входа, нейтральные регистрация и сброс пароля (шаг 7 Ф4), запрос e-mail при входе через VK ID без адреса и счётчик писем по адресу (шаг 15 Ф5, срез 1).
Что и зачем: [roles-permissions.md](../../docs/05-architecture/roles-permissions.md) (роли, области, сроки), [ADR-021](../../docs/05-architecture/adr/ADR-021-api-gateway.md) (шлюз проверяет токены), [ADR-010](../../docs/05-architecture/adr/ADR-010-keycloak-sms-codes.md).

| Файл | Что делает |
| --- | --- |
| `gen_realm.py` | Генератор: создаёт `realm/dgm-realm.json` из таблиц в начале файла (роли, области, клиенты, сроки, потоки входа). Идентификаторы потоков детерминированы, повторный запуск даёт тот же файл. `--check` сверяет файл с результатом генерации |
| `realm/dgm-realm.json` | Результат генерации, его читает Keycloak при первом запуске (`--import-realm`). Руками не правится. Секретов нет: `${DGM_PLATFORM_CLIENT_SECRET}`, `${DGM_VKID_CLIENT_SECRET}`, `${DGM_PUBLIC_ORIGIN}` подставляются из окружения |
| `entrypoint.sh` | Точка входа контейнера: читает секреты из `/run/secrets`, копирует файл realm в каталог в памяти, запускает `kc.sh start --optimized --import-realm` |
| `sms-otp/` | Расширение Keycloak (Java 21, один JAR): шаги потоков `sms-otp`, `dgm-cookie`, `dgm-auth-level`, `dgm-register`, `dgm-reset-email`, `dgm-vk-email`, тема входа и писем `dgm` (русский и английский). Логика без классов Keycloak лежит в `core/` и проверяется обычными модульными тестами в Gradle-модуле `:infra:keycloak-sms-otp`; шаги-адаптеры собираются в образе (`docker/Dockerfile.keycloak`) и проверяются на живом Keycloak (`make keycloak-check`, `make sms-login-check`) |
| `provision_test_users.py` | Создаёт 11 тестовых пользователей (3 покупателя, 2 продавца, 2 модератора, 2 оператора поддержки, 2 администратора) со случайными паролями; секреты TOTP у продавца, модератора, оператора и администратора. Данные пишет в `secrets/test_users.json` (права 0600, в Git не входит) |
| `reimport_realm.py` | Удаляет realm `dgm`, чтобы при следующем запуске Keycloak применил файл заново (`make keycloak-reimport`) |

Образ собирается Compose из [`docker/Dockerfile.keycloak`](../../docker/Dockerfile.keycloak): официальный образ Keycloak, расширение (компилируется `javac --release 21` в этапе на Temurin 25 по библиотекам самого Keycloak), `kc.sh build` с PostgreSQL, кэшем `local`, `/auth` как путём и портом управления на `/`, curl для проверки готовности.

## Как работает вход

| Что | Как |
| --- | --- |
| Адрес | Браузер ходит на шлюз `https://localhost:8443/auth`, он же издатель `iss` токенов. Между контейнерами Keycloak отвечает и по имени `keycloak:8443`, адрес для запросов подбирается из запроса |
| Роли | Одна роль на пользователя: `buyer`, `seller`, `moderator`, `support-operator`, `admin`. Роль по умолчанию даёт только `buyer`. У продавца и сотрудников она снята |
| Клиенты | `dgm-web` (покупатель), `dgm-staff` (продавец и сотрудники), `dgm-sms` (сессия по SMS: `orders.read`, `support.write`), `platform-service` (служебный, Admin API в пределах `manage-users`, `view-users`, `query-users`). Код авторизации с PKCE S256, без неявного потока и выдачи токена по паролю |
| Области | Область токена выдаётся только роли из таблицы раздела 3 roles-permissions.md; `fullScopeAllowed=false`: роли в токен попадают только через области клиента |
| Второй фактор | У продавца, модератора, оператора и администратора обязателен TOTP: условный подпоток по роли с обязательной формой OTP (условия «если настроен» нет, иначе вход без фактора возможен). Вход через VK ID и по SMS для этих ролей закрыт |
| Вход по SMS | Клиент `dgm-sms`, поток `sms-login`: шаг `sms-otp` показывает форму номера, затем форму кода. Кодов Keycloak не знает: номер уходит в `issueOtpCode`, код в `verifyOtpCode` платформы по mTLS (сертификат `keycloak`, заголовок `Idempotency-Key` на каждую попытку). Любой корректный номер ведёт к форме кода, привязан он или нет (ST-06); привязку и право входа решает платформа. После верного кода Keycloak находит пользователя по `userId` из ответа. Сотрудникам и продавцам вход закрыт (`dgm-sms-deny-nonbuyer`). Платформа недоступна: форма номера с сообщением «временно недоступен», остальные способы входа работают |
| Уровни входа (F3-3) | Шаг `sms-otp` ставит заметку сессии `auth_level=sms`. Шаг `dgm-cookie` заменяет стандартный `auth-cookie`: если сессия браузера помечена `sms`, SSO не принимается и клиент `dgm-web` или `dgm-staff` просит пароль. После пароля (`dgm-browser-forms`) или VK ID (`dgm-vk-post-login`) шаг `dgm-auth-level` возвращает метку `full`, и SSO снова работает. Токен сессии по SMS: `amr = [sms]`, 15 минут, без refresh |
| Регистрация и сброс пароля (Р-8, ST-06) | Поток `registration` состоит из одного шага `dgm-register`: ответ и время ответа одинаковы для свободного и занятого адреса (минимум 1,2 с). Свободный адрес получает письмо со ссылкой подтверждения, занятый — письмо «Попытка регистрации на ваш e-mail» (тема `dgm`, шаблон `register-duplicate`). Слабый пароль отклоняется политикой одинаково для обоих. Сброс пароля: `dgm-reset-email` оборачивает стандартный шаг и выравнивает время ответа (минимум 0,8 с). Число писем на один адрес считает платформа (F4-1, `consumeEmailQuota`, общий счётчик регистрации, сброса и запроса e-mail в потоке VK ID: 3 за 10 минут и 10 за сутки): шаг занимает место **до** отправки, при отказе письма нет, а страница и время ответа прежние, поэтому отказ не выдаёт, что на адрес недавно писали. Адрес в Redis хранится как HMAC с перцем, не открытым |
| Вход через VK ID без e-mail (Р-194, F4-3) | Первым шагом потока `dgm-first-broker-login` стоит обязательный `dgm-vk-email`; остальные шаги (создание или привязка) вынесены в подпоток `dgm-create-or-link`, иначе Keycloak не выполнит альтернативные рядом с обязательным. Если VK ID передал адрес, шаг ничего не делает. Если нет: форма адреса, затем форма кода из письма (`issueOtpCode` и `verifyOtpCode` с `purpose=vk_email`, 6 цифр, 5 минут, 5 попыток; место в счётчике писем платформа занимает сама). Платформа не ищет учётную запись по адресу, поэтому страница и время ответа не зависят от того, занят ли он. После верного кода адрес записывается в данные входа, учётная запись создаётся стандартным шагом, а тот же шаг `dgm-vk-email`, стоящий в потоке последним, помечает адрес подтверждённым (доверие к провайдеру на адрес, которого он не передавал, не распространяется, F5-52). **Адрес, занятый существующей учётной записью, не привязывается**: гость доказал владение ящиком, но не записью, поэтому вход заканчивается сообщением «Не удалось завершить вход, обратитесь в поддержку», в журнале Keycloak остаётся `EMAIL_IN_USE` без адреса |
| Токен | `aud=dgm-api`, `phone_verified`, `seller_id` (атрибут пользователя, ставит платформа при одобрении продавца; у остальных нет), `amr` (`pwd`, `otp`, `vk`, `sms`, срок хранения не меньше срока сессии), e-mail только в id-токене. Access живёт 5 минут, refresh одноразовый (повторное использование отзывает сессию) |
| Пароли | Argon2, длина не меньше 12, пять неудач закрывают вход на 15 минут |
| Почта | SMTP на `external-stubs:1025`: письма видны в заглушке |
| VK ID | Внешний провайдер `vkid` на заглушке (`/vkid`), PKCE, подпись токена провайдера проверяется; без e-mail в ответе поток просит адрес (строка выше) |

## Команды

```bash
make up SET=dev-auth DEBUG=1      # PostgreSQL, Redis, заглушки, Keycloak и шлюз; порт Keycloak 127.0.0.1:18445, шлюз https://localhost:8443
make keycloak-users               # тестовые пользователи, пароли в secrets/test_users.json
make keycloak-check               # вход по ролям, второй фактор, сроки, перебор, VK ID, Argon2 в базе, регистрация, сброс пароля (около 4 минут)
make sms-login-check              # вход по SMS на настоящей платформе (набор full, DEBUG=1, make keycloak-users)
make keycloak-test                # модульные тесты клиента входа, сеть не нужна
make realm                        # пересоздать файл realm после правки gen_realm.py
make keycloak-reimport            # применить изменённый realm к поднятому стенду (пользователи пропадут)
```

Консоль администратора: `https://localhost:18445/auth/admin/` (отладочный порт, сертификат частного центра `secrets/tls_ca.crt`), пользователь `dgm-admin`, пароль в `secrets/keycloak_admin`. Перед первым открытием выполните `make keycloak-console` (`enable_admin_console.py`): без этого консоль перенаправляет на шлюз (404) или зависает на проверке iframe, потому что адреса входа realm `master` строятся по публичному адресу шлюза. Тесты скрипта: `make keycloak-test`.

## Как менять realm

1. Правят `gen_realm.py` (не JSON) и выполняют `make realm`. Проверка `tools/docs-checks/check_realm.py` сверяет файл с roles-permissions.md: роли, области, сроки, второй фактор, Argon2, отсутствие секретов, структуру потоков. Если правило меняется, сначала правят документ.
2. На работающем стенде применяют `make keycloak-reimport`. Keycloak применяет файл realm **только** на пустой базе (или если realm с таким именем отсутствует), поэтому простая правка файла уже созданный realm не меняет.
3. На сервере realm не удаляют: изменения вносят миграцией через Admin API (порядок опишет руководство Ф6).

## Известные ограничения

| Ограничение | Что делать |
| --- | --- |
| Сразу после первой настройки TOTP токен сотрудника несёт `amr = [pwd]` без `otp` (находка F4-2: настройка не записывается как пройденный способ входа). Шлюз и `AccessRules` такой токен отклонят | Интерфейс после настройки отправляет сотрудника на повторный вход с `prompt=login` (проверено в `make keycloak-check`: пароль, затем код, `amr = [otp, pwd]`). Пользовательский шаг «выйти и войти» разовый, у каждого сотрудника только при первом входе |
| Если Redis или платформа недоступны, письма регистрации и сброса пароля не уходят, а страница остаётся прежней («проверьте почту»): режим отказа счётчика писем (ADR-010), чтобы сбой не стал способом слать письма без счёта | Предупреждение в журнале Keycloak и метрики платформы. Гость в потоке VK ID при сбое видит «временно недоступно». Redis платформы входит в состав стенда (compose) |
| Консоль администратора открывается в браузере только после `make keycloak-console`: у realm `master` задаётся свой «Frontend URL» (отладочный порт). `KC_HOSTNAME_ADMIN` в `compose.debug.yaml` один не помогает (F3-23) | Команда повторяема и обратима (`OFF=1`), настройка пропадает с томами. На сервере консоль наружу не публикуется (runbook, раздел 2.1), порядок доступа через туннель Ф6 должен учесть тот же «Frontend URL» |
| `KC_PROXY_HEADERS=xforwarded` доверяет заголовкам `X-Forwarded-*` | Шлюз обязан перезаписывать их (шаг 13), прямой доступ к Keycloak снаружи закрыт |
| Память на границе правила: куча 384 МБ, лимит контейнера 672 МБ, пик в CI 569 МБ (85 %) | Замер в [memory-measurements.md](../../docs/09-operations/memory-measurements.md). Лимит Keycloak пересматривается первым, когда в Ф4 появятся реальные сеансы |
