# services

Прикладные сервисы (Java, Spring Boot). Логические границы описаны в [декомпозиции](../docs/05-architecture/). На релизе R1 часть сервисов объединяется в крупные процессы, границы сохраняются внутри кода.

## Миграции базы

Миграции Flyway лежат в `services/<сервис>/src/main/resources/db/migration/` и **создаются скриптом**, а не пишутся руками: `python3 tools/docs-checks/db/gen_migrations.py` (цель `make db-migrations`). Источник те же части DDL, из которых собран `docs/07-data/ddl/<сервис>.sql`, поэтому документ и миграции не расходятся (склейка миграций равна DDL по SHA-256, проверяет `gen_migrations.py --check` в CI).

```
db/migration/
  common/V1__common.sql          outbox, processed_event, idempotency_key, функция контроля статусов
  <схема модуля>/V<n>__<схема>.sql   по одной на схему: seller_onboarding, catalog, inventory, orders, payments, delivery, identity, support, notification, audit_admin
  access/V<последняя>__access.sql    роли и права на созданные таблицы
```

Flyway читает все подпапки (расположение по умолчанию `classpath:db/migration`), номера версий сквозные внутри сервиса. Каждый модуль владеет своей папкой (правило модульности 7). Применённую миграцию править нельзя: Flyway сверяет контрольную сумму и остановит сервис ошибкой. Пока выпуск R1 не вышел, базовые миграции пересобираются целиком (на стенде `make reset`), затем изменения идут только новыми миграциями.

Сервис применяет миграции при старте под ролью `migrator_<сервис>` (секрет `db_migrator_<сервис>`), а работает под ролями `app_<модуль>`. Таблица истории `flyway_schema_history` принадлежит мигратору и не читается рабочими ролями.
