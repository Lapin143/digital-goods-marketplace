## 1. Как читать

Оформление и поля те же, что в [TC-accounts.md](TC-accounts.md) (раздел 1) и [шаблоне](_template-test-case.md). Тесты конкуренции работают так:

- сервис запускается в процессе теста на стенде `dev-kit` (настоящие PostgreSQL, Redis и Kafka), запросы идут по HTTPS от имени вызывающих сервисов (`order-service`, `delivery-service`, `api-gateway`) с их сертификатами; соседей заказа (каталог, остатки, платежи) подменяет один локальный HTTP-сервер теста;
- потоки стартуют по общей защёлке (`dgm.kit.testing.Concurrent.race`): без неё первый поток успевает закончить до старта последнего и гонки нет;
- пул соединений сервиса 7, поэтому из потоков тест обращается к сервису по HTTP, а к базе ходит только главный поток после гонки (у роли миграций предел 2 соединения);
- доказательство это запрос к базе (`GROUP BY … HAVING`, сверка числа ключей с резервами), а не только ответы потоков;
- один прогон ничего не доказывает: задание `concurrency` повторяет тесты с тегом `concurrency` 50 раз подряд.

В тестах короткий срок резерва (6 секунд, `reservation.ttl-seconds`) и частые таймер и сверка (свойства `InventoryStandIT`). На стенде и сервере действуют параметры платформы.

## 3. Тест-кейсы

### TC-030. Двойная выдача: параллельные заказы на последние ключи пула

| Поле | Содержание |
| --- | --- |
| ID | TC-030 |
| User story | US-5.2 (сценарий 1) |
| Требования | FT-5.2, NFT-2.2 |
| Уровень | L3 |
| Тип | конкуренция |
| Приоритет | Высокий |
| Автоматизация | JUnit на стенде |
| Тег в коде | TC-030 |
| Где в коде | `services/inventory-service/src/test/java/dgm/inventory/ReservationConcurrencyIT.java` |

**Предусловия.** Стенд `dev-kit`, сервис запущен в тесте. Товар `key_pool` в статусе «опубликован» с пулом из пяти ключей (первый случай) и из десяти ключей (второй случай), загруженных продавцом через шлюз. Вызывающий это `order-service` по mTLS.

**Шаги.**

1. Двадцать потоков по общей защёлке одновременно вызывают `reserveKeys` каждый для своего заказа на один ключ (пул из пяти ключей).
2. Десять потоков одновременно вызывают `reserveKeys` каждый для своего заказа на три ключа (пул из десяти ключей).
3. После каждого шага проверить базу: число резервов, число зарезервированных ключей, повторы привязки к заказу и резерву, резервы с числом ключей не равным количеству.
4. Сверить события `stock.changed` в Outbox: версии и остаток.

**Ожидаемый результат.** Шаг 1: ровно пять ответов 201 и пятнадцать 409 `insufficient-stock`, в базе пять резервов и пять зарезервированных ключей, свободных нет, ни один заказ и ни один резерв не держит больше одного ключа (INV-01, INV-05). Шаг 2: ровно три резерва по три ключа, один ключ свободен, частичного резерва нет ни у одного заказа. Шаг 3: запросы `GROUP BY … HAVING count(*) > 1` и сверка числа ключей с количеством резерва не находят нарушений. Шаг 4: события остатка написаны только для загрузки и успешных резервов (отказы события не пишут), версия растёт на единицу без пропусков, остаток падает на единицу с каждым резервом.

### TC-031. Оплата и истечение одного резерва на границе срока: один исход, ключи не потеряны и не удвоены

| Поле | Содержание |
| --- | --- |
| ID | TC-031 |
| User story | US-5.6 (сценарии 1, 3) |
| Требования | FT-6.5, FT-5.2, NFT-2.2 |
| Уровень | L3 |
| Тип | конкуренция |
| Приоритет | Высокий |
| Автоматизация | JUnit на стенде |
| Тег в коде | TC-031 |
| Где в коде | `services/inventory-service/src/test/java/dgm/inventory/ReservationConcurrencyIT.java` |

**Предусловия.** Стенд `dev-kit`, сервис запущен в тесте, срок резерва 6 секунд. Товар `key_pool` с пулом из десяти ключей, четыре заказа по одному ключу, у каждого активный резерв.

**Шаги.**

1. Дождаться границы срока самого раннего резерва (за 15 мс до неё).
2. Восемь потоков по общей защёлке: на каждый заказ один поток вызывает `confirmReservation`, другой снимает тот же резерв по сроку (вызов исполнителя таймера). Таймер и сверка сервиса работают параллельно.
3. После гонки проверить базу по каждому заказу: статусы резервов, ключи, события `reservation.expired`.
4. Проверить очередь сроков в Redis и общую сверку ключей товара.

**Ожидаемый результат.** Каждое подтверждение отвечает 200 со статусом `used` в любом порядке исходов. У каждого заказа ровно один использованный резерв и ни одного активного (INV-06), ровно один выданный ключ и ни одного зарезервированного. Если истечение успело первым, подтверждение вернуло `reReserved = true`, у заказа два резерва (снятый по сроку и новый использованный) и одно событие `reservation.expired`; если успело подтверждение, `reReserved = false`, резерв один и события истечения нет. Выданных ключей столько же, сколько оплаченных заказов, свободных на столько же меньше, чем в пуле: ни один ключ не потерян и не выдан дважды (INV-04). Резервов с числом ключей не равным количеству нет. В очереди сроков не остаётся резервов этих заказов, поздний срабатывающий таймер ничего не меняет.

### TC-032. Одно уведомление шлюза приходит много раз и вперемешку с противоположным: один переход, одна запись, одно событие

| Поле | Содержание |
| --- | --- |
| ID | TC-032 |
| User story | US-5.5 (сценарии 1, 3) |
| Требования | FT-6.2, NFT-2.3 |
| Уровень | L3 |
| Тип | конкуренция |
| Приоритет | Высокий |
| Автоматизация | JUnit на стенде |
| Тег в коде | TC-032 |
| Где в коде | `services/payment-service/src/test/java/dgm/payment/PaymentWebhookConcurrencyIT.java` |

**Предусловия.** Стенд `dev-kit`, сервис запущен в тесте, заглушка шлюза в режиме `hold`. Платёж с открытой сессией (`created`), у шлюза платёж оплачен, вебхук заглушка не отправляла. Вызывающий это `api-gateway` по mTLS, подпись вебхука настоящая.

**Шаги.**

1. Пять потоков по общей защёлке присылают одно и то же подписанное уведомление `payment.paid`, затем то же уведомление приходит ещё пять раз по очереди.
2. Проверить базу `payment_db`: статус платежа, строки `payment_event`, Outbox.
3. Для другого платежа: шесть потоков по общей защёлке присылают поровну `payment.paid` и `payment.declined` (разные идентификаторы событий шлюза).

**Ожидаемый результат.** Шаг 1: все десять ответов 200. Шаг 2: платёж `confirmed`, одна строка платежа заказа, одна строка `payment_event` с исходом `applied` и ни одной с другим исходом (дедупликация по паре «внешний идентификатор платежа, тип», INV-14), одно событие `payment.confirmed` в Outbox и больше никаких событий заказа. Строку платежа держит `FOR UPDATE`, поэтому проигравшие потоки ждут и находят запись победителя. Шаг 3: все ответы 200; платёж `confirmed` или `rejected`, в Outbox ровно одно событие, и оно соответствует итоговому статусу; в `payment_event` две записи, исходы `applied` и `anomaly` (проигравшее уведомление записано как аномалия, а не как второй исход), SM-02 не допустила второго перехода.

### TC-033. Повтор и перестановка событий у потребителей заказа и статусов письма: оплата и истечение резерва, «доставлено» и «ошибка» от провайдера в любом порядке и одновременно, один исход, платёж не теряется

| Поле | Содержание |
| --- | --- |
| ID | TC-033 |
| User story | US-5.4 (сценарии 3, 4), US-5.5, US-5.6, US-6.4 (сценарий 4) |
| Требования | FT-6.2, FT-6.5, FT-7.3, NFT-2.3 |
| Уровень | L3 |
| Тип | конкуренция |
| Приоритет | Высокий |
| Автоматизация | JUnit; JUnit на стенде |
| Тег в коде | TC-033 |
| Где в коде | `services/delivery-service/src/test/java/dgm/delivery/delivery/DeliveryStatusConcurrencyIT.java`, `services/delivery-service/src/test/java/dgm/delivery/delivery/service/DeliveryStatusesTest.java`, `services/order-service/src/test/java/dgm/order/OrderPaymentRaceIT.java`, `services/order-service/src/test/java/dgm/order/orders/events/SagaEventsTest.java` |

**Предусловия.** Заказ «ожидает оплаты». Модульные тесты работают через настоящий каркас потребителя на подмене базы, Outbox и сервиса остатков; тесты на стенде (`dev-kit`) вызывают оркестратор из двух и четырёх потоков по общей защёлке, пул соединений сервиса 7, заказ у каждого раунда свой (8 раундов), соседей заказа заменяет локальный HTTP-сервер теста, подтверждение резерва отвечает по режиму «ключи есть» или «ключей нет». Часть TC-033 для выдачи (шаг 14) проверяет статусы письма от провайдера: сервис запущен в тесте на стенде `dev-kit`, выдача «отправлено» засеяна напрямую в базу (без Kafka и почты), уведомление присылается по HTTPS от имени `api-gateway` с подписью настоящим секретом `delivery_webhook_secret`; опрос провайдера вызывает тест, базу в гонке не трогает ни один поток. Повтор `order.paid` и `user.anonymized` у потребителей выдачи проверяют TC-602 и TC-605 ([TC-delivery.md](TC-delivery.md)), потому что их результат это строка выдачи, а не исход гонки.

**Шаги.**

1. Подать `payment.confirmed` и `reservation.expired` по одному заказу в обоих порядках (подтверждение, истечение и истечение, подтверждение), каждое событие два раза подряд. Выполнить при «ключи есть» и при «ключей нет».
2. В двух потоках одновременно: подтверждение оплаты (решение по резерву и переход) и `reservation.expired`; 8 раундов при «ключи есть» и 8 при «ключей нет».
3. В четырёх потоках одновременно применить одно и то же решение об оплате.
4. Выдача, статус письма: восемь потоков по общей защёлке присылают одно и то же уведомление `delivered` по одной выдаче «отправлено».
5. Выдача, статус письма: два потока одновременно присылают `delivered` и `failed` по одной выдаче; 8 раундов, выдача в каждом раунде своя.
6. Выдача, статус письма: один поток присылает `delivered` вебхуком, другой одновременно выполняет проходы опроса, у провайдера письмо уже «доставлено»; 4 раунда.
7. Модульно: применение статусов к подмене базы в любом порядке и повторе по трём заказам, «ошибка» после «доставлено» и «доставлено» после «ошибки».

**Ожидаемый результат.** Шаг 1: при любом порядке и повторе итог один. Ключи есть: заказ «оплачен», одно `order.paid`, `latePayment = true`, если отмена обработана раньше оплаты, и `false`, если позже; команды возврата нет. Ключей нет: заказ «отменён» с причиной `reservation_expired`, одно `order.cancelled`, одна команда `order.refund-requested`, `order.paid` нет. Запись `processed_event` по одной на событие, повторное событие соседа не вызывает. Шаг 2: платёж не теряется. Ключи есть: заказ «оплачен» (T4, а если истечение выиграло гонку, T7 с признаком поздней оплаты), одно `order.paid`, отмен не больше одной, `latePayment` равно «отмена была», возврата нет. Ключей нет: заказ «отменён», ровно одна отмена и одна команда возврата, в любом порядке. Шаг 3: перевод выполняет один участник, остальные видят другой статус под блокировкой строки и ничего не меняют, одно событие `order.paid`. Шаг 4: все ответы 200, выдача «доставлено», одна запись в `provider_status_event` и одно событие `delivery.delivered` (дубль получает пустое «уже есть» после блокировки уникальной записи, ADR-006). Шаг 5: все ответы 200, итог «доставлено» или «ошибка» (T5 или T6, SM-06 второго перехода не допускает), записан только победивший статус (проигравший откатывается вместе с записью статуса), событие итога одно и соответствует статусу, второго события итога нет. Шаг 6: итог «доставлено», одна запись, одно событие, как если бы пришёл только один из двух путей. Шаг 7: в любом порядке выдача заканчивает в одном итоговом статусе, подтверждённая доставка не отзывается, повтор не пишет второго события.

### TC-034. Параллельное открытие платёжной сессии одного заказа: один платёж у шлюза

| Поле | Содержание |
| --- | --- |
| ID | TC-034 |
| User story | US-5.2 (сценарии 1, 4) |
| Требования | FT-6.1, NFT-2.3 |
| Уровень | L3 |
| Тип | конкуренция |
| Приоритет | Высокий |
| Автоматизация | JUnit на стенде |
| Тег в коде | TC-034 |
| Где в коде | `services/payment-service/src/test/java/dgm/payment/PaymentSessionConcurrencyIT.java` |

**Предусловия.** Стенд `dev-kit`, сервис запущен в тесте, заглушка внешнего шлюза в режиме «платёж ждёт оплаты» (`hold`). Вызывающий это `order-service` по mTLS. Заказ ещё не имеет платежа.

**Шаги.**

1. Двадцать потоков по общей защёлке вызывают `openPaymentSession` для одного заказа, каждый со своим `Idempotency-Key`.
2. Проверить базу `payment_db` (строки платежей заказа) и заглушку шлюза (платежи, созданные по заказу).
3. Повторить для одного общего `Idempotency-Key` у всех двадцати потоков, затем один вызов с тем же ключом после гонки.

**Ожидаемый результат.** Шаг 1: все двадцать ответов 201 с одним и тем же `paymentId` и одной и той же `sessionUrl` (платёж уникален по заказу, INV-11; потерявший гонку вызов читает победившую запись и отдаёт ту же сессию). Шаг 2: в `payments.payment` одна строка заказа, запрос `GROUP BY order_id HAVING count(*) > 1` пуст; у шлюза один платёж по заказу, потому что ключ идемпотентности вызова шлюза равен идентификатору платежа (ADR-015). Шаг 3: каждый ответ это 201 или 409 `request-in-progress` (фильтр идемпотентности ADR-006 не пускает второй вызов, пока первый не завершён), хотя бы один вызов получил сессию, строка платежа и платёж у шлюза по-прежнему по одному; повтор после гонки отвечает 201 с заголовком `Idempotency-Replayed: true`.

### TC-038. Повторный запрос возврата и гонки вокруг него: один возврат, одно событие, одна запись аудита

| Поле | Содержание |
| --- | --- |
| ID | TC-038 |
| User story | US-5.7 (сценарий 1), US-5.8 (сценарии 2, 3) |
| Требования | FT-6.4, NFT-2.3 |
| Уровень | L3 |
| Тип | конкуренция |
| Приоритет | Высокий |
| Автоматизация | JUnit на стенде |
| Тег в коде | TC-038 |
| Где в коде | `services/payment-service/src/test/java/dgm/payment/RefundConcurrencyIT.java` |

**Предусловия.** Стенд `dev-kit`, сервис запущен в тесте, платёж подтверждён вебхуком. Для шагов 2 и 3 возврат передан администратору (заглушка шлюза отказывает в возврате, прошло пять попыток). Вызывающие это `order-service` (команды в Kafka) и `api-gateway` (отметка, вебхук) по mTLS.

**Шаги.**

1. Опубликовать шесть одинаковых команд `order.refund-requested` по одному заказу (причины чередуются), шлюз возвращает деньги сразу.
2. Пять потоков по общей защёлке отмечают один возврат выполненным вручную, каждый со своим `Idempotency-Key`.
3. Шесть потоков по общей защёлке: три присылают одно подписанное уведомление `refund.completed`, три отмечают тот же возврат выполненным вручную.

**Ожидаемый результат.** Шаг 1: все команды обработаны, попытка возврата одна и она `succeeded`, у платежа один внешний идентификатор возврата, в Outbox одно событие `payment.refunded`, причина возврата от первой команды. Шаг 2: один ответ 200 и четыре 409 `refund-not-allowed`; платёж `refunded`, одно событие `payment.refunded` с `manual = true`, одна запись `audit.recorded`, новых попыток возврата нет. Шаг 3: уведомления шлюза получают 200 в любом исходе; платёж `refunded`, ровно одно событие `payment.refunded`; запись аудита есть тогда и только тогда, когда выиграла отметка администратора, и тогда успешна ровно одна отметка, а иначе все отметки получили 409. Строку платежа держит `FOR UPDATE`, проигравшие находят итог победителя (INV-15).

### TC-042. Лимит неоплаченных заказов при параллельных запросах покупателя и повтор одного ключа: ровно три заказа, один заказ на ключ

| Поле | Содержание |
| --- | --- |
| ID | TC-042 |
| User story | US-5.1 (сценарий 7) |
| Требования | FT-5.1, NFT-2.3 |
| Уровень | L3 |
| Тип | конкуренция |
| Приоритет | Высокий |
| Автоматизация | JUnit на стенде |
| Тег в коде | TC-042 |
| Где в коде | `services/order-service/src/test/java/dgm/order/OrderLimitConcurrencyIT.java` |

**Предусловия.** Стенд `dev-kit`, сервис запущен в тесте, миграции базы заказов применены. Каталог, остатки и платежи это локальный HTTP-сервер теста, в пуле 20 ключей. Лимит по умолчанию 3. Вызывающий это `api-gateway` по mTLS с токеном покупателя.

**Шаги.**

1. Десять потоков по общей защёлке оформляют по заказу на одну единицу одного товара, один покупатель, у каждого свой `Idempotency-Key`.
2. Десять потоков по общей защёлке присылают один и тот же запрос с одним и тем же `Idempotency-Key`; затем тот же запрос присылается ещё раз после гонки.

**Ожидаемый результат.** Шаг 1: ровно три ответа 201 и семь 409 `unpaid-orders-limit`; в базе три заказа покупателя «ожидает оплаты», ни одного «создан» и «отменён» (отказанные по лимиту заказов не создавали, подсчёт и вставка идут под блокировкой покупателя, Р-142); остатки и платежи вызваны ровно по три раза, в пуле осталось 17 ключей; по одному событию `order.created` на каждый заказ. Шаг 2: успешные ответы описывают один и тот же заказ, остальные получают 409 `request-in-progress`; в базе один заказ, соседи вызваны по одному разу, в пуле осталось 19 ключей (ключ идемпотентности занимается до первого вызова соседа и освобождается только при неудаче, Р-150); повтор после гонки отдаёт сохранённый ответ с `Idempotency-Replayed: true`.

### TC-043. Два диспетчера берут очередь выдачи одновременно: каждая выдача даёт одно письмо и одну попытку

| Поле | Содержание |
| --- | --- |
| ID | TC-043 |
| User story | US-6.1, US-6.4 |
| Требования | FT-7.0, FT-7.3, NFT-2.3 |
| Уровень | L3 |
| Тип | конкуренция |
| Приоритет | Высокий |
| Автоматизация | JUnit на стенде |
| Тег в коде | TC-043 |
| Где в коде | `services/delivery-service/src/test/java/dgm/delivery/delivery/DeliveryDispatchConcurrencyIT.java` |

**Предусловия.** Стенд `dev-kit`, сервис запущен в тесте, миграции базы выдачи применены. Сервис остатков это локальный HTTP-сервер теста, у каждого заказа один ключ. Почтовая заглушка не склеивает повторы по идентификатору сообщения (режим `dedupe = false`), поэтому второе письмо по той же выдаче было бы видно. Фоновый диспетчер отключён. В очереди 44 выдачи, срок которых наступил вчера, то есть вдвое больше пачки в 20 выдач.

**Шаги.**

1. Два потока по общей защёлке выполняют проход диспетчера одновременно: каждый берёт пачку выдач с арендой строки и обрабатывает её.
2. Дальше проходы выполняет один поток, пока все 44 выдачи не станут «отправлено».

**Ожидаемый результат.** Шаг 1: оба прохода взяли хотя бы по одной выдаче. Шаг 2: у каждой из 44 выдач ровно одно письмо в заглушке, ровно одна строка попытки и `attempt_no = 1`, ключи запрошены ровно один раз, в Outbox ровно одно событие `delivery.accepted`. Двух писем по одной выдаче нет: одну выдачу не взяли оба прохода (`FOR UPDATE SKIP LOCKED` внутри аренды строки, ADR-011).

### TC-044. Два прохода контроля 30 минут берут просроченные контроли одновременно: одно событие `delivery.overdue` на заказ

| Поле | Содержание |
| --- | --- |
| ID | TC-044 |
| User story | US-6.5 (сценарий 1) |
| Требования | FT-7.3, NFT-2.4 |
| Уровень | L3 |
| Тип | конкуренция |
| Приоритет | Высокий |
| Автоматизация | JUnit на стенде |
| Тег в коде | TC-044 |
| Где в коде | `services/delivery-service/src/test/java/dgm/delivery/delivery/DeliveryStatusConcurrencyIT.java` |

**Предусловия.** Стенд `dev-kit`, сервис запущен в тесте, миграции базы выдачи применены. Фоновый контроль отключён, проход вызывает тест. В базе 60 выдач «отправлено» с открытым контролем, срок которого наступил два года назад (такие берутся раньше просроченных контролей, оставшихся на стенде от прошлых прогонов), то есть больше порции прохода в 50 контролей.

**Шаги.**

1. Два потока по общей защёлке выполняют проход контроля одновременно: каждый блокирует порцию просроченных контролей (`FOR UPDATE SKIP LOCKED`), передаёт их в поддержку и пишет событие в той же транзакции.
2. Дальше проходы выполняет один поток, пока все 60 контролей не будут переданы.

**Ожидаемый результат.** Шаг 1: оба прохода передали хотя бы один контроль (порция прохода меньше числа контролей, поэтому ни один проход не берёт все). Шаг 2: у каждого из 60 заказов контроль `handed_over`, ровно одно событие `delivery.overdue` в Outbox и статус выдачи «отправлено» (контроль его не меняет). Одно событие на заказ гарантируют блокировка строки с пропуском занятых и переход `open` в `handed_over` только из `open` (ADR-011): второй проход не видит строку, которую держит первый, а после его фиксации она уже не `open`.
