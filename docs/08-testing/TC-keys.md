## 1. Как читать

Оформление и поля те же, что в [TC-accounts.md](TC-accounts.md) (раздел 1) и [шаблоне](_template-test-case.md). Тест-кейсы этой области проверяются на пяти уровнях:

- модульные тесты (`*Test.java`, задание `build`): разбор списка, шифрование и HMAC, служба пула на подменном хранилище, контроллер на `MockMvc`;
- интеграционные тесты на стенде (`*IT.java`, задание `kit`, набор `dev-kit`): настоящие PostgreSQL, Kafka и Redis, сервис запускается в процессе теста, запросы идут по HTTPS через клиент шлюза;
- тесты конкуренции (`KeyConcurrencyIT`, тег `concurrency`): отдельная задача Gradle `concurrencyTest`, потоки стартуют по общей защёлке (`dgm.kit.testing.Concurrent`); короткая серия из 3 запусков идёт в задании `kit`, серия из 50 в задании `concurrency` (ночью и вручную);
- Newman (`make e2e`): сценарий `tools/api-tests/scenarios/keys.json` и матрица прав ST-02 для трёх операций пула;
- сквозная проверка стенда: `tools/stand-checks/canary_checks.py` вызывается из `make seller-approval-check` после того, как продавец прошёл заявку, вход с TOTP и модерацию товара.

Значения ключей в тестах одноразовые (`UUID`, для канарейки `CANARY-<UUID>`) и реальных ключей не содержат.

### TC-401. Загрузка списком: принятые, дубли и пустые строки названы по номерам, значений в ответе нет

| Поле | Содержание |
| --- | --- |
| ID | TC-401 |
| User story | US-4.2 (сценарии 1 – 3) |
| Требования | FT-4.1, FT-4.2 |
| Уровень | L3 |
| Тип | API |
| Приоритет | Высокий |
| Автоматизация | JUnit; JUnit на стенде; Python на стенде |
| Тег в коде | TC-401 |
| Где в коде | `services/inventory-service/src/test/java/dgm/inventory/inventory/keys/KeyBatchTest.java`, `services/inventory-service/src/test/java/dgm/inventory/inventory/keys/KeyPoolServiceTest.java`, `services/inventory-service/src/test/java/dgm/inventory/inventory/keys/KeyPoolControllerTest.java`, `services/inventory-service/src/test/java/dgm/inventory/KeyPoolIT.java`, `tools/stand-checks/canary_checks.py` |

**Предусловия.** Продавец с токеном кабинета (роль `seller`, область `seller.catalog`, `amr = pwd, otp`, claim `seller_id`). Товар продавца со способом выдачи `key_pool` в статусе «черновик», «на модерации», «опубликован» или «отклонён». В пуле нет ни одного ключа.

**Шаги.**

1. `POST /api/v1/seller/products/{productId}/key-batches` со списком из пяти разных значений, повтором первого и строкой из пробелов.
2. Повторить ту же загрузку.
3. Загрузить одно из значений в пул другого товара того же продавца.
4. Загрузить список из одного значения и 1 500 пустых строк.

**Ожидаемый результат.** Шаг 1: 200, `accepted = 5`, повтор назван `duplicate_in_upload`, пустая строка `empty`, номера строк идут с единицы, в ответе нет ни одного значения ключа, `Cache-Control: no-store`. Остаток равен 5. Шаг 2: `accepted = 0`, все значения `duplicate_in_pool`, остаток прежний. Шаг 3: значение принято, дубли считаются только внутри товара. Шаг 4: `rejectedTotal = 1500`, а список `rejected` показывает первые 1 000 строк с номера 2 (остальные видны только в счётчике). Каждый принятый ключ лежит в базе зашифрованным (TC-410).

**Предусловия.** Как в TC-401. Пул содержит один ключ.

**Шаги.**

1. `POST /api/v1/seller/products/{productId}/key-files` с `Content-Type: text/csv`, переводами строки `\r\n`, последней строкой без перевода и меткой порядка байтов в начале.

Шаг 2: `accepted = 1`, вторая строка `duplicate_in_pool`, третья `too_long`, номера строк верны. Файл нигде не сохраняется: читается из запроса потоком.

| --- | --- |
| ID | TC-404 |
| User story | US-4.2 (сценарий 2) |
| Требования | FT-4.1 |
| Уровень | L3 |
| Тип | конкуренция |
| Приоритет | Высокий |
| Автоматизация | JUnit; JUnit на стенде |
| Тег в коде | TC-404 |
| Где в коде | `services/inventory-service/src/test/java/dgm/inventory/inventory/keys/KeyPoolServiceTest.java`, `services/inventory-service/src/test/java/dgm/inventory/KeyConcurrencyIT.java` |

**Предусловия.** Стенд `dev-kit`, сервис запущен в тесте, пул сервиса 7 соединений. Товар с одним ключом в пуле (он создаёт ключ данных). Шесть сессий продавца (не больше пула, иначе тест ждал бы не гонку, а соединения).

**Шаги.**

1. Шесть потоков по общей защёлке одновременно загружают одно и то же значение.
2. Шесть потоков одновременно загружают пересекающиеся окна одного длинного списка (по 150 значений со сдвигом 40).
3. Список и файл CSV с теми же значениями отправляются одновременно.
4. После каждого шага проверить базу запросом `GROUP BY hmac HAVING count(*) > 1`.

**Ожидаемый результат.** Шаг 1: ровно один ответ с `accepted = 1`, остальные пять с `accepted = 0` и причиной `duplicate_in_pool`. Шаг 2: в пуле каждое из 350 разных значений встречается один раз, остаток равен числу разных значений, событий `stock.changed` столько же, сколько загрузок, принявших хотя бы один ключ, `available` в них растёт, `version` не убывает. Шаг 3: действует одна загрузка, вторая видит дубли. Запрос шага 4 даёт пустую выборку. Защиту создают строка товара (`select … for update` сериализует загрузки одного товара) и уникальный индекс `(product_id, hmac)` с `on conflict do nothing`; при снятии любой из них тест краснеет (запасной контроль шага 15).

**Предусловия.** Товар с пулом из 99 995 ключей (в тесте пул доводится прямой вставкой, после теста удаляется владельцем таблицы: рабочая роль удалять не вправе, TC-411). Второй сценарий: пул из 99 990 ключей и шесть сессий.

| --- | --- |

| Требования | FT-4.0, FT-4.1 |
| Уровень | L3 |
| Тип | интеграционный |
| Приоритет | Высокий |

| Тег в коде | TC-407 |
| Где в коде | `services/inventory-service/src/test/java/dgm/inventory/inventory/registry/ProductRegistryServiceTest.java`, `services/inventory-service/src/test/java/dgm/inventory/inventory/keys/KeyPoolServiceTest.java`, `services/inventory-service/src/test/java/dgm/inventory/KeyPoolIT.java`, `tools/stand-checks/canary_checks.py` |

**Предусловия.** Стенд с Kafka. В теме `catalog.events` события `product.created`, `product.updated`, `product.published`, `product.rejected`, `product.blocked`.

**Шаги.**

1. Прислать `product.created` с продавцом, способом выдачи, статусом и версией.
2. Прислать `product.updated` с большей, равной и меньшей версией.
3. Прислать `product.published`, `product.rejected`, `product.blocked` (без версии) и решение по неизвестному товару.
4. Прислать испорченные события: без версии, с версией 0 или строкой, с неизвестным статусом, с `productId`, который не UUID, и событие чужого типа (`seller.approved`).
5. Загрузить ключи в товары со статусами `draft`, `on_moderation`, `published`, `rejected`, `blocked`, `archived` и в товар со способом выдачи `seller_api`.

**Ожидаемый результат.** Копия хранит владельца, способ выдачи, статус и версию. Более новая версия обновляет копию, равная и старая игнорируются. Решения модератора меняют только статус копии (Р-95). Решение по неизвестному товару игнорируется. Испорченное событие не повторяется, а сразу уходит в очередь недоставленных `catalog.events.dlq`; в тексте ошибки названо поле, но не значение. Ключи принимаются у `draft`, `on_moderation`, `published`, `rejected` и отклоняются у `blocked`, `archived` и у способа `seller_api`. На стенде загрузка отвечает 404, пока копия не пришла, затем 200.

1. Каждая из трёх операций (`uploadKeyBatch`, `uploadKeyFile`, `getProductStock`) для товара другого продавца и для неизвестного идентификатора.
2. Те же операции без токена, с токеном без области `seller.catalog`, с токеном покупателя и модератора, с токеном продавца без второго фактора (`amr = pwd`) и с сессией по SMS.
3. Токен продавца без claim `seller_id` (выдан до одобрения заявки).
4. Через Newman: гость, покупатель, модератор, администратор и продавец без профиля на тех же операциях.

**Ожидаемый результат.** Чужой и неизвестный товар неразличимы: 404 одинакового вида. Без токена 401 `unauthenticated`. Токен без области `seller.catalog`, роль покупателя или модератора: 403 `forbidden`. Продавец без второго фактора: 403 `second-factor-required` (ST-13), сессия по SMS: 403. Покупатель, модератор, оператор поддержки и администратор в матрице ST-02 получают 403, продавец допускается при условии (ячейка «Усл»). Токен без `seller_id` ничем не владеет: 403 «нет профиля продавца». Ни в одном ответе нет отправленных значений ключей.

### TC-410. Значение хранится зашифрованным, HMAC не раскрывает короткие ключи

| Поле | Содержание |
| --- | --- |
| ID | TC-410 |
| User story | US-4.4 (сценарий 2) |
| Требования | FT-4.2, NFT-3.2 |
| Уровень | L1 |
| Тип | безопасность |
| Приоритет | Высокий |
| Автоматизация | JUnit; JUnit на стенде |
| Тег в коде | TC-410 |
| Где в коде | `services/inventory-service/src/test/java/dgm/inventory/inventory/crypto/KeyCipherTest.java`, `services/inventory-service/src/test/java/dgm/inventory/inventory/crypto/KeyHasherTest.java`, `services/inventory-service/src/test/java/dgm/inventory/inventory/keys/KeyPoolServiceTest.java`, `services/inventory-service/src/test/java/dgm/inventory/KeyPoolIT.java` |

**Предусловия.** Мастер-ключ (`inventory_kek`, 32 байта в Base64) и секрет HMAC (`inventory_hmac`) лежат в секретах стенда, не в базе.

**Шаги.**

1. Зашифровать значение, расшифровать обратно.
2. Зашифровать одно значение дважды.
3. Подменить идентификатор ключа или товара в связанных данных, исказить шифртекст, взять чужой ключ данных, чужой мастер-ключ.
4. Посчитать HMAC для разных товаров, секретов, пробелов по краям и регистров.
5. Загрузить ключи через API и прочитать таблицу `inventory.key` под ролью миграций.

**Ожидаемый результат.** Расшифровка возвращает исходное значение. Одинаковые значения дают разные `nonce` и шифртекст. Подмена связанных данных, искажение и неверный ключ отвергаются с ошибкой без значения в тексте. Ключ данных хранится обёрнутым мастер-ключом (60 байт, AES-256-GCM), первая загрузка создаёт его под advisory-блокировкой базы, следующие используют его же. HMAC-SHA-256 покрывает `productId`, нулевой байт и значение без краевых пробелов, регистр значим, другой товар или секрет даёт другой HMAC. В таблице значение есть только как шифртекст: открытого текста нет ни в одной колонке.

### TC-411. Ограничения базы: привязка к заказу, переходы SM-03, уникальность, права роли

| Поле | Содержание |
| --- | --- |

| User story | US-4.2, US-4.4 |
| Требования | FT-4.1, FT-4.2 |
| Уровень | L3 |

**Предусловия.** Стенд `dev-kit`, миграции применены. Проверки идут под ролью миграций (у рабочей роли все соединения заняты сервисом), права рабочей роли смотрит `has_table_privilege`.

**Шаги.**

INV-04: недопустимый переход отвергает триггер текстом «недопустимый переход статуса X -> Y в таблице key». INV-01, второй рубеж: перепривязка закреплённого ключа и смена идентификатора или товара отвергаются триггером `key_immutable`. У рабочей роли есть `select`, `insert`, `update`, нет `delete` и `truncate`.

### TC-412. Канарейка ST-01: значения ключей не найдены нигде, кроме зашифрованной колонки
