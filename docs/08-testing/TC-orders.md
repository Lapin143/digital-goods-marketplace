## 1. Как читать

Оформление и поля те же, что в [TC-accounts.md](TC-accounts.md) (раздел 1) и [шаблоне](_template-test-case.md). Тест-кейсы этой области проверяются на трёх уровнях:

- модульные тесты (`*Test.java`, задание `build`): разбор тела уведомления, машина состояний, общий код применения исхода на подмене базы и Outbox (`FakePayments`), цепочка вебхука, сверка и сопоставление уведомлений, клиент шлюза на локальном HTTP-сервере;
- интеграционные тесты на стенде (`*IT.java`, задание `kit`, набор `dev-kit`): настоящие PostgreSQL и Kafka, настоящая заглушка шлюза, настоящие сертификаты вызывающих; подпись вебхука считается настоящим секретом `payment_webhook_secret`;
- заглушка шлюза в режиме `hold` сама исходов не присылает: статус платежа у шлюза меняет команда `send=false`, уведомление присылает тест, с любыми дефектами подписи, времени, суммы и порядка. Сверка и сопоставление несопоставленных уведомлений в интеграционных тестах вызываются явно, фоновые проходы там отложены, чтобы не подтверждать платежи, которые тест держит в статусе «создан».

Уведомления шлюза проверяются по цепочке ADR-015: подпись и метка времени, разбор, поиск платежа, сумма и валюта, дедупликация, запрос статуса у шлюза (шаг 4а, Р-134), смена статуса по SM-02 в одной транзакции с записью в Outbox. Ответ 200 без тела получают и обработанное уведомление, и повтор, и неизвестный платёж, и расхождение, и опровергнутое шлюзом: шлюз не должен повторять их бесконечно.

### TC-501. Платёжная сессия: открытие, повтор, отказ шлюза, срок короче резерва

| Поле | Содержание |
| --- | --- |
| ID | TC-501 |
| User story | US-5.2 (сценарии 1, 4) |
| Требования | FT-5.2, FT-6.0, FT-6.1, NFT-2.3 |
| Уровень | L3 |
| Тип | API |
| Приоритет | Высокий |
| Автоматизация | JUnit; JUnit на стенде |
| Тег в коде | TC-501 |
| Где в коде | `services/payment-service/src/test/java/dgm/payment/PaymentSessionIT.java`, `services/payment-service/src/test/java/dgm/payment/payments/session/PaymentSessionServiceTest.java`, `services/payment-service/src/test/java/dgm/payment/payments/session/PaymentSessionControllerTest.java`, `services/payment-service/src/test/java/dgm/payment/payments/session/PaymentSessionBodiesTest.java`, `services/payment-service/src/test/java/dgm/payment/payments/session/SessionSettingsTest.java`, `services/payment-service/src/test/java/dgm/payment/payments/gateway/HttpPaymentGatewayTest.java` |

**Предусловия.** Стенд `dev-kit`, сервис запущен в тесте, заглушка шлюза в режиме `hold`. Вызывающий это `order-service` по mTLS. Срок платёжной сессии короче срока резерва не меньше чем на запас (INV-07).

**Шаги.**

1. Вызвать `openPaymentSession` для нового заказа, затем повторить вызов с тем же `Idempotency-Key`, затем с новым ключом и тем же заказом.
2. Вызвать с тем же ключом и другим телом, с другой суммой для того же заказа, с телом, нарушающим контракт, и со сроком сессии вне границ резерва.
3. Включить отказ шлюза (503 на создание платежа), вызвать, затем вернуть шлюз и повторить. Повторить при потерянном ответе шлюза (платёж создан, ответ не дошёл).
4. Сменить статус платежа в базе и вызвать снова. Вызвать от имени чужого сервиса и без сертификата.
5. Запустить сервис со сроками, нарушающими INV-07 (сессия равна резерву или длиннее, запас меньше положенного).

**Ожидаемый результат.** Шаг 1: 201 с `paymentId`, `sessionUrl`, `sessionExpiresAt`, внешний идентификатор платежа наружу не отдаётся, у шлюза ровно один платёж; повтор с тем же ключом отдаёт сохранённый ответ с `Idempotency-Replayed: true` (документы равны, порядок полей может отличаться), повтор с новым ключом отдаёт ту же сессию, строка платежа одна (INV-11). Шаг 2: 422 `idempotency-key-reuse`; 409 `state-conflict` без изменения платежа; 422 `validation-failed` с указателями на поля; 422 при сроке в прошлом и дальше границы резерва, ничего не записано. Шаг 3: 503 `payment-session-unavailable` с `Retry-After`, строка платежа остаётся без внешнего идентификатора и у шлюза платежа нет; после восстановления шлюза повтор продолжает с той же строки, платёж у шлюза один; при потерянном ответе клиент шлюза повторяет вызов с тем же ключом (идентификатор платежа), платёж у шлюза один (клиент: 2 секунды на попытку, до трёх попыток, пауза 300 и 700 мс, отказ 4xx не повторяется, открытый предохранитель не обращается к шлюзу, ключ шлюза не попадает в тексты ошибок). Шаг 4: 409 для платежа в другом статусе; 403 для чужого вызывающего, отказ соединения без сертификата. Шаг 5: сервис не стартует, причина названа (`INV-07`, сроки в секундах).

**Шаги.**

2. Состарить запись на два часа и дважды запустить проход планировщика сопоставления.

**Ожидаемый результат.** Шаг 1: оба ответа 200, одна запись в `unmatched_notification` (уникальна по паре «платёж, тип»), платёж не создаётся. Шаг 2: оповещение (журнал уровня ERROR и метрика `payment_unmatched_alerts_total`) поднимается один раз, запись остаётся несопоставленной. Шаг 3: планировщик находит платёж, сверяет его со шлюзом общим кодом, платёж подтверждается, запись получает `matched_at`, а оповещение у сопоставленной записи снимается (ограничение базы `ck_unmatched_notification_alert`); если шлюз не ответил, запись остаётся и проход повторится. Запись с чужим внешним идентификатором закрывается как аномалия. Шаг 4: внешний идентификатор берётся из уведомления, дальше цепочка как в TC-502.

### TC-508. Шлюз не ответил на запрос статуса и потерянное уведомление: 503, повтор, сверка

| Поле | Содержание |

| ID | TC-508 |

| Требования | FT-6.2, NFT-2.3 |
| Уровень | L3 |
| Тип | интеграционный |
| Приоритет | Высокий |
| Автоматизация | JUnit; JUnit на стенде |
| Тег в коде | TC-508 |
| Где в коде | `services/payment-service/src/test/java/dgm/payment/PaymentWebhookIT.java`, `services/payment-service/src/test/java/dgm/payment/payments/webhook/PaymentWebhookServiceTest.java`, `services/payment-service/src/test/java/dgm/payment/payments/reconcile/PaymentReconciliationTest.java`, `services/payment-service/src/test/java/dgm/payment/payments/reconcile/PaymentReconcilerTest.java`, `services/payment-service/src/test/java/dgm/payment/payments/gateway/HttpPaymentGatewayTest.java` |

**Предусловия.** Платёж с открытой сессией, у шлюза платёж оплачен, вебхук потерян. Заглушка шлюза умеет отказывать на запрос статуса (`status.failFirst`).

**Шаги.**

1. Отключить ответы статуса у шлюза и прислать подписанное `payment.paid`. Вернуть шлюз и прислать то же уведомление.
2. Не присылать уведомление вовсе. Запустить сверку платежа, затем прислать запоздавшее уведомление.
3. Запустить сверку для платежа, отклонённого у шлюза, и для платежа, ждущего оплаты. Запустить проходы по возрасту платежей (моложе 2 часов, от 2 до 24 часов, старше 24 часов) и с лимитом пачки.
4. Проверить клиент: запрос статуса с повторами и одной попыткой, незнакомый статус, ответ без суммы, неизвестный платёж (404).

**Ожидаемый результат.** Шаг 1: первый ответ 503 `dependency-unavailable` с `Retry-After: 5`, ничего не записано, платёж «создан»; второй ответ 200, платёж подтверждён, одно событие в Outbox. Шаг 2: сверка подтверждает платёж с исходом `reconcile.paid` и одним событием `payment.confirmed`; запоздавшее уведомление это повтор исхода (200, не аномалия, второго события нет), повторная сверка ничего не меняет. Шаг 3: отклонённый у шлюза платёж становится `rejected`, ждущий остаётся «создан»; молодые платежи берёт частый проход, платежи от 2 до 24 часов реже, старше суток только считаются (`payments_stale_open`) и попадают в отчёт; за один проход обрабатывается не больше пачки; сбой шлюза на одном платеже не мешает остальным, сбой прохода журналируется и не останавливает планировщик. Шаг 4: сверка и сопоставление повторяют запрос по правилам повторов, запрос внутри вебхука делает одну попытку за 2 секунды; незнакомый статус шлюза это `UNKNOWN` и для платежа «создан» аномалия; ответ без суммы это временная неудача; 404 это отказ без повторов.
