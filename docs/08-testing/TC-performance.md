## 3. Тест-кейсы

### TC-062. Нагрузка-ориентир: создание заказа с резервом, 10 заказов в секунду, 95-й процентиль не больше 1 с

| Поле | Содержание |
| --- | --- |
| ID | TC-062 |
| User story | US-5.1, US-5.2 |
| Требования | NFT-1.2 |
| Уровень | L6 |
| Тип | нагрузочный |
| Приоритет | Средний |
| Автоматизация | k6; Python на стенде |
| Тег в коде | TC-062 |
| Где в коде | `tools/load/order.k6.js`, `tools/load/order_run.py` |

**Предусловия.** Набор `full` с рабочими сроками и отладочным файлом (`make up SET=full DEBUG=1`), пользователи Keycloak созданы (`make keycloak-users`), k6 в `PATH`. Резерв держится 15 минут, поэтому 300 неоплаченных заказов за время замера не истекают. Лимиты шлюза не меняются: заказы раздаются покупателям по кругу, и трёх неоплаченных заказов на покупателя и десяти заказов в минуту на пользователя хватает.

**Шаги.**

1. Запустить `make load-order`. Скрипт `order_run.py` заводит продавца, одобряет заявку, публикует один товар с 400 ключами и сто покупателей (телефон подтверждён, профиль на платформе), каждый покупатель входит заново, токены пишутся в `build/load/order-fixture.json`.
2. Платёжная заглушка переводится в режим `hold`. Сценарий `order.k6.js` 30 секунд отправляет 10 запросов в секунду `POST /api/v1/orders` (300 заказов, по три на покупателя, новый ключ идемпотентности в каждом).
3. После замера сверить базы заказов и остатков.

**Ожидаемый результат.** Шаг 2: на все запросы ответ 201 со статусом `awaiting_payment` (резерв активен), отказов нет, 95-й процентиль времени ответа меньше 1000 мс. На раннере нарушение порога даёт предупреждение, а не красный запуск (`LOAD_STRICT=1` делает его красным): результат это ориентир, зачёт по методике ([nfr-methodology.md](nfr-methodology.md), раздел 3.1) снимается на сервере с трассировкой OpenTelemetry. Шаг 3: заказов товара в базе заказов ровно столько, сколько ответов 201; ключей у товара столько же, сколько загружено, ни один не потерян; ни один заказ не держит больше одного ключа, резервов не больше заказов (INV-01, INV-05).

### TC-063. Сервисы без состояния сессии: два экземпляра, один перезапускается посреди серии запросов

| Поле | Содержание |
| --- | --- |
| ID | TC-063 |
| User story | US-8.11 |
| Требования | NFT-1.3 |
| Уровень | L6 |
| Тип | эксплуатационный |
| Приоритет | Средний |
| Автоматизация | Python на стенде |
| Тег в коде | TC-063 |
| Где в коде | `tools/stand-checks/stateless_check.py` |

**Предусловия.** Стенд `dev-auth` и `dev-purchase` с `DEBUG=1`, пользователи Keycloak созданы; токен покупателя выдан до начала серии.

**Шаги.**

1. Поднять по два экземпляра `order-service` и `catalog-service` (`docker compose --scale`) и дождаться состояния healthy у всех четырёх.
2. Опрашивать каждый экземпляр `order-service` напрямую два с половиной раза в секунду одним и тем же токеном, экземпляры `catalog-service` тоже.
3. На 15-й секунде перезапустить второй экземпляр `order-service`, серия идёт 100 секунд.
4. Сравнить ответы экземпляров, проверить заголовки и вернуть по одному экземпляру.

**Ожидаемый результат.** Шаг 3: первый экземпляр отвечает 200 на всех запросах серии, второй до перезапуска отвечает 200, во время перезапуска недоступен и после него снова отвечает 200 тем же токеном. Шаг 4: тела ответов двух экземпляров каждого сервиса совпадают, заголовка `Set-Cookie` нет ни в одном ответе. Статическая часть (правила ArchUnit `noHttpSessions` и `noMutableStaticFields`) выполняется в модульных тестах сервисов. Полный сценарий покупки при двух экземплярах появится на сервере в Ф4.

| Автоматизация | Python на стенде |

| Где в коде | `tools/stand-checks/timing_checks.py` |

**Предусловия.** Набор `full` с ускоренными сроками, перед проверкой выполнены `orders-check`, `payments-check`, `purchase-check`, `delivery-check`, `concurrency-check` и `ui-smoke`: они оставили в базах оплаченные заказы и выдачи. Проверка своих заказов не создаёт.

**Шаги.**

1. Выбрать первичные выдачи, ушедшие с первой попытки (заглушка почты без отказов, как в методике), и найти у каждой оплату заказа.

**Ожидаемый результат.** В выборке не меньше десяти выдач, метки согласованы (письмо принято не раньше оплаты с допуском часов в одну секунду), 95-й процентиль не больше 60 с. Печатаются размер выборки, медиана, 95-й процентиль и максимум. На стенде с ускоренными сроками это показывает долю собственной логики платформы; зачёт по методике (серия 1 000 оплаченных заказов, рабочие сроки) снимается на сервере.

### TC-066. Заказ без выдачи попадает в поддержку в срок, неразобранных оплаченных заказов нет

| Поле | Содержание |
| --- | --- |
| ID | TC-066 |
| User story | US-6.5, US-8.9 |
| Требования | NFT-2.4 |
| Уровень | L6 |
| Тип | интеграционный |
| Приоритет | Средний |
| Автоматизация | Python на стенде |
| Тег в коде | TC-066 |
| Где в коде | `tools/stand-checks/timing_checks.py` |

**Предусловия.** Те же, что у TC-064, и выполнен `delivery-check` (сценарии недоставки и контроля доставки оставили обращения системы). Срок контроля на стенде 180 с (`TIMING_CONTROL_SECONDS`), срок разбора 300 с (`TIMING_HANDLING_SECONDS`, на сервере 3600 с).

**Шаги.**

1. Найти обращения системы и оплату каждого их заказа, вычислить время от оплаты до появления обращения.
2. Найти оплаченные через стенд заказы, которые ждут выдачи, у которых нет ни обращения, ни отмены, ни возврата, ни выдачи. Заказы тестовых данных (идентификатор начинается с `0199e0a0-0000-`, их оплата записана миграцией, а не событием) в выборку не входят.

**Ожидаемый результат.** Шаг 1: обращения системы есть; обращение `delivery_overdue` появилось не позже срока контроля плюс 90 с, обращения других причин не позже 30 минут от оплаты. Шаг 2: оплаченных заказов без выдачи и без обращения старше срока разбора нет. Печатаются число обращений по причинам и диапазон времени.

### TC-067. Данных карты на платформе нет: ни мест для них, ни следов в базах и журналах

| Поле | Содержание |
| --- | --- |
| ID | TC-067 |
| User story | US-5.3 |
| Требования | NFT-5.1 |
| Уровень | L6 |
| Тип | безопасность |
| Приоритет | Высокий |
| Автоматизация | Python на стенде |
| Тег в коде | TC-067 |
| Где в коде | `tools/stand-checks/timing_checks.py` |

**Предусловия.** Те же, что у TC-064. Платёжная заглушка не принимает карту: оплата идёт кнопкой на её странице. Поэтому проверка показывает отсутствие мест для данных карты и следов номеров, а не обработку настоящей карты.

**Шаги.**

1. Проверить поиск на контрольной строке: номер вида `4111 1111 1111 1111` находится, время в миллисекундах и номер ключа нет.
2. Перебрать столбцы баз каталога, остатков, заказов, платежей, выдач и платформы и поля контрактов OpenAPI и AsyncAPI: ни одно имя не должно быть номером, сроком или кодом карты.
3. Найти в журналах контейнеров стенда и в дампах шести баз числа, похожие на номер карты: 13 – 19 цифр, префикс платёжной системы, контрольная цифра Луна.

**Ожидаемый результат.** Шаг 1: контроль проходит, поиск работает. Шаг 2: таких столбцов и полей нет. Шаг 3: журналы и дампы настоящие (непустые, в них идентификаторы запросов и заказов), чисел, похожих на номер карты, нет.

### TC-070. Контракты API: линтер Spectral, структура контрактов и сверка настоящих ответов со схемами OpenAPI

| Поле | Содержание |
| --- | --- |
| ID | TC-070 |
| User story | US-8.13 |
| Требования | NFT-6.2 |
| Уровень | L4 |
| Тип | API |
| Приоритет | Высокий |
| Автоматизация | Python на стенде |
| Тег в коде | TC-070 |
| Где в коде | `tools/stand-checks/check_contract.py` |

**Предусловия.** Контракты `docs/06-api/openapi/*.yaml` и `docs/06-api/asyncapi/asyncapi.yaml`; для сверки ответов поднят набор `dev-kit` и выполнены интеграционные тесты сервисов (они записывают каждый JSON-ответ в `build/contract-samples`).

**Шаги.**

1. Запустить Spectral по всем контрактам OpenAPI (задание `docs`).
2. Запустить `check_openapi.py` и `check_asyncapi.py`: структура контрактов, коды ответов, примеры по схемам, события и конверт.
3. Запустить `tools/stand-checks/check_contract.py`: образцы настоящих ответов сверяются со схемой ответа операции.
4. Убрать образец готовой операции, подменить поле ответа и добавить лишнее поле (самопроверка `tools/ci/selftest.sh`).

**Ожидаемый результат.** Шаг 1 и 2: ошибок нет, у каждой операции описаны коды ответов, примеры подходят под схемы. Шаг 3: тело каждого образца подходит под схему своего кода (JSON Schema 2020-12, форматы `uuid` и `date-time`), код описан в операции, тело ошибки подходит под `Problem`, поле `status` равно коду ответа; для каждой готовой операции из реестра `operations.txt` образец есть. Шаг 4: проверка краснеет на пропавшем образце, на поле не по схеме и на лишнем поле.
