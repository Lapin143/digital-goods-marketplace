## 1. Как читать

Оформление и поля те же, что в [TC-accounts.md](TC-accounts.md) (раздел 1) и [шаблоне](_template-test-case.md). Тесты журнала аудита проверяют четыре границы: чтение журнала (права, запись о чтении до ответа, отказ без данных), форму записи (разбор события строже, чем контракт, и не пускает открытое персональное значение), базу (права роли и триггеры) и конкуренцию (одно событие на двух экземплярах потребителя).

Запись аудита проверяется без подмены базы и Kafka: интеграционный тест публикует событие `audit.recorded` от имени `catalog-service` (права Kafka выданы по сертификату) и читает журнал под рабочей ролью `app_audit_writer`, а неизменяемость проверяет ещё и под ролью-мигратором, то есть под владельцем схемы.

## 3. Тест-кейсы

### TC-802. Журнал, тема `audit.events` и ответы API не содержат открытых e-mail и телефона, в том числе после анонимизации (NFT-5.3, ADR-014, канарейка)

| Поле | Содержание |
| --- | --- |
| ID | TC-802 |
| User story | US-8.6, US-8.7 |
| Требования | NFT-5.3, FT-11.2 |
| Уровень | L5 |
| Тип | безопасность |
| Приоритет | Высокий |
| Автоматизация | Python на стенде |
| Тег в коде | TC-802 |
| Где в коде | `tools/stand-checks/audit_checks.py` |

**Предусловия.** Набор `full` с `DEBUG=1`, тестовые пользователи Keycloak (`make keycloak-users`); администратор `admin-1` со вторым фактором и областью `staff.audit`; SMS-заглушка принимает сообщения.

**Шаги.**

1. Зарегистрировать одноразового покупателя с уникальным e-mail, подтвердить адрес, войти.
2. Подтвердить уникальный номер телефона через шлюз: запрос кода, код из SMS-заглушки, проверка кода.
3. Дождаться записи `user.phone_confirmed` и прочитать её: исполнитель, роль, изменения, адрес исполнителя.
4. Администратор деактивирует и анонимизирует запись покупателя; дождаться записей `user.deactivated` и `user.anonymized`.
5. Искать e-mail, его локальную часть, телефон с плюсом и без, национальный номер из десяти цифр, каждое значение как есть, в записи hex и в Base64 (обычном и для адресов): в ответе API журнала по объекту покупателя, в дампе схемы `audit_admin` (`pg_dump --column-inserts`, таблица и её секции) и в теме `audit.events` целиком (чтение без группы потребителей).
6. Контроль каждого поиска: записи этого покупателя обязаны найтись в дампе (не меньше трёх строк), в теме (не меньше трёх событий) и в ответе API (три действия).

**Ожидаемый результат.** Шаг 3: запись есть через несколько секунд, исполнитель сам покупатель, роль `buyer`, адрес исполнителя это хеш из 64 знаков, у изменения `phone` признак `personal = true`, значение «до» пусто, «после» хеш из 64 знаков, поле `phone_confirmed` меняется с `false` на `true`. Шаг 4: обе записи есть, исполнитель роли `admin`, в изменениях нет значений, которые не были бы хешем. Шаг 5: ни одно значение не найдено нигде. Шаг 6: контроль найден. Если поиск не нашёл записей покупателя, проверка красная: пустой результат без контроля ничего не доказывает. Модульный уровень (разбор записи, отказ открытому значению, хеш считает владелец данных) проверяют `AuditEntryTest`, `AuditRecordsTest` и TC-813.

Шаг 4: 200 с прежним ETag, версия не растёт, новых записей аудита и событий нет. Шаг 6: каждое значение попало в Outbox событием `config.changed` ровно один раз за проход, из четырёх потоков проход делает тот, кто взял консультативную блокировку, остальные уступают и не публикуют ничего (ноль), повтор безвреден. Шаг 7: блокировка пары берётся в порядке `payment-session.ttl-seconds`, затем `reservation.ttl-seconds`; при отказе публикации значение и версия прежние; `changed`, `unchanged`, `conflict` и `invalid` считаются раздельно.

### TC-807. Значение вне границ, нарушение INV-07, чужая версия и недостаток прав отклоняются, ничего не записав

| Поле | Содержание |
| --- | --- |
| ID | TC-807 |
| User story | US-8.3 (сценарии 2, 3 и 4) |
| Требования | FT-11.1, FT-5.2, NFT-3.6 |
| Уровень | L3 |
| Тип | API |
| Приоритет | Высокий |
| Автоматизация | JUnit; JUnit на стенде |
| Тег в коде | TC-807 |
| Где в коде | `services/platform-service/src/test/java/dgm/platform/auditadmin/service/ParameterServiceTest.java`, `services/platform-service/src/test/java/dgm/platform/auditadmin/controller/ParameterControllerTest.java`, `services/platform-service/src/test/java/dgm/platform/PlatformServiceIT.java` |

**Предусловия.** Стенд `dev-kit`; платёжная сессия 720 секунд (границы 60 – 3599), резерв 900 секунд (границы 300 – 3600); администратор со вторым фактором и областью `staff.admin`.

**Шаги.**

1. Задать резерву `0`, `-5`, `100`, `99999`, `"900"`, `1200.5` и `null`.
2. Задать сессии значение, равное резерву (900); задать резерву значение, равное сессии (720).
3. Правка без `If-Match`, с `If-Match: 1` (не строгий ETag), с чужой версией, по неизвестному ключу; тело не JSON, битый JSON, лишнее поле.
4. Правка и чтение списка токеном модератора с областью `staff.admin`, токеном администратора с сеансом по SMS, запрос без токена.
5. Две противоположные правки пары одновременно, шесть раз подряд: сессия 600 → 1500 при резерве 2000 и резерв 2000 → 1000 при сессии 600 (каждая допустима, вместе нарушают INV-07).
6. Модульный уровень: отказ ограничения таблицы даёт тот же 422, а не 500; слишком большое целое; тело длиннее 1 КБ.

**Ожидаемый результат.** Шаг 1: 422 `validation-failed`, в `errors` указатель `/value` и допустимые границы «от 300 до 3600»; значение и версия не изменились. Шаг 2: 422, в тексте назван парный параметр и его текущее значение (INV-07). Шаг 3: 428, 400, 412, 404, 415, 400, 422 (поле `unit` лишнее); в Outbox новых записей аудита и событий нет. Шаг 4: 403 (роль и сеанс по SMS), 401 без токена; значение не изменилось. Шаг 5: в каждом раунде ровно один 200 и один 422, итоговая пара всегда удовлетворяет «сессия строго короче резерва», потому что обе правки берут блокировку строк пары в одном порядке и сверяют значение с текущим значением парного параметра. Шаг 6: 422 с кодом `out_of_range` и текстом «Допустимо от … до …» вместо 500; значение за пределами 64-битного целого тоже 422 `out_of_range`; тело больше 1 КБ получает 413 `payload-too-large` без разбора содержимого, событий и записей аудита нет.

### TC-808. Слушатель применяет параметр только версией выше сохранённой, закреплённый ключ и значение вне границ не применяются, смена срока не требует перезапуска

| --- | --- |
| ID | TC-808 |
| User story | US-8.3 (сценарий 1: новое значение действует без перезапуска), US-8.3 (сценарии 2 и 3: границы и INV-07 при применении) |
| Требования | FT-11.1, FT-5.2, NFT-3.6 |
| Уровень | L3 |
| Тип | интеграционный |
| Приоритет | Высокий |
| Автоматизация | JUnit; JUnit на стенде |
| Тег в коде | TC-808 |
| Где в коде | `libs/service-kit/src/test/java/dgm/kit/config/ConfigRegistryTest.java`, `libs/service-kit/src/test/java/dgm/kit/config/ConfigChangeTest.java`, `libs/service-kit/src/test/java/dgm/kit/config/ConfigListenerTest.java`, `libs/service-kit/src/test/java/dgm/kit/integration/ConfigListenerIT.java`, `services/order-service/src/test/java/dgm/order/orders/service/OrderSettingsTest.java`, `services/inventory-service/src/test/java/dgm/inventory/inventory/reservation/ReservationServiceTest.java`, `services/payment-service/src/test/java/dgm/payment/payments/session/SessionSettingsTest.java`, `services/catalog-service/src/test/java/dgm/catalog/catalog/CatalogConfigurationTest.java`, `services/catalog-service/src/test/java/dgm/catalog/sellers/SellersConfigurationTest.java` |

**Предусловия.** Стенд `dev-kit`: Kafka с сжатой темой `platform.config`, права записи у `platform-service` и чтения у `order-service` выданы по сертификатам. У каждого теста свой ключ с меткой запуска, поэтому значения платформы и соседних тестов в теме не мешают.

**Шаги.**

1. Слушатель с зарегистрированным ключом (значение из настроек 10, границы 1 – 1000) читает тему. Опубликовать `config.changed` с версией 3 (значение 30), затем с версией 2 (значение 20), затем с версией 4 (значение 40).
2. Остановить слушатель, опубликовать версию 3 для другого ключа и запустить второй экземпляр с тем же значением из настроек.
3. Закрепить один ключ (`dgm.config.pinned-keys`) и опубликовать для него и для незакреплённого ключа версию 2 со значением 900.
4. Опубликовать в тему нечитаемую запись, затем корректное значение того же ключа.
5. Опубликовать значение вне границ ключа, затем допустимое. Для пары «резерв и платёжная сессия» опубликовать резерв 1000 (версия 2), сессию 600 (версия 2), сессию 1000 (версия 3), резерв 600 (версия 3), сессию 999 (версия 4).
6. Опубликовать значение ключа, которого у сервиса нет.
7. Модульный уровень: заказ, резерв, платёжная сессия и каталог читают значение из реестра при каждом обращении; резерв, созданный до смены срока, сохраняет прежний срок, новый берёт новый; у `payment-service` запас сессии до конца резерва (60 секунд) держится при каждом применении; границы сервиса шире границ платформы, потому что профиль `fast-time` задаёт секунды; источник записей падает и возвращается (чтение начинается заново с начала темы); значение из `application.yml` действует, пока ничего не пришло.

**Ожидаемый результат.** Шаг 1: значение 30 с версией 3 применено, версия 2 пропущена как устаревшая (`config_rejected_total{reason="stale-config"}` равен 1), затем применено значение 40 с версией 4 (`config_applied_total` равен 2, `config_version` равен 4). Шаг 2: второй экземпляр без запроса к платформе читает тему с начала и получает актуальное значение. Шаг 3: закреплённый ключ сохраняет значение из настроек и версию 0 (`config_pinned_total` равен 1), незакреплённый получает 900. Шаг 4: запись пропущена (`config_invalid_total` не меньше 1), следующая применена, поток слушателя работает. Шаг 5: значение вне границ не применено (`reason="out-of-range"`), допустимое после него применено; пара: сессия 600 применена, сессия 1000 и резерв 600 отклонены (`reason="inv-07"`, по одному на ключ), сессия 999 применена, резерв остался 1000 с версией 2. Шаг 4: запись `audit.viewed` (объект `audit-log`, `journal`, роль `admin`, изменений нет, параметров поиска нет), `Cache-Control: no-store`, записи от новых к старым, вторая страница по курсору без повторов, диапазон в будущем пуст, `occurredTo` не включается. Шаг 5: 403, 403, 401, 400 или 422 для каждого ошибочного параметра. Шаг 6: 404 или 405 для каждого сочетания, ни одного ответа 2xx (INV-42). Шаг 7: `permission denied for table audit_log` для обеих ролей и обеих операций, чтение под обеими ролями работает, запись в API до и после совпадает, число записей не уменьшилось. Проверка прав ролей на уровне базы, `TRUNCATE` и триггер владельца это TC-812.

### TC-816. Параметры платформы на стенде: лимит неоплаченных заказов, комиссия, перезапуск сервиса заказов, срок ссылки на документ, возврат к умолчанию

| Поле | Содержание |
| --- | --- |
| ID | TC-816 |
| User story | US-8.3, US-8.4, US-5.1 |
| Требования | FT-5.1, FT-9.0, FT-11.1, FT-11.2 |
| Уровень | L5 |
| Тип | интеграционный |
| Приоритет | Высокий |
| Автоматизация | Python на стенде |
| Тег в коде | TC-816 |
| Где в коде | `tools/stand-checks/parameters_checks.py` |

**Предусловия.** Набор `full` с ускоренными сроками (`make fast-up DEBUG=1`), тестовые пользователи Keycloak; `admin-1` и `moderator-1` входят с TOTP; товар с запасом ключей из фикстуры покупки; параметры платформы равны значениям по умолчанию (иначе проверка красная в конце); ключи `orders.max-unpaid`, `commission.default-rate-bp` и `seller.document-link-ttl-seconds` не закреплены в профиле `fast-time`.

**Шаги.**

1. Администратор ставит `orders.max-unpaid` = 1, дожидается строки «Параметр orders.max-unpaid = 1» в журнале `order-service`. Новый покупатель оформляет заказ и сразу второй.
2. Администратор возвращает значение 3, дожидается применения; тот же покупатель оформляет второй заказ.
3. Прочитать журнал аудита по ключу `orders.max-unpaid`.
4. Новый покупатель оформляет заказ при ставке 200. Администратор ставит `commission.default-rate-bp` = 300, дожидается применения; второй покупатель оформляет заказ. Прочитать ставку и комиссию обоих заказов в базе заказов.
5. Перезапустить контейнер `order-service`, дождаться готовности и строки «Параметр commission.default-rate-bp = 300» после запуска; оформить заказ.
6. Вернуть ставку 200, дождаться применения, оформить заказ.
7. Подать заявку продавца, прочитать срок ссылки на документ в карточке модератора, поставить `seller.document-link-ttl-seconds` = 60, дождаться применения в `catalog-service`, прочитать срок ссылки снова.
8. Вернуть все затронутые параметры к значению по умолчанию, проверить список параметров.
9. Пересоздать `order-service` с `DGM_CONFIG_ENABLED=false` и выполнить сценарий лимита (шаги 1 и 2) с ожиданием 15 секунд; затем пересоздать сервис как был и выполнить сценарий ещё раз.

**Ожидаемый результат.** Шаг 1: платформа принимает правку (200, значение 1), слушатель применяет её, первый заказ создан (201), второй получает 409 `unpaid-orders-limit` с пределом 1. Шаг 2: второй заказ создан (201). Шаг 3: две записи `parameter.changed` за время прогона, значения «до» и «после» `3 → 1` и `1 → 3` (строками), исполнитель `admin-1`, роль `admin`: так восстанавливается, кто и когда менял параметр. Шаг 4: ставка 200 и комиссия 2998 копеек у первого заказа, ставка 300 и комиссия 4497 копеек у второго (математическое округление, цена 1499 ₽), первый заказ после правки не изменился. Шаг 5: после перезапуска слушатель прочитал тему с начала и снова применил 300 без запроса к платформе, заказ после перезапуска со ставкой 300. Шаг 6: ставка 200 и комиссия 2998 копеек. Шаг 7: срок ссылки около 300 секунд до правки и около 60 секунд после. Шаг 8: каждый затронутый параметр равен значению по умолчанию, иначе проверка красная. Шаг 9: без слушателя сценарий красный (применение не видно за 15 секунд, второй заказ проходит), со слушателем зелёный; если без слушателя он остаётся зелёным, проверка проверяет не слушатель. Границы значений, INV-07, чужая версия и недостаток прав это TC-807, слушатель на настоящей Kafka это TC-808, расчёт комиссии это TC-809.
