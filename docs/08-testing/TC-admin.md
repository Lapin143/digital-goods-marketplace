## 1. Как читать

Оформление и поля те же, что в [TC-accounts.md](TC-accounts.md) (раздел 1) и [шаблоне](_template-test-case.md). Тесты журнала аудита проверяют три границы: форму записи (разбор события строже, чем контракт, и не пускает открытое персональное значение), базу (права роли и триггеры) и конкуренцию (одно событие на двух экземплярах потребителя).

Запись аудита проверяется без подмены базы и Kafka: интеграционный тест публикует событие `audit.recorded` от имени `catalog-service` (права Kafka выданы по сертификату) и читает журнал под рабочей ролью `app_audit_writer`, а неизменяемость проверяет ещё и под ролью-мигратором, то есть под владельцем схемы.

## 3. Тест-кейсы

### TC-812. Журнал только добавляется, секции создаёт задание (ST-09, IT-8)

| Поле | Содержание |
| --- | --- |
| ID | TC-812 |
| User story | US-8.7 (сценарий 1) |
| Требования | FT-11.2, NFT-5.2 |
| Уровень | L7 |
| Тип | безопасность |
| Приоритет | Высокий |
| Автоматизация | JUnit; JUnit на стенде |
| Тег в коде | TC-812 |
| Где в коде | `services/platform-service/src/test/java/dgm/platform/auditadmin/service/AuditPartitionServiceTest.java`, `services/platform-service/src/test/java/dgm/platform/PlatformServiceIT.java` |

**Предусловия.** Стенд `dev-kit`: платформа с миграциями, в журнале есть запись, созданная приёмником по событию `audit.recorded`.

**Шаги.**

1. Под ролью приёмника `app_audit_writer` выполнить `UPDATE`, `DELETE`, `TRUNCATE` таблицы `audit_admin.audit_log` и её месячной секции, а также `CREATE TABLE` в схеме `audit_admin`.
2. Под этой же ролью вставить запись с открытым значением e-mail в персональном поле.
3. Под владельцем схемы (роль-мигратор) выполнить `UPDATE` записи, перенос записи в другую секцию правкой времени, `DELETE`, `TRUNCATE` таблицы, месячной секции и страховочной секции.
4. Выполнить проход задания секций четырьмя потоками одновременно и проверить, что созданы секции на текущий месяц и три вперёд, а в страховочной секции строк нет. Отдельно проверить расчёт первого дня месяца по UTC на границе месяцев и значение метрики `audit_default_rows`.
5. Записать событие аудита в Outbox внутри транзакции, которая затем откатывается, и во второй раз внутри зафиксированной транзакции.

**Ожидаемый результат.** Шаг 1: `SQLSTATE 42501` (нет права) для каждой операции. Шаг 2: `23514`, ограничение `ck_audit_log_changes`. Шаг 3: `23001` для каждой операции, у владельца права есть, но запрещает триггер (INV-42), сообщение называет ограничение `ck_audit_log_append_only`. Шаг 4: проходы заканчиваются без ошибок (4 месяца или уступка блокировке второму экземпляру, ноль), секции `audit_log_ГГГГ_ММ` существуют, метрика `audit_default_rows` равна числу строк страховочной секции. Шаг 5: после отката в Outbox события нет, после фиксации оно есть (IT-8). Запись в журнале осталась без изменений. Если снять триггер `trg_audit_log_no_update`, проверка шага 3 красная: `UPDATE` под владельцем пройдёт.

### TC-813. Запись аудита доходит до журнала без потерь и дублей, открытое персональное значение уходит в DLQ

| Поле | Содержание |
| --- | --- |
| ID | TC-813 |
| User story | US-8.6 (сценарии 1 и 2), US-8.7 (сценарий 2) |
| Требования | FT-11.2, NFT-3.6, NFT-5.3 |
| Уровень | L3 |
| Тип | интеграционный |
| Приоритет | Высокий |
| Автоматизация | JUnit; JUnit на стенде |
| Тег в коде | TC-813 |
| Где в коде | `services/platform-service/src/test/java/dgm/platform/auditadmin/domain/AuditEntryTest.java`, `services/platform-service/src/test/java/dgm/platform/auditadmin/service/AuditRecordServiceTest.java`, `services/platform-service/src/test/java/dgm/platform/auditadmin/consumer/AuditConsumerTest.java`, `services/platform-service/src/test/java/dgm/platform/PlatformServiceIT.java` |

**Предусловия.** Стенд `dev-kit`; платформа читает тему `audit.events` в группе `platform-service`.

**Шаги.**

1. Опубликовать `audit.recorded` от имени `catalog-service` (действие модератора с неперсональными полями: строка и число). Прочитать запись в журнале.
2. Опубликовать то же событие повторно (тот же идентификатор), затем событие-метку; дождаться метки. Опубликовать второе событие с тем же содержимым, но новым идентификатором.
3. Вызвать приёмник для одного события из восьми потоков одновременно.
4. Опубликовать событие, где персональное поле `email` несёт открытое значение (`ivan.petrov@mail.example`). Прочитать `audit.events.dlq`.
5. На модульном уровне подать данные вне схемы (лишнее поле, роль или действие не из схемы, тип объекта с заглавной буквой, строка вместо списка изменений, вложенный объект в значении, хеш в верхнем регистре или короче 64 знаков), отказ базы по ограничению таблицы и недоступность базы.

**Ожидаемый результат.** Шаг 1: ровно одна запись с исполнителем, ролью, действием, объектом, значениями до и после «как есть» (в том числе число `3` и `5`), временем действия из события, идентификатором RecordID версии 7 и сквозным идентификатором; строка в `processed_event` для `audit-consumer` одна. Шаг 2: после дубля запись по-прежнему одна, второе событие с другим идентификатором даёт вторую запись. Шаг 3: применило ровно одно обращение, в журнале одна запись (`ON CONFLICT (event_id, occurred_at) DO NOTHING`). Шаг 4: запись в `audit.events.dlq` с `dlq-consumer = audit-consumer`, `dlq-attempts = 1` (повторов нет), `dlq-error-class = dgm.kit.events.FatalEventException`; в сообщении об ошибке есть имя поля `email`, самого значения нет; в журнале записи нет, отметки об обработке тоже (после исправления запись можно вернуть из DLQ). Шаг 5: каждое нарушение это неисправимая ошибка (DLQ сразу), счётчик `audit_records_total{result="rejected"}` растёт; недоступность базы не считается неисправимой, потребитель повторяет события с паузами 1, 5, 25 секунд. Событие в DLQ хранит исходный конверт (оно возникает только при ошибке в самом сервисе-издателе, срок хранения темы 14 суток).

### TC-814. IP исполнителя: у сотрудника как есть, у пользователя хеш

| Поле | Содержание |
| --- | --- |
| ID | TC-814 |
| User story | US-8.7 (сценарий 3) |
| Требования | FT-11.2, NFT-5.3 |
| Уровень | L3 |
| Тип | интеграционный |
| Приоритет | Высокий |
| Автоматизация | JUnit; JUnit на стенде |
| Тег в коде | TC-814 |
| Где в коде | `services/platform-service/src/test/java/dgm/platform/auditadmin/domain/AuditEntryTest.java`, `services/platform-service/src/test/java/dgm/platform/PlatformServiceIT.java` |

**Предусловия.** Стенд `dev-kit`; журнал доступен роли приёмника на чтение.

**Шаги.**

1. Опубликовать `audit.recorded` с действием сотрудника: `actorIp = 203.0.113.7`, `actorIpHashed = false`.
2. Опубликовать действие пользователя: `actorIp` это 64 шестнадцатеричных знака, `actorIpHashed = true`, у персонального поля `phone` значение «после» тоже хеш.
3. Опубликовать действие системы (`actorRole = system`, `actorIp` пустая строка).
4. Опубликовать действие пользователя с открытым адресом `198.51.100.23` и признаком `actorIpHashed = true`.

**Ожидаемый результат.** Шаг 1: в журнале `actor_ip = 203.0.113.7`, `actor_ip_hashed = false`. Шаг 2: `actor_ip` равен присланному хешу, `actor_ip_hashed = true`, в `changes` нет открытого номера. Шаг 3: `actor_ip` пуст (`NULL`), `actor_ip_hashed = false`. Шаг 4: запись в `audit.events.dlq`, в журнале записи нет, в сообщении об ошибке адреса нет (ограничение `ck_audit_log_actor_ip` держит то же правило на уровне базы).
