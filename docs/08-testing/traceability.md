| Поле | Содержание |
| --- | --- |
| Документ | Матрица трассировки маркетплейса цифровых товаров, версия 2 (конец Ф2) |
| Источники | [Требования v1.5](../02-requirements/requirements_v1.5.md), приложение B (цели), [user stories](../02-requirements/README.md), [процессы и статусные модели](../03-processes/README.md), [use cases](../02-requirements/README.md), [контракты OpenAPI](../06-api/openapi/README.md), [каталог событий](../06-api/events/README.md) |
| Релиз | R1 полностью, строки R2 и R3 даны для полноты картины |
| Статус | Заполнены пять колонок: цель, требование, история, процесс, API или событие. Колонки «Тест-кейс» и «Код» пусты и заполняются в Ф4. Скрипт `check_traceability.py` сверяет колонку «API / событие» с контрактами |
| Связанные документы | [Методика проверки NFR](nfr-methodology.md), [README раздела](README.md) |

Цепочка: BG → FT/NFT → US → BPMN / UC / SM → API или событие → TC → код.

Матрица растёт по фазам: v1 после Ф1 (цель, требование, story, процесс), v2 после Ф2 (API и события), v3 после Ф4 (тест-кейсы и код). Веха закрывается, когда в матрице нет пустых клеток для объёма этой вехи.

## 1. Как читать

В матрице 91 строк: по одной на каждое из 62 функциональных (FT) и 29 нефункциональных (NFT) требований. Строки разбиты на разделы по релизам, внутри раздела идут по номеру.

| Колонка | Что в ней | Откуда взято |
| --- | --- | --- |
| BG | Бизнес-цель, которой служит требование. Прочерк, если приложение B цели не называет | Приложение B требований v1.5 |
| Требование | Идентификатор и короткое название. Полный текст в требованиях. Если требование делится по релизам, это сказано в скобках | Разделы 3 и 6 требований v1.5 |
| User story | Все истории, в чьём поле «Требования» есть это требование | Поле «Требования» в файлах US-NN |
| Процесс / UC / SM | BPMN, use cases и статусные модели, где требование реализуется. Объединены ссылки из поля «Процесс или use case» историй и из шапок самих процессов | Поле «Процесс или use case» историй, шапки BPMN, UC и SM |
| API / событие | Операции OpenAPI (`operationId`) и события AsyncAPI, которыми требование реализуется. Если интерфейса нет, прочерк с причиной, раздел 4 | Поле `x-stories` операций в [контрактах OpenAPI](../06-api/openapi/README.md), [каталог событий](../06-api/events/README.md) |
| Тест-кейс | Пусто. Заполняется в Ф4 | `docs/08-testing/TC-*.md` |
| Код | Пусто. Заполняется в Ф4 | Модули и классы реализации |

Идентификаторы записаны без ссылок, чтобы матрицу было удобно искать и сравнивать по версиям. Операции и события записаны в обратных кавычках. Где лежит файл с нужным идентификатором:

| Идентификатор | Где искать |
| --- | --- |
| FT-x.y, NFT-x.y, BG-0x | [requirements_v1.5.md](../02-requirements/requirements_v1.5.md) |
| US-N.M | Файл эпика `US-NN-*.md` в каталоге [02-requirements](../02-requirements/README.md), таблица эпиков в README |
| UC-0N | `UC-0N-*.md` там же |
| BPMN-0N, SM-NN | Каталог [03-processes](../03-processes/README.md) |
| `operationId` | [Каталог операций](../06-api/openapi/README.md), файл контракта сервиса в том же каталоге |
| `имя.события` | [Каталог событий](../06-api/events/README.md), контракт [asyncapi.yaml](../06-api/asyncapi/asyncapi.yaml) |

Как проверяется каждое нефункциональное требование, написано в [методике проверки NFR](nfr-methodology.md): строка методики имеет тот же идентификатор, поэтому в клетках NFT она отдельно не дублируется.

**Как собрана колонка «API / событие».** Операция попадает в строку, если хотя бы одна из её историй (`x-stories` контракта) есть в колонке «User story» этой строки. Из такого набора в строку записаны операции, которые реализуют требование напрямую: у сквозных требований (журнал аудита, письма, ограничение частоты) полный набор был бы длиннее двадцати операций и ничего не говорил бы. Событие попадает в строку, если требование видно по нему: событие создаёт результат требования (`order.paid` для выдачи) или передаёт его другому сервису (`seller.approved` для письма заявителю). Каждая из 68 операций и каждое из 55 событий встречается в матрице хотя бы один раз, и каждая операция в строке связана с ней через историю: это проверяет `check_traceability.py`.

## 4. Прочерки в колонках процесса и интерфейса

**Колонка процесса.** Одиннадцать требований не связаны ни с одним BPMN, UC или SM. В каждой клетке записана причина, причины делятся на три класса.

| Класс | Требования | Почему допустимо |
| --- | --- | --- |
| Стандартный поток провайдера идентификации | FT-1.1, FT-1.2 | В историях US-1.2 и US-1.4 записано «отдельного процесса нет». Потоки входа через VK ID и восстановления пароля реализует Keycloak, свою логику здесь писать не нужно (Ф3) |

| Свойство системы | NFT-1.1, NFT-1.3, NFT-4.0, NFT-4.1, NFT-4.2, NFT-7.0 | У этих требований нет бизнес-процесса. Они проверяются измерением и обзором конфигурации по [методике](nfr-methodology.md) |

## 5. Находки

Это результат сверки матрицы с исходными документами. Правок требований v1.5 не делалось, всё нужное для v1.6 записано в [отчёте о Ф1](../00-phase1-report.md) и ниже.

1. **Нет требования без истории.** Для каждого из 91 требования найдена хотя бы одна история. Нет и истории без требования: все 83 истории попали в матрицу. Каждый из 23 процессов, use cases и статусных моделей привязан хотя бы к одному требованию.
2. **Требования без цели BG.** 50 из 91 требований не названы в приложении B: 18 функциональных и 19 нефункциональных R1, а также 13 требований R2 и R3. Это не ошибка трассировки, приложение B перечисляет только те требования, что прямо служат целям. Но для R1 такие прочерки в колонке BG остаются. Требования без цели: функциональные FT-1.0, FT-1.1, FT-1.2, FT-1.3, FT-1.4, FT-1.5, FT-1.7, FT-3.0, FT-3.3, FT-3.4, FT-4.0, FT-4.2, FT-4.3, FT-4.4, FT-11.0, FT-11.1, FT-11.2, FT-11.4; нефункциональные NFT-3.0, NFT-3.1, NFT-3.2, NFT-3.3, NFT-3.5, NFT-3.6, NFT-3.7, NFT-4.0, NFT-4.1, NFT-4.2, NFT-4.3, NFT-5.0, NFT-5.1, NFT-5.2, NFT-5.3, NFT-6.0, NFT-6.1, NFT-6.2, NFT-7.0. Для v1.6 нужно либо дополнить приложение B, либо записать, что инфраструктурные и сквозные требования от целей не зависят.
3. **Сквозные требования.** У некоторых требований много историй: FT-11.2 (17), NFT-5.3 (13), FT-11.0 (10), NFT-6.1 (10). Это сквозные требования (журнал аудита, письма, метрики). Для них в Ф4 нужны не один тест-кейс, а набор по сценариям, иначе клетка «Тест-кейс» будет формально заполнена, но смысл не покроет.
4. **Требования без процесса.** Одиннадцать, разбор в разделе 4.
5. **NFT-6.2 только в историях R2.** Контракты OpenAPI нужны с Ф2 для API R1, но единственная история с этим требованием US-11.2 относится к R2. В v1.6 стоит добавить критерий приёмки в одну из историй R1 либо отдельную историю. Пока опора на методику: строка NFT-6.2 там привязана к Ф2.
6. **Требования, делящиеся по релизам.** FT-4.0, FT-4.3 и FT-11.4 реализуются в R1 и R2. Тест-кейсы и код для них в Ф4 нужно разделять: часть R1 проверяется в срезах 1–3, часть R2 в Ф5.
7. **NFT-3.4 относится к R2 по историям.** У нефункциональных требований столбца релиза нет, поэтому NFT-3.4 легко принять за требование R1. По истории US-11.1 он относится к R2, проверяется в Ф5 и вынесен в раздел 3.1.
8. **Исправлена лишняя связь.** При сверке в поле «Требования» истории US-8.10 (резервное копирование) нашлось FT-5.2 (резерв и платёжная сессия), которого нет ни в таблице эпика, ни в критериях приёмки. Ссылка убрана, FT-5.2 по-прежнему покрыто историями US-4.6, US-5.2, US-5.4, US-5.6 и US-8.3.
9. **Каждая операция и каждое событие привязаны к требованию.** Все 68 операций OpenAPI и все 55 событий AsyncAPI встретились в матрице хотя бы раз, работ «просто так» нет. У операций это следует из поля `x-stories`, у событий из каталога издателей и потребителей.
10. **Требования без операции.** У 38 требований из 91 нет операций, разбор в разделе 4. Для шести функциональных требований R1 (FT-1.0, FT-1.1, FT-1.2, FT-2.2, FT-6.5, FT-7.1) это значит, что тест-кейс Ф4 не сможет сослаться на вызов API: поток Keycloak проверяется через вход пользователя, а поздняя оплата, письмо заявителю и защита от двойной выдачи через события и состояния сервисов (раздел 7 стратегии тестирования, TC-007, TC-008, TC-030).
11. **Широкие связи через истории.** Привязка по `x-stories` даёт для FT-11.2 25 операций, для NFT-5.3 21 операцию: каждая операция сотрудника пишет действие в журнал. В матрице оставлены прямые операции (`listAuditRecords`, событие `audit.recorded`), остальные видны по строкам своих основных требований. Связь «операция сотрудника → запись аудита» проверяется тестом NFT-3.6 по матрице прав, а не этой колонкой.
12. **События R2 уже в контракте, операций R2 ещё нет.** В 18 из 21 строк R2 и R3 заполнены события (18 черновиков событий R2 привязаны к требованиям), в трёх остальных (FT-9.1, FT-10.1, FT-11.3) нет ни операций, ни событий. Операции появятся с контрактами Ф5. Это не пробел Ф2: план проекта ставит обновление контрактов перед каждым блоком R2.

## 7. Как пользоваться матрицей

**Оценка влияния изменения.** Если требование меняется, по строке видно, что затронуто. Пример: срок резерва в FT-5.2 меняется с 15 минут на 20. Строка FT-5.2 перечисляет истории US-4.6, US-5.2, US-5.4, US-5.6, US-8.3 и процессы BPMN-01, BPMN-02, BPMN-03, UC-01, UC-05, SM-01, SM-02, SM-03, SM-08. Эти документы нужно проверить и поправить, а в Ф4 затронутыми окажутся их тест-кейсы и код.

**Проверка полноты.** Пустая клетка в первых пяти колонках у R1 означает требование без цели, истории, процесса или интерфейса (прочерк с причиной не считается пустой клеткой). Обратная ситуация, история без требования, выявляется поиском: идентификатор истории должен встретиться хотя бы в одной строке.

**Движение вперёд.** В Ф2 заполнена колонка «API / событие»: для каждой строки с функцией системы указана операция или событие. В Ф4 добавляются тест-кейсы (по тегам `@Tag("TC-NNN")` в коде, [стратегия тестирования](test-strategy.md), раздел 13) и код. Пример: NFT-2.2 связан с историями US-5.6, US-6.2 и процессами BPMN-01, UC-01, UC-03, UC-05, SM-01, SM-03, SM-08. Тест на конкуренцию ключей, описанный в методике, в Ф4 получит свой идентификатор тест-кейса и встанет в эту строку.

**Что уметь объяснить.** Матрица доказывает две вещи: что у каждого требования есть реализация и проверка, и что нет работ «просто так». Если в проекте есть история или тест, которых нет в матрице, это либо пропущенное требование, либо лишняя работа.
