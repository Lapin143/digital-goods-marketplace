## 1. Как читать

Оформление и поля те же, что в [TC-accounts.md](TC-accounts.md) (раздел 1) и [шаблоне](_template-test-case.md). Сквозной сценарий идёт на наборе `full` без подмены сервисов: шлюз, Keycloak, платформа, каталог, Kafka, объектное хранилище, заглушки SMS и почты. Проверки лежат в скриптах стенда и интеграционных тестах, поэтому номер сквозного сценария стоит рядом с номерами тест-кейсов его шагов. Сценарии запускаются заданием `e2e` (`make sms-login-check`, `make seller-approval-check`) и заданием `kit` (`PlatformServiceIT`, `SellerModerationIT`).

## 3. Тест-кейсы

### TC-003. Первая покупка, часть 1: телефон не подтверждён, код из SMS, подтверждение, токен с `phone_verified = true`

| Поле | Содержание |
| --- | --- |
| ID | TC-003 |
| User story | US-1.6 (сценарии 1, 2); часть 2 с заказом относится к срезу 2 (Р-4) |
| Требования | FT-1.5, NFT-3.7 |
| Уровень | L5 |
| Тип | интеграционный |
| Приоритет | Высокий |
| Автоматизация | Python на стенде |
| Тег в коде | TC-003 |
| Где в коде | `tools/stand-checks/sms_login_checks.py` |

**Предусловия.** Стенд `full` (шлюз, Keycloak, платформа, заглушка SMS-провайдера); покупатель с подтверждённым e-mail, телефона у него нет.

**Шаги.**

1. Войти паролем и прочитать токен: признака `phone_verified` в нём нет.
2. `POST /api/v1/phone-confirmations` с номером; код приходит в заглушку SMS.
3. Отправить неверный код, затем верный (`…/verify`).
4. Запросить код ещё раз; войти заново и прочитать новый токен.

**Ожидаемый результат.** Шаг 2: 201 и идентификатор запроса, SMS с шестизначным кодом уходит один раз. Шаг 3: неверный код даёт 422 `otp-invalid` с числом оставшихся попыток, верный 200, телефон подтверждён. Шаг 4: повторный запрос кода 409 (телефон уже подтверждён); платформа передала Keycloak признак, и в новом токене `phone_verified = true`. Вторая часть сценария (`createOrder`, повтор заказа, BPMN-01 E1) проверяется в срезе 2, до тех пор TC-003 считается пройденным наполовину.

### TC-013. Заявка продавца от подачи до роли: отказ с паузой, доработка, просрочка, одобрение, обязательный второй фактор

| Поле | Содержание |
| --- | --- |
| ID | TC-013 |
| User story | US-2.1; US-2.2; US-2.3; US-2.5 |
| Требования | FT-2.0, FT-2.1, FT-2.2, FT-2.4, FT-1.3 |
| Уровень | L5 |
| Тип | интеграционный |
| Приоритет | Высокий |
| Автоматизация | JUnit на стенде; Python на стенде |
| Тег в коде | TC-013 |
| Где в коде | `services/catalog-service/src/test/java/dgm/catalog/SellerModerationIT.java`, `services/platform-service/src/test/java/dgm/platform/PlatformServiceIT.java`, `tools/stand-checks/seller_approval_checks.py` |

**Предусловия.** Стенд `full` (шлюз, Keycloak, каталог, платформа, Kafka, объектное хранилище); два покупателя с поданными заявками и документами; moderator-1 с кодом TOTP.

**Шаги.**

1. Модератор открывает очередь и карточку заявки, отклоняет первую заявку без причины и затем с причиной.
2. Заявитель видит причину, пытается подать заявку снова в течение 24 часов и после паузы.
3. Модератор возвращает вторую заявку на доработку, заявитель исправляет и подаёт снова (BPMN-02 E2, E3).
4. Заявка остаётся без решения дольше 3 суток; модератор всё равно может её решить (E4).
5. Модератор одобряет заявку; повторное решение невозможно.
6. Новый продавец входит в Keycloak: настройка TOTP, затем кабинет с токеном без второго фактора и с ним.

**Ожидаемый результат.** Шаг 1: без причины 422, с причиной 200, статус `rejected`. Шаг 2: до конца паузы новая заявка 409 `application-pause-active`, после неё допускается. Шаг 3: статус `returned`, пауза не начинается, повторная подача 200. Шаг 4: задача помечает заявку просроченной один раз, решение принимается. Шаг 5: платформа получает одно событие, у покупателя ровно одна роль `seller`, в токене `seller_id`, Keycloak требует TOTP; повторное решение 409. Шаг 6: токен без `otp` открывает кабинет с ответом 403 `second-factor-required`, токен с `otp` (`amr = otp, pwd`) пропускается шлюзом.

### TC-014. Вход по коду из SMS: ограниченная сессия, неотличимость чужого номера, письмо владельцу

| Поле | Содержание |
| --- | --- |
| ID | TC-014 |
| User story | US-1.7 (сценарии 1, 2, 5) |
| Требования | FT-1.7, NFT-3.7 |
| Уровень | L5 |
| Тип | интеграционный |
| Приоритет | Высокий |
| Автоматизация | JUnit на стенде; Python на стенде |
| Тег в коде | TC-014 |
| Где в коде | `services/platform-service/src/test/java/dgm/platform/PlatformServiceIT.java`, `tools/stand-checks/sms_login_checks.py` |

**Предусловия.** Стенд `full` (Keycloak с расширением `sms-otp`, платформа, заглушки SMS и почты); покупатель с подтверждённым телефоном.

**Шаги.**

1. Войти через клиент `dgm-sms`: ввести номер, получить код, ввести код.
2. Вызвать с полученным токеном операции, которым нужен полный вход: подтверждение телефона, кабинет сотрудников, оформление заказа.
3. Повторить вход для номера, не привязанного к учётной записи.
4. Дождаться письма владельцу о входе по SMS; повторно доставить то же событие.

**Ожидаемый результат.** Шаг 1: выдан токен с `amr = [sms]`, областями `orders.read` и `support.write`, `phone_verified = true`, сроком не больше 15 минут и без refresh-токена. Шаг 2: 403 для каждой операции. Шаг 3: страницы, сообщение об ошибке и время ответа те же, что для привязанного номера, SMS уходит только владельцу (ST-06). Шаг 4: владельцу приходит одно письмо «Вход в аккаунт по коду из SMS» без номера телефона, дубль события второго письма не даёт.
