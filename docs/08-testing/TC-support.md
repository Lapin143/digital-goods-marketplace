## 1. Как читать

Оформление и поля те же, что в [TC-accounts.md](TC-accounts.md) (раздел 1) и [шаблоне](_template-test-case.md). Проверки обращения покупателя идут по модели чтения `support.order_view` (ADR-017): в `order-service` платформа не ходит, поэтому и тесты не поднимают соседа, а кладут выданный заказ в модель чтения событиями `order.paid` и `order.issued`, как это делает потребитель.

Время в модульных тестах ведут управляемые часы (`ManualClock`): граница 72 часов проверяется на значениях 71:59:59, 72:00:00 и 72:00:01, час лимита частоты проходит без ожидания. Интеграционный тест проверяет то, что подменой не доказать: гонку десяти запросов через частичный уникальный индекс `uq_ticket_order_id_open`, откат вставки при отказе по лимиту, ключ идемпотентности в той же транзакции модуля `support` и настоящий скрипт Redis.

## 3. Тест-кейсы

### TC-701. Обращение создаётся по выданному заказу, одно открытое на заказ, повтор с тем же ключом отвечает прежним ответом, десять одновременных запросов дают одно обращение

| Поле | Содержание |
| --- | --- |
| ID | TC-701 |
| User story | US-7.1 (сценарии 1 и 4), US-1.7 (сессия по SMS) |
| Требования | FT-7.2, INV-21, INV-23, NFT-3.5 |
| Уровень | L3 |
| Тип | конкуренция |
| Приоритет | Высокий |
| Автоматизация | JUnit; JUnit на стенде |
| Тег в коде | TC-701 |
| Где в коде | `services/platform-service/src/test/java/dgm/platform/support/service/TicketCreationTest.java`, `services/platform-service/src/test/java/dgm/platform/support/controller/SupportTicketControllerTest.java`, `services/platform-service/src/test/java/dgm/platform/PlatformServiceIT.java` |

**Предусловия.** Стенд `dev-kit`; платформа запущена; покупатель в Keycloak (заглушка) с областью `support.write`; выданный заказ покупателя в модели чтения поддержки, с первичной выдачи прошёл час.

**Шаги.**

1. Покупатель отправляет `POST /api/v1/support-tickets` с `orderId`, причиной `key_not_received` и ключом идемпотентности.
2. Покупатель отправляет тот же запрос ещё раз с тем же ключом, затем с новым ключом.
3. Десять запросов с десятью разными ключами уходят одновременно по одному заказу (`Concurrent.race`).
4. Покупатель читает список (`orderId` и `status` как фильтры, страница по курсору) и карточку; другой покупатель читает чужую карточку.
5. Модульный уровень: форма тела (лишнее поле, неверный UUID, чужая причина, пустое тело, не JSON, не тот тип содержимого), порядок страниц «новые выше», фильтры, решённое обращение разрешает новое, обращение системы тоже занимает заказ (INV-21).

**Ожидаемый результат.** Шаг 1: 201, `Location` на карточку, `Cache-Control: no-store`, поля ровно по схеме `SupportTicket` (идентификатор обращения и заказа, источник `buyer`, причина `key_not_received`, статус `created`, время создания, `resolvedAt`, `resolution` и `emailChange` равны `null`), в Outbox одно событие `ticket.created` без адреса, ключа и кода. Шаг 2: тот же ключ даёт прежний ответ с `Idempotency-Replayed: true` и не создаёт второго обращения и второго события; новый ключ при открытом обращении даёт 409 `ticket-already-open`. Шаг 3: ровно одно 201 и девять 409 `ticket-already-open`, в таблице одна строка по заказу, событие одно (вставка `ON CONFLICT DO NOTHING` по частичному индексу, событие пишется только при настоящей вставке). Шаг 4: список только своих обращений, чужая карточка даёт 404, как несуществующая. Шаг 5: как описано; ответы не содержат значений ключей, адресов и кодов (поля закрыты схемой).

### TC-702. Окно 72 часа считается от первичной выдачи, повторная отправка его не продлевает, значение берётся из параметра

| Поле | Содержание |
| --- | --- |
| ID | TC-702 |
| User story | US-7.1 (сценарии 2 и 3) |
| Требования | FT-7.2, FT-11.1, INV-17, INV-22 |
| Уровень | L3 |
| Тип | API |
| Приоритет | Высокий |
| Автоматизация | JUnit; JUnit на стенде |
| Тег в коде | TC-702 |
| Где в коде | `services/platform-service/src/test/java/dgm/platform/support/service/TicketWindowTest.java`, `services/platform-service/src/test/java/dgm/platform/PlatformServiceIT.java` |

**Предусловия.** Как в TC-701; параметр `support.window-seconds` равен 259200 (72 часа).

**Шаги.**

1. Создать обращения по заказам, выданным 71:59:59 и ровно 72:00:00 назад.
2. Создать обращение по заказу, выданному 72:00:01 назад.
3. Сдвинуть часы так, чтобы окно закрылось, не меняя модель чтения: время считает сервис по своим часам, а не момент записи проекции.
4. Применить повторное событие `order.issued` с новым временем по заказу с закрытым окном (повторная отправка создаёт новую выдачу) и повторить создание.
5. Сузить окно параметром до часа и расширить до трёх часов по заказу, выданному два часа назад.
6. Покупатель с сессией по SMS (без `pwd`) создаёт обращение по свежему заказу.

**Ожидаемый результат.** Шаг 1: оба обращения созданы (граница включена). Шаг 2: 409 `ticket-window-closed`, обращения и события нет, счётчик лимита не тратится. Шаг 3: отказ после закрытия окна. Шаг 4: время первичной выдачи не сдвигается (INV-17), отказ остаётся. Шаг 5: значение читается из параметра, смена действует без перезапуска. Шаг 6: 201, сессия по SMS допущена к операции (US-1.7, `x-sms-session: allowed`).

### TC-703. Чужой и несуществующий заказ неразличимы, заказ не «выдан» даёт отказ, лимит частоты даёт 429 с `Retry-After` и не оставляет обращения

| Поле | Содержание |
| --- | --- |
| ID | TC-703 |
| User story | US-7.1 (сценарии 5 и 6) |
| Требования | FT-7.2, NFT-3.5 |
| Уровень | L3 |
| Тип | безопасность |
| Приоритет | Высокий |
| Автоматизация | JUnit; JUnit на стенде |
| Тег в коде | TC-703 |
| Где в коде | `services/platform-service/src/test/java/dgm/platform/support/service/TicketRefusalsTest.java`, `services/platform-service/src/test/java/dgm/platform/PlatformServiceIT.java` |

**Предусловия.** Как в TC-701; параметр `support.requests-per-hour` равен 5; у покупателя нет обращений за последний час; Redis доступен.

**Шаги.**

1. Покупатель создаёт обращение по заказу другого покупателя и по случайному идентификатору.
2. Покупатель создаёт обращение по заказу в статусе «оплачен».
3. Покупатель создаёт пять обращений по пяти выданным заказам, затем шестое.
4. Перед этим покупатель восемь раз получает 409 по заказу с открытым обращением.
5. Час проходит, покупатель повторяет шестое обращение.
6. Лимит меняется параметром на 1 и на 3.

**Ожидаемый результат.** Шаг 1: оба ответа 404 с одинаковым текстом (доступ по владельцу, а не по номеру), обращений нет. Шаг 2: 409 `state-conflict`. Шаг 3: пять `201`, шестое 429 `rate-limited` с положительным `Retry-After`; строки обращения по шестому заказу нет и события `ticket.created` нет (вставка откатывается вместе с транзакцией). Шаг 4: отказы 409 счётчик лимита не тратят (в окно записывается только создание, которое состоялось). Шаг 5: после часа от первого обращения создание проходит; `Retry-After` в отказе равен времени до освобождения самой старой отметки окна. Шаг 6: лимит читается из параметра без перезапуска; у каждого покупателя счётчик свой (ключ `platform:support:requests:<buyerId>`).

### TC-704. Очередь оператора показывает обращения двух источников, старые выше, без значений ключей и адресов; покупатель и оператор без второго фактора её не видят

| Уровень | L3 |
| Тип | API |
| Приоритет | Высокий |

**Предусловия.** Стенд `dev-kit`; платформа запущена; в модели чтения поддержки есть выданные заказы; оператор с ролью `support-operator`, областью `staff.support` и вторым фактором (`amr` содержит `otp`).

**Шаги.**

1. В очереди есть обращение покупателя (создано запросом `createSupportTicket`) и обращение системы (событие `delivery.overdue`), созданное позже.

5. Покупатель, оператор без второго фактора, модератор и запрос без токена читают очередь.

Шаг 3: каждое обращение ровно один раз, последняя страница без курсора, при равном времени порядок по идентификатору. Шаг 4: взятое обращение уходит из очереди по умолчанию и видно только в выборке своего оператора. Шаг 5: 403 (покупатель, оператор без `otp`, модератор), 401 без токена. Шаг 6: 422 `validation-failed`, ошибки всех трёх параметров в одном ответе; неизвестный параметр называется в ошибке.

### TC-705. Взятие в работу записывает оператора и событие аудита; два оператора одновременно: ровно один 200 и один 409, двадцать повторов подряд

| Поле | Содержание |
| --- | --- |
| ID | TC-705 |
| User story | US-7.2 (сценарии 2 и 3) |
| Требования | FT-7.5, FT-7.3, INV-43, NFT-3.5 |
| Уровень | L3 |
| Тип | конкуренция |
| Приоритет | Высокий |
| Автоматизация | JUnit; JUnit на стенде; Newman |
| Тег в коде | TC-705 |
| Где в коде | `services/platform-service/src/test/java/dgm/platform/support/service/TicketTakeTest.java`, `services/platform-service/src/test/java/dgm/platform/support/controller/StaffSupportControllerTest.java`, `services/platform-service/src/test/java/dgm/platform/PlatformServiceIT.java`, `tools/api-tests/scenarios/support.json` |

**Предусловия.** Как в TC-704; два оператора; обращение в статусе `created`.

**Шаги.**

1. Первый оператор берёт обращение (`POST /api/v1/staff/support-tickets/{ticketId}/take`, ключ идемпотентности).
2. Второй оператор берёт то же обращение; первый оператор берёт его второй раз; берётся решённое обращение и неизвестный идентификатор.
3. Два оператора одновременно берут свежее обращение (`Concurrent.race`); круг повторяется двадцать раз, каждый раз с новым обращением.
4. Запись аудита проходит `audit.events` и попадает в журнал.
5. Взять обращение покупателем и администратором.

**Ожидаемый результат.** Шаг 1: 200, статус `in_progress`, оператор и время взятия записаны, время создания прежнее; в Outbox той же транзакции одна запись аудита `support.ticket_taken` (исполнитель, роль `support-operator`, адрес как есть, объект `ticket`, изменения статуса, оператора и заказа). Шаг 2: 409 `state-conflict`, обращение осталось у первого, второй записи аудита нет; решённое обращение 409, неизвестное 404. Шаг 3: в каждом круге ровно один 200 и один 409, оператор в базе совпадает с получившим 200, событий аудита ровно одно; условие `status = 'created'` в `UPDATE` единственное, что решает гонку (правило 15), проигравший ждёт блокировку строки и после неё не находит статус «создано». Шаг 4: запись в журнале за время порядка секунд (проверки аудита шага 8). Шаг 5: 403.

Шаг 3: 503 `dependency-unavailable`, записи кода из письма нет, этап `awaiting_email_code` с проверкой телефона `passed`, покупатель запрашивает письмо операцией `requestEmailChangeCode` (`step = new_email`), и оно уходит. Шаг 4: до проверки телефона 409 `state-conflict` (порядок этапов нарушен); верный код из письма даёт `new_email_check = passed`, состояние остаётся `awaiting_email_code`: адрес подтверждён, завершение смены выполняет шаг 15 (TC-710). Шаг 5: 409 `state-conflict`, подтверждённая смена не заменяется, коды заново не запрашиваются.

### TC-715. Нет обращения в работе: смена недоступна чужому оператору, по обращению в очереди и без подтверждённого телефона, коды не запрашивает чужой покупатель

**Предусловия.** Как в TC-711; второй оператор; второй покупатель; обращение в очереди (не взято); покупатель без подтверждённого телефона.

**Шаги.**

1. Оператор начинает смену: по обращению, которое взял другой оператор; по обращению в очереди и по возвращённому в очередь; по неизвестному обращению; с неверной формой идентификатора.
2. Покупатель вызывает операцию оператора; оператор без второго фактора; вызов без `Idempotency-Key`.
3. Оператор читает состояние смены: не начата; обращение другого оператора.
4. Покупатель запрашивает и проверяет код: смена не начата, чужое обращение другого покупателя, письмо раньше телефона, обращение вернули в очередь после начала смены; оператор вызывает операции покупателя.
5. Оператор начинает смену по обращению покупателя без подтверждённого телефона или с деактивированной учётной записью.

**Ожидаемый результат.** Шаг 1: 409 `ticket-not-in-progress` (чужое обращение, в очереди), 404 (нет обращения, неверная форма идентификатора); SMS не отправляется, этап и запись аудита не создаются (US-7.4, сценарий 6). Шаг 2: 403 (роль покупателя, нет второго фактора), 400 `idempotency-key-required`. Шаг 3: 404 в обоих случаях (условие U10: состояние читает только оператор, у которого обращение в работе). Шаг 4: 409 `state-conflict` (смена не начата, этап не тот, обращение не в работе), 404 для чужого обращения (неотличимо от отсутствующего), 403 для оператора. Шаг 5: 409 `state-conflict`, SMS не уходит, записей этапа нет.
