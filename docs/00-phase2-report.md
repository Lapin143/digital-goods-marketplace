## 1. Итог

Фаза Ф2 завершена: архитектура релиза R1 нарисована в нотации C4, решения записаны в ADR, контракты REST и событий лежат в формате OpenAPI и AsyncAPI, схемы шести баз выполняются на PostgreSQL 16 и проходят тесты конкуренции, стратегия тестирования привязана к 29 NFT и 44 инвариантам, матрица трассировки показывает путь каждого требования до операции или события. Открытых вопросов по архитектуре нет. Все расхождения, найденные при сверке документов друг с другом, либо исправлены, либо записаны ниже как замечания для требований v1.6 или как задачи Ф3 и Ф4.

Что значит «можно писать код без догадок». Для каждого сервиса R1 известны его границы, база и таблицы, операции и события, права ролей, сроки и повторы, порядок отказов и тест, который это проверит. Для вопроса «что делать, если…» есть место в документах, а скрипты `tools/docs-checks` каждый раз проверяют, что документы не расходятся между собой.

## 3. Принятые решения

### 3.1. Как нарисована и разложена система

| Решение | Суть | Почему так |
| --- | --- | --- |
| C4 на Mermaid | Диаграммы C4 нарисованы обычным `flowchart` с единым оформлением, а не встроенными блоками `C4*` Mermaid | Встроенные блоки дают нечитаемую раскладку. Structurizr и PlantUML красивее, но требуют отдельного инструмента, а Mermaid GitHub рисует сам. Альтернативы разобраны в [c4-notation.md](05-architecture/c4-notation.md) |
| Шесть сервисов на R1 | `catalog-service` (подключение продавцов и каталог), `inventory-service`, `order-service`, `payment-service`, `delivery-service`, `platform-service` (идентификация, поддержка, уведомления, аудит и параметры). В R2 добавляется `finance-service` | Три правила: критический путь покупки не объединяем, сторону предложения объединяем, всё вне критического пути собираем в один служебный сервис ([ADR-002](05-architecture/adr/ADR-002-microservices-consolidation.md)) |
| Каждый контекст ровно в одном сервисе, у каждого сервиса своя база | 7 баз на одном экземпляре PostgreSQL (6 сервисов и Keycloak), доступ по ролям и схемам. Модули внутри сервиса не лезут в таблицы друг друга | Принцип разделения сервисов позже: границы остаются, объединён только процесс |
| Принцип «ключ видит один сервис» уточнён | Открытое значение знают два сервиса: `inventory-service` расшифровывает, `delivery-service` получает по mTLS и держит в памяти на время формирования письма. Kafka, логи и остальные сервисы значения не видят | Письмо с ключом отправляет «Выдача» напрямую провайдеру, иначе ключ пошёл бы через Kafka (NFT-3.2) |
| Один веб-интерфейс на все роли | Роли различаются маршрутами и правами | Один код и один сборочный конвейер. Разделение допустимо, если интерфейс сотрудников начнёт выпускаться отдельно |
| Заглушки внешних систем одним контейнером на Node.js | Платёж, почта, SMS, VK ID, банк | Лёгкий процесс, помещается в профиль `stubs`. Подтверждается замером в Ф3 |

### 3.3. Правила, которые действуют сразу в нескольких документах

| Правило | Где действует | Почему так |
| --- | --- | --- |
| Идентификаторы это UUID версии 7, создаёт сервис-владелец. Исключение: идентификатор пользователя это `sub` Keycloak | conventions 3, все контракты, DDL | Вставка по возрастанию не рвёт индексы, идентификатор можно получить до записи |
| Деньги это объект `Money` с суммой в копейках (целое) и валютой. Проценты в базисных пунктах. Комиссия `(сумма × ставка + 5000) / 10000` | conventions 4, OpenAPI, DDL | Нет дробей и округления на стороне клиента |
| Время в UTC (RFC 3339), длительности целыми секундами, часы внедряются (`Clock`) | conventions 5, [test-strategy](08-testing/test-strategy.md) 11 | Сроки в 15 и 30 минут проверяются на ускоренных часах, без ожидания |
| Чужой объект отвечает 404, а не 403 | roles-permissions, условие U1 | Нельзя проверить, существует ли объект |
| Ошибки по RFC 9457, реестр из 38 типов, нейтральные ответы для занятых e-mail и номера | conventions 9, OpenAPI | Нельзя перебрать адреса и номера (требование Ф1) |
| События в конверте CloudEvents, изменение схемы через двойную публикацию, перечисления открытые | conventions 11, AsyncAPI | Потребители переходят независимо, без реестра схем |
| Адрес остаётся в Kafka до 7 суток и в DLQ до 14, при анонимизации события не стираются | conventions 11.7 | Остаточный риск принят, доступ к Kafka закрыт mTLS (находка F10-1) |
| Сессия по SMS открывает только чтение заказов и обращений. Новых заказов, смены пароля и e-mail нет | roles-permissions 5, ADR-010 | SMS слабее приложения-аутентификатора. Номер сотрудника или продавца в ответе не раскрывается |
| Второй фактор обязателен для продавца, модератора, оператора и администратора. Покупателя защищает подтверждённый телефон | roles-permissions 6 | Требование FT-1.3 |
| Отказы в доступе пишутся в журнал безопасности, а не в журнал аудита | roles-permissions 11 | Журнал аудита ведёт действия сотрудников и не должен разрастаться перебором |
| Профиль `fast-time` включается только в тестах, реальные сроки только в нагрузочных проверках | time-budgets 5, test-strategy 11 | Правила проверяются на пропорциях сроков, а не на часах |

### 3.4. Бюджеты и стенд

- **Время.** Путь «оплата → письмо принято» (NFT-2.0) складывается из шагов с 95-м перцентилем 7,5 с при пределе 60 с. При тайм-ауте провайдера 5 с в 60 секунд укладываются две попытки отправки, а не три: ADR-011 и SEQ-03 исправлены, NFT-2.0 это 95-й перцентиль. Тайм-аут шлюза для создания заказа 15 с.
- **Память.** Лимиты по контейнерам сведены в 9 групп и 7 готовых наборов. Набор `server` занимает 5632 МБ, для сервера нужно не меньше 8 ГБ. Набор для ноутбука с 3 ГБ у WSL выбирается из готовых, стек наблюдаемости (1056 МБ) на ноутбук не входит. Все цифры предварительные, замеры в Ф3.
- **Единая точка входа.** Порт 443 на `api-gateway`, интерфейс и файлы продавцов проходят через его маршруты. Redis без тома, потеря Redis допустима (сверка восстанавливает таймеры). Kafka в одном экземпляре, потеря диска означает восстановление из Outbox и сверок.

### 3.5. Тестирование

- **Пирамида из 8 уровней.** Много модульных и интеграционных проверок, мало сквозных и нагрузочных. PostgreSQL, Kafka и Redis в интеграционных тестах настоящие (Testcontainers), имитируются только соседние сервисы в модульных тестах.
- **Контракт первичен.** Pact не вводится: контракты OpenAPI и AsyncAPI лежат в репозитории, а скрипты и Spectral проверяют код по ним.
- **16 сквозных сценариев** на диаграммы SEQ и группы исключений BPMN. Больше сценариев дублировали бы интеграционные тесты и замедляли обратную связь.
- **Каждому инварианту назначен вид проверки** (IT-1…IT-10). IT-1, «попытка нарушить ограничение SQL-запросом от роли сервиса», ставится везде, где в физической модели написано «ограничение в базе».
- **Нумерация TC** по трём цифрам: область определяется первой цифрой, R2 и R3 лежат в областях 900–999, поэтому новые эпики не сдвигают номера R1.
- **Нагрузка на ноутбуке не проводится**, тесты k6 идут на сервере. Решение об аренде принимается в Ф4 по замерам Ф3 (D-1).
