# ADR-014. Журнал аудита без персональных данных

| Поле | Содержание |
| --- | --- |
| Статус | Принято |
| Дата | 2026-10-03 |
| Требования | FT-1.4, FT-11.2, NFT-3.6, NFT-5.0, NFT-5.2, NFT-5.3, раздел 8.2 требований (152-ФЗ) |
| Инварианты | INV-42, INV-43, INV-44 |
| Связанные документы | [domain-model.md](../../04-domain/domain-model.md) (разделы 4.1, 4.16, 6.6), [bounded-contexts.md](../../04-domain/bounded-contexts.md) |
| Связанные ADR | [ADR-003](ADR-003-kafka-events.md), [ADR-005](ADR-005-transactional-outbox.md), [ADR-006](ADR-006-idempotency.md), [ADR-010](ADR-010-keycloak-sms-codes.md) |

## Контекст

Журнал аудита фиксирует действия администраторов, модераторов и операторов поддержки, а также смену телефона и e-mail самим пользователем (FT-11.2, NFT-3.6). Он неизменяемый: записи не удаляются и не правятся (NFT-5.2). Одновременно закон требует хранить персональные данные граждан РФ в РФ (NFT-5.0) и уметь их удалять или обезличивать по запросу (FT-1.4, раздел 6.2 требований).

Противоречие: если в неизменяемый журнал попадёт e-mail или телефон в открытом виде, его нельзя будет обезличить, не нарушив неизменяемость. Требование NFT-5.3 разрешает противоречие: в журнале для персональных полей лежат идентификатор объекта, имя поля и HMAC-хеш значения до и после, а сами данные только в таблице пользователей, где их можно обезличить без изменения журнала.

Нужно определить, что именно записывается, кто считает хеш, как гарантируется, что действие и запись не расходятся, и как выполняется обезличивание.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| 1. Хранить значения в открытом виде | Максимально наглядно для расследований | Персональные данные в неизменяемой записи нельзя обезличить. Нарушает NFT-5.2 и NFT-5.3, риск по 152-ФЗ |
| 2. Хранить только имена полей и идентификаторы, без значений и хешей | Персональных данных нет вообще | Нельзя доказать, на что поле было изменено, нельзя заметить смену «на то же значение». Слабая ценность для разбора инцидентов и споров с оператором |
| 3. Шифровать значения в журнале, удалять ключ шифрования при обезличивании | Позволяет расследование при наличии ключа | В журнале остаётся шифртекст персональных данных (остаётся персональными данными). Нужны управление ключами и доступ к расшифровке, больше поверхность риска |
| 4. HMAC-хеш значения с ключом, выведенным отдельно для каждого пользователя (выбрано) | Хеш позволяет проверить значение («было ли это e-mail X») и обнаружить смену на то же значение. Секрет вне базы, поэтому утечка журнала сама по себе ничего не раскрывает. Обезличивание удалением «соли» пользователя делает хеши навсегда несопоставимыми без изменения строк журнала | Это псевдонимизация, а не полное обезличивание, пока жив секрет и известна соль. Нужно хранить соль пользователя и секрет. Сложнее простого хеша |
| 5. Цепочка хешей записей (запись содержит хеш предыдущей) | Обнаруживает правку журнала администратором базы | Сериализует вставки (общий последний хеш), усложняет параллельную запись. Не нужна для требований R1 (неизменяемость обеспечивают права и триггеры), остаётся возможным развитием |

## Решение

Выбран вариант 4.

### Что записывается

Запись журнала (`audit_log`, таблица добавляется только вставкой):

| Поле | Содержание |
| --- | --- |
| `id` | Последовательный идентификатор |
| `event_id` | Идентификатор события (UUID), уникален: повторная доставка события не создаёт вторую запись ([ADR-006](ADR-006-idempotency.md)) |
| `occurred_at` | Время действия |
| `actor_id`, `actor_role` | Кто выполнил действие и в какой роли (идентификатор пользователя, не имя) |
| `action` | Что сделано: код действия (например, `product.rejected`, `user.role_assigned`, `refund.marked_manual`) |
| `object_type`, `object_id` | Тип и идентификатор объекта |
| `changes` | Список изменений: имя поля, признак «персональное», значения до и после. Для персональных полей только HMAC-хеш, для остальных значение как есть |
| `actor_ip` | Для сотрудника как есть, для обычного пользователя HMAC-хеш |
| `correlation_id` | Сквозной идентификатор (NFT-6.0) |

**Чего в журнале нет никогда:** значений ключей, паролей, токенов, данных карт, e-mail, телефонов и имён в открытом виде, тел писем.

### Что считается персональным полем

Персональные поля: e-mail, номер телефона, имя, реквизиты вывода средств (R2), адрес доставки, IP-адрес обычного пользователя. Остальные поля (статусы, идентификаторы, значения параметров платформы, суммы, причины решений) не персональные и записываются как есть: это нужно, чтобы журнал параметров содержал значения «до и после» (комиссия, время резерва, [domain-model.md](../../04-domain/domain-model.md), раздел 4.15).

### Как считается хеш

```
K_user = HMAC-SHA-256(секрет_аудита, соль_пользователя)
хеш    = HMAC-SHA-256(K_user, имя_поля || 0x00 || нормализованное_значение)
```

- `секрет_аудита` (256 бит) хранится в хранилище секретов `platform-service`, не в базе ([c4-containers.md](../c4-containers.md), раздел 7.1).
- `соль_пользователя` (128 бит, случайная) создаётся при регистрации и хранится вместе с учётной записью (в таблице пользователей расширения платформы, там же, где персональные данные).
- Имя поля входит в хеш: одно и то же значение в разных полях даёт разные хеши, перекрёстное сопоставление не работает.
- Значение нормализуется (e-mail: нижний регистр и обрезка пробелов, телефон: формат E.164).
- Для IP обычного пользователя: тот же способ, имя поля `ip`.

Хеш считает тот сервис, **который владеет персональными данными** (модуль `identity` и модуль `support` в `platform-service`). Открытое значение не покидает этого сервиса и не попадает в Kafka: в событии аудита уже лежит хеш. Остальные сервисы в аудите персональных данных не передают, их события содержат идентификаторы и неперсональные значения.

### Как действие и запись не расходятся (INV-43)

1. Сервис выполняет действие и в **той же транзакции** записывает в Outbox событие `audit.recorded` ([ADR-005](ADR-005-transactional-outbox.md)). Действия без события аудита не бывает.
2. Событие уходит в тему `audit.events` ([ADR-003](ADR-003-kafka-events.md)).
3. Модуль `audit_admin` читает тему и вставляет запись в `audit_log`, дубли убирает уникальный `event_id` ([ADR-006](ADR-006-idempotency.md)). Запись появляется в течение нескольких секунд после действия.

Гарантия: «минимум один раз, без дублей». Сбой между шагами не теряет запись, потому что событие лежит в Outbox и в теме, пока не обработано.

### Неизменяемость (NFT-5.2)

| Мера | Что даёт |
| --- | --- |
| Роль базы приложения имеет только `INSERT` и `SELECT` на `audit_log` | Приложение не может править и удалять записи |
| Триггеры на `UPDATE`, `DELETE`, `TRUNCATE` вызывают ошибку | Защита от ошибки администратора и кода |
| Секционирование по месяцам, архивация старых секций, без удаления | Таблица не раздувается, записи сохраняются |
| Журнал читает только администратор через отдельный запрос, редактирования в интерфейсе нет | Следует из матрицы прав (шаг 9) |
| Срок хранения: не менее 3 лет, политика настраивается | Записи не удаляются автоматически |

### Обезличивание пользователя

Процедура по запросу пользователя или по решению администратора (FT-1.4). Журнал не меняется.

| Шаг | Что происходит | Где |
| --- | --- | --- |
| 1 | Учётная запись деактивируется, сессии отзываются | Keycloak, `identity` |
| 2 | Персональные поля пользователя заменяются: e-mail на служебное значение `anonymized-<id>@invalid`, телефон очищается, имя на «Удалён» | `platform_db`, Keycloak |
| 3 | **Соль пользователя удаляется.** Выводимый ключ `K_user` больше нельзя восстановить, поэтому хеши в журнале невозможно сопоставить с любым значением даже при утечке секрета аудита | `platform_db` |
| 4 | Событие `user.anonymized` (только идентификатор, без данных) читают `order-service` и `delivery-service` и заменяют снимки e-mail в заказах и выдачах служебным значением (INV-44) | `order_db`, `delivery_db` |
| 5 | Запись о самом обезличивании попадает в журнал | `audit_log` |

Финансовая история (заказы, платежи, операции баланса) сохраняется без персональных данных, как требует NFT-5.2. Данные об обращениях поддержки не содержат персональных значений (только идентификаторы и результат проверки кода).

### Журналы приложений и трассировка

Правило того же уровня: в журналах приложений и трассировке нет e-mail, телефонов и имён, только идентификаторы пользователей. Если значение попало бы в сообщение, фильтр логирования маскирует e-mail и телефон. Правило входит в соглашения (`conventions.md`, шаг 10) и проверяется тестом: поиск тестовых e-mail и телефонов в журналах после сценариев.

## Последствия

**Плюсы:**

- Журнал неизменяем и при этом не блокирует обезличивание: персональные данные в нём уже в виде хеша, а удаление соли делает хеши несопоставимыми (NFT-5.3).
- Утечка журнала не раскрывает персональные данные: без секрета аудита хеш не вычислить.
- Хеш позволяет доказать значение («была ли смена на этот e-mail») и заметить смену «на то же значение».
- Действие и запись согласованы Outbox: аудит не теряется при сбое.

**Минусы и риски:**

- Хеши остаются **псевдонимизацией**, пока соль жива и секрет известен: для короткого пространства значений (номер телефона) возможен перебор при утечке секрета вместе с солью. Поэтому секрет вне базы, а соль удаляется при обезличивании. Юридическую оценку статуса хешей необходимо получить до выхода в промышленную эксплуатацию (см. условие пересмотра).
- Нельзя восстановить значение из журнала при расследовании: можно лишь проверить гипотезу. Это сознательная цена защиты.
- Запись в журнале появляется с задержкой в секунды, а не в момент действия. Для аудита приемлемо.
- Нужно хранить соль пользователя и секрет и защищать их так же тщательно, как другие секреты. Потеря секрета делает прежние хеши непроверяемыми.
- Три места хранят снимки e-mail (учётная запись, заказ, выдача): обезличивание должно затрагивать их одновременно, иначе остаются ПД (INV-44). Поэтому процедура событийная и проверяется тестом.

## Когда пересмотреть

- Юридическая оценка покажет, что псевдонимизированные хеши остаются персональными данными и подлежат удалению: перейти на вариант без хешей (имя поля и идентификатор) для персональных полей или шифровать значения с уничтожением ключа (вариант 3).
- Потребуется доказуемая неизменяемость для внешнего аудита: добавить цепочку хешей записей (вариант 5) и выгрузку в хранилище с запретом перезаписи.
- Появятся персональные поля в других сервисах (R2: реквизиты продавца): перенести расчёт хеша в владельца этих данных, секрет аудита раздавать только по необходимости.
- Объём журнала вырастет настолько, что секционирование и архив понадобятся ранее: вынести журнал в отдельную базу.
