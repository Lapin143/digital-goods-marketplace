# ADR-009. Шифрование ключей (AES-256) и HMAC для проверки дублей

| Инварианты | INV-03, INV-20, INV-23 |

## Контекст

Ключ (код активации, лицензия, подарочная карта) это деньги в чистом виде. Кто прочитал значение, тот может его использовать. Требования (NFT-3.2, FT-4.2): ключи хранятся в зашифрованном виде (AES-256), не попадают в интерфейс после загрузки, логи и ответы API; мастер-ключ шифрования и секрет HMAC лежат вне базы данных.

Параллельно нужна проверка дублей внутри товара (FT-4.1) без расшифровки всего пула. Одинаковые значения в разных товарах допустимы, внутри товара нет. Короткие ключи (например, 16 знаков из ограниченного алфавита) можно подобрать перебором, если сравнивать по обычному хешу: поэтому требуется HMAC с секретом сервера, а не просто хеш.

Угрозы, которые нужно перекрыть: утечка дампа или резервной копии базы, SQL-инъекция, доступ администратора базы данных, утечка логов или трассировки, ошибка разработчика (значение в сообщении об ошибке), утечка мастер-ключа отдельно от базы.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| 1. Шифрование диска или базы целиком (TDE, LUKS) | Не нужен код в приложении | Защищает только от кражи носителя. Любой запрос к базе, резервная копия и администратор видят значения в открытом виде. Не соответствует требованию «зашифрованы и мастер-ключ вне базы» |
| 2. Шифрование на уровне приложения, один мастер-ключ напрямую шифрует значения | Просто | Ротация мастер-ключа означает перешифровать все ключи сразу. Компрометация мастер-ключа раскрывает всё без «второго слоя» |
| 3. Шифрование приложением, двухуровневое (envelope): мастер-ключ (KEK) шифрует ключи данных (DEK), DEK шифруют значения (выбрано) | Ротация KEK меняет только небольшую таблицу DEK. Новый DEK вводится без остановки: старые значения читаются по номеру версии. Привычная схема облачных KMS | Ещё одна таблица и немного кода. Нужно помнить версии |
| 4. Детерминированное шифрование (AES-SIV) вместо HMAC для проверки дублей | Один механизм | Один ключ и для чтения, и для сравнения: утечка ключа раскрывает и значения, и позволяет сопоставлять шифртексты. Смешаны две задачи, у которых разные требования к ротации |
| 5. Соль и медленный хеш (bcrypt, Argon2) для дублей | Устойчив к перебору | Соль случайна, поэтому два одинаковых значения дают разные хеши: уникальный индекс не работает, дубль не обнаружить |
| 6. Простой хеш SHA-256 для дублей | Просто, индекс работает | При утечке базы короткие ключи подбираются перебором за часы. Не соответствует FT-4.1 |

## Решение

Выбраны вариант 3 для значений и HMAC-SHA-256 с отдельным секретом для проверки дублей.

### Три секрета и где они лежат

| Секрет | Назначение | Где хранится | Ротация |
| --- | --- | --- | --- |
| Мастер-ключ (KEK), 256 бит | Шифрует ключи данных (DEK) | Хранилище секретов (секреты Docker и Kubernetes), файл `/run/secrets/inventory_kek` смонтирован в контейнер `inventory-service`. Не в базе, не в переменных окружения, не в образе и не в Git | Раз в год и при компрометации: новая версия KEK, перешифровка таблицы DEK (минуты) |
| Ключ данных (DEK), 256 бит, несколько версий | Шифрует значения ключей | В `inventory_db`, таблица `data_key`, зашифрован KEK (AES-256-GCM) | Новая версия раз в год или при подозрении: новые ключи шифруются новой версией, старые читаются по версии. Фоновая перешифровка старых значений по желанию |
| Секрет HMAC, 256 бит | Подпись для проверки дублей | Хранилище секретов, отдельный файл `/run/secrets/inventory_hmac`. Отдельный от KEK | Только при компрометации: фоновая миграция (расшифровать, пересчитать HMAC, записать), так как индекс зависит от секрета |

Секреты читаются при старте и держатся в памяти. Сервис не запускается без них. Резервная копия мастер-ключа и секрета HMAC хранится отдельно от резервных копий базы (минимум две копии, в разных местах): потеря KEK означает потерю всех ключей, поэтому порядок копирования и восстановления входит в руководство эксплуатации (Ф3).

### Шифрование значения

| Параметр | Значение |
| --- | --- |
| Алгоритм | AES-256-GCM (`AES/GCM/NoPadding`), шифрование с проверкой целостности |
| Nonce | 96 бит, случайный на каждое шифрование, хранится рядом |
| Дополнительные аутентифицируемые данные (AAD) | Идентификатор ключа и идентификатор товара. Шифртекст, перенесённый в другую строку или в другой товар, не расшифруется |
| Лимит DEK | Не более 2^32 шифрований на один DEK (рекомендация NIST). На нашем объёме недостижимо, но версия DEK меняется ежегодно |
| Что хранится в строке | `dek_id`, `nonce`, `ciphertext` (включая тег), `hmac`, `hmac_version`. Открытого значения нет нигде |

### HMAC для дублей

`hmac = HMAC-SHA-256(секрет_hmac, идентификатор_товара || 0x00 || значение)`, где значение предварительно нормализуется: убираются пробелы и перевод строки по краям, больше ничего (регистр значим). Включение идентификатора товара в подпись означает, что одинаковые значения в разных товарах дают разные HMAC (допустимо по FT-4.1) и не сопоставляются между товарами. Уникальный индекс `(product_id, hmac)` отклоняет дубль без расшифровки (INV-03, [ADR-007](ADR-007-double-issue-protection.md)).

### Загрузка пула (вручную и CSV)

1. Значения принимаются потоком по HTTPS через `api-gateway` в `inventory-service`. Тело запроса не логируется ни шлюзом, ни сервисом, размер ограничен (2 МБ, не более 10 000 строк за один файл). Пул до 100 000 ключей (глоссарий) набирается несколькими загрузками.
2. Сервис читает строки потоком: нормализация, вычисление HMAC, шифрование DEK, вставка пачками по 500 строк (`INSERT ... ON CONFLICT (product_id, hmac) DO NOTHING`, число отклонённых дублей считается по результату).
3. **Файл CSV нигде не сохраняется**: ни в объектном хранилище, ни на диске. Иначе копия с открытыми значениями жила бы вне шифрования, и защита теряла бы смысл. Ответ продавцу: сколько принято и сколько отклонено как дубли, с номерами строк, без значений.
4. Повторная загрузка того же файла безопасна: дубли отклоняются, принятые строки не двоятся ([ADR-006](ADR-006-idempotency.md)).

### Кто видит открытое значение

Открытое значение ключа существует в памяти двух сервисов и нигде больше.

| Сервис | Когда | Как |
| --- | --- | --- |
| `inventory-service` | Расшифровывает по запросу «значения ключей по заказу» | Только для заказа, ключи которого «выданы». Ответ в памяти, без записи |
| `delivery-service` | Получает значения, вкладывает в письмо, отдаёт провайдеру | Запрос по mTLS ([ADR-022](README.md)), сертификат определяет клиента: разрешён только `delivery-service`. В базу, события, логи значение не пишется ([ADR-011](ADR-011-guaranteed-delivery.md)) |

Оператор поддержки значение не видит ни в каком виде: он запускает повторную отправку, а письмо формирует выдача (FT-7.5, INV-23). Администратор и продавец после загрузки значения не видят тоже.

### Что попадает в журналы, события и трассировку

Ничего. Это набор правил, проверяемых тестами:

- Значение ключа обёрнуто в тип `SecretValue` с замаскированным `toString` и без сериализации в JSON и атрибуты трассировки.
- Ответ на «значения ключей по заказу» имеет заголовок `Cache-Control: no-store`, фильтр логирования тел запросов выключен для этого маршрута и для маршрута загрузки.
- Сообщения об ошибках содержат идентификаторы и номера строк, не значения.
- В событиях Kafka и в обращениях поддержки значений нет (INV-20).
- Тест «канарейка»: в интеграционном стенде загружается пул с заранее известными значениями, выполняется покупка и выдача, затем все журналы контейнеров, события Kafka и дамп `delivery_db` проверяются поиском этих значений. Ожидается ноль совпадений (NFT-3.2).

### Ротация и сбои

| Ситуация | Что делаем |
| --- | --- |
| Плановая смена KEK | Новый файл секрета с версией, сервис перешифровывает таблицу DEK, старый KEK удаляется после проверки |
| Плановая смена DEK | Новая версия для новых ключей, старые читаются |
| Компрометация KEK или DEK | Смена KEK, смена DEK, фоновая перешифровка всех значений, оценка раскрытых ключей и оповещение продавцов (процесс в модели угроз, шаг 9) |
| Компрометация секрета HMAC | Новый секрет, миграция HMAC, на время миграции проверка дублей идёт по паре версий |
| Потеря KEK без копии | Значения невосстановимы. Мера: резервные копии секретов, проверка восстановления раз в квартал |

## Последствия

**Плюсы:**

- Дамп базы, резервная копия или SQL-инъекция дают только шифртекст: без KEK ключи не прочитать.
- HMAC с секретом вне базы делает перебор коротких ключей по утечке базы бесполезным (FT-4.1).
- Двухуровневая схема даёт ротацию без остановки и без «большой перешифровки».
- Открытое значение существует в памяти двух сервисов и только на время запроса, сужена поверхность атаки.

**Минусы и риски:**

- Потеря мастер-ключа равна потере всех ключей. Нужна дисциплина резервных копий секретов и проверка восстановления.
- Секрет в памяти процесса: снимок памяти или отладчик раскрывают значения. Мера: ограничить доступ к хосту, не включать дампы памяти.
- Секрет в файле Docker или Kubernetes слабее выделенного хранилища с аудитом (Vault, KMS). Для стенда этого достаточно, в R3 переход на KMS или Vault.
- Миграция при смене секрета HMAC требует расшифровки всего пула и поэтому делается как плановая операция.
- Загрузка потоком без сохранения файла усложняет разбор ошибок: при сбое в середине файла продавец загружает его заново, дубли безопасны.
- Дополнительная нагрузка шифрования пренебрежимо мала при R1 (тысячи ключей).

## Когда пересмотреть

- Проект переедет на облако с KMS или появится Vault: вынести KEK туда, DEK шифровать через KMS.
- Требования регулятора или клиентов потребуют HSM или двойного контроля мастер-ключа.
- Объём пула вырастет до миллионов ключей: пересмотреть пачки загрузки, индекс по HMAC, секционирование.
- Появятся ключи с коротким сроком жизни или одноразовые токены: добавить политику удаления шифртекста после срока.
