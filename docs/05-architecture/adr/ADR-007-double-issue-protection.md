# ADR-007. Защита от двойной выдачи ключа: блокировка строк и ограничения базы

## Контекст

Один ключ нельзя выдать двум заказам. Допустимое число таких случаев ноль, даже при одновременных запросах (NFT-2.2). Опасные ситуации:

- Два покупателя одновременно оформляют заказ на последние ключи пула.
- Один и тот же запрос приходит дважды (повтор клиента, повтор события).
- Оплата и истечение резерва происходят в одну секунду ([ADR-013](ADR-013-late-payment.md)).
- Ошибка в коде, которая забыла проверить статус ключа.

Резерв охватывает всё заказанное количество, частичного резерва нет (INV-05). При этом оформление заказа с резервом должно укладываться в 1 секунду (NFT-1.2), а пулы бывают большими (тысячи ключей), поэтому ожидание на блокировках недопустимо.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| 1. Распределённая блокировка в Redis (Redlock или `SET NX PX`) | Знакомый приём, не нагружает базу | Блокировка не атомарна с записью в PostgreSQL. Если процесс «завис» дольше срока блокировки (пауза сборщика мусора, сеть), два владельца работают одновременно. Нужны токены ограждения (fencing), которые всё равно проверяет база. Потеря или перезапуск Redis снимает все блокировки. Redis становится критической зависимостью покупки. База остаётся единственным источником истины, а значит ограничения в ней обязательны, и блокировка в Redis лишь дублирует их |
| 2. Уровень изоляции `SERIALIZABLE` | Корректность без явных блокировок | При конкуренции за одни и те же строки СУБД отменяет транзакции (ошибка сериализации), нужен цикл повторов. Нагрузка и задержка растут именно в акции на популярный товар |
| 3. Оптимистичная блокировка ключа (колонка версии) | Нет ожидания на блокировках | Читаем свободные ключи, пытаемся занять, при конфликте повторяем. Много лишних попыток при конкуренции. Сложнее код, чем один запрос |
| 4. Блокировка строк `FOR UPDATE` без пропуска | Просто | Вторая транзакция ждёт, пока первая завершится. Блокировка нескольких строк в разном порядке даёт взаимные блокировки (deadlock). Задержка растёт с очередью |
| 5. Очередь на товар: все резервы одного товара обрабатывает один потребитель (ключ партиции равен товару) | Нет конкуренции по определению | Резерв должен быть синхронным и быстрым (NFT-1.2), очередь делает его асинхронным. Усложняет сагу ([ADR-004](ADR-004-saga-purchase.md)) |
| 6. `FOR UPDATE SKIP LOCKED` в одной транзакции, плюс ограничения и условные обновления как последний рубеж (выбрано) | Нет ожидания: занятые строки пропускаются, параллельные заказы получают разные ключи. Нет взаимных блокировок. Корректность держит сама база, внешних компонентов нет. Простой запрос | Возможна «ложная нехватка»: при гонке с транзакцией, которая потом откатится, второй заказ мог увидеть меньше свободных ключей и получить отказ (редко и безопасно). Нужны правильные индексы |

## Решение

Выбран вариант 6. Защита двухуровневая: **блокировка строк при выборе ключей** (не допускает гонку) и **ограничения и условные обновления в базе** (ловят ошибку кода, если гонка всё же прошла).

### Резерв ключей

Выполняется одной транзакцией в `inventory_db` по запросу «зарезервировать ключи» ([ADR-004](ADR-004-saga-purchase.md), шаг 2):

```sql
BEGIN;

-- сначала резерв: ключ ссылается на него внешним ключом fk_key_reservation_id
INSERT INTO reservation (id, order_id, product_id, quantity, status, expires_at)
VALUES (:reservation_id, :order_id, :product_id, :quantity, 'active', now() + :ttl);

WITH picked AS (
  SELECT id
  FROM   key
  WHERE  product_id = :product_id
    AND  status = 'free'
  ORDER  BY id
  LIMIT  :quantity
  FOR UPDATE SKIP LOCKED          -- занятые другой транзакцией строки пропускаются
)
UPDATE key k
SET    status = 'reserved', order_id = :order_id, reservation_id = :reservation_id
FROM   picked
WHERE  k.id = picked.id
RETURNING k.id;

-- если вернулось меньше :quantity строк: ROLLBACK (резерв откатывается вместе с ключами), ответ «ключей не хватает» (INV-05)

COMMIT;
```

Порядок важен: ключ со статусом «зарезервирован» обязан ссылаться на существующий резерв, поэтому вставка резерва идёт первой. Откат при нехватке ключей отменяет и вставку резерва, частичного резерва не остаётся. Порядок проверен на PostgreSQL 16 ([физическая модель](../../07-data/README.md), находка F12-1).

Параллельные заказы на последние ключи: пул 10 ключей, заказы A и B по 5 штук одновременно. A блокирует ключи 1-5, B пропускает их и блокирует 6-10: оба получают по 5 разных ключей. Если A и B по 6 штук, A получит 6, B увидит только 4 свободных, вернёт «не хватает» и откатится: резерв всё или ничего.

`ORDER BY id` делает выбор детерминированным (старые ключи уходят первыми) и снижает пересечения. Индекс для запроса частичный: `(product_id, id) WHERE status = 'free'`. Он держит выборку быстрой при пуле в десятки тысяч ключей.

### Последний рубеж: ограничения в базе

| Защита | Что гарантирует |
| --- | --- |
| Строка ключа одна и принадлежит одному заказу: колонка `order_id` в самой строке | Ключ не может принадлежать двум заказам одновременно (INV-01) |
| `CHECK`: статус «свободен» только при пустом `order_id`, статусы «зарезервирован» и «выдан» только при заполненном (INV-02) | Нельзя оставить ключ привязанным после снятия резерва или свободным после выдачи |
| Условные обновления: `UPDATE key SET status = 'issued' WHERE order_id = :o AND reservation_id = :r AND status = 'reserved'`, число изменённых строк обязано равняться количеству | Подтверждение резерва не затронет чужие и уже изменённые ключи. Расхождение числа строк откатывает транзакцию |
| Триггер `BEFORE UPDATE`: переход из «выдан» в «свободен» или «зарезервирован» и любой переход из «аннулирован» запрещён (INV-04) | Главная защита SM-03: выданный ключ не вернётся в оборот даже при ошибке кода |
| Уникальный индекс `(product_id, hmac)` | Дубли значений внутри товара не загружаются (INV-03, [ADR-009](ADR-009-key-encryption-hmac.md)) |
| Частичный уникальный индекс резерва `(order_id) WHERE status = 'active'` | У заказа не больше одного активного резерва (INV-06) |
| Роль базы приложения без прав `DELETE` на `key` | Ключ нельзя удалить из оборота случайным запросом |

### Подтверждение резерва и снятие

Подтверждение ([ADR-004](ADR-004-saga-purchase.md), шаг 5) и снятие резерва по сроку, отказу или отмене ([ADR-012](ADR-012-reservation-redis-timer.md)) выполняются условными обновлениями «если сейчас активен»: побеждает тот, кто первым зафиксировал изменение, второй получает ноль изменённых строк и действует по правилам поздней оплаты ([ADR-013](ADR-013-late-payment.md)). Блокировка строки резерва `SELECT ... FOR UPDATE` берётся на время обработки одной операции.

### Проверка

Автоматический тест с Testcontainers (PostgreSQL 16): 50 потоков одновременно резервируют ключи из пула в 20 штук по 1-3 ключа. Утверждения: ни один ключ не привязан к двум заказам, число зарезервированных ключей не превышает размер пула, каждый заказ получил весь объём или ничего. Тот же сценарий проверяется на уровне SQL при проектировании физической модели (шаг 12). Дополнительно: тест «ключ в статусе «выдан» нельзя перевести в «свободен»» (должен сработать триггер).

## Последствия

**Плюсы:**

- Дубль ключа невозможен без нарушения ограничений базы, а не «маловероятен»: защита держится на самой СУБД.
- Никакого ожидания: занятые строки пропускаются, нет взаимных блокировок, задержка резерва не растёт с очередью (NFT-1.2).
- Нет зависимости от Redis на этом пути: потеря Redis не ломает выдачу.
- Правило «всё или ничего» (INV-05) выражено структурой транзакции.

**Минусы и риски:**

- Ложная нехватка при гонке с откатываемой транзакцией: покупатель получит отказ при формально достаточном остатке. Метрика отказов по нехватке сравнивается с остатком, всплески разбираются.
- Корректность зависит от индексов и от того, что весь доступ к ключам идёт через один модуль `inventory`. Защита: ArchUnit-правила, роль базы только на нужные операции, триггер на переходы.
- Блокировки держатся до конца транзакции: транзакция резерва должна быть короткой (никаких внешних вызовов внутри).
- Пул с миллионами ключей потребует секционирования таблицы или отдельного хранилища: за пределами R1.

## Когда пересмотреть

- Профиль нагрузки изменится на тысячи резервов в секунду на один товар: рассмотреть очередь на товар или счётчик остатка с отдельным распределением ключей.
- Появится выдача ключей несколькими базами (шардирование по продавцам): пересмотреть, как гарантировать уникальность ключа между шардами.
- Метрика «ложной нехватки» покажет заметные потери продаж: добавить один повтор выборки при нехватке.
