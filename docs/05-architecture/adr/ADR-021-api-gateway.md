## Контекст

API Gateway единая точка входа в систему из интернета (раздел 8.2 требований): покупатели, продавцы, сотрудники работают через веб-интерфейс, в R2 продавцы вызывают API по ключу (FT-10.0), внешние системы (платёжный шлюз, e-mail-провайдер, SMS-провайдер) присылают уведомления.

Что должен делать шлюз:

1. Проверять токен доступа (JWT от Keycloak): подпись, срок, издатель, адресат.
2. Ограничивать частоту запросов с учётом пользователя, IP и маршрута, в том числе распределённо через Redis (NFT-3.5).
3. Маршрутизировать запросы к сервисам и пропускать вебхуки внешних систем без токена (подпись проверяет сервис).
4. В R2 проверять API-ключ продавца (хранится только хеш, NFT-3.4) и передавать сервису идентификатор продавца.
5. Ограничивать размер тела и срок запроса, добавлять сквозные заголовки (`traceparent`, `X-Correlation-Id`, NFT-6.0), отдавать метрики (NFT-6.1).

Ограничения среды: ноутбук с 8 ГБ памяти, у WSL 3 ГБ, поэтому память шлюза имеет значение. Команда пишет на Java и Spring.

Чего шлюз делать **не должен**: бизнес-логику, агрегацию ответов, тонкую авторизацию по ролям и владельцу ресурса. Умный шлюз превращается в ещё один сервис с бизнес-правилами и становится узким местом всех релизов.

## Рассмотренные варианты

| Критерий | Spring Cloud Gateway | Kong (без базы, декларативная конфигурация) | Traefik | NGINX |
| --- | --- | --- | --- | --- |
| Проверка JWT с автоматическим получением ключей Keycloak (JWKS) и их ротацией | Да, resource server из Spring Security | В открытой версии ограничена (подключение по ключам потребителей, плагин OIDC коммерческий, есть сторонние) | Через внешний сервис проверки (`forwardAuth`), сам не проверяет | Только с коммерческой версией или через Lua |
| Распределённое ограничение частоты через Redis | Да, `RedisRateLimiter`, по пользователю, IP, ключу | Да, плагин `rate-limiting` с Redis | Только в пределах одного экземпляра в открытой версии | `limit_req` в пределах одного экземпляра, Redis через Lua |
| API-ключ продавца со сверкой хеша в сервисе и кэшем | Своим фильтром на Java, привычный код | Плагин `key-auth` хранит ключи в самом Kong, наша модель с хешем в `catalog-service` потребует своего плагина | Через `forwardAuth` | Через Lua или `auth_request` |
| Память | 300-400 МБ (JVM, Netty) | 150-300 МБ | 50-100 МБ | 20-50 МБ |
| Свой код и тесты | Java, те же инструменты, что у сервисов (WebTestClient) | Плагины на Lua, Go или JavaScript, другой стек | Плагины на Go, ограниченно | Lua |
| Метрики и трассировка | Micrometer, OpenTelemetry, как в сервисах | Плагины Prometheus и OpenTelemetry | Prometheus, OpenTelemetry | Через модули |
| Единая модель для разработчика и сопровождения | Один язык и один инструмент сборки на весь проект | Отдельная технология и конфигурация | Отдельная технология | Отдельная технология |

Оценка:

- **Spring Cloud Gateway.** Закрывает все пять функций без стороннего кода. Минусы: больше памяти, чем у лёгких прокси; реактивная модель (WebFlux) непривычна; соблазн добавить логику.
- **Kong.** Зрелый, с богатой экосистемой, но ключевая для нас функция (проверка JWT по JWKS Keycloak) в открытой версии требует обходных путей, а плагины пишутся на другом стеке. Оправдан при большом числе внешних интеграций и командах.
- **Traefik.** Лёгкий и удобный для Compose и k3s как входной прокси, но без проверки токена и без распределённого ограничения частоты в открытой версии. Подходит как внешний ingress перед шлюзом, не вместо него.
- **NGINX.** Самый лёгкий и быстрый, но проверка токена, ограничение частоты с Redis и API-ключи нужно собирать из Lua или внешних сервисов. Сопровождение таких конфигураций сложнее самого шлюза.

## Решение

Выбран **Spring Cloud Gateway**. Причины: функции из списка закрываются штатными средствами и коротким Java-кодом, тот же язык, тесты и метрики, что у сервисов; 300-400 МБ памяти укладываются в бюджет (шаг 8); цель проекта включает привычный стек Spring.

### Правило «тонкого шлюза»

Шлюз выполняет только перечисленное. Всё остальное запрещено и проверяется на ревью и тестами.

| Разрешено | Запрещено |
| --- | --- |
| Маршрутизация по пути | Бизнес-логика, правила предметной области |
| Проверка токена: подпись, срок, издатель (`iss`), адресат (`aud`) | Агрегация ответов нескольких сервисов, преобразование тел |
| Грубая проверка области токена (`scope`) на маршрут | Проверка ролей и владельца ресурса (это делает сервис) |
| Ограничение частоты, размера тела, времени запроса | Хранение состояния, кроме счётчиков в Redis |
| Нормализация заголовков: `traceparent`, `X-Correlation-Id`, удаление внешних заголовков с внутренним смыслом | Подмена токена, передача личности в заголовках вместо токена |
| R2: проверка API-ключа и передача `X-Seller-Id` для маршрутов API продавца | Обращения к базам данных |

Токен передаётся сервису **без изменений**, а каждый сервис сам проверяет его подпись и срок как resource server. Это защита в глубину: сервис не доверяет «вежливому» заголовку, если до него добрался запрос в обход шлюза ([ADR-022](ADR-022-internal-traffic-encryption.md)).

### Маршруты

Пути версионируются (`/api/v1`, Ф5, [ADR-018](README.md)). Пример группировки, точные пути задаёт OpenAPI (шаг 11).

| Группа | Аутентификация | Область | Куда | Лимит по умолчанию |
| --- | --- | --- | --- | --- |
| Витрина: каталог, карточка, поиск | Не нужна | | `catalog-service` | 60 запросов в минуту с IP, пик 120 |
| Веб-интерфейс: `/` | Не нужна | | `web-app` | 300 запросов в минуту с IP, статические файлы |
| Документы продавцов: `/files/**` | Подписанная ссылка, подпись проверяет `object-storage` | | `object-storage` | 60 запросов в минуту с IP, срок ссылки 5 минут |
| Покупатель: заказ, история, обращения | JWT | `orders.read`, `orders.create`, `support.write` | `order-service`, `platform-service` | 120 в минуту на пользователя. `POST /orders` 10 в минуту |
| Кабинет учётной записи: телефон, смена e-mail, смена номера | JWT | `account.manage` (нет у сессий по SMS) | `platform-service` | 30 в минуту на пользователя |
| Заявка на статус продавца | JWT | `seller.apply` (нет у сессий по SMS) | `catalog-service` | 30 в минуту на пользователя |
| Продавец: товары, ключи, остатки | JWT с 2FA | `seller.catalog` | `catalog-service`, `inventory-service` | 60 в минуту на пользователя, загрузка пулов 6 в час |
| Кабинеты сотрудников | JWT с 2FA | `staff.moderation`, `staff.support`, `staff.admin`, `staff.audit` | `platform-service`, `catalog-service`, `payment-service` | 120 в минуту на пользователя |
| Вебхуки шлюза, e-mail- и SMS-провайдера | Подпись проверяет сервис | | `payment-service`, `delivery-service`, `platform-service` | 300 в минуту с IP источника, тело до 64 КБ |
| Вход и токены Keycloak | Не нужна | | `keycloak` | 30 в минуту с IP, дополнительно защита Keycloak от подбора пароля |
| R2: API продавца | API-ключ | `seller.api` | `delivery-service`, `catalog-service`, `inventory-service` | 600 в минуту на ключ (NFT-3.5) |

Маршрут `/files/**` не отдаёт документ сам: шлюз пересылает запрос в `object-storage` без изменений. Хост и параметры запроса сохраняются, потому что подпись ссылки S3 покрывает их, любое изменение даёт отказ хранилища. Ссылку создаёт `catalog-service` ([SEQ-06](../sequence-seller-approval.md)). Единая точка входа на порту 443 нужна, чтобы наружу публиковался один сертификат и один набор лимитов ([c4-deployment.md](../c4-deployment.md), раздел 9).

Все лимиты это значения по умолчанию, настраиваются конфигурацией (часть параметров платформы, FT-11.1, подключается в Ф4). Лимиты кодов подтверждения реализует `platform-service`, а не шлюз ([ADR-010](ADR-010-keycloak-sms-codes.md)).

### Ограничение частоты и сбой Redis

Алгоритм «корзина токенов» (`RedisRateLimiter`), ключ лимита зависит от группы: пользователь из токена, иначе IP, для R2 идентификатор API-ключа. При превышении ответ 429 с заголовком `Retry-After`. Если Redis недоступен, **шлюз пропускает запросы** (доступность важнее точности лимита), пишет метрику и оповещение. Критичные для безопасности лимиты (коды, SMS) находятся в `platform-service` и при недоступности Redis работают в режиме отказа ([ADR-010](ADR-010-keycloak-sms-codes.md)).

### API-ключ продавца (R2)

Фильтр шлюза берёт ключ из заголовка `X-Api-Key`, считает SHA-256 и спрашивает `catalog-service` (модуль `seller_onboarding`) по внутреннему вызову: действителен ли ключ, какой продавец, какие права. Ответ кэшируется в Redis на **30 секунд**. Отзыв ключа вступает в силу не позднее чем через 30 секунд. Подписка шлюза на события Kafka не вводится, чтобы шлюз не получил новую тяжёлую зависимость. Значение ключа в журналы не пишется.

### Прочее

- **Безопасность.** TLS 1.2 и выше на входе (NFT-3.3), на стенде сертификат частного центра, на сервере публично доверенный. Размер тела ограничен 2 МБ (загрузка пулов, [ADR-009](ADR-009-key-encryption-hmac.md)), сроки соединения и чтения заданы. Тела запросов к маршрутам загрузки ключей и выдачи не логируются.
- **CORS.** Разрешены только источники веб-интерфейса.
- **Сквозная трассировка.** Шлюз создаёт `traceparent`, если его нет, и `X-Correlation-Id` (NFT-6.0).
- **Метрики.** Число запросов, задержки (95-й перцентиль), коды ответов, отказы по лимиту, ошибки проверки токена (NFT-6.1).
- **Масштабирование.** Шлюз без состояния, счётчики в Redis, можно запускать несколько экземпляров (NFT-1.3).

## Последствия

**Плюсы:**

- Одна технология и один набор инструментов с сервисами: тот же язык, тесты, метрики. Нет отдельной сущности «конфигурация прокси», которую знает один человек.
- Проверка токена с автоматической ротацией ключей Keycloak и распределённый лимит из коробки.
- Простая реализация API-ключей R2 нужной нам модели (хеш в `catalog-service`, кэш).
- Защита в глубину: сервис не доверяет шлюзу вслепую, токен проверяется дважды.

**Минусы и риски:**

- Шлюз потребляет 300-400 МБ памяти. Это существенная часть бюджета ноутбука. В профиле `core` он нужен, при нехватке памяти допустим профиль без части сервисов, но не без шлюза.
- Реактивная модель сложнее императивной: ошибки блокирующего кода в потоках Netty. Защита: фильтры без блокирующих вызовов, нагрузочные тесты в Ф5.
- Искушение добавить «немного логики» в шлюз. Защита: правило тонкого шлюза, список разрешённых фильтров, ревью.
- Шлюз единая точка отказа. На стенде один экземпляр, при росте несколько за балансировщиком (Ф6).
- Отзыв API-ключа действует с задержкой до 30 секунд.

## Когда пересмотреть

- Замеры памяти в Ф3 покажут, что шлюз не помещается в профиль `core`: заменить на NGINX или Traefik с внешней проверкой токена отдельной небольшой службой, либо сократить остальной стек.
- Число внешних потребителей API вырастет (партнёры, тарифы, портал разработчика): оценить Kong или облачный шлюз с готовым управлением ключами.
- Появятся требования к WAF, защите от ботов и управлению сертификатами на входе: добавить внешний ingress (Traefik или NGINX) перед шлюзом.
- Нагрузка на шлюз станет узким местом: масштабировать горизонтально, при необходимости вынести проверку токена на уровень ingress.
