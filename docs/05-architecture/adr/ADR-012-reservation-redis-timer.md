# ADR-012. Резерв: PostgreSQL как источник истины, Redis как таймер

| Поле | Содержание |
| --- | --- |
| Статус | Принято |

| Требования | FT-5.2, FT-6.3, FT-6.5, NFT-1.0, NFT-1.2, NFT-3.5, NFT-4.3, раздел 8.2 требований |
| Инварианты | INV-05, INV-06, INV-07 |
| Связанные документы | [SM-08](../../03-processes/SM-08-reservation.md), [SM-03](../../03-processes/SM-03-key.md), [SM-01](../../03-processes/SM-01-order.md) (T6), [BPMN-01](../../03-processes/BPMN-01-purchase.md) (E4) |
| Связанные ADR | [ADR-004](ADR-004-saga-purchase.md), [ADR-007](ADR-007-double-issue-protection.md), [ADR-013](ADR-013-late-payment.md) |

## Контекст

Ключи заказа остаются закреплёнными за ним 15 минут (параметр платформы, FT-5.2). Если оплаты нет, резерв надо снять, ключи вернуть в продажу и отменить заказ (T6, E4). Снимать резерв точно по сроку важно: заморозка ключей дольше срока лишает продавца продаж, снятие раньше срока лишает покупателя законного времени на оплату.

Задачи, которые решает механизм:

1. **Хранение резерва.** Резерв, ключи и заказ должны меняться согласованно (INV-05, INV-06).
2. **Срабатывание по времени.** Нужен таймер на 15 минут для каждого резерва, переживающий сбой.
3. **Гонка с оплатой.** Оплата и истечение срока могут совпасть ([ADR-013](ADR-013-late-payment.md)).

Раздел 8.2 требований уже фиксирует направление: источник истины в PostgreSQL, Redis с TTL только запускает снятие, сверяющая задача исправляет расхождения.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| 1. Резерв только в Redis (запись с TTL) | Быстро, срок «из коробки» | Резерв, ключи и заказ меняются в двух хранилищах: нет общей транзакции. Перезапуск или вытеснение записи теряют резерв, ключи остаются замороженными или резерв исчезает при активной оплате. Нарушает INV-05 и INV-06 |
| 2. Резерв только в PostgreSQL, периодический опрос просроченных | Одно хранилище, транзакционно, проще всего, надёжно | Точность равна интервалу опроса: чтобы снимать с точностью секунды, нужен частый опрос. Redis в таймере не нужен вовсе |
| 3. Redis с TTL и уведомлениями об истечении (keyspace notifications) | Срабатывание ровно по сроку, без опроса | Уведомления доставляются без гарантий: если подписчик в момент истечения недоступен, событие пропадает. Использовать нельзя как единственный механизм |
| 4. PostgreSQL как источник истины, отсортированное множество в Redis как таймер, сверяющая задача как страховка (выбрано) | Точность в секунды при обычной работе. Потеря Redis не теряет данных: резерв в базе, страховка снимает просроченные. Состояние и таймер разведены: таймер можно потерять и восстановить | Два механизма срабатывания. Таймер Redis не атомарен с базой, поэтому нужна идемпотентная обработка и сверка |

Честная оценка: вариант 2 проще и для нагрузки R1 вполне хватает. Вариант 4 выбран, потому что он следует разделу 8.2, даёт точность в секунды без частого опроса базы и показывает рабочий шаблон «источник истины и ускоритель» (Redis уже есть в стенде для кэша и ограничения частоты). Корректность держит база и сверяющая задача, Redis только ускоряет.

## Решение

Выбран вариант 4.

### Что где лежит

| Данные | Хранилище | Роль |
| --- | --- | --- |
| Резерв (статус, срок `expires_at`, причина снятия) и привязка ключей | PostgreSQL, `inventory_db` | Источник истины. Все решения принимаются по нему |
| Расписание срабатываний | Redis, отсортированное множество `reservation:expiry`, оценка равна времени окончания, элемент равен идентификатору резерва | Таймер. Может быть потеряно целиком без последствий для данных |

### Жизненный цикл таймера

| Событие | Действие |
| --- | --- |
| Резерв создан (транзакция зафиксирована) | `ZADD reservation:expiry <окончание> <идентификатор резерва>`. Если Redis недоступен, ошибка пишется в журнал и в метрику, резерв остаётся валидным, снимет его сверяющая задача |
| Исполнитель таймера, раз в секунду | `ZRANGEBYSCORE reservation:expiry -inf <сейчас> LIMIT 0 100`. Для каждого элемента вызывается снятие по сроку (ниже). После обработки элемент удаляется из множества `ZREM` |
| Резерв использован или снят раньше срока | `ZREM` (необязателен: исполнитель найдёт неактивный резерв и просто уберёт элемент) |
| Старт сервиса | Все активные резервы из базы записываются в множество (`ZADD`), так восстанавливается таймер после потери Redis |

### Снятие по сроку (общее для таймера и сверки)

Условное обновление по времени базы данных, выполняется в одной транзакции:

```sql
UPDATE reservation
SET    status = 'released', release_reason = 'expired', released_at = now()
WHERE  id = :id AND status = 'active' AND expires_at <= now();
-- если обновлена одна строка:
UPDATE key SET status = 'free', order_id = NULL, reservation_id = NULL
WHERE  reservation_id = :id AND status = 'reserved';
-- запись события reservation.expired в outbox (одна транзакция)
```

Если обновлено ноль строк, резерв уже использован, снят или срок ещё не наступил: ничего не меняется. Это делает обработку идемпотентной: два экземпляра сервиса или таймер вместе со сверкой не снимут резерв дважды ([ADR-006](ADR-006-idempotency.md)). Время сравнивается по часам базы, а не по часам приложения, поэтому расхождение часов серверов не влияет на решение.

### Сверяющая задача

Раз в 60 секунд: `SELECT id FROM reservation WHERE status = 'active' AND expires_at < now() - interval '30 seconds' ORDER BY expires_at LIMIT 100 FOR UPDATE SKIP LOCKED`, для каждой строки то же снятие по сроку. Запас в 30 секунд даёт таймеру Redis время сработать первым, так что в норме сверка ничего не находит. Находка сверки это сигнал о проблеме таймера: увеличивается метрика `reservation_reconciled_total`, при росте выше нуля срабатывает оповещение.

### Поведение при потере Redis

| Ситуация | Что происходит | Влияние |
| --- | --- | --- |
| Redis недоступен при создании резерва | Резерв создаётся, таймер не поставлен | Резерв снимется сверкой на 30-90 секунд позже срока |
| Redis перезапущен без данных (таймеры потеряны) | Сверка снимает все просроченные резервы. При старте сервиса таймер восстанавливается из базы | Задержка снятия до 90 секунд для резервов, чей срок пришёлся на простой |
| Redis долго недоступен | Резервы снимает только сверка с точностью до 90 секунд | Покупка и оплата работают, продажи не страдают |
| Исполнитель упал после чтения из Redis до записи в базу | Элемент остаётся в множестве, будет обработан повторно | Идемпотентность не даёт двойного эффекта |

Резервирование и оплата **не зависят** от Redis (ключи резервируются в базе, [ADR-007](ADR-007-double-issue-protection.md)). Потеря Redis ухудшает только точность срока.

### Гонка с оплатой

Подтверждение резерва ([ADR-004](ADR-004-saga-purchase.md), шаг 5) и снятие по сроку выполняют условные обновления «если сейчас активен». Побеждает тот, кто первым зафиксировал изменение. Если резерв уже снят, обработка идёт по правилам поздней оплаты ([ADR-013](ADR-013-late-payment.md)). Срок оплаты на стороне шлюза (12 минут) строго короче резерва (15 минут, INV-07), запас в 3 минуты закрывает основную часть задержек уведомления.

### Настройки Redis

Один экземпляр на стенде используется для кэша каталога, счётчиков ограничения частоты, одноразовых кодов и таймеров резерва.

| Настройка | Значение | Причина |
| --- | --- | --- |
| `maxmemory` | 128 МБ | Хватает на кэш карточек и коды с большим запасом, укладывается в бюджет памяти |
| `maxmemory-policy` | `volatile-lru` | Вытесняются только записи с TTL (кэш). Множество таймера без TTL не вытесняется |
| Хранение | AOF `everysec` необязательно | Данные Redis не источник истины, потеря допустима |

Одноразовые коды (TTL 5 минут) тоже записи с TTL: в случае нехватки памяти их вытеснение превратилось бы в отказ входа. Поэтому объём кэша ограничен на уровне приложения, а метрика вытеснений (`evicted_keys`) под оповещением ([ADR-010](README.md)).

## Последствия

**Плюсы:**

- Данные о резервах и ключах согласованы транзакционно, Redis не может «потерять» резерв.
- Срок срабатывает с точностью до секунды в обычной работе без частого опроса базы.
- Потеря Redis не останавливает продажи: ухудшается только точность срока (до 90 секунд).
- Идемпотентное снятие позволяет запускать таймер, сверку и несколько экземпляров сервиса одновременно.

**Минусы и риски:**

- Два механизма срабатывания требуют тестов на сбои: потеря Redis, падение между чтением и записью, одновременный запуск таймера и сверки.
- Таймер не атомарен с базой, поэтому правило «все решения по базе» нельзя нарушать (никакой логики «если в Redis нет, значит снят»).
- Оценка таймера задаётся по часам приложения, снятие проверяется по часам базы. Допустимо: таймер лишь предлагает, база решает.
- Redis добавляет компонент в профиль `core`, хотя вариант 2 справился бы без него. Это осознанный выбор ради шаблона и точности.

## Когда пересмотреть

- Замеры в Ф3 покажут, что опрос базы раз в секунду по частичному индексу дешевле и проще, чем Redis: упростить до варианта 2.
- Redis станет недоступен чаще, чем раз в месяц, или его нагрузка вырастет: вынести таймеры в отдельный экземпляр.
- Нагрузка вырастет до тысяч резервов в секунду: пересмотреть пачки исполнителя и частоту сверки.
- Срок резерва станет зависеть от товара или продавца: хранить срок в резерве (уже хранится) и позволить разный TTL.
