## Контекст

С Ф4 у проекта появляется настоящий интерфейс: витрина и вход, кабинет продавца, рабочее место модератора (срез 1), затем заказ и история заказов (срез 2), поддержка, параметры и аудит (срез 3). В Ф3 `frontend/web-app` это страница-заглушка на nginx без сборки. В [c4-containers.md](../c4-containers.md) указаны React и TypeScript, а сборщик и остальной стек нигде не выбраны.

Требования и ограничения:

1. **Тонкий слой над контрактами.** Бизнес-правила проверяются сервисами; интерфейс показывает данные и собирает запросы ([решение 4 стратегии тестирования](../../08-testing/test-strategy.md)).
2. **Русский язык без жёстко заданных текстов** (NFT-7.0): все тексты в словаре, правило ESLint запрещает строки в разметке.
3. **Три группы пользователей и три способа входа.** Покупатель входит через клиент `dgm-web`, продавец и сотрудники через `dgm-staff` (обязательный второй фактор), вход по коду из SMS через `dgm-sms` (ограниченная сессия 15 минут, без refresh-токена, [ADR-010](ADR-010-keycloak-sms-codes.md)).
4. **Цепочка поставок** (T-42): чем меньше пакетов, тем меньше риск. В Ф3 заглушки внешних систем вообще без пакетов; для интерфейса без пакетов не обойтись, но их число и версии контролируются.
5. **Память и время сборки.** Контейнер `web-app` 64 МБ ([memory-budget.md](../../09-operations/memory-budget.md)), раздаёт только статические файлы. Сборка идёт в CI (в рабочей среде `npm install` недоступен).
6. **Один адрес.** Интерфейс и API на одном адресе шлюза, поэтому CORS не нужен.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| 1. Vite, React, строгий TypeScript, свои компоненты, `oidc-client-ts`, типы из OpenAPI | Минимум зависимостей, полный контроль доступности и русских текстов, сборка статикой для nginx. Типы запросов выводятся из контрактов и ловят расхождение с API при сборке | Больше собственного кода (кнопки, таблицы, формы), чем с готовой библиотекой |
| 2. React с готовой библиотекой компонентов (MUI, Ant Design) | Быстрый старт, готовые таблицы и формы | Десятки транзитивных пакетов и тяжёлая сборка, чужая локализация, сложнее выдержать единый вид и WCAG AA без борьбы с библиотекой |
| 3. Next.js | Серверный рендеринг, маршрутизация из коробки | Нужен серверный процесс Node и память под него, которых в бюджете нет. Серверная часть не требуется: все данные приходят из API |
| 4. Серверные шаблоны (Thymeleaf в сервисах) | Нет отдельного фронтенда | Смешивает интерфейс с сервисами, противоречит контейнеру `web-app` и разделению ролей, вход через OIDC в браузере был бы сложнее |

## Решение

Выбран вариант 1. Состав:

| Что | Выбор |
| --- | --- |
| Сборщик и язык | Vite, React 19, TypeScript в строгом режиме |
| Маршрутизация и данные | React Router, TanStack Query |
| Вход | `oidc-client-ts`: код авторизации с PKCE, токены только в памяти, обновление по refresh-токену для `dgm-web` и `dgm-staff` |
| Клиент API | Типы из OpenAPI (`openapi-typescript` при сборке), тонкая обёртка запроса: `Idempotency-Key`, `If-Match`, разбор `application/problem+json` |
| Стили и компоненты | CSS-модули и свои компоненты; адаптив 360–2560 px, WCAG AA, навигация с клавиатуры |
| Тексты | Словарь `ru.json`, правило ESLint против строковых литералов в разметке (NFT-7.0) |
| Проверки | ESLint, `tsc --noEmit`, Vitest и Testing Library в задании `web` CI; 3–5 дымовых сценариев Playwright по решению 4 стратегии, если останется время |
| Поставка | Многоэтапный `Dockerfile`: сборка в образе Node, раздача статики nginx без прав root |

**Два менеджера входа** (решение Р-24 руководства Ф4). Одно приложение держит два экземпляра `UserManager`: маршруты `/seller/*` и `/staff/*` идут через `dgm-staff`, остальные через `dgm-web`. Вход по коду из SMS открывается со страницы «нет доступа к e-mail» и ведёт на `dgm-sms`; приложение в этом режиме показывает только заказы и обращения. Выбор клиента определяется по префиксу маршрута, а не по роли: роль известна только после входа.

**Версии зависимостей** фиксируются в `package-lock.json`, обновления приходят запросами Dependabot, сборка использует `npm ci`. Новая зависимость проходит то же обсуждение, что и в сервисах: что делает, чем заменить собственным кодом, как давно развивается.

## Последствия

**Плюсы:**
- Короткая цепочка поставок, воспроизводимая сборка, статика на nginx (64 МБ).
- Типы из контракта ловят расхождение API и интерфейса при сборке, а не в браузере.
- Доступность и русская локализация под нашим контролем.

**Минусы и риски:**
- Свои компоненты занимают часть часов среза (оценка вшита в шаги 16–19). Смягчение: компонентов немного, их набор растёт по мере экранов.
- Токены в памяти пропадают при перезагрузке страницы, вход проходит заново (тихо, если сессия Keycloak жива). Это осознанная плата за защиту от кражи токена из хранилища браузера (угроза T-07).
- Playwright не входит в критерии выхода: интерфейс проверяется на уровне API, а дымовые сценарии это бонус.

## Когда пересмотреть

Если появятся требования к серверному рендерингу (SEO витрины в публичной демке) или число экранов вырастет настолько, что своих компонентов станет слишком много: тогда оценивается готовая библиотека, которая совместима с WCAG AA и русской локализацией и не тащит десятки пакетов.
