## Контекст

Ф3 первая фаза с исполняемым кодом, поэтому нужно один раз и явно решить вопросы, которые иначе решались бы случайно в каждом модуле: какая версия Java, чем собирать, как устроен репозиторий, как строятся образы и откуда берутся версии зависимостей. Отложенный в плане вопрос D-4 («версии после проверки актуальных релизов») закрывается здесь и в [versions.md](../../09-operations/versions.md).

Условия:

1. Проект ведёт один человек, который не пишет Java ежедневно, а часть работы выполняет ИИ-ассистент. Значит, инструменты должны быть стандартными, а конфигурация короткой и проверяемой.
2. Код нельзя собрать там, где он пишется: реестры пакетов и образов из рабочей среды недоступны. Единственный судья GitHub Actions ([план Ф3](../../00-phase3-guide.md)). Сборка должна быть быстрой на раннере и воспроизводимой.
3. Ноутбук с 8 ГБ памяти и 3 ГБ для WSL. Сервисы в Compose ограничены `Xmx` 160–192 МБ ([memory-budget.md](../../09-operations/memory-budget.md)), поэтому выбор среды выполнения влияет на то, помещаются ли наборы.
4. В документах Ф2 сборщик назван по-разному: [c4-deployment.md](../c4-deployment.md) и memory-budget говорят «из Gradle и IDE», а [c4-components.md](../c4-components.md) говорил «Maven-зависимостью». Нужно единое решение.
5. Проект показывается в резюме, значит в нём важны воспроизводимость, цепочка поставок и читаемость.

## Рассмотренные варианты

Сборщик (основное решение):

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| Gradle, Kotlin DSL, один мультипроект, каталог версий `libs.versions.toml` | Инкрементальная сборка и кэш сборки: на раннере и ноутбуке пересобирается только изменённое. Каталог версий даёт одну точку правды. Запуск сервисов из Gradle и IDE уже предусмотрен наборами `dev-*` ([c4-deployment.md](../c4-deployment.md)). Стандарт в большинстве Java-команд, в том числе в крупных компаниях. Контракты видны как типизированный Kotlin | Кривая обучения выше, чем у Maven. Файл `gradle-wrapper.jar` двоичный и лежит в репозитории (проверяется контрольной суммой). Kotlin DSL медленнее разбирается при первом запуске |
| Maven, многомодульный проект | Декларативный XML, жёсткий жизненный цикл, много примеров. Родительский POM Spring Boot даёт готовые настройки | Нет кэша сборки уровня Gradle, пересборка всех модулей дольше. Общая логика сборки (проверки, сборка образов) растягивается на плагины и профили. Расходится с остальными документами Ф2 |
| Gradle, Groovy DSL | Много примеров в документации и на форумах | Динамическая типизация: ошибки в сборке находятся при запуске, а не в редакторе. Новый код проекта лучше писать на Kotlin DSL, который Gradle считает основным |

Версия Java:

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| Java 25 LTS | Линейка с долгой поддержкой (Temurin не раньше 2031 года). Spring Boot 4.1 поддерживает Java 17–26. Виртуальные потоки без закрепления на мониторах, компактные заголовки объектов (`-XX:+UseCompactObjectHeaders`) могут уменьшить кучу, что для лимитов 160 МБ важно: эффект проверяется замером в шаге 18, а не принимается на веру | Образ Keycloak может поставляться с другой Java: расширения собираются с `--release 21`. Часть инструментов (старые плагины) может отставать от 25 |
| Java 21 LTS | Самая распространённая версия в промышленности, все инструменты её поддерживают | Поддержка линейки заканчивается раньше, чем у 25, ради того же набора возможностей Spring |
| Java 26 | Самые новые возможности | Не LTS, поддержка шесть месяцев, нарушает правило 2 из [versions.md](../../09-operations/versions.md) |

Структура репозитория:

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| Один репозиторий (монорепозиторий) с мультипроектом Gradle: `libs/service-kit`, `services/*` | Контракт, код и документ меняются одним commit. Одна ссылка для резюме и один конвейер CI. Общая библиотека `service-kit` подключается как проект, без публикации артефакта. Матрица трассировки ссылается на пути в одном дереве | Все сервисы собираются одним конвейером, поэтому нужны фильтры по изменённым путям (позже). Нет независимого владения репозиториями, но команда одна |
| По репозиторию на сервис | Независимые релизы и права доступа, как в больших компаниях | Для проекта из шести сервисов и одного разработчика избыточно: публикация `service-kit` в реестр, синхронизация версий, шесть конвейеров. Документы и контракты пришлось бы разносить |
| Монорепозиторий на Maven с общим родительским POM | Знакомая модель | Те же ограничения Maven, что выше |

Сборка образов:

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| Dockerfile с многоэтапной сборкой по слоям Spring Boot (`-Djarmode=tools extract --layers`) | Полный контроль: пользователь без прав, файловая система только для чтения, `Xmx` из бюджета. Слои зависимостей кэшируются, образ перестраивается за секунды. Понятен любому, кто читал Docker | Файл нужно сопровождать. Базовый образ нужно обновлять (Dependabot и Trivy) |
| `bootBuildImage` (Cloud Native Buildpacks) | Нет Dockerfile, есть список материалов (SBOM) | Скачивает построитель образов объёмом около 1 ГБ, медленнее на раннере, меньше контроля над пользователем и памятью |
| Jib | Не нужен демон Docker, быстрый и воспроизводимый | Ещё один плагин, а Docker всё равно нужен для Compose и интеграционных тестов. Отладка сложнее |
| Нативный образ GraalVM | Малая память и быстрый старт | Долгая сборка (минуты на сервис), много памяти при сборке, ручные настройки отражения для Spring Security и Kafka. На раннере и ноутбуке неоправданно |

## Решение

Выбраны: **Java 25 (Temurin)**, **Gradle 9.8.0 с Kotlin DSL**, **один мультипроект в одном репозитории**, **образы по Dockerfile со слоями Spring Boot**.

Правила, которые из этого следуют:

1. **Структура.** Корень содержит `settings.gradle.kts`, `build.gradle.kts`, `gradle/libs.versions.toml`, wrapper. Проекты: `:libs:service-kit`, `:services:<имя-сервиса>` (шесть сервисов), `:services:api-gateway`. Общий код между сервисами только `service-kit` (правило модульности 5 из [decomposition.md](../decomposition.md)), DTO сервисов не разделяются.
2. **Версии.** Библиотеки Spring получают версии из BOM Spring Boot 4.1.1 и Spring Cloud 2025.1.3. Явные версии только у библиотек вне BOM и только в каталоге. Wrapper закреплён контрольной суммой, действие `setup-gradle` её проверяет.
3. **Java.** Компилятор `--release 25` для сервисов и библиотеки. Расширение Keycloak (шаг 10) собирается с `--release 21`. Предупреждения компилятора в собственных пакетах считаются ошибками.
4. **Образы.** Один параметризованный Dockerfile для сервисов: этап распаковки слоёв, итоговый образ на `eclipse-temurin:25-jre-noble`, пользователь UID 10001, `read_only: true`, временный каталог в памяти, `JAVA_TOOL_OPTIONS` с `Xmx` из [memory-budget.md](../../09-operations/memory-budget.md). Дайджест базового образа записывается в метку образа.
5. **Запуск.** Сервисы можно запускать из Gradle и IDE при инфраструктуре в Compose (наборы `dev-*`) и целиком из образов (набор `full`). Конфигурация одна ([c4-deployment.md](../c4-deployment.md), раздел 3).
6. **Исправление документов Ф2.** В `c4-components.md` «Maven-зависимостью» заменено на «зависимостью Gradle (проект `:libs:service-kit`)». Другие упоминания Maven в документах отсутствуют (проверено поиском).

## Последствия

**Плюсы:**
- Одно решение вместо нескольких случайных: сборка, версии и образы одинаковы во всех модулях и в CI.
- Быстрая обратная связь на раннере: кэш Gradle и слои образов. Это важно, потому что CI единственный судья.
- Версии не расходятся: BOM Spring плюс каталог. Обновление идёт через Dependabot одним pull request.
- Монорепозиторий упрощает трассировку и атомарные изменения контракта и кода.
- Образы малы, безопасны (без прав, только для чтения) и укладываются в лимиты памяти.

**Минусы и риски:**
- Gradle сложнее Maven для новичка. Смягчение: конфигурация вынесена в соглашения, `Makefile` скрывает команды, руководство разработчика описывает типовые действия.
- Двоичный `gradle-wrapper.jar` в репозитории. Смягчение: проверка контрольной суммы, wrapper создаётся и проверяется в CI.
- Java 25 новее, чем Java 21, часть инструментов может отстать. Смягчение: сборка идёт на раннере с Temurin 25, при проблеме выбор откатывается на 21 одной строкой каталога (LTS, версия Spring та же).
- Плавающий тег базового образа даёт исправления безопасности автоматически, но снижает воспроизводимость. Смягчение: дайджест в метке образа, сканирование Trivy.
- Монорепозиторий связывает релизы сервисов. Для проекта из одной команды это допустимо, независимые релизы появятся при разделении ([ADR-002](ADR-002-microservices-consolidation.md)).

## Когда пересмотреть

- Если сборка в CI дольше 15 минут при кэше, нужны фильтры изменённых путей или раздельные конвейеры.
- Если нужен независимый выпуск сервиса другой командой, выделить его в отдельный репозиторий и опубликовать `service-kit` артефактом.
- Если Java 25 вызовет несовместимость с обязательным инструментом, вернуться на Java 21 LTS.
- Если измерение (шаг 18) покажет, что нативный образ даёт выигрыш по памяти, достаточный для включения `full` в 3 ГБ, рассмотреть его для шлюза и читающих сервисов.
- При выходе Spring Cloud 2026.0 в стабильной версии проверить совместимость и обновить обе линейки вместе.
