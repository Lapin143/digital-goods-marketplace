# ADR-022. Шифрование внутреннего трафика: mTLS между сервисами, TLS к хранилищам

| Связанные ADR | [ADR-003](ADR-003-kafka-events.md), [ADR-009](ADR-009-key-encryption-hmac.md), [ADR-010](ADR-010-keycloak-sms-codes.md), [ADR-021](ADR-021-api-gateway.md) |

## Контекст

Требование NFT-3.3: данные передаются только по TLS. На входе из интернета это выполняется естественно. Вопрос находки 12 отчёта Ф1: что делать с трафиком **внутри** стенда, между контейнерами, то есть в сети Docker Compose (локально) и в сети k3s (на сервере). Через эту сеть идут:

- значения ключей от `inventory-service` к `delivery-service` (NFT-3.2: открытые значения, самый ценный трафик);
- токены пользователей от шлюза к сервисам, персональные данные (e-mail, телефон) в запросах и событиях;
- обращения к PostgreSQL, Kafka, Redis и объектному хранилищу, где лежат персональные данные и платёжные идентификаторы;
- вызовы между Keycloak и `platform-service` (коды входа).

Угрозы: перехват трафика на хосте (другой контейнер, скомпрометированный контейнер, администратор хоста), подмена сервиса (кто угодно в сети называет себя `delivery-service` и запрашивает значения ключей), доступ в обход шлюза. Модель угроз (шаг 9) разберёт их подробно.

Ограничения: 3 ГБ памяти в WSL и малая команда. Решение не должно добавлять тяжёлых компонентов и ручного труда на каждый сертификат.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| 1. Доверять сети Compose и k3s: внутри обычный HTTP | Проще всего, нет сертификатов | Нарушает NFT-3.3 буквально. Значения ключей идут открытым текстом. Любой контейнер в сети может слушать или представиться чужим сервисом. Сетевые политики Kubernetes ограничивают доступ, но не шифруют |
| 2. Одностороннее TLS (сервер доказывает себя, клиент нет) плюс сетевые политики | Шифрование есть, сертификаты нужны только серверам | Сервис не знает, кто его вызывает: к конечной точке значений ключей сможет обратиться любой контейнер с токеном или без. Идентичность вызывающего пришлось бы строить поверх (отдельные токены между сервисами) |
| 3. mTLS между сервисами, TLS с проверкой сертификата и аутентификацией к хранилищам, один частный центр сертификации (выбрано) | Шифрование и взаимная аутентификация. Сертификат вызывающего определяет, кому разрешён конкретный маршрут (например, значения ключей только `delivery-service`). Без дополнительных компонентов, средствами Spring Boot и самих хранилищ | Нужен центр сертификации, выпуск, обновление и хранение сертификатов. Сложнее отладка (нужны сертификаты для curl) |
| 4. Сервисная сетка (Linkerd, Istio) с автоматическим mTLS | Автоматическое шифрование и ротация без изменения кода, метрики | Прокси на каждый под: +20-50 МБ на сервис, плюс управляющий слой (Istio заметно тяжелее). Не работает в Compose (только Kubernetes). Для 6 сервисов избыточно |
| 5. Шифрование на уровне сети (WireGuard между узлами, например встроенный режим k3s) | Прозрачно шифрует весь трафик между узлами | Не работает на одном хосте между контейнерами, не даёт идентичности вызывающего, нет в Compose. Остаётся дополнением к варианту 3 для нескольких узлов |

## Решение

Выбран вариант 3: **весь трафик между контейнерами зашифрован, а между сервисами ещё и взаимно аутентифицирован**.

### Что и чем защищено

| Связь | Защита | Как проверяется вызывающий |
| --- | --- | --- |
| Интернет → `api-gateway` | TLS 1.2 и выше (1.3 предпочтительно), сертификат: на сервере публично доверенный, на ноутбуке частный центр | Токен (JWT) или подпись вебхука |
| `api-gateway` → сервисы, сервис → сервис (REST), Keycloak ↔ `platform-service` | **mTLS**: сервер требует клиентский сертификат (`client-auth=need`), клиент проверяет сертификат сервера по частному центру | Сертификат: имя из SAN сверяется со списком разрешённых вызывающих для маршрута |
| `delivery-service` → `inventory-service`, значения ключей | mTLS, разрешён только сертификат `delivery-service` | Список разрешённых вызывающих у маршрута, остальные получают 403 ([ADR-009](ADR-009-key-encryption-hmac.md)) |
| Сервисы → PostgreSQL | TLS (`ssl=on`, клиент `sslmode=verify-full`), отдельная роль базы на сервис, пароль `scram-sha-256` из секретов | Роль и пароль, права только на свою базу |
| Сервисы → Kafka | TLS-слушатель, аутентификация сертификатом клиента, права на темы по имени сертификата (ACL): запись только в свою тему, чтение только нужных ([ADR-003](ADR-003-kafka-events.md)) | Сертификат клиента и ACL |
| Сервисы → Redis | TLS-порт, пользователи ACL по сервисам, пароли из секретов | Пользователь ACL с правами на свои ключи |
| Сервисы → объектное хранилище | TLS, учётные данные на сервис с политикой доступа к своему бакету ([ADR-024](ADR-024-object-storage.md)) | Ключи доступа |
| Сервисы → внешние системы (шлюз, e-mail, SMS) | TLS, проверка сертификата провайдера | Ключи доступа провайдера из секретов |

Токен пользователя остаётся и внутри: каждый сервис сам проверяет JWT ([ADR-021](ADR-021-api-gateway.md)). mTLS отвечает на вопрос «какой сервис звонит», токен на вопрос «от чьего имени».

### Частный центр сертификации

| Параметр | Значение |
| --- | --- |
| Состав | Корневой сертификат центра и по одному сертификату на каждый контейнер (сервисы, Kafka, PostgreSQL, Redis, MinIO, Keycloak) |
| Алгоритм | ECDSA P-256 |
| Срок | Корень 5 лет, сертификаты контейнеров 90 дней. Отзыв не используется, срок короткий |
| Имена | SAN содержит DNS-имя контейнера в сети (например, `inventory-service`) |
| Выпуск | Скрипт (`infra/pki`, Ф3) на основе `openssl` или `step`: генерирует центр и сертификаты, кладёт в секреты Docker (Compose) и в секреты Kubernetes (k3s, позже cert-manager, [ADR-020](README.md)) |
| Хранение | Закрытый ключ центра **не хранится в Git** и не попадает в образы. Файлы сертификатов в `.gitignore`. Сервисы получают только свой ключ и сертификат центра |
| Обновление | Spring Boot (SSL-пакеты) перечитывает файлы при обновлении без перезапуска, повторный выпуск раз в 60 дней скриптом или заданием |
| Проверка | Клиенты проверяют цепочку и имя сервера, отключение проверки запрещено правилами сборки |

### Правила авторизации по сертификату

У каждого внутреннего маршрута есть список разрешённых вызывающих. Он лежит в конфигурации сервиса и проверяется до обработчика.

| Маршрут | Разрешено |
| --- | --- |
| `inventory-service`: значения ключей по заказу | `delivery-service` |
| `inventory-service`: зарезервировать, подтвердить резерв | `order-service` |
| `payment-service`: открыть платёжную сессию | `order-service` |
| `order-service`: обновить адрес доставки | `platform-service` |
| `platform-service`: отправить и проверить код входа | `keycloak` |
| Остальные внутренние маршруты | Перечисляются в OpenAPI ([openapi/README.md](../../06-api/openapi/README.md), расширение `x-allowed-callers`) |

Маршруты для пользователей доступны с сертификатом `api-gateway` и токеном.

### Профили

TLS и mTLS включены **во всех профилях**, в том числе на ноутбуке: профиль без шифрования не вводится, чтобы ошибки сертификатов не открывались впервые на сервере. Удобство для разработчика обеспечивают скрипт `make certs`, готовые сертификаты для `curl` и тестов, поддержка в Testcontainers.

## Последствия

**Плюсы:**

- Выполняется NFT-3.3 буквально: нет трафика без шифрования. Ключи и персональные данные не уходят по сети открытым текстом.
- Подмена сервиса и обращение в обход шлюза без сертификата невозможны. Значения ключей отдаются только `delivery-service`.
- Права на темы Kafka и ключи Redis по сервисам ограничивают ущерб от взломанного сервиса.
- Без дополнительных компонентов: нет сетки, нет прокси на каждый сервис.

**Минусы и риски:**

- Операционная сложность: центр сертификации, срок сертификатов, ошибки «сертификат истёк» и «неверное имя». Защита: скрипт выпуска, оповещение за 14 дней до окончания срока, документированная процедура.
- Закрытый ключ центра самый ценный секрет инфраструктуры. Хранится вне Git и вне образов, на сервере в защищённом хранилище секретов. При компрометации перевыпуск всех сертификатов.
- Отладка сложнее (нужны сертификаты для curl, шифрованный трафик нельзя прочитать при анализе). Компенсируется журналами и трассировкой.
- Небольшие затраты процессора и памяти на шифрование (единицы процентов при нагрузке R1).
- Шифрование внутри узла не защищает от компрометации самого хоста (процесс с доступом к памяти, администратор с доступом к секретам). Для этого нужны меры уровня хоста (модель угроз, шаг 9).

## Когда пересмотреть

- Перейдём на несколько узлов k3s или управляемый Kubernetes: оценить сервисную сетку или WireGuard между узлами для автоматической ротации.
- Появится управляемый центр сертификации (cert-manager с внешним издателем, Vault): заменить скрипт выпуска.
- Число сервисов вырастет настолько, что ручное управление списками разрешённых вызывающих станет неудобным: перейти на политики сетки или централизованные политики.
- Замеры в Ф3 покажут, что шифрование заметно влияет на задержку: проверить настройки (возобновление сессий, размер пула соединений), а не отключать защиту.
