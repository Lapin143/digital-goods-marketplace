# ADR-010. Keycloak и подтверждение телефона по SMS: коды в `platform-service`, тонкое расширение Keycloak

## Контекст

Keycloak даёт регистрацию, вход, OAuth2 и JWT, 2FA для сотрудников и продавцов (TOTP), брокер внешнего входа (VK ID, в проекте через эмуляцию). Но SMS-подтверждения «из коробки» в нём нет. Нужны четыре сценария с одноразовыми кодами:

| Сценарий | Кто и когда | Источник |
| --- | --- | --- |
| Подтверждение телефона | Вошедший покупатель до первой покупки. Код на SMS, номер привязывается к учётной записи и уникален | FT-1.5, BPMN-01 |
| Вход по коду из SMS | Покупатель без доступа к e-mail. Не вошёл, называет номер, вводит код. Сессия ограничена | FT-1.7, BPMN-04 |
| Смена e-mail по обращению | Покупатель вводит сам: код на телефон учётной записи, затем код на новый e-mail. Оператор видит только результат | FT-7.5, BPMN-04 |
| Смена номера (R2) | Код на e-mail учётной записи, затем SMS на новый номер | FT-1.6, BPMN-07 |

Для всех кодов действуют общие правила: срок не более 5 минут, не более 5 попыток ввода (NFT-3.7), не более 3 запросов за 10 минут и 10 за сутки на учётную запись и на номер (NFT-3.5, настраивается по FT-11.1). Вопросы, оставленные Ф1 (BPMN-01, решение 3; BPMN-04, решение 4): кто владеет кодами, где они хранятся, что делает Keycloak, а что платформа. Решение нужно до начала Ф3, потому что оно меняет сборку образа Keycloak и состав `platform-service`.

## Рассмотренные варианты

### Кто владеет логикой кодов

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| 1. Свой сервис авторизации вместо Keycloak | Полный контроль, любые сценарии | Придётся заново написать OAuth2/OIDC, токены, 2FA, сессии, внешний вход. Безопасность «самописной авторизации» это главный риск проекта. Противоречит NFT-3.0 и разделу 8.2 |
| 2. Расширение Keycloak целиком: аутентификатор, REST-ресурс, хранилище кодов, отправка SMS | Keycloak владеет всем, что связано со входом. Есть готовые сторонние расширения | Бизнес-правила (лимиты из параметров платформы, этапы смены e-mail и номера, привязка к обращению) живут внутри продукта со своим циклом обновлений. Тесты и отладка тяжелее. Сценарии вне входа (подтверждение телефона, смена e-mail, смена номера) всё равно вызывают это расширение из `platform-service`. Готовые расширения не знают наших лимитов и этапов |
| 3. Коды целиком в `platform-service`, вход по SMS без расширения Keycloak (отдельный маршрут выдаёт токен) | Одно место для кодов | Токен по SMS нужно выпустить в обход Keycloak (обмен токенов, имперсонация): нестабильные возможности, лишняя поверхность атаки. Сессия и её ограничения вне Keycloak |
| 4. Коды в `platform-service`, в Keycloak тонкий аутентификатор, который только вызывает `platform-service` (выбрано) | Одно место для всех правил и сценариев. Keycloak остаётся стандартным: токен выпускает он, SPI это связующий код на 150 строк. Лимиты и параметры берутся из платформы. Тесты логики без контейнера Keycloak | Вход по SMS зависит от доступности `platform-service` (другие способы входа не зависят). Нужен образ Keycloak с JAR расширения и поддержка SPI при обновлении |

### Где хранятся коды

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| 1. PostgreSQL (`platform_db`) | Долговечно, транзакционно с состоянием учётной записи, видно SQL | Нужны очистка просроченных, чаще запись. Нагрузка на базу от кода с жизнью 5 минут |
| 2. Redis с TTL (выбрано) | Срок жизни и счётчики из коробки, атомарные операции (Lua), нет очистки. Код по природе временный: потеря Redis означает «запросите код заново» | Данные теряются при перезапуске и вытеснении (см. [ADR-012](ADR-012-reservation-redis-timer.md)). Нужно следить за политикой вытеснения |

Долговечное состояние (какой этап смены номера или e-mail пройден, привязанный номер) остаётся в `platform_db` и не зависит от Redis. В Redis только то, что можно выбросить.

## Решение

Выбраны вариант 4 («владелец логики») и вариант 2 («хранение в Redis»).

### Границы ответственности

| Часть | Keycloak | `platform-service` |
| --- | --- | --- |
| Регистрация, вход по паролю, VK ID, 2FA (TOTP) сотрудников и продавцов, токены | Да, стандартно | Нет |
| Вход по коду из SMS | Аутентификатор `sms-otp` (SPI): принимает номер и код, вызывает `platform-service`, выпускает токен | Хранит код, считает попытки и лимиты, находит учётную запись по номеру, шлёт SMS |
| Подтверждение телефона, смена e-mail по обращению, смена номера | Не участвует (кроме смены e-mail и роли через Admin REST) | Вся логика: этапы, коды, проверка уникальности, запись результата |
| Хранение номера, признак «телефон подтверждён» | Нет | `platform_db`, расширение учётной записи, уникальный индекс по номеру (INV-34) |
| Отправка SMS и писем с кодом | Нет (письма Keycloak о подтверждении почты и сбросе пароля идут по SMTP, [c4-containers.md](../c4-containers.md), раздел 4) | Модуль `notification` через SMS-провайдера и e-mail-провайдера |

Вызовы между ними (REST по mTLS, [ADR-022](ADR-022-internal-traffic-encryption.md)): Keycloak → `platform-service` (отправить и проверить код входа), `platform-service` → Keycloak (Admin REST: роль, e-mail, деактивация).

### Модель кода

| Параметр | Значение |
| --- | --- |
| Содержимое | 6 цифр, генератор `SecureRandom` |
| Срок жизни | 5 минут (NFT-3.7), TTL записи в Redis |
| Попытки ввода | 5 на код (NFT-3.7), после пятой неудачи код погашен |
| Одноразовость | Успешная проверка гасит код атомарно (скрипт Lua: проверить и удалить). Новый запрос кода гасит предыдущий для той же цели |
| Что хранится | Хеш кода (HMAC-SHA-256 с секретом `otp_pepper` вне Redis), назначение, цель (HMAC номера или адреса), идентификатор учётной записи, привязка к контексту (идентификатор обращения или действия), счётчик попыток. Сам код нигде не хранится и в журналы не пишется |
| Назначения кода | `phone_confirm`, `sms_login`, `email_change_phone`, `email_change_new_email`, `phone_change_email`, `phone_change_sms`. Код для одного назначения и контекста не подходит к другому |
| Текст SMS | Только код и название сервиса с предупреждением «никому не сообщайте». Персональных данных нет |

### Ограничение частоты (NFT-3.5)

| Что считается | Лимит по умолчанию | Реализация |
| --- | --- | --- |
| Запросы кода на учётную запись | 3 за 10 минут, 10 за сутки | Скользящее окно в Redis, один скрипт Lua |
| Запросы кода на номер телефона (в том числе для входа, когда учётная запись неизвестна) | 3 за 10 минут, 10 за сутки | То же |
| Запросы входа по SMS с одного IP | 10 в час | Дополнительно к лимитам шлюза |
| Погашенных из-за попыток кодов подряд | 3 за час, затем вход по SMS для этого номера закрыт на час | Защита от перебора по нескольким кодам |
| Общий потолок SMS в сутки | Параметр платформы (по умолчанию 1000), оповещение при 80% | Защита бюджета от массовой отправки (SMS pumping) |
| Допустимые номера | Только +7 (R1) | Проверка формата E.164 и кода страны |

Лимиты читаются из параметров платформы (копия значений, пришедших событием `platform.config`, FT-11.1). **При недоступности Redis отправка кода запрещается** (отказ в доступе безопаснее и дешевле, чем неограниченная отправка SMS), остальные функции работают.

### Вход по SMS и ограниченная сессия (FT-1.7)

1. Покупатель называет номер. Аутентификатор Keycloak вызывает `platform-service`.
2. Ответ **не раскрывает**, привязан ли номер к учётной записи: всегда «если номер привязан, код отправлен». Для неизвестного номера SMS не отправляется (экономия бюджета), но запрос учитывается в лимитах номера и IP, а время ответа выравнивается.
3. Покупатель вводит код, `platform-service` проверяет и возвращает идентификатор учётной записи. Аутентификатор выпускает токен.
4. **Ограничения такой сессии:**

| Мера | Реализация |
| --- | --- |
| Только заказы и обращения | Токен получает только область `orders.read` и `support.write`, но не `account.manage`. Шлюз пропускает маршруты `/account/**` только с `account.manage`, сервисы проверяют область ещё раз |
| Нельзя менять пароль, e-mail, номер, оформлять новые заказы | Те же области. Оформление нового заказа требует область `orders.create`, её у такого токена нет |
| Короткая жизнь | Токен 15 минут, без refresh-токена, сессия не дольше часа |
| Признак способа входа | В токене заявлено `amr = ["sms"]`, это видно сервисам и журналу аудита |
| Ключи не показываются в кабинете | Так задумано в FT-5.4, красть нечего |

### Сценарии смены e-mail и номера

Все этапы хранятся в `platform_db` (какой пройден), код каждого этапа в Redis. Покупатель вводит коды сам в форме обращения или кабинета, оператор получает только результат проверки.

| Сценарий | Этапы |
| --- | --- |
| Подтверждение телефона | Запрос кода (номер проверяется на уникальность до отправки) → ввод кода → запись номера и признака (уникальный индекс гасит гонку) |
| Смена e-mail по обращению | Оператор вводит новый адрес → код на телефон учётной записи → ввод покупателем → проверка уникальности нового адреса → код на новый адрес → ввод → смена в Keycloak (Admin REST) → событие аудита (хеши до и после, [ADR-014](ADR-014-audit-log-no-pii.md)) → повторная отправка ключа |
| Смена номера (R2) | Код на e-mail учётной записи и новый номер в одной форме → проверка кода → проверка уникальности нового номера → SMS на новый номер → ввод → замена номера и признака |

Занятый номер или адрес (FT-1.5, BPMN-01 E1, BPMN-04 E7, BPMN-07 E3): код не отправляется, пользователь видит нейтральное сообщение «Использовать нельзя» без указания причины. Это раскрывает занятость номера только вошедшему пользователю в пределах дневного лимита запросов, остаточный риск разобран в модели угроз (шаг 9).

### Сборка и эксплуатация

JAR расширения (`sms-otp`) собирается в CI и копируется в образ Keycloak (`/opt/keycloak/providers`). Расширение содержит один класс аутентификатора и фабрику, без бизнес-правил. Настройки: адрес `platform-service`, клиентский сертификат для mTLS. Realm описывается как код (экспорт, Ф3).

## Последствия

**Плюсы:**

- Все правила кодов (срок, попытки, лимиты, этапы, уникальность) в одном месте и покрываются тестами без поднятия Keycloak.
- Keycloak остаётся стандартным: токены и 2FA стандартные, обновление Keycloak затрагивает небольшой связующий код.
- Один механизм обслуживает четыре сценария с общим учётом лимитов.
- Ограниченная сессия по SMS задана областями токена и проверяется дважды (шлюз и сервис), а не одним флагом.

**Минусы и риски:**

- Подмена SIM-карты остаётся главным остаточным риском: SMS слабее приложения-аутентификатора. Меры ограничивают ущерб (ограниченная сессия, лимиты, письмо о смене e-mail), но не устраняют его. Риск принят и разобран в модели угроз (шаг 9, находка 11 отчёта Ф1).
- Вход по SMS зависит от `platform-service` и Redis. Вход по паролю и VK ID не зависит.
- Образ Keycloak собирается с JAR расширения: нужен процесс сборки и совместимость с версией Keycloak. Метод расширения (SPI аутентификатора) стабилен, но проверяется при каждом обновлении.
- Redis теряет коды при перезапуске и вытеснении: пользователь запрашивает код заново. Допустимо.
- Сценарии кодов добавляют нагрузку на SMS-бюджет: нужны потолок и оповещение.
- Нейтральные сообщения усложняют поддержку («почему не пришёл код»): оператор видит причину по метрике и журналу, покупатель нет.

## Когда пересмотреть

- Поддержка SPI расширения для новой версии Keycloak станет дорогой: перейти на вариант 3 или обмен токенов, когда возможности станут стабильными.
- Мошенничество с SMS или подмена SIM начнут реально происходить: заменить SMS-вход на приложение-аутентификатор или passkey, оставив SMS как резерв.
- Нагрузка кодов вырастет настолько, что потери при вытеснении Redis станут заметны: перенести коды в PostgreSQL.
- Keycloak получит штатный SMS-аутентификатор с нужными лимитами: заменить расширение.
