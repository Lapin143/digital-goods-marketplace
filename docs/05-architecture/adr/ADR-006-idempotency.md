# ADR-006. Идемпотентность запросов, событий и платежей

| Поле | Содержание |
| --- | --- |
| Статус | Принято |
| Дата | 2026-10-03 |
| Требования | FT-5.1, FT-6.1, FT-6.2, FT-6.4, FT-7.1, FT-7.5, NFT-2.2, NFT-2.3, раздел 8.2 требований |
| Связанные ADR | [ADR-003](ADR-003-kafka-events.md), [ADR-004](ADR-004-saga-purchase.md), [ADR-005](ADR-005-transactional-outbox.md), [ADR-007](README.md), [ADR-015](ADR-015-payment-gateway-integration.md) |

## Контекст

В системе повторы неизбежны и это нормально:

- Покупатель дважды нажимает «Оформить заказ» или обновляет страницу после тайм-аута.
- Платёжный шлюз повторно присылает уведомление, потому что не получил ответ вовремя (FT-6.2).
- Kafka доставляет событие минимум один раз ([ADR-003](ADR-003-kafka-events.md)), публикатор Outbox после падения шлёт событие снова ([ADR-005](ADR-005-transactional-outbox.md)).
- Вызов шлюза или провайдера почты завершился тайм-аутом, и неизвестно, дошёл ли он: приходится повторять.

Требование NFT-2.3 формулирует цель: повторная обработка одного и того же события (оплата, выдача, письмо, возврат) не создаёт дублей. Доставка «минимум один раз» плюс идемпотентная обработка даёт «эффективно один раз».

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| 1. Только уникальные ограничения в базе | Простейшая защита данных, работает всегда | Защищает таблицу, но не побочные эффекты: письмо и вызов шлюза уже случились до нарушения ограничения. Повторный запрос получает ошибку, а не прежний ответ. Потребитель, получивший дубль, падает с исключением и уходит в повторы и DLQ, хотя всё в порядке |
| 2. Ключ дедупликации в Redis (`SETNX` с TTL) | Быстро, не нагружает базу | Запись в Redis не атомарна с изменением базы: падение между ними даёт либо потерю, либо дубль. Потеря Redis стирает защиту. Не годится для денег |
| 3. Kafka exactly-once (транзакции, идемпотентный издатель) | Не нужна своя таблица | Покрывает только цепочку «Kafka - Kafka». HTTP-запросы покупателя, уведомления шлюза и запись в базу вне её. Не решает задачу |
| 4. Три уровня в PostgreSQL, в одной транзакции с изменением данных (выбрано) | Атомарно с бизнес-изменением: данные и пометка «обработано» фиксируются вместе. Повтор запроса возвращает прежний ответ. Дубль события молча пропускается. Последний рубеж, уникальные ограничения, ловит ошибки кода | Три механизма вместо одного. Таблицы нужно чистить. Дисциплина: обязательное правило для каждого обработчика, проверяется тестами «доставить дважды» |

## Решение

Выбран вариант 4. Идемпотентность строится на трёх уровнях, и каждый обработчик использует все уровни, применимые к нему.

### Уровень 1. Ключ идемпотентности запроса (HTTP)

Для операций, которые создают или меняют ресурсы и могут быть повторены клиентом, клиент передаёт заголовок `Idempotency-Key` (UUID версии 4). Обязателен для `POST /orders` и для всех `POST`-операций, меняющих состояние: создание обращения, заявки продавца, товара.

```sql
-- в базе каждого сервиса, который принимает такие запросы
idempotency_key (
  scope         text        not null,   -- кто: идентификатор пользователя или клиента
  key           uuid        not null,   -- значение заголовка
  endpoint      text        not null,   -- метод и шаблон пути
  request_hash  bytea       not null,   -- SHA-256 тела запроса
  state         text        not null,   -- in_progress | completed
  response_code int,
  response_body jsonb,
  created_at    timestamptz not null default now(),
  primary key (scope, key)
)
```

| Ситуация | Что делает сервис |
| --- | --- |
| Ключ новый | Вставляет строку `in_progress`, выполняет операцию, в той же транзакции сохраняет ответ и ставит `completed` |
| Тот же ключ, то же тело, `completed` | Возвращает сохранённый ответ без повторного выполнения (в том числе тот же идентификатор заказа) |
| Тот же ключ, другое тело | Ответ 422, тип проблемы `idempotency-key-reuse`: ключ нельзя использовать для другого запроса |
| Тот же ключ, `in_progress` | Ответ 409, тип проблемы `request-in-progress`, заголовок `Retry-After: 1` |
| Нет заголовка у обязательной операции | Ответ 400, тип проблемы `idempotency-key-required` |

Срок хранения 24 часа, ежедневная очистка. Пример: покупатель с нестабильной связью повторяет `POST /orders` с тем же ключом и получает тот же заказ, а не второй резерв.

### Уровень 2. Таблица обработанных событий (Kafka и webhook)

```sql
-- в базе каждого сервиса, который читает события
processed_event (
  consumer      text        not null,   -- имя обработчика внутри сервиса
  event_id      uuid        not null,   -- идентификатор события из конверта
  processed_at  timestamptz not null default now(),
  primary key (consumer, event_id)
)
```

Обработчик события начинает локальную транзакцию, делает `insert ... on conflict do nothing` в `processed_event`. Если строка вставлена, применяет изменение и пишет события в Outbox, затем commit. Если не вставлена, это дубль: транзакция завершается без изменений, а смещение Kafka подтверждается. Срок хранения 14 суток (больше срока хранения тем, 7 суток, с запасом), очистка раз в сутки.

Источники без собственного идентификатора события дедуплицируются по **бизнес-ключу**, который заменяет `event_id`:

| Вход | Ключ дедупликации | Где проверяется |
| --- | --- | --- |
| Любое событие Kafka | `event_id` из конверта (UUID, задаётся при записи в Outbox) | `processed_event` потребителя |
| Уведомление платёжного шлюза | Идентификатор платежа у шлюза и тип события; если шлюз присылает собственный идентификатор уведомления, то он | `payment_event` в `payment-service`, уникальный индекс |
| Статус письма от e-mail-провайдера | Идентификатор сообщения у провайдера и статус (принято, доставлено, отказ) | `delivery_event` в `delivery-service` |
| Статус SMS от провайдера | Идентификатор запроса кода и статус | `notification_event` в `platform-service` |
| Команда оператора (повторная отправка, смена e-mail) | Идентификатор действия, который создаёт интерфейс (`Idempotency-Key`) | Уровень 1 |

### Уровень 3. Уникальные ограничения предметной области

Последний рубеж: даже если ошибка в коде пропустит дубль, база его не примет. Ограничения выведены из инвариантов доменной модели.

| Ограничение | Таблица | Что защищает |
| --- | --- | --- |
| Один платёж на заказ: `unique (order_id)` | `payment` | FT-6.1, INV-11, INV-14 |
| Один внешний идентификатор платежа: `unique (gateway_payment_id)` | `payment` | Привязка уведомления к платежу, INV-14 |
| Один возврат на платёж: `unique (payment_id)` по полю `refund` либо уникальный внешний идентификатор возврата | `payment` | Возврат всегда полный и один (FT-8.4), INV-15 |
| Одна «первичная» выдача на заказ: частичный `unique (order_id) where type = 'primary'` | `delivery` | SM-06, INV-18: повторное событие не создаёт вторую первичную выдачу |
| Не более одной выдачи «в очереди» на заказ: частичный `unique (order_id) where status = 'queued'` | `delivery` | SM-06: письмо не уходит дважды |
| Не более одного активного резерва на заказ: частичный `unique (order_id) where status = 'active'` | `reservation` | SM-08, INV-06 |
| Один ключ у одного заказа: `order_id` в строке ключа и условие обновления `where status = 'reserved' and reservation_id = ?` | `key` | FT-7.1, NFT-2.2, INV-01, INV-02, подробнее [ADR-007](README.md) |
| Не более одного открытого обращения на заказ: частичный `unique (order_id) where status in ('created', 'in_progress')` | `ticket` | SM-07, INV-21 |

### Идемпотентность исходящих вызовов

| Вызов | Что передаётся | Эффект повтора |
| --- | --- | --- |
| `order-service` → `inventory-service`: зарезервировать и подтвердить резерв | Идентификатор заказа как естественный ключ операции | Повтор возвращает уже созданный резерв и результат подтверждения, второго резерва нет |
| `order-service` → `payment-service`: открыть платёжную сессию | Идентификатор заказа | Один платёж на заказ, повтор возвращает прежнюю ссылку на оплату |
| `payment-service` → шлюз: создать платёж | `Idempotency-Key` = идентификатор заказа | Потерянный ответ не создаёт второй платёж (BPMN-01, решение 7) |
| `payment-service` → шлюз: запросить возврат | `Idempotency-Key` = `refund-` и идентификатор платежа | Повтор не создаёт второй возврат (FT-6.4) |
| `delivery-service` → e-mail-провайдер: письмо | Идентификатор выдачи как идентификатор сообщения | Провайдер, поддерживающий дедупликацию, не пошлёт письмо дважды. Если не поддерживает, возможно редкое повторное письмо с теми же значениями ключей, но не новые ключи |

**Что осознанно допускается:** в редком случае покупатель получит одно и то же письмо с ключом дважды (отправка прошла, ответ потерян). Это неприятно, но безопасно: выдаются те же ключи. Недопустимо выдать другой ключ или создать вторую выдачу.

## Последствия

**Плюсы:**

- Повторы на любом уровне безопасны: покупатель не получает два заказа, шлюз не создаёт два платежа, потребитель не делает дубль изменений (NFT-2.3).
- Идемпотентность атомарна с бизнес-изменением (одна транзакция), поэтому нет окон между «обработано» и «применено».
- Уровень 3 страхует ошибки уровней 1 и 2 и документирует инварианты ограничениями схемы.

**Минусы и риски:**

- Каждый обработчик обязан использовать `processed_event`. Забытая проверка даёт дубль на уровне логики. Защита: общая инфраструктурная обёртка обработчика, ArchUnit-правило «обработчик события не обходит обёртку», тест «каждое событие доставляется дважды».
- Таблицы `idempotency_key` и `processed_event` растут и требуют очистки по расписанию.
- Идентификатор события должен быть стабилен при повторной публикации. Он задаётся при записи в Outbox, а не при отправке ([ADR-005](ADR-005-transactional-outbox.md)).
- Ключ идемпотентности запроса ограничивает срок повтора 24 часами: клиент, повторяющий запрос позже, получит новую операцию.

## Когда пересмотреть

- Появятся потребители вне нашего контура (партнёры, API продавца в R2), которым нужны другие правила повторов: описать их в публичном контракте API и версионировании ([ADR-018](README.md), Ф5).
- Рост нагрузки сделает таблицу `processed_event` узким местом: перейти на секционирование по дате или на хранение «последнего обработанного смещения» там, где порядок гарантирован.
- Появятся операции, где повтор в течение 24 часов нежелателен как «тот же ответ»: добавить срок действия ключа, зависящий от операции.
