## Контекст

Регистрацию, вход через VK ID и восстановление пароля ведёт Keycloak: так задумано в [ADR-010](ADR-010-keycloak-sms-codes.md) и в стандартных потоках OAuth2. При этом платформе нужна своя запись об учётной записи (`identity.user_account`): телефон и признак его подтверждения, роль, признак второго фактора, статус и соль аудита, а событие `user.registered` публикуется платформой. Документы Ф2 не говорят, **как факт регистрации попадает из Keycloak в платформу**. В срезе 1 Ф4 это нужно сразу: `createPhoneConfirmation` работает с записью платформы, `listStaffUsers` показывает пользователей, `changeUserRole` и `deactivateUser` меняют запись и Keycloak согласованно.

Ограничения:

1. **Новые операции в контракте не придумываем без необходимости.** Контракты Ф2 приняты на веху M2, а любая внутренняя операция добавляет ещё один маршрут, ещё один список вызывающих и ещё один тест.
2. **Keycloak не должен знать бизнес-правил платформы** ([ADR-010](ADR-010-keycloak-sms-codes.md): расширения тонкие, без логики).
3. **Сбой одной из сторон не должен терять учётную запись.** Платформа может быть недоступна в момент регистрации, Keycloak может быть недоступен в момент назначения роли (NFT-4.3).
4. **Имя и признак второго фактора** (`name`, `has_2fa`) в профиле realm не заданы: токен их либо не содержит, либо содержит как claims `name` и `amr`.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| 1. Создание при первом обращении к платформе (JIT) плюс сверка с Keycloak раз в минуту по Admin REST | Новых операций и расширений нет. Запись появляется ровно тогда, когда она нужна. Сверка закрывает «тихих» пользователей и сотрудников, которые ни разу не вызывали платформу, а также потерянные изменения | Пользователь, который ничего не вызывал в платформе, появляется в её базе с задержкой до минуты. Имя берётся из claims и может быть неполным |
| 2. Слушатель событий Keycloak (`REGISTER`) вызывает внутреннюю операцию платформы | Запись создаётся в момент регистрации | Ещё одно расширение Keycloak и новая внутренняя операция с mTLS. Событие может потеряться, если платформа недоступна, поэтому сверка всё равно нужна |
| 3. Только сверка раз в минуту, без создания при обращении | Одна точка создания записи | Первый вызов `createPhoneConfirmation` сразу после регистрации может получить 404 «нет учётной записи» |
| 4. Регистрация идёт через платформу, а в Keycloak пользователя создаёт платформа | Платформа владеет записью с самого начала | Нарушает стандартные потоки (VK ID, восстановление пароля, подтверждение почты), заново пишет то, что умеет Keycloak. Противоречит [ADR-010](ADR-010-keycloak-sms-codes.md) |

## Решение

Выбран вариант 1: **создание при первом обращении плюс сверка**.

1. **Создание при первом обращении (JIT).** Фильтр безопасности каркаса и сервисный слой модуля `identity` при обращении аутентифицированного пользователя ищут запись с `id = sub`. Если её нет, создают в одной транзакции: запись `user_account` (роль `buyer`, статус `active`, `audit_salt` из 16 случайных байт), событие `user.registered` в Outbox и запись аудита. Конфликт одновременного создания (два первых запроса) разрешается первичным ключом: проигравший запрос перечитывает запись.
2. **Откуда берутся поля.** Адрес: claim `email` в нормализованном виде. Имя: claim `name`, при его отсутствии `preferred_username`, при отсутствии часть адреса до `@`. Признак `has_2fa`: claim `amr` содержит `otp`. Роль: по claims `realm_access.roles`, `buyer` по умолчанию.
3. **Сверка (`identity-reconciler`).** Раз в минуту под блокировкой лидера читает пользователей Keycloak постранично (Admin REST), создаёт отсутствующие записи тем же путём, обновляет `has_2fa` по наличию credential типа `otp`, повторяет то, что не дошло до Keycloak: признак `phone_verified`, роль, отключение. Для роли и деактивации образцом служит база платформы.
4. **Порядок записи при изменениях из платформы** (`changeUserRole`, `deactivateUser`, подтверждение телефона): сначала база и Outbox в одной транзакции, затем вызов Admin REST (таймаут 2 секунды), при сбое сверка повторяет вызов. Ни одно изменение не ждёт Keycloak внутри транзакции базы.
5. **Роль «Продавец»** вручную не назначается (INV-36): её ставит `seller-role-handler` по событию `seller.approved`, вместе с атрибутом `seller_id` для токена и обязательным вторым фактором (решение Р-18 руководства Ф4).
6. **Изменения в консоли Keycloak в обход платформы** (сброс фактора, отключение учётной записи) сверка замечает не всегда. Для состояния, образцом которого служит платформа, она возвращает Keycloak к записи платформы; сброс второго фактора консолью администратор записывает в журнал вручную до среза 3 ([runbook.md](../../09-operations/runbook.md)).

Признак `keycloak_synced` из AsyncAPI и `events/README.md` в DDL отсутствует (есть только `phone_synced_to_idp`). Решение: отдельный столбец не вводится, потому что для роли и деактивации образцом служит база платформы и сверка сравнивает состояния, а не читает флаг; упоминания признака убираются из описаний.

## Последствия

**Плюсы:**
- Ни одной новой операции и ни одного нового расширения Keycloak: срез 1 опирается на уже принятые контракты.
- Потеря вызова или сбой Keycloak не теряет изменение: сверка приводит стороны к согласию за минуту.
- Сотрудники, созданные в консоли Keycloak, появляются в `listStaffUsers` без отдельной процедуры.
- Логика создания записи одна и проверяется одним набором тестов.

**Минусы и риски:**
- Запись пользователя, который ничего не делал в платформе, появляется с задержкой до минуты. Для демо это безопасно: первые же действия (подтверждение телефона, заявка продавца) создают запись сразу.
- JIT-создание делается внутри запроса пользователя: при недоступной базе платформы первый запрос получит 503. Это ожидаемое поведение, повтор безопасен.
- Имя из claims может быть неполным (`preferred_username` или часть адреса). Смягчение: пользователь меняет имя в кабинете (R2), для R1 имя нигде не влияет на права.
- Сверка читает пользователей Keycloak постранично и нагрузку не создаёт на малых объёмах, но при тысячах пользователей её нужно перевести на чтение по метке времени создания.

## Когда пересмотреть

Если число пользователей вырастет настолько, что постраничное чтение занимает больше минуты, или появится требование получать `user.registered` в момент регистрации (например, приветственное письмо, которое нельзя отправлять с задержкой): тогда вводится слушатель событий Keycloak (вариант 2) как дополнение к сверке, а не вместо неё.
