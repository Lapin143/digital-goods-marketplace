## Контекст

У товара с выдачей по API (R2) нет пула ключей: продавец сам называет, сколько единиц готов выдать, а ключ платформа запрашивает у него после оплаты (FT-4.0, FT-7.4). Остаток здесь число, и с ним работают два независимых участника:

- **Система** уменьшает остаток при оформлении заказа, восстанавливает при отмене заказа и истечении резерва (FT-4.3).
- **Продавец** правит остаток вручную в кабинете или через API продавца (FT-4.3, FT-10.1).

Опасная ситуация («продавец правит, пока идёт заказ»): остаток 10. Продавец открыл форму и видит 10. Пока он думает, три заказа уменьшили остаток до 7. Продавец вводит 12 и сохраняет. Если запись простая («установить 12»), три проданные единицы «воскреснут»: платформа продаст на три единицы больше, чем продавец готов выдать, и позже получит от него отказ по API (тайм-аут, T10, возвраты). Раздел 8.2 требований прямо называет цель: ручная правка не должна затирать новые заказы.

Остаток не бывает отрицательным (INV-08). Товар с нулевым остатком недоступен для заказа (INV-09, FT-4.4).

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| 1. Пессимистичная блокировка: `SELECT ... FOR UPDATE` на строке остатка | Привычная, корректна внутри одной транзакции | **Не решает проблему.** Потерянное обновление возникает не внутри транзакции, а между чтением формы и записью (время на размышление человека). Блокировка на время формы заблокировала бы оформление заказов на минуты. Для самого уменьшения она не нужна, достаточно одного атомарного `UPDATE` |
| 2. «Последняя запись побеждает» | Проще всего | Затирает новые заказы. Нарушает цель раздела 8.2 |
| 3. Правка дельтой («+5», «-3») вместо абсолютного значения | Операции коммутативны, конфликтов нет | Другой интерфейс: продавцы привыкли вводить итоговое число. Для API продавца меняет контракт. Остаётся дополнением, но не заменой |
| 4. Оптимистичная блокировка: версия записи, правка применяется, только если версия не изменилась (выбрано) | Конфликт обнаруживается и объясняется продавцу. Нет блокировок на время формы. Один дешёвый условный `UPDATE` | Продавец иногда получает отказ и должен повторить правку на свежих данных. Нужна поддержка версии в интерфейсе и API |

## Решение

Выбран вариант 4. Запись остатка (`api_stock`) хранит количество и **версию**, которая растёт при любом изменении.

| Операция | Запрос | Результат |
| --- | --- | --- |
| Резерв при заказе | `UPDATE api_stock SET quantity = quantity - :n, version = version + 1 WHERE product_id = :p AND quantity >= :n` | Одна строка: резерв создан (запись резерва в той же транзакции). Ноль строк: остатка не хватает. `CHECK (quantity >= 0)` страхует код (INV-08) |
| Восстановление при снятии резерва (срок, отказ в оплате, отмена) | `UPDATE api_stock SET quantity = quantity + :n, version = version + 1 WHERE product_id = :p` | Остаток растёт на количество резерва. Идемпотентно, потому что резерв снимается условно «если активен» ([ADR-007](ADR-007-double-issue-protection.md)) |
| Правка продавцом | `UPDATE api_stock SET quantity = :q, version = version + 1 WHERE product_id = :p AND version = :v` | Одна строка: принято. Ноль строк: версия устарела |

Правило клиента: продавец отправляет новое значение вместе с версией, которую он видел (`If-Match`). При несовпадении сервис отвечает кодом **412 Precondition Failed** (тип проблемы `stale-version`) и возвращает текущий остаток и версию. Интерфейс показывает «остаток изменился: сейчас 7, было 10» и просит подтвердить правку на свежем значении. Если заголовок не передан, ответ 428 Precondition Required. Операции системы (резерв, восстановление) версию не проверяют: они не «правят», а двигают остаток атомарно.

Что означает число, которое вводит продавец: **доступный остаток на сейчас**. Резервы, уже действующие в момент правки, не входят в него, а при их снятии вернутся в остаток сверху. Это согласуется с FT-4.3 («восстанавливается при отмене заказа или истечении резерва») и показывается продавцу в подсказке.

Событие «остаток изменился» публикуется через Outbox при каждом изменении количества (витрина `catalog-service` обновляет доступность, товар с нулём скрывается от оформления, INV-09). Для товаров с пулом версия не нужна: остаток равен числу свободных ключей и считается из строк ключей ([ADR-007](ADR-007-double-issue-protection.md)).

**Проверка.** Тест на конкуренцию: 100 параллельных резервов по 1 единице при остатке 60 заканчиваются ровно 60 успехами, остаток равен нулю, не отрицателен. Тест «продавец правит, пока идёт заказ»: правка со старой версией отклоняется кодом 412, остаток не изменён.

## Последствия

**Плюсы:**

- Правка продавца не затирает новые заказы, платформа не продаёт больше, чем продавец подтвердил (цель раздела 8.2).
- Резерв и восстановление это один атомарный запрос без явных блокировок и взаимных блокировок.
- Остаток не уходит в минус на уровне базы.

**Минусы и риски:**

- Продавец может получить отказ 412 и повторить правку. Это ожидаемое поведение, интерфейс объясняет причину.
- Две схемы остатка (число свободных ключей для пула и запись с версией для API) нужно держать согласованными в витрине: общая обработка события «остаток изменился».
- Для массовых правок через API продавца (R2) клиент обязан работать с версией. Это зафиксируется в контракте OpenAPI (`ETag` и `If-Match`).
- Структура данных появляется уже в физической модели R1, но функциональность включается в R2, поэтому таблица создаётся миграцией R2.

## Когда пересмотреть

- Продавцы жалуются на частые отказы 412: добавить правку дельтой (вариант 3) как второй способ.
- Остаток начнёт зависеть не только от продавца и заказов (например, синхронизация со складом продавца в реальном времени): пересмотреть модель остатка как событийно поддерживаемую.
- Для API-товаров потребуется частичная выдача или резервы разных сроков: расширить модель резервов.
