# ADR-003. Kafka для событий между сервисами

| Поле | Содержание |
| --- | --- |
| Статус | Принято |
| Дата | 2026-10-03 |
| Требования | NFT-2.0, NFT-2.3, NFT-4.3, NFT-6.0, NFT-1.3, раздел 8.2 требований |
| Связанные ADR | [ADR-002](ADR-002-microservices-consolidation.md), [ADR-005](ADR-005-transactional-outbox.md), [ADR-006](ADR-006-idempotency.md), [ADR-011](ADR-011-guaranteed-delivery.md) |

## Контекст

Сервисы R1 должны обмениваться фактами («платёж подтверждён», «заказ оплачен», «письмо принято») так, чтобы:

- сбой или медленная работа получателя не останавливали отправителя (NFT-4.3: выдача и письма не блокируют оплату);
- факт переживал перезапуск получателя и не терялся (NFT-2.3, NFT-4.3);
- один факт мог читать несколько сервисов: заказ оплачен читают выдача и служебный сервис, в R2 ещё и финансы;
- по событию можно было проследить заказ сквозным идентификатором (NFT-6.0).

Ограничения среды: ноутбук с 8 ГБ памяти, у WSL 3 ГБ, один арендованный сервер. Нагрузка скромная, около 0,06 заказа в секунду на пике ([decomposition.md](../decomposition.md), раздел 2.1), поэтому выбор определяют не пропускная способность, а модель доставки, повторное чтение и память.

Синхронными остаются только вызовы, где без ответа нельзя продолжить: карточка товара, резерв и подтверждение резерва, платёжная сессия, значения ключей для письма ([c4-containers.md](../c4-containers.md), раздел 3). Всё остальное идёт событиями.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| 1. Прямые вызовы REST между всеми сервисами, без брокера | Нет ещё одного компонента, просто отлаживать | Платёж зависит от доступности выдачи и уведомлений. Каждому отправителю нужны свои повторы и очередь недоставленного. Один факт для трёх получателей это три вызова и три точки отказа. Нарушает NFT-4.3 |
| 2. RabbitMQ | Лёгкий по памяти (около 150-300 МБ), готовые очереди, задержка и очередь недоставленных из коробки, привычная модель «задача и исполнитель» | Сообщение исчезает после чтения, повторно прочитать и восстановить получателя по журналу нельзя. Новый подписчик не получит прошлых событий. Порядок гарантирован в пределах одной очереди, а не по ключу. Для событий предметной области, которые читают несколько сервисов, нужен обмен «fanout» и по очереди на каждого. Как очередь задач для выдачи рассматривается отдельно в [ADR-011](ADR-011-guaranteed-delivery.md) |
| 3. Kafka, один брокер в режиме KRaft (выбрано) | Журнал событий: хранение 7 суток, повторное чтение, новый подписчик подключается с нужного места. Порядок по ключу (идентификатор заказа). Группа потребителей на сервис, несколько читателей одного факта без дополнительных настроек. Стандарт для событийных архитектур, этого ждут на собеседованиях | Больше памяти (около 512 МБ кучи на брокер). Нет задержки и очереди недоставленных из коробки, их строим сами. Доставка «минимум один раз», дубли убираем идемпотентностью. Один брокер на стенде не отказоустойчив |
| 4. Redis Streams или LISTEN/NOTIFY в PostgreSQL | Не нужен новый компонент | Redis уже хранит временные данные и не должен быть единственным носителем фактов. LISTEN/NOTIFY теряет сообщения без подписчика и привязывает сервисы к одной базе |

## Решение

Выбран вариант 3: Apache Kafka, один брокер в режиме KRaft (без ZooKeeper). События публикуются через Transactional Outbox ([ADR-005](ADR-005-transactional-outbox.md)) и читаются идемпотентно ([ADR-006](ADR-006-idempotency.md)).

**Темы.** Одна тема на сервис-издатель и область: все события одного источника лежат в одной теме, поэтому порядок событий одного заказа сохраняется.

| Тема | Издатель | Партиций | Хранение |
| --- | --- | --- | --- |
| `catalog.events` | `catalog-service` | 3 | 7 суток |
| `inventory.events` | `inventory-service` | 3 | 7 суток |
| `order.events` | `order-service` | 3 | 7 суток |
| `payment.events` | `payment-service` | 3 | 7 суток |
| `delivery.events` | `delivery-service` | 3 | 7 суток |
| `identity.events` | `platform-service` (`identity`) | 1 | 7 суток |
| `support.events` | `platform-service` (`support`) | 1 | 7 суток |
| `notification.events` | `platform-service` (`notification`) | 1 | 7 суток |
| `audit.events` | все сервисы | 1 | 30 суток |
| `platform.config` | `platform-service` (`audit_admin`) | 1 | Сжатие по ключу, хранится последнее значение каждого параметра |
| `<тема>.dlq` | потребитель, отказавшийся от сообщения | как у исходной | 14 суток |

Тема R2: `finance.events` (споры и баланс). События API продавца идут через `delivery.events`. Точные имена тем, схемы и примеры фиксирует AsyncAPI (шаг 10).

**Ключ сообщения** это идентификатор агрегата (для событий заказа, платежа, выдачи и резерва это идентификатор заказа, для событий каталога идентификатор товара или профиля). Один заказ всегда попадает в одну партицию, поэтому его события читаются по порядку.

**Гарантии.**

| Сторона | Настройка | Зачем |
| --- | --- | --- |
| Издатель (публикатор Outbox) | `acks=all`, `enable.idempotence=true`, `max.in.flight.requests.per.connection=5`, ключ сообщения = идентификатор агрегата | Брокер не пишет дубль при повторе отправки, порядок по ключу сохраняется |
| Потребитель | Группа `group.id` = имя сервиса. `enable.auto.commit=false`, подтверждение смещения после фиксации транзакции базы, `auto.offset.reset=earliest` | Обработка «минимум один раз»: при сбое сообщение придёт снова, а не потеряется |
| Обработка | Таблица обработанных событий в той же транзакции, что и изменение данных ([ADR-006](ADR-006-idempotency.md)) | Дубль не меняет результат: «эффективно один раз» |
| Ошибки | Три повтора с паузами 1, 5 и 25 секунд, затем сообщение уходит в `<тема>.dlq`, чтение продолжается ([ADR-011](ADR-011-guaranteed-delivery.md)) | Одно «ядовитое» сообщение не останавливает партицию навсегда |

**Транзакции Kafka (exactly-once) не используются.** Они обещают атомарность только внутри Kafka (чтение из темы и запись в тему), а изменение базы данных в эту транзакцию не входит. Сквозную гарантию даёт связка Outbox, «минимум один раз» и идемпотентный потребитель.

**Формат сообщений.** JSON в конверте в духе CloudEvents (идентификатор события, тип, время, идентификатор агрегата, версия схемы, `traceparent`, сквозной `X-Correlation-Id`). Реестр схем (Confluent Schema Registry, Avro) не вводится: ещё один контейнер на 3 ГБ памяти не оправдан, схемы лежат в репозитории (AsyncAPI и JSON Schema), совместимость проверяют контрактные тесты в CI. Конвенции описаны в `conventions.md` (шаг 10).

**Что не передаётся через Kafka.** Значения ключей и тела писем с ключами. Выдача запрашивает значения у `inventory-service` по mTLS и отдаёт письмо провайдеру напрямую (NFT-3.2, [c4-containers.md](../c4-containers.md), раздел 4). Персональные данные в событиях ограничены минимумом: идентификаторы и то, что нужно получателю. Снимок e-mail покупателя лежит только в событии заказа, на которое подписана выдача, и хранится в теме 7 суток; это отмечено в модели угроз (шаг 9).

## Последствия

**Плюсы:**

- Платёж, заказ и выдача развязаны во времени: недоступность выдачи или почты не мешает принять оплату, события ждут в теме (NFT-4.3).
- Повторное чтение журнала даёт воспроизведение: потерянный по ошибке заказ можно догнать повторным чтением или возвратом из `.dlq`.
- Новые подписчики (финансы в R2, метрики) подключаются без изменения издателей.
- Порядок событий одного заказа сохраняется ключом партиционирования.

**Минусы и риски:**

- Согласованность между сервисами событийная, а не транзакционная: нужны сага ([ADR-004](ADR-004-saga-purchase.md)), Outbox и идемпотентность. Это сложнее, чем прямой вызов, и требует тестов на повторы, порядок и сбои.
- Один брокер без репликации на стенде. Потеря диска брокера означает потерю необработанных событий. Смягчение: источник истины остаётся в базах сервисов, а Outbox хранит неопубликованное. В R3 переход на три брокера с `replication.factor=3`.
- Брокер добавляет около 512 МБ к бюджету памяти (учтено в бюджете памяти, шаг 8). Профили Compose позволяют не запускать лишнее.
- При блокирующих повторах сообщение, ушедшее в DLQ, обрабатывается позже следующих событий того же заказа. Потребители защищены проверкой допустимости перехода статусов (SM-01 и другие), поздние события игнорируются или вызывают сверку.
- Нет задержанной доставки: повторы выдачи и возвратов строятся на таблицах с полем «следующая попытка», не на Kafka ([ADR-011](ADR-011-guaranteed-delivery.md)).

## Когда пересмотреть

- Нагрузка вырастет настолько, что одного брокера мало (порядок сотен событий в секунду), либо потребуется отказоустойчивость: три брокера и `replication.factor=3`.
- Окажется, что большинство обменов нужны как очередь задач с задержкой, а не как журнал событий: рассмотреть RabbitMQ как дополнение, не как замену.
- Появится потребность в строгой проверке совместимости схем между командами: добавить реестр схем.
