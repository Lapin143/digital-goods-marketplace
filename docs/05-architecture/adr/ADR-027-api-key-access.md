## Контекст

Продавец с большим каталогом загружает ключи, правит остаток и читает заказы из своей системы, а не из кабинета (FT-10.0, FT-10.1). Токен кабинета для этого не подходит: он живёт 5 минут, требует второго фактора и выдаётся браузерному потоку. Нужен долгоживущий секрет, который продавец кладёт в свою систему, и этот секрет нельзя сделать опасным: утечка должна ограничивать ущерб, а отзыв должен работать быстро.

Ограничения:

1. **Платформа хранит только хеш ключа** (NFT-3.4, INV-41): база `catalog_db` не должна содержать значения, которым можно воспользоваться.
2. **Права ключа уже, чем права продавца в кабинете.** Выпуск и отзыв ключей, подключение системы, заявка, реквизиты и вывод остаются только за токеном с 2FA, иначе кража одного ключа даёт возможность выпустить себе десять ещё (Р-185).
3. **Сервисы не знают про ключи.** Шесть сервисов уже проверяют токен, роль и владельца по единому каркасу ([ADR-021](ADR-021-api-gateway.md)); учить каждый проверять ключ значило бы дублировать код и открыть путь к рассинхрону.
4. **Один набор лимитов.** Лимит `seller.api` (600 в минуту на ключ) и лимит `seller-upload` (6 загрузок в час на продавца, общий для кабинета и API) считает шлюз (NFT-3.5, Р-188).
5. **Отзыв не позднее 30 секунд** (решение ADR-021), без подписки шлюза на Kafka.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| 1. Токен OAuth2 по `client_credentials` из Keycloak: на каждый ключ клиент Keycloak | Стандартный механизм, сервисы уже проверяют JWT. Срок и отзыв средствами Keycloak | Клиент Keycloak на каждый ключ: админ-вызовы при выпуске и отзыве, ещё одна зависимость на критическом пути выпуска. Продавцу нужно сначала получить токен (ещё один вызов и ещё один сбой). Отзыв действует до конца жизни токена. Права клиента придётся кодировать областями и ролями realm |
| 2. Подписанные запросы (HMAC каждого запроса общим секретом) | Секрет не передаётся по сети, защита от повтора по метке времени | Продавец обязан написать подпись для каждого запроса, любой curl превращается в программу. Платформе нужен сам секрет, а не хеш (противоречит NFT-3.4). Чтение заказов из BI-инструмента становится тяжёлым |
| 3. **API-ключ в заголовке с проверкой на шлюзе: шлюз считает SHA-256, спрашивает `catalog-service`, кэширует ответ, передаёт сервису личность заголовком по mTLS** | Для продавца один заголовок. В базе только хеш. Отзыв действует до 30 секунд. Лимиты и метрики на шлюзе, сервисы не знают про ключи. Одна точка проверки | Кэш создаёт окно отзыва. Сервис должен доверять заголовку личности, а доверие держится на mTLS и на правильной настройке шлюза: ошибка конфигурации превращает заголовок в подделку (разобрано в T-45) |
| 4. JWT, выпущенный самим шлюзом (обмен ключа на короткий токен) | Сервисы проверяют уже знакомый JWT | Шлюз становится издателем токенов: ещё одна пара ключей подписи с ротацией, ещё один издатель в проверке `iss`. Лишний вызов на стороне продавца. Выигрыш только в том, что сервис не читает заголовок |

## Решение

Выбран вариант 3: **API-ключ с проверкой на шлюзе**.

1. **Значение ключа.** Префикс `dgm_` и 40 символов base64url от 30 случайных байт (240 бит). Показывается один раз в ответе `createApiKey`; в базе SHA-256 (`bytea`, 32 байта) и отпечаток (первые 8 символов после префикса) для списка и журнала. Хеш без соли допустим: значение случайное и длинное, перебор невозможен, а поиск идёт по хешу. Имя ключа до 60 символов, не больше пяти активных ключей на продавца (атомарная проверка при вставке, U20).
2. **Выпуск и отзыв только по токену.** `createApiKey`, `revokeApiKey`, `listApiKeys` и подключение системы продавца доступны по токену с 2FA, по ключу нельзя (схема `sellerApiKey` у этих операций не указана). Повтор `createApiKey` с тем же `Idempotency-Key` возвращает метаданные ключа **без значения** (Р-198): потерявший ответ отзывает ключ и выпускает новый, а сохранённый ответ не становится вторым местом хранения секрета.
3. **Проверка на шлюзе.** Фильтр читает `X-Api-Key`, считает SHA-256 и спрашивает `catalog-service` внутренним вызовом `checkApiKey` (POST, чтобы хеш не попадал в адрес и журнал). Ответ: действителен ли ключ, какой продавец, статус профиля продавца. Положительный ответ кэшируется в Redis на **30 секунд**, отказ на 5 секунд (подбор не нагружает базу). Для неизвестного, отозванного и испорченного ключа ответ один: 401 `unauthenticated` без подсказки, что именно не так.
4. **Доверие заголовку личности (Р-186).** После проверки шлюз добавляет `X-Seller-Id` и `X-Auth-Kind: api-key` и передаёт запрос сервису по mTLS. Сервис принимает эти заголовки **только** когда сертификат клиента имеет CN `api-gateway` и только у операций со схемой `sellerApiKey` (флаг `x-seller-api` в контракте). Иначе заголовок игнорируется, а запрос без токена получает 401. Шлюз удаляет те же заголовки из внешнего запроса до разбора, поэтому клиент не может их подставить. `CurrentUser` в `service-kit` получает второй источник личности: профиль продавца из заголовка с видом входа «API-ключ» и областью `seller.api`.
5. **Права и лимиты.** Ключ даёт операции «API продавца»: загрузка пула и файла, правка остатка, список заказов, чтение своих товаров, ответ на запрос выдачи ([ADR-028](ADR-028-seller-delivery-request.md)). Условие U3 (профиль продавца «одобрен») действует и для ключа, но статус профиля берётся из ответа проверки, а не из токена. Лимиты: `seller.api` 600 в минуту, счётчик по идентификатору ключа; `seller-upload` 6 в час, счётчик по профилю продавца, общий для кабинета и API (кто загружает, неважно). При недоступном Redis шлюз пропускает запросы, как в [ADR-021](ADR-021-api-gateway.md).
6. **Что нигде не попадает.** Значение ключа не пишется в журналы, трассировку, метрики, события и тексты ошибок (`SecretValue`, `Redaction`, канарейка ST-01). Ключ приходит в заголовке, а не в адресе, поэтому журналы доступа шлюза его не видят.
7. **Заблокированный продавец** (R2, срез 3) пользоваться ключом не может, кроме чтения заказов: статус профиля приходит с ответом проверки.
8. **События.** `api-key.issued` и `api-key.revoked` публикуются через Outbox ([ADR-005](ADR-005-transactional-outbox.md)) для аудита; кэш шлюза по ним не сбрасывается (шлюз не подписан на Kafka), отзыв действует по истечении кэша.

## Последствия

**Плюсы:**

- Продавцу достаточно одного заголовка; ни клиента Keycloak, ни подписи запросов.
- В базе нет значения, которым можно воспользоваться (NFT-3.4); кража базы ключей не даёт доступа.
- Сервисы не знают про ключи: проверка в одной точке, код проверки покрыт одним набором тестов.
- Один набор лимитов и метрик на шлюзе; лимит загрузки общий для кабинета и API, продавца не обойти вторым каналом.
- Новых зависимостей у шлюза нет: он уже ходит в `catalog-service` и Redis.

**Минусы и риски:**

- Окно отзыва до 30 секунд: украденный ключ работает ещё полминуты после нажатия «Отозвать». Для демо-проекта принято, параметр кэша выносится в конфигурацию (строка в [ADR-021](ADR-021-api-gateway.md)).
- Доверие заголовку держится на mTLS и на удалении заголовка шлюзом. Ошибка в одном из двух мест открывает подделку личности продавца; закрывается тестом «тот же запрос с сертификатом другого сервиса даёт 401» (T-45, ST-02, ST-08).
- Шлюз зависит от доступности `catalog-service` для первого запроса с ключом; при его отказе проверка отвечает 503 и повтор безопасен, закэшированные ключи продолжают работать.
- Ключ без срока жизни: продавец сам отвечает за его хранение. Смягчение: не более пяти ключей, имя и отпечаток в списке, отзыв в один вызов.

## Когда пересмотреть

- Внешних потребителей API станет больше десятка (партнёры, тарифы, портал разработчика): оценить Kong или облачный шлюз с управлением ключами ([ADR-021](ADR-021-api-gateway.md)).
- Появится требование мгновенного отзыва (меньше 5 секунд): добавить сброс кэша шлюза по событию `api-key.revoked` или перейти на проверку без кэша для операций записи.
- Продавцы потребуют срока жизни и ротации ключа по расписанию: добавить поле срока и предупреждение за 7 дней (R3).
- Понадобится отличать системы внутри одного продавца (разные права у разных ключей): ввести области ключа вместо единого набора «API продавца».
