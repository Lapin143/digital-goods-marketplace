# ADR-005. Transactional Outbox для публикации событий

| Поле | Содержание |
| --- | --- |
| Статус | Принято |
| Дата | 2026-10-03 |
| Требования | NFT-2.3, NFT-2.4, NFT-4.3, NFT-6.0, NFT-6.1, раздел 8.2 требований |
| Связанные ADR | [ADR-003](ADR-003-kafka-events.md), [ADR-004](ADR-004-saga-purchase.md), [ADR-006](ADR-006-idempotency.md) |

## Контекст

Сервис меняет данные в своей базе и сообщает об этом остальным событием в Kafka. Это две разные системы без общей транзакции (проблема двойной записи, dual write). Любой порядок опасен:

| Порядок | Что случится при падении между двумя действиями |
| --- | --- |
| Сначала commit в базу, потом отправка в Kafka | База изменена, событие не отправлено. Заказ «оплачен», а выдача об этом не узнает: ключ не уйдёт покупателю |
| Сначала отправка в Kafka, потом commit | Событие отправлено, а изменение откатилось (ошибка, падение). Выдача отправит ключ по заказу, который в базе не оплачен |

Требование NFT-4.3 и раздел 8.2 прямо называют цель: событие не теряется, если сервис упал после записи в базу. Нужен способ сделать «изменить данные» и «решить опубликовать событие» одной атомарной операцией.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| 1. Публикация из кода сразу после commit | Просто, не нужно ничего строить | Не решает проблему: падение между commit и отправкой теряет событие. Повтор в памяти исчезает при перезапуске |
| 2. Публикация до commit (внутри транзакции) | Событие не теряется при падении после commit | Событие уходит, а транзакция может откатиться: получатели видят несуществующий факт. Хуже потери |
| 3. Распределённая транзакция базы и Kafka (XA, 2PC) | Атомарность | Kafka не участвует в XA. Транзакции Kafka охватывают только Kafka. Блокировки и сложность не оправданы |
| 4. Transactional Outbox с опросом таблицы (выбрано) | Событие записывается в ту же транзакцию, что и данные, значит оно сохраняется тогда и только тогда, когда сохранены данные. Не нужны новые компоненты. Всё видно запросом SQL | Задержка публикации около сотен миллисекунд (интервал опроса). Нагрузка опросом на базу. Дубли при повторе публикации, их убирает потребитель ([ADR-006](ADR-006-idempotency.md)). Нужна очистка таблицы |
| 5. Outbox с чтением журнала транзакций (CDC, Debezium) | Нет опроса, задержка единицы миллисекунд, порядок по журналу | Отдельная JVM (Kafka Connect и Debezium) на 500-1000 МБ, логическая репликация PostgreSQL, отдельная эксплуатация. Не помещается в бюджет памяти ноутбука. Остаётся путём развития |

## Решение

Выбран вариант 4: **таблица `outbox` в базе каждого сервиса и публикатор, который опрашивает её и отправляет события в Kafka**.

**Запись.** Прикладной код в той же транзакции, что меняет данные, добавляет строку в `outbox`. Публиковать в Kafka напрямую из бизнес-кода запрещено, это проверяется ArchUnit ([decomposition.md](../decomposition.md), раздел 7).

```sql
-- одинаковая для всех сервисов схема таблицы (логический вид, DDL в шаге 12)
outbox (
  id            bigint generated always as identity primary key,
  event_id      uuid        not null unique,   -- идентификатор события, ключ дедупликации у потребителей
  aggregate_type text       not null,          -- Order, Payment, Delivery...
  aggregate_id  text        not null,          -- ключ партиции в Kafka
  event_type    text        not null,          -- order.paid, payment.confirmed...
  topic         text        not null,
  payload       jsonb       not null,
  headers       jsonb       not null,          -- traceparent, correlation id, версия схемы
  created_at    timestamptz not null default now(),
  published_at  timestamptz,                   -- null: ещё не отправлено
  attempts      int         not null default 0,
  failed_at     timestamptz                    -- заполнено, если событие припарковано после 10 неудачных попыток
)
-- частичный индекс по (id) where published_at is null and failed_at is null
```

**Публикатор.**

| Параметр | Значение |
| --- | --- |
| Опрос | Планировщик с паузой 200 мс между циклами. Если в цикле есть записи, следующий цикл сразу |
| Выборка | Пачка до 100 строк, упорядоченных по `id`, где `published_at is null` и `failed_at is null` |
| Один публикатор на сервис | Активный экземпляр определяется консультативной блокировкой `pg_try_advisory_lock` с фиксированным ключом в базе сервиса. Остальные экземпляры ждут. Так порядок по `id` сохраняется при нескольких экземплярах сервиса |
| Отправка | Синхронная, `acks=all`, идемпотентный издатель ([ADR-003](ADR-003-kafka-events.md)). После подтверждения брокера `published_at = now()` |
| Сбой отправки | Строка остаётся неотправленной, `attempts` растёт, пауза нарастает 1, 2, 4 ... до 30 с. После 10 неудач строка паркуется (`failed_at`) и публикатор идёт дальше. Это порядок нарушает, поэтому парковка сопровождается оповещением и разбором вручную |
| Задержка | Цель: 95% событий в Kafka не позднее 500 мс после commit. Метрика `outbox_lag_seconds` (возраст самой старой неотправленной строки), оповещение при значении больше 60 с |
| Очистка | Ежедневно удаляются отправленные строки старше 3 суток пачками по 1000. Припаркованные не удаляются, пока не разобраны |

**Гарантии.**

- Событие в Kafka появится **минимум один раз**: если публикатор упал после отправки и до пометки `published_at`, после перезапуска он отправит событие снова. Потребитель убирает дубль по `event_id` ([ADR-006](ADR-006-idempotency.md)).
- Порядок событий одного агрегата сохраняется: один публикатор, `id` по возрастанию, ключ сообщения равен `aggregate_id`.
- Событие не может появиться без изменения данных и не может потеряться при падении сервиса после commit.

**Что идёт через Outbox.** Все события из [c4-containers.md](../c4-containers.md), раздел 8, в том числе внутренние события `platform-service` между его модулями (правило 4 раздела 7 [decomposition.md](../decomposition.md)). События аудита тоже. Прямая публикация без Outbox не допускается нигде.

**Таблица входящих событий.** Парой к Outbox служит таблица обработанных событий на стороне потребителя, она описана в [ADR-006](ADR-006-idempotency.md).

## Последствия

**Плюсы:**

- Потеря события при падении сервиса исключена, закрыто требование раздела 8.2 и NFT-4.3.
- Дополнительных контейнеров нет: достаточно таблицы и планировщика, нагрузка на память нулевая.
- Состояние публикации видно запросом SQL. Диагностика проста: «что не отправлено и почему».
- Путь к CDC открыт: схема таблицы и конверт события при переходе на Debezium не меняются.

**Минусы и риски:**

- Задержка публикации до сотен миллисекунд, но она укладывается в бюджеты (NFT-2.0: 60 с на всю цепочку выдачи, `time-budgets.md`, шаг 8).
- Постоянный опрос нагружает базу. На нагрузке R1 это единицы запросов в секунду на сервис. Частичный индекс держит опрос дешёвым.
- Публикатор с блокировкой это одна точка последовательности. При падении экземпляра блокировка снимается вместе с соединением, другой экземпляр берёт её за секунды.
- Дубли событий неизбежны, поэтому каждый потребитель обязан быть идемпотентным. Это проверяется тестом: каждое событие доставляется дважды, результат не меняется.
- Парковка после 10 неудач нарушает порядок событий агрегата. Редкий случай, требует оповещения и ручного разбора.

## Когда пересмотреть

- Задержка публикации или нагрузка опросом стали заметны в замерах (десятки событий в секунду на сервис): перейти на CDC с Debezium на сервере, схема таблицы сохраняется.
- Несколько экземпляров публикатора потребовалось запускать параллельно ради пропускной способности: разделить по ключу агрегата и снять единую блокировку.
- Spring Modulith или другая библиотека предложит готовый реестр публикации событий с зафиксированной семантикой: сравнить со своим решением и при совпадении заменить код библиотекой.
