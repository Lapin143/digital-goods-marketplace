# Ф4, срез 1 «Продавцы, товары, ключи»: пошаговый план

**Для кого:** системный аналитик, который ведёт проект. Фаза Ф3 закончена, веха M3 закрыта, итоги в [отчёте о Ф3](00-phase3-report.md).
**Время:** около 80 часов (разброс 60–95), неделя 6 и далее [плана проекта](00-project-plan.md). Это больше, чем план отводит на всю Ф4 (50–70 часов). Расчёт и что с этим делать в разделе «Время по шагам».
**Результат:** срез 1 из трёх срезов Ф4. Работающий сценарий «регистрация → вход → заявка продавца → решение модератора → товар → модерация товара → загрузка ключей → товар на витрине» в трёх экранах (каталог, продавец, модератор), тесты, зелёный CI и документы, совпадающие с кодом.

Этот документ описывает только срез 1. Руководства по срезам 2 и 3 пишутся перед их началом, когда будет понятно, что реально получилось в срезе 1: так в Ф3 оценка шагов по ходу работы уточнялась три раза.

**Главная идея среза: вертикальный срез по требованиям, а не слой за слоем.** В Ф3 была тонкая нить через все слои. В Ф4 нить превращается в полосу: каждая операция контракта реализуется целиком (валидация, права, база, события, Outbox, аудит, тест), а не «сначала все контроллеры, потом вся логика». Срез закрывается не тогда, когда написан код, а когда выполнены условия [раздела 14 стратегии тестирования](08-testing/test-strategy.md): тест-кейс на каждое требование, зелёные тесты безопасности, сверка «документы = код», пройденный руками сценарий.

## Ограничения среды

Те же, что в Ф3 ([руководство Ф3](00-phase3-guide.md), раздел «Ограничения среды»): **любой Java- и Docker-код проверяется только запуском в GitHub Actions**, итерации идут в ветке `ci/sandbox`, диагностика читается по аннотациям. Один запуск занимает около 12 минут, поэтому правило прежнее: маленькие шаги, самая дешёвая проверка на каждом.

Что добавляется в Ф4:

| Что | Следствие |
| --- | --- |
| Фронтенд на React нужно собирать и проверять | В облачном рабочем месте `npm install` недоступен, поэтому сборка, линтер и типы работают только в CI (новое задание `web`). Файлы пишутся «вслепую», с проверкой по типам из OpenAPI, которую запускает CI |
| Keycloak с расширением, шлюз и три сервиса одновременно | Набор `dev-sellers` (раздел «Решения», Р-17) занимает по лимитам около 3,5 ГБ и **на ноутбуке с лимитом WSL 3 ГБ не помещается**. Сквозные проверки идут в CI на наборе `full`. Руками на ноутбуке срез проходится при `memory=4GB` в `.wslconfig` (замер в шаге 21) или на сервере (решение D-1, неделя 7) |
| Интеграционным тестам каталога нужно объектное хранилище | Новый набор `dev-kit` (`infra`, `stubs`, `storage`): 1568 МБ по лимитам, на ноутбук помещается. Задание `kit` в CI переходит на него |
| Миграции Flyway при правке DDL | Пока выпуск R1 не вышел, базовые миграции пересобираются генератором (Р-16). После `git pull` на ноутбуке нужен `make reset` |

## Общие правила

### Рабочий цикл для каждого шага

1. Подготовьте артефакты шага в рабочей копии.
2. Прогоните то, что можно проверить локально: `tools/docs-checks/run_all.sh` (с ключом `--db`, если менялся DDL), разбор YAML и JSON, Python и Node без зависимостей.
3. Всё, что требует Java, Docker или npm, отправьте в `ci/sandbox` и дождитесь зелёного запуска. Ошибку читайте по аннотациям, исправляйте причину, а не симптом.
4. Один артефакт или одна связанная группа дают один commit. Тест пишется в том же commit, что и код, который он проверяет.
5. Когда шаг зелёный, результат переносится на `main`, отправляется на GitHub и в папку `C:\dev\digital-goods-marketplace`, и только потом идёт следующий шаг.
6. Если код расходится с документом, сначала решите, что правильно (раздел «Решения»), потом правьте один из них отдельным commit.
7. **Контрольные точки К1 – К4** (после шагов 9, 13, 15, 19): полный зелёный запуск на `main`, замеры памяти из задания `services`, обновление статуса проекта и пересчёт прогноза.

### Правила кода среза

| № | Правило | Почему |
| --- | --- | --- |
| 1 | Операция реализуется целиком: проверка прав по матрице, валидация по схеме, ответ по схеме, запись в базу, событие через Outbox, запись аудита в одной транзакции с решением, тест | Иначе «срез» превращается в слои |

## Если что-то пошло не так

| Проблема | Что делать |
| --- | --- |
| Запуск CI красный, причина неясна | Читайте аннотации задания и шага. Нет диагностики: добавьте её через `diag.sh` и повторите. Не угадывайте |
| Сервис не стартует после правки DDL: ошибка контрольной суммы Flyway | На стенде остался том со старыми миграциями. `make reset` (Р-16) |
| Keycloak не принимает расширение или поток входа падает | Журнал контейнера `keycloak` через `make logs S=keycloak`, затем `make keycloak-check`. Если за 3 часа уровень входа (Р-9) или нейтральная регистрация (Р-8) не получаются, берите запасной вариант и пишите находку: время дороже идеального решения |
| Тест конкуренции «иногда падает» | Не переписывайте тест. Сначала ищите гонку в коде: такие тесты чаще всего находят настоящую ошибку (решение 8 стратегии) |
| `npm ci` в CI падает на подписи или версии | Фиксируйте версию в `package-lock.json`, не обновляйте вслепую; новую зависимость обсуждайте (риск цепочки поставок T-42) |
| Контейнер завершается по OOM | Не повышайте лимит вслепую: снимите пик, сравните с правилом 85 %, запишите причину в бюджет |
| Токен не проходит на шлюзе после одобрения заявки | Токен выдан до смены роли. Выйдите и войдите заново, настройте TOTP; в токене должны быть роль `seller`, `amr` с `otp` и `seller_id` |
| Срез не помещается в часы | Не режьте тесты и документы молча. Таблица сокращений в разделе «Время по шагам», решение принимаете вы после К2 |
