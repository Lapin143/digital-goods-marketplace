## US-9.1. Открытие спора по выданному заказу

| Поле | Содержание |
| --- | --- |
| ID | US-9.1 |
| Релиз | R2 |
| Требования | FT-8.0, FT-8.5, FT-8.1, FT-10.3, FT-11.0 |
| Процесс или use case | BPMN-05 (шаги 1, 2 и 3, исключение E1), SM-09/T1 |

### История

**Как** покупатель, **я хочу** открыть спор по выданному заказу и указать причину, **чтобы** вернуть деньги или получить другой ключ, если товар не подошёл.

### Критерии приёмки

**Сценарий 1. Спор открыт**
- **Дано** заказ «выдан», с первичной выдачи прошло 71 час, споров по заказу не было
- **Когда** покупатель открывает спор и указывает причину
- **Тогда** создаётся спор в статусе «открыт», продавец получает уведомление и при подключённом webhook ещё и webhook, покупателю уходит письмо «спор открыт»

**Сценарий 2. Окно закрыто или спор уже был**
- **Дано** с первичной выдачи прошло больше 72 часов, либо по заказу уже открывался спор, в том числе решённый
- **Когда** покупатель пытается открыть спор
- **Тогда** спор не создаётся, деньги не замораживаются, покупатель видит причину отказа

### Примечания

- Повторная отправка ключа по обращению окно 72 часа не сдвигает (определение «выдан» в разделе 4 требований).

## US-9.2. Ответ продавца на спор

| Поле | Содержание |
| --- | --- |
| ID | US-9.2 |
| Релиз | R2 |
| Требования | FT-8.1 |
| Процесс или use case | BPMN-05 (шаг 6, исключение E5), SM-09 (раздел «Ответ продавца и сроки») |

### История

**Как** продавец, **я хочу** ответить на спор покупателя, **чтобы** модератор увидел мою версию до решения.

### Критерии приёмки

**Сценарий 1. Ответ сохранён**
- **Дано** спор не решён
- **Когда** продавец отвечает в любой момент до решения
- **Тогда** ответ сохраняется и виден модератору, статус спора не меняется
- **И** если продавец не ответил, спор решается в обычный срок, срока ответа нет

### Примечания

- Заблокированный продавец тоже может отвечать на споры (SM-05, раздел «Что значит заблокирован»).

## US-9.3. Заморозка денег на время спора

| Поле | Содержание |
| --- | --- |
| ID | US-9.3 |
| Релиз | R2 |
| Требования | FT-8.3, FT-9.2 |
| Процесс или use case | BPMN-05 (шаг 4), BPMN-06 (исключение E6), SM-09/T2, SM-11/T3, T4, T5 |

### История

**Как** система, **я хочу** замораживать деньги по заказу, пока спор открыт, **чтобы** продавец не вывел деньги, которые может потребоваться вернуть.

### Критерии приёмки

**Сценарий 1. Деньги заморожены по спору**
- **Дано** спор открыт, начисление и комиссия по заказу в статусе «заморожена» (удержание)
- **Когда** спор переходит в «ожидает решения»
- **Тогда** операции получают причину заморозки «спор» и не входят в доступный остаток, даже когда 7 дней с выдачи истекли

**Сценарий 2. Спор решён отказом или заменой ключа**
- **Дано** спор решён отказом в возврате или заменой ключа
- **Когда** решение исполнено
- **Тогда** операции возвращаются в «удержание», если 7 дней ещё не прошли, либо становятся «доступна», если срок уже вышел

### Примечания

- При просрочке решения модератором деньги остаются замороженными: автоматического решения нет (US-9.4).

## US-9.4. Решение модератора по спору в срок

| Поле | Содержание |
| --- | --- |
| ID | US-9.4 |
| Релиз | R2 |
| Требования | FT-8.2, FT-11.2, NFT-5.3, NFT-6.1 |
| Процесс или use case | BPMN-05 (шаг 7, исключение E4), SM-09/T3, T4 |

### История

**Как** модератор, **я хочу** принять решение по спору: возврат, отказ в возврате или замена ключа, **чтобы** спор был решён в течение 24 часов.

### Критерии приёмки

**Сценарий 1. Решение принято**
- **Дано** спор «ожидает решения», с открытия прошло меньше 24 часов
- **Когда** модератор выбирает возврат, отказ в возврате или замену ключа
- **Тогда** решение записывается в спор и в журнал аудита без персональных данных в открытом виде, платформа исполняет его, после исполнения спор становится «решён», покупатель получает письмо, продавец уведомление

**Сценарий 2. Просрочка решения**
- **Дано** с открытия спора прошло 24 часа, решения нет
- **Когда** срок истёк
- **Тогда** администратор получает оповещение, в метрики идёт просрочка, спор остаётся в очереди, деньги заморожены, автоматического решения нет

### Примечания

- Если спор возвращён модератору из-за отсутствия ключа для замены (US-9.6), 24 часа отсчитываются заново.

## US-9.5. Возврат покупателю по решению спора

| Поле | Содержание |
| --- | --- |
| ID | US-9.5 |
| Релиз | R2 |
| Требования | FT-8.4, FT-9.5, FT-6.4, FT-11.0 |
| Процесс или use case | BPMN-05 (ветка «Возврат», исключение E3), SM-01/T11, SM-02/T4, SM-11/T6 |

### История

**Как** покупатель, **я хочу** получить деньги обратно, если модератор решил спор возвратом, **чтобы** не оплачивать товар, который мне не подошёл.

### Критерии приёмки

**Сценарий 1. Возврат выполнен**
- **Дано** модератор решил спор возвратом
- **Когда** шлюз подтверждает возврат всей суммы
- **Тогда** платёж и заказ получают статус «возвращён», спор «решён», покупатель получает письмо
- **И** начисление продавцу и комиссия платформы сторнируются целиком, комиссия не взимается
- **И** ключ остаётся «выдан» и в оборот не возвращается

**Сценарий 2. Автоматический возврат не прошёл**
- **Дано** шлюз не принял запрос возврата, попытки исчерпаны
- **Когда** возврат попадает в очередь администратора и администратор отмечает ручной возврат выполненным
- **Тогда** дальше процесс идёт как после подтверждения шлюза (US-5.8)

### Примечания

- Возврат всегда полный, частичных возвратов нет (FT-8.4).

## US-9.6. Замена ключа по решению спора

| Поле | Содержание |
| --- | --- |
| ID | US-9.6 |
| Релиз | R2 |
| Требования | FT-8.6, FT-7.4, FT-7.1 |
| Процесс или use case | BPMN-05 (ветка «Замена ключа», исключение E2), SM-03/T5, SM-06/T1, SM-09/T3 |

### История

**Как** покупатель, **я хочу** получить новый рабочий ключ, если модератор решил заменить ключ, **чтобы** пользоваться товаром без возврата денег.

### Критерии приёмки

**Сценарий 1. Ключ заменён**
- **Дано** модератор решил заменить ключ, в пуле есть свободный ключ (либо продавец с выдачей по API вернул ключ за 10 минут)
- **Когда** новый ключ найден
- **Тогда** прежний ключ получает статус «аннулирован», создаётся выдача типа «повторная», покупатель получает письмо с новым ключом, спор «решён»
- **И** сроки окон обращения, спора и удержания не сдвигаются

**Сценарий 2. Нового ключа нет**
- **Дано** пул пуст, либо продавец с выдачей по API не ответил за 10 минут или вернул ошибку
- **Когда** замена невозможна
- **Тогда** спор возвращается модератору на новое решение, срок 24 часа отсчитывается заново, автоматического возврата нет, деньги остаются замороженными

### Примечания

- Возврат модератору из-за отсутствия ключа не открывает повторный спор: спор по заказу один (FT-8.5).

## Решения и открытые вопросы

Открытых вопросов нет. Решения по процессу уже приняты в BPMN-05 и SM-09, эпик R2 повторяет их в виде историй. Подробные критерии приёмки с отдельными сценариями на каждое исключение уточняются при планировании R2 (граница детализации R2 в Ф1).
