## US-11.1. Выпуск и отзыв API-ключа

| Поле | Содержание |
| --- | --- |
| ID | US-11.1 |
| Релиз | R2 |
| Требования | FT-10.0, NFT-3.4 |
| Процесс или use case | Отдельного процесса нет |

### История

**Как** продавец, **я хочу** выпустить и отозвать API-ключ в личном кабинете, **чтобы** подключить свою систему и закрыть доступ при утечке.

### Критерии приёмки

**Сценарий 1. Ключ выпущен и показан один раз**
- **Дано** продавец одобрен и не заблокирован
- **Когда** он выпускает API-ключ
- **Тогда** значение ключа показывается один раз, в базе хранится только его хеш, статус ключа «активен»

**Сценарий 2. Ключ отозван**
- **Дано** API-ключ в статусе «активен»
- **Когда** продавец отзывает его
- **Тогда** статус «отозван», запросы с этим ключом отклоняются

### Примечания

- Значение ключа после выпуска восстановить нельзя: при потере выпускается новый ключ (NFT-3.4).

## US-11.2. Загрузка пулов и список заказов через API

| Поле | Содержание |
| --- | --- |
| ID | US-11.2 |
| Релиз | R2 |
| Требования | FT-10.1, FT-4.1, NFT-3.5, NFT-6.2 |
| Процесс или use case | BPMN-03 (загрузка пула), SM-03/T1 |

### История

**Как** продавец, **я хочу** загружать ключи и получать список заказов через API, **чтобы** автоматизировать работу со своей системой.

### Критерии приёмки

**Сценарий 1. Загрузка и список заказов**
- **Дано** у продавца есть активный API-ключ и товар с пулом
- **Когда** он отправляет ключи через API и запрашивает список заказов
- **Тогда** ключи принимаются по тем же правилам, что в US-4.2, и список содержит только заказы этого продавца
- **И** превышение лимита частоты запросов к API отклоняется (NFT-3.5)

### Примечания

- Дубликаты, пределы размеров и защита ключей действуют так же, как при загрузке из кабинета (US-4.2, US-4.3, US-4.4).

## US-11.3. Ответ на запрос выдачи ключа

| Поле | Содержание |
| --- | --- |
| ID | US-11.3 |
| Релиз | R2 |
| Требования | FT-10.2, FT-7.4 |
| Процесс или use case | SM-01/T10, SM-08/T5, US-6.7 |

### История

**Как** продавец с выдачей по API, **я хочу** отвечать на запросы платформы ключом, **чтобы** покупатель получал товар, ключи которого хранятся у меня.

### Критерии приёмки

**Сценарий 1. Ответ на запрос выдачи**
- **Дано** оплачен заказ на товар с выдачей по API, платформа отправила запрос продавцу
- **Когда** продавец отвечает ключом в течение 10 минут
- **Тогда** ключ принимается и выдаётся покупателю (US-6.7), на повторный ответ по тому же запросу платформа не создаёт второй ключ

### Примечания

- Без ответа за 10 минут или при ошибке заказ отменяется и деньги возвращаются (US-6.7).

## US-11.4. Webhook-уведомления о заказах и спорах

| Поле | Содержание |
| --- | --- |
| ID | US-11.4 |
| Релиз | R2 |
| Требования | FT-10.3, FT-8.1, NFT-4.3 |
| Процесс или use case | BPMN-05 (шаги 3 и 8), SM-09 |

### История

**Как** продавец, **я хочу** получать webhook о заказах и спорах, **чтобы** реагировать на события, не опрашивая платформу.

### Критерии приёмки

**Сценарий 1. Webhook доставлен с повторами**
- **Дано** у продавца подключён webhook, по его заказу открыт спор
- **Когда** платформа отправляет уведомление и адрес продавца не отвечает
- **Тогда** отправка повторяется с нарастающей задержкой, событие не теряется, продавец получает его после восстановления адреса

### Примечания

- Уведомление о споре продавец получает и в кабинете независимо от webhook (US-9.1).

## Решения и открытые вопросы

Открытых вопросов нет. Правила приняты в требованиях и в BPMN-05, эпик R2 повторяет их в виде историй. Формат запросов и событий уточняется контрактами в Ф2 (граница детализации R2 в Ф1).
