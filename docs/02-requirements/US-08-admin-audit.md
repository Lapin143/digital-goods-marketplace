## US-8.1. Управление ролями пользователей

| Поле | Содержание |
| --- | --- |
| ID | US-8.1 |
| Релиз | R1 |
| Требования | FT-1.4, FT-1.3, FT-11.2, NFT-3.0 |
| Процесс или use case | BPMN-02 (шаг 6, роль «Продавец» назначает одобрение заявки) |

### История

**Как** администратор, **я хочу** назначать и снимать роли сотрудников, **чтобы** у каждого человека был доступ только к тому, что нужно по работе.

### Критерии приёмки

**Сценарий 1. Роль назначена**
- **Дано** администратор вошёл со вторым фактором, пользователь зарегистрирован с ролью «Покупатель»
- **Когда** администратор назначает ему роль «Модератор», «Оператор поддержки» или «Администратор»
- **Тогда** роль меняется, при следующем входе пользователь обязан настроить второй фактор
- **И** в журнал аудита пишется запись: кто, кому, какая роль была и какая стала

**Сценарий 2. Роль «Продавец» вручную не назначается**
- **Дано** пользователь не прошёл модерацию заявки
- **Когда** администратор пытается назначить ему роль «Продавец»
- **Тогда** действие отклоняется: роль появляется только после одобрения заявки модератором (US-2.2)

**Сценарий 3. Последний администратор**
- **Дано** в системе один активный администратор
- **Когда** он пытается снять с себя роль «Администратор»
- **Тогда** действие отклоняется, в системе всегда остаётся хотя бы один активный администратор

**Сценарий 4. Недостаточно прав**
- **Дано** пользователь с ролью «Модератор», «Оператор поддержки», «Продавец» или «Покупатель»
- **Когда** он пытается изменить роль другого пользователя
- **Тогда** действие отклоняется, запись об отказе доступа попадает в лог безопасности

### Примечания

- У пользователя одна роль (раздел 6.1 требований). Роль «Продавец» назначается один раз при одобрении заявки (SM-05/T3).
- Правила «Продавец вручную не назначается» и «остаётся хотя бы один администратор» приняты как уточнения FT-1.4, они защищают цель BG-05.

## US-8.2. Деактивация учётной записи с сохранением истории

| Поле | Содержание |
| --- | --- |
| ID | US-8.2 |
| Релиз | R1 |
| Требования | FT-1.4, FT-11.2, NFT-5.2, NFT-5.3 |
| Процесс или use case | Отдельного процесса нет. Хранение и удаление описаны в разделе 6.2 требований |

### История

**Как** администратор, **я хочу** деактивировать учётную запись, сохранив историю заказов и действий, **чтобы** закрыть доступ, не потеряв финансовые и аудиторские записи.

### Критерии приёмки

**Сценарий 1. Учётная запись деактивирована**
- **Дано** у пользователя есть заказы, обращения и записи в журнале аудита
- **Когда** администратор деактивирует учётную запись
- **Тогда** статус пользователя «деактивирован», вход невозможен, активные сессии завершаются
- **И** заказы, платежи, финансовые операции и записи журнала сохраняются
- **И** действие записывается в журнал аудита

**Сценарий 2. Анонимизация по запросу**
- **Дано** учётная запись деактивирована, поступил запрос на удаление персональных данных
- **Когда** администратор запускает анонимизацию
- **Тогда** e-mail, номер телефона и имя заменяются обезличенными значениями, включая снимки адреса доставки в заказах и выдачах
- **И** финансовые записи не удаляются, журнал аудита не меняется

**Сценарий 3. Последний администратор**
- **Дано** в системе один активный администратор
- **Когда** кто-либо пытается деактивировать его учётную запись
- **Тогда** действие отклоняется

### Примечания

- Статус учётной записи «заблокирован» из раздела 6.1 в R1 не используется: в требованиях нет функции, которая переводит в него учётную запись (замечание для версии 1.6, итоговый отчёт Ф1).
- Требования не определяют, что происходит с товарами и открытыми заказами деактивированного продавца. В R1 статусы его товаров не меняются: убрать товар с витрины можно блокировкой модератора (US-3.5), а в R2 блокировкой продавца (US-2.6). Каскад деактивации вынесен в замечания для версии 1.6.

## US-8.3. Настройка параметров платформы

| Поле | Содержание |
| --- | --- |
| ID | US-8.3 |
| Релиз | R1 |
| Требования | FT-11.1, FT-5.2, FT-11.2 |
| Процесс или use case | BPMN-01 (сроки), BPMN-02 (пауза после отказа), SM-08 |

### История

**Как** администратор, **я хочу** менять параметры платформы без выпуска новой версии, **чтобы** настраивать сроки и лимиты по мере роста.

### Критерии приёмки

**Сценарий 1. Параметр изменён**
- **Дано** действует резерв 15 минут
- **Когда** администратор задаёт срок резерва 20 минут и сохраняет
- **Тогда** новые заказы получают резерв 20 минут, уже созданные заказы сохраняют прежний срок
- **И** изменение записывается в журнал аудита: параметр, значение до и после

**Сценарий 2. Платёжная сессия не короче резерва**
- **Дано** резерв 15 минут
- **Когда** администратор задаёт срок платёжной сессии 15 минут или больше, либо уменьшает резерв до значения не больше сессии
- **Тогда** изменение отклоняется: платёжная сессия всегда должна быть короче резерва

**Сценарий 3. Недопустимое значение**
- **Дано** администратор редактирует параметр
- **Когда** он вводит ноль, отрицательное число или не число
- **Тогда** значение не сохраняется, администратор видит допустимые границы

**Сценарий 4. Недостаточно прав**
- **Дано** пользователь не администратор
- **Когда** он пытается изменить параметр
- **Тогда** действие отклоняется

### Примечания

- В состав параметров входят: комиссия, время резерва, срок платёжной сессии, окно обращения в поддержку, пауза после отказа продавцу, лимиты запросов кодов подтверждения, минимальная сумма вывода и срок обработки заявки на вывод (FT-11.1, FT-7.2, FT-2.4, NFT-3.5, FT-9.3).
- В R2 при сохранении параметров дополнительно проверяется, что окно спора плюс срок решения короче удержания (SM-11, решение 4).
- Параметры не содержат персональных данных, поэтому значения в журнале хранятся как есть (NFT-5.3).

## US-8.4. Комиссия платформы по умолчанию

| Поле | Содержание |
| --- | --- |
| ID | US-8.4 |
| Релиз | R1 |
| Требования | FT-9.0, FT-11.1 |
| Процесс или use case | BPMN-01, SM-01 |

### История

**Как** администратор, **я хочу** задавать комиссию платформы, **чтобы** платформа зарабатывала на каждом заказе и могла менять ставку.

### Критерии приёмки

**Сценарий 1. Комиссия по умолчанию**
- **Дано** ставка комиссии 2%
- **Когда** создаётся заказ на сумму 1 000 ₽
- **Тогда** в заказе фиксируется комиссия 20 ₽

**Сценарий 2. Смена ставки**
- **Дано** ставка 2%, есть созданные заказы
- **Когда** администратор задаёт ставку 3%
- **Тогда** новые заказы получают комиссию по 3%, комиссия в созданных заказах не меняется

**Сценарий 3. Округление**
- **Дано** ставка 2%
- **Когда** создаются заказы на 10,25 ₽ и на 12,50 ₽
- **Тогда** комиссия считается в копейках с математическим округлением: 0,21 ₽ и 0,25 ₽

**Сценарий 4. Недопустимая ставка**
- **Дано** администратор задаёт ставку
- **Когда** она меньше 0% или больше 100%
- **Тогда** значение не сохраняется

### Примечания

- В R1 комиссия хранится в заказе (раздел 6.1 требований). Баланс продавца и расчёт выплат начинаются с R2 (эпик 10). Ступенчатая шкала по обороту продавца относится к R3 (US-12.1).
- Правило округления закреплено в SM-11 (решение 2): отчёты по комиссии строятся по этим значениям.

## US-8.5. Письма покупателю по ключевым событиям

| Поле | Содержание |
| --- | --- |
| ID | US-8.5 |
| Релиз | R1 |
| Требования | FT-11.0, NFT-2.3, NFT-4.3 |
| Процесс или use case | BPMN-01, BPMN-04, SM-01 (раздел «Уведомления покупателю»), [UC-01](UC-01-purchase.md) |

### История

**Как** покупатель, **я хочу** получать письма о ключевых событиях по заказу, **чтобы** знать, что с моим заказом, не заходя в кабинет.

### Критерии приёмки

**Сценарий 1. Письма по событиям**
- **Дано** покупатель оформил заказ
- **Когда** наступают события: заказ создан (SM-01/T2), заказ оплачен (T4 или T7), ключ выдан (T9), возврат (T8), смена e-mail по обращению
- **Тогда** на соответствующий адрес уходит одно письмо по каждому событию

**Сценарий 2. Адрес письма**
- **Дано** e-mail в учётной записи отличается от адреса в заказе
- **Когда** отправляются письма по заказу
- **Тогда** они уходят на адрес из снимка в заказе, а письма об изменениях учётной записи на адрес учётной записи

**Сценарий 3. Ключ только в письме о выдаче**
- **Дано** покупатель получил письма по заказу
- **Когда** проверяется содержимое писем
- **Тогда** значение ключа есть только в письме «Ключ выдан», в остальных письмах его нет

**Сценарий 4. Сбой провайдера и повторное событие**
- **Дано** событие наступило
- **Когда** провайдер не принял письмо, либо событие пришло повторно
- **Тогда** отправка повторяется с нарастающей задержкой, событие не теряется, а повторное событие не создаёт второго письма

### Примечания

- События «статус спора» и «смена номера телефона» из FT-11.0 относятся к R2 (US-9.1, US-9.4, US-1.8).
- Письма отправляет сервис «Уведомления» по событиям, которые публикуют другие сервисы (раздел 8.2 требований).

## US-8.6. Запись действий сотрудников в журнал аудита

| Поле | Содержание |
| --- | --- |
| ID | US-8.6 |
| Релиз | R1 |
| Требования | FT-11.2, NFT-3.6, NFT-5.3 |
| Процесс или use case | BPMN-02 (шаг 5), BPMN-03 (шаг 6), BPMN-04 (шаг 6), BPMN-01 (E8) |

### История

**Как** администратор, **я хочу** видеть в журнале аудита каждое действие администраторов, модераторов и операторов поддержки, **чтобы** можно было разобрать любой спорный случай.

### Критерии приёмки

**Сценарий 1. Действие записано**
- **Дано** сотрудник выполнил действие: модератор принял решение по заявке или товару, оператор повторно отправил ключ или сменил e-mail, администратор изменил параметр, роль или отметил возврат
- **Когда** действие выполнено
- **Тогда** в журнале появляется запись: идентификатор исполнителя, роль, действие, объект, имена изменённых полей, значения до и после, время, IP исполнителя

**Сценарий 2. Запись не теряется при сбое**
- **Дано** сервис выполнил действие, сервис аудита недоступен
- **Когда** сервис аудита восстанавливается
- **Тогда** запись о действии доходит до журнала, действия без записи не бывает: действие и событие аудита сохраняются в одной транзакции

**Сценарий 3. Администратор просматривает журнал**
- **Дано** в журнале есть записи
- **Когда** администратор открывает журнал
- **Тогда** он видит записи с исполнителем, действием, объектом и временем, новые сверху

**Сценарий 4. Журнал не доступен другим ролям**
- **Дано** пользователь не администратор
- **Когда** он пытается открыть журнал аудита
- **Тогда** доступ отклоняется

### Примечания

- Действия самого пользователя по смене номера телефона и e-mail также записываются (FT-11.2, US-1.8). Смена e-mail через поддержку записывается как действие оператора (US-7.4).
- Для событий аудита используется Transactional Outbox (раздел 8.2 требований).

## US-8.7. Журнал аудита неизменяем и не содержит персональных данных

| Поле | Содержание |
| --- | --- |
| ID | US-8.7 |
| Релиз | R1 |
| Требования | FT-11.2, NFT-5.2, NFT-5.3, NFT-5.0 |
| Процесс или use case | Отдельного процесса нет. Хранение описано в разделе 6.2 требований |

### История

**Как** администратор, **я хочу** иметь журнал аудита, который нельзя изменить и в котором нет персональных данных в открытом виде, **чтобы** журнал оставался доказательством и не нарушал 152-ФЗ.

### Критерии приёмки

**Сценарий 1. Записи нельзя менять и удалять**
- **Дано** в журнале есть записи
- **Когда** пользователь любой роли или рабочая учётная запись сервиса пытается изменить или удалить запись, в том числе прямым запросом к базе
- **Тогда** операция отклоняется, возможно только добавление записей

**Сценарий 2. Персональные поля хранятся хешами**
- **Дано** сотрудник сменил e-mail покупателя
- **Когда** запись попадает в журнал
- **Тогда** в ней есть ID объекта, имя поля и HMAC-хеши значения до и после, самого e-mail нет
- **И** для неперсональных полей, например срока резерва, значения до и после хранятся как есть

**Сценарий 3. IP исполнителя**
- **Дано** действие выполнили сотрудник и пользователь
- **Когда** записи попадают в журнал
- **Тогда** IP сотрудника хранится как есть, IP пользователя в виде HMAC-хеша

**Сценарий 4. Анонимизация не меняет журнал**
- **Дано** учётная запись пользователя анонимизирована (US-8.2)
- **Когда** сравниваются записи журнала до и после анонимизации
- **Тогда** они совпадают байт в байт: журнал не содержал персональных данных в открытом виде

### Примечания

- Персональные данные лежат только в таблице пользователей, где их можно анонимизировать без правки журнала (NFT-5.3).
- Журнал хранится на серверах в РФ (NFT-5.0).

## US-8.8. Оповещение о просрочке модерации

| Поле | Содержание |
| --- | --- |
| ID | US-8.8 |
| Релиз | R1 |
| Требования | FT-2.1, FT-3.2, NFT-6.1 |
| Процесс или use case | BPMN-02 (исключение E3), BPMN-03 (исключение E5), SM-05, SM-04, [UC-02](UC-02-seller-application.md) |

### История

**Как** администратор, **я хочу** получать оповещение, когда заявка продавца или товар ждут решения больше 3 суток, **чтобы** вмешаться и не держать продавцов в очереди.

### Критерии приёмки

**Сценарий 1. Просрочена заявка продавца**
- **Дано** заявка в статусе «на проверке» находится в очереди
- **Когда** с постановки в очередь проходит 3 суток без решения
- **Тогда** администратор получает оповещение, в метрику сроков модерации записывается просрочка
- **И** статус заявки не меняется, решения автоматически не принимается

**Сценарий 2. Просрочен товар**
- **Дано** товар в статусе «на модерации» находится в очереди
- **Когда** с постановки в очередь проходит 3 суток без решения
- **Тогда** администратор получает оповещение, в метрику сроков модерации записывается просрочка, товар остаётся в очереди, автоматического решения нет

**Сценарий 3. Решение принято вовремя**
- **Дано** заявка или товар в очереди 2 суток 23 часа
- **Когда** модератор принимает решение
- **Тогда** оповещения нет, просрочки в метрике нет

**Сценарий 4. Срок начинается заново**
- **Дано** заявка возвращена на доработку, либо товар исправлен после отказа или изменён опубликованный
- **Когда** заявитель или продавец отправляет объект на проверку повторно
- **Тогда** срок 3 суток отсчитывается заново с повторной постановки в очередь

### Примечания

- Просроченный объект остаётся в очереди и может быть решён модератором позже в обычном порядке.
- В R2 такое же оповещение действует для споров (24 часа, US-9.4) и заявок на вывод (3 суток, US-10.4).

## US-8.9. Метрики, оповещения и сквозная трассировка заказа

| Поле | Содержание |
| --- | --- |
| ID | US-8.9 |
| Релиз | R1 |
| Требования | FT-7.3, NFT-6.0, NFT-6.1, NFT-2.4 |
| Процесс или use case | BPMN-01 (шаги 9 и 11, исключения E7, E9, E11), SM-06 |

### История

**Как** администратор, **я хочу** видеть метрики выдачи и оплаты, получать оповещения о проблемах и проследить любой заказ по всем сервисам, **чтобы** замечать сбои раньше покупателей и быстро разбирать конкретный заказ.

### Критерии приёмки

**Сценарий 1. Метрики доступны**
- **Дано** платформа обрабатывает заказы
- **Когда** администратор открывает панель метрик
- **Тогда** он видит время выдачи, число заказов в очереди поддержки, ошибки платежей, число поздних оплат и автовозвратов, сроки модерации

**Сценарий 2. Оповещение о зависшей выдаче**
- **Дано** оплаченный заказ без доставки
- **Когда** проходит 30 минут с оплаты, либо попытки отправки исчерпаны
- **Тогда** администратор получает оповещение (US-6.4, US-6.5)

**Сценарий 3. Сквозной идентификатор заказа**
- **Дано** заказ прошёл оформление, оплату и выдачу
- **Когда** администратор ищет заказ по идентификатору в логах и трассировке
- **Тогда** он видит записи всех участвовавших сервисов по этому заказу в хронологическом порядке

**Сценарий 4. Ключ и данные карты не попадают в логи**
- **Дано** администратор просматривает логи и трассировку заказа
- **Когда** он ищет значение ключа и данные банковской карты
- **Тогда** их в логах нет (NFT-3.2, NFT-5.1)

### Примечания

- Стек наблюдаемости определён в разделе 8.2 требований: Prometheus, Grafana, Loki, OpenTelemetry. Выбор конкретных порогов оповещений делается в Ф2 и Ф6.

## US-8.10. Резервное копирование и восстановление

| Поле | Содержание |
| --- | --- |
| ID | US-8.10 |
| Релиз | R1 |
| Требования | NFT-4.0, NFT-4.1, NFT-4.2 |
| Процесс или use case | Отдельного процесса нет. Хранение описано в разделе 6.2 требований |

### История

**Как** администратор, **я хочу** восстанавливать платформу из резервной копии в установленные сроки, **чтобы** после сбоя потерять не больше 15 минут данных и вернуть работу за 1 час.

### Критерии приёмки

**Сценарий 1. Копии создаются по расписанию**
- **Дано** платформа работает штатно
- **Когда** проверяется расписание копирования
- **Тогда** полная копия каждой базы создаётся ежедневно, журнал транзакций архивируется непрерывно

**Сценарий 2. Восстановление после потери базы**
- **Дано** база данных сервиса потеряна, есть ежедневная копия и архив журнала транзакций
- **Когда** администратор запускает восстановление
- **Тогда** данные восстановлены на момент не раньше чем за 15 минут до сбоя (RPO), сервис снова работает не позднее чем через 1 час (RTO)

**Сценарий 3. Доступность за месяц**
- **Дано** прошёл календарный месяц
- **Когда** считается доступность платформы
- **Тогда** она составляет не менее 99,5%, плановые окна обслуживания в простой не входят

### Примечания

- Значение 99,5% действует для MVP и затем пересматривается до 99,9% (NFT-4.0).
- Сбой внешнего сервиса (почта, платёжный шлюз) не приводит к потере заказа: операции повторяются, неудачные попадают в очередь на разбор. Эти критерии описаны в US-5.2, US-6.4 и US-8.5 (NFT-4.3).
- Проверка NFT-4.1 и NFT-4.2 выполняется учением по восстановлению (методика в `docs/08-testing/nfr-methodology.md`, шаг 7 Ф1).

## US-8.11. Масштабирование сервисов без потери сессий

| Поле | Содержание |
| --- | --- |
| ID | US-8.11 |
| Релиз | R1 |
| Требования | NFT-1.3, NFT-1.0 |
| Процесс или use case | Отдельного процесса нет. Решение описано в разделе 8.2 требований |

### История

**Как** администратор, **я хочу** добавлять экземпляры сервиса, не теряя пользовательских сессий, **чтобы** справляться с ростом нагрузки без простоя.

### Критерии приёмки

**Сценарий 1. Добавлен второй экземпляр**
- **Дано** сервис работает в одном экземпляре, пользователь вошёл в систему
- **Когда** администратор запускает второй экземпляр
- **Тогда** запросы распределяются между экземплярами, пользователь остаётся вошедшим и повторного входа не требуется

**Сценарий 2. Остановлен один из экземпляров**
- **Дано** сервис работает в двух экземплярах, пользователь вошёл в систему
- **Когда** один экземпляр останавливается
- **Тогда** пользователь продолжает работу через второй экземпляр без повторного входа

### Примечания

- Сервисы не хранят состояние сессии внутри себя: токены проверяются на шлюзе, состояние лежит в базе и Redis (NFT-1.3).
- Нагрузочная проверка масштабирования описана в методике NFR (шаг 7 Ф1).

## US-8.12. Интерфейс на русском языке с выносом текстов

| Поле | Содержание |
| --- | --- |
| ID | US-8.12 |
| Релиз | R1 |
| Требования | NFT-7.0 |
| Процесс или use case | Отдельного процесса нет. Требования к интерфейсу описаны в разделе 7 |

### История

**Как** гость, **я хочу** видеть интерфейс платформы на русском языке, **чтобы** пользоваться ей без перевода.

### Критерии приёмки

**Сценарий 1. Все тексты на русском**
- **Дано** гость или пользователь любой роли
- **Когда** он открывает экраны платформы, получает сообщения об ошибках и письма
- **Тогда** все тексты на русском языке

**Сценарий 2. Тексты вынесены из кода**
- **Дано** исходный код интерфейса и писем
- **Когда** проверяется наличие русских строк в коде

## Решения и открытые вопросы

Открытых вопросов нет. Решения, принятые при написании историй:

1. **Роль «Продавец» вручную не назначается.** Иначе администратор мог бы обойти модерацию, а цель BG-05 требует модерации 100% продавцов (US-8.1).
2. **В системе всегда есть хотя бы один активный администратор.** Последнего администратора нельзя лишить роли или деактивировать (US-8.1, US-8.2).
3. **Статус учётной записи «заблокирован» в R1 не используется.** Переходов в него в требованиях нет. Замечание вынесено в итоговый отчёт Ф1.
4. **Каскад деактивации продавца вне R1.** Статусы товаров деактивированного продавца не меняются, товары скрываются блокировкой модератора. Замечание вынесено в итоговый отчёт Ф1.
5. **Журнал аудита наполняется через Outbox.** Действие и событие аудита сохраняются в одной транзакции, поэтому действия без записи в журнале не бывает (US-8.6).
6. **Письма о смене e-mail по обращению уходят на оба адреса** (US-7.4).
7. **Эксплуатационные истории US-8.10 – US-8.12.** Требования NFT-1.3, NFT-4.0 – NFT-4.2 и NFT-7.0 не относятся к сценариям пользователей, но проверяются. Для них написаны отдельные истории со сценариями, чтобы каждое требование R1 имело проверяемый критерий и строку в матрице трассировки.
