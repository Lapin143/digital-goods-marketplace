| Требования | FT-2.0, FT-2.1, FT-2.2, FT-2.3, FT-2.4, FT-11.1, FT-11.2, FT-11.4, NFT-5.3 |
| Процессы | [BPMN-02](../03-processes/BPMN-02-seller-onboarding.md), статусная модель [SM-05](../03-processes/SM-05-seller-profile.md) |

Эпик описывает путь от заявки на статус продавца до рабочего кабинета: анкета, решение модератора, уведомление, повторная заявка после отказа. Заявитель это зарегистрированный пользователь с ролью «Покупатель». Роль «Продавец» ему назначается только после одобрения заявки. Оповещение о просрочке рассмотрения вынесено в [эпик 8](US-08-admin-audit.md) (US-8.8).

## US-2.1. Подача заявки на статус продавца

| Поле | Содержание |
| --- | --- |
| ID | US-2.1 |
| Релиз | R1 |
| Требования | FT-2.0 |
| Процесс или use case | BPMN-02 (шаги 1 и 2), SM-05/T1, T2, T7, UC-02 |

### История

**Как** покупатель, **я хочу** заполнить анкету продавца и отправить её на проверку, **чтобы** получить доступ к кабинету продавца и продавать товары.

### Критерии приёмки

**Сценарий 1. Анкета сохранена как черновик**
- **Дано** зарегистрированный пользователь ещё не подавал заявку
- **Когда** он заполняет часть анкеты: тип (ИП, самозанятый, юрлицо), наименование, реквизиты, описание ассортимента, документы, и сохраняет
- **Тогда** профиль получает статус «черновик» и в очередь модератора не попадает

**Сценарий 2. Заявка отправлена**
- **Дано** анкета заполнена полностью, документы приложены
- **Когда** пользователь отправляет заявку
- **Тогда** документы сохраняются в S3-совместимом хранилище в РФ, профиль получает статус «на проверке»
- **И** заявка попадает в очередь модератора, начинается срок рассмотрения 3 суток

**Сценарий 3. Анкета заполнена не полностью**
- **Дано** в анкете не указан тип, наименование, реквизиты, описание ассортимента или нет документов
- **Когда** пользователь пытается отправить заявку
- **Тогда** заявка не отправляется, профиль остаётся «черновик», незаполненные поля выделены

**Сценарий 4. Заявка уже на проверке**
- **Дано** профиль в статусе «на проверке»
- **Когда** пользователь пытается отправить заявку ещё раз
- **Тогда** вторая заявка не создаётся, изменить анкету во время проверки нельзя

**Сценарий 5. Повторная отправка после доработки**
- **Дано** профиль в статусе «на доработке», заявитель исправил анкету и документы
- **Когда** он отправляет заявку повторно
- **Тогда** профиль получает статус «на проверке», срок рассмотрения 3 суток отсчитывается заново

### Примечания

- Профиль продавца у пользователя один. Заявка это его переход из «черновик» в «на проверке» (SM-05).
- Ссылки на документы хранятся в профиле, сами файлы в S3-совместимом хранилище в РФ (NFT-5.0).

## US-2.2. Одобрение заявки модератором

| Поле | Содержание |
| --- | --- |
| ID | US-2.2 |
| Релиз | R1 |
| Требования | FT-2.1, FT-1.3, FT-11.2, NFT-5.3 |
| Процесс или use case | BPMN-02 (шаги 4 и 6), SM-05/T3, UC-02 |

### История

**Как** модератор, **я хочу** одобрить заявку после проверки анкеты и документов, **чтобы** добросовестный продавец получил доступ к платформе.

### Критерии приёмки

**Сценарий 1. Заявка одобрена**
- **Дано** заявка в статусе «на проверке» находится в очереди модератора
- **Когда** модератор нажимает «Одобрить»
- **Тогда** профиль получает статус «одобрен», пользователю назначается роль «Продавец», от него требуется настроить второй фактор
- **И** в журнал аудита пишется запись: кто, в какой роли, какое действие, над каким объектом, когда, без персональных данных в открытом виде

**Сценарий 2. Заявка уже решена другим модератором**
- **Дано** заявка получила решение другого модератора, профиль не в статусе «на проверке»
- **Когда** второй модератор нажимает «Одобрить»
- **Тогда** решение не применяется, роль не назначается второй раз, модератор видит актуальный статус заявки

**Сценарий 3. Роль не выдаётся до решения**
- **Дано** заявка в статусе «на проверке»
- **Когда** заявитель пытается открыть кабинет продавца
- **Тогда** доступ закрыт, роль «Продавец» у пользователя отсутствует

### Примечания

- Одобренный профиль можно только заблокировать (US-2.6, R2). Отозвать одобрение иначе нельзя (SM-05, решение 2).
- Автоматического одобрения нет: проверку выполняет человек (BG-05).

## US-2.3. Отказ по заявке или возврат на доработку

| Поле | Содержание |
| --- | --- |
| ID | US-2.3 |
| Релиз | R1 |
| Требования | FT-2.1, FT-2.4, FT-11.2, NFT-5.3 |
| Процесс или use case | BPMN-02 (исключения E1 и E2), SM-05/T4, T5, UC-02 |

### История

**Как** модератор, **я хочу** отклонить заявку с причиной или вернуть её на доработку с комментарием, **чтобы** заявитель понимал, что исправить.

### Критерии приёмки

**Сценарий 1. Заявка отклонена**
- **Дано** заявка в статусе «на проверке»
- **Когда** модератор отклоняет заявку и указывает причину
- **Тогда** профиль получает статус «отклонён», причина и дата отказа записываются в профиль, роль «Продавец» не выдаётся
- **И** решение попадает в журнал аудита

**Сценарий 2. Заявка возвращена на доработку**
- **Дано** заявка в статусе «на проверке»
- **Когда** модератор возвращает заявку и указывает комментарий
- **Тогда** профиль получает статус «на доработке», комментарий сохраняется, заявка выходит из очереди модератора
- **И** срока на доработку нет, автоматического закрытия заявки нет

**Сценарий 3. Причина или комментарий не указаны**
- **Дано** модератор выбрал «Отклонить» или «Вернуть на доработку»
- **Когда** он отправляет решение без причины или комментария
- **Тогда** решение не сохраняется, профиль остаётся «на проверке», модератор видит, что поле обязательно

### Примечания

- Отказ меняется только новой заявкой и новым решением (US-2.5).
- Автоматического решения по просроченной заявке нет, оповещение администратора описано в US-8.8.

## US-2.4. Уведомление заявителя о решении

| Поле | Содержание |
| --- | --- |
| ID | US-2.4 |
| Релиз | R1 |
| Требования | FT-2.2, FT-11.4, NFT-4.3 |
| Процесс или use case | BPMN-02 (шаг 7), SM-05/T3, T4, T5 |

### История

**Как** покупатель, подавший заявку на статус продавца, **я хочу** получить письмо с решением по заявке и увидеть его в кабинете, **чтобы** знать, можно ли начинать продавать или что нужно исправить.

### Критерии приёмки

**Сценарий 1. Письмо о решении**
- **Дано** модератор принял решение по заявке
- **Когда** решение записано
- **Тогда** на e-mail заявителя уходит письмо: при одобрении с указанием настроить второй фактор, при отказе с причиной, при возврате на доработку с комментарием
- **И** то же решение и причина или комментарий видны в кабинете заявителя

**Сценарий 2. Почтовый провайдер не принял письмо**
- **Дано** решение записано, провайдер не принял письмо
- **Когда** сервис уведомлений получает отказ
- **Тогда** отправка повторяется с нарастающей задержкой, решение по заявке не откатывается
- **И** заявитель видит решение в кабинете независимо от судьбы письма

### Примечания

- Для продавца письма о решениях по товару описаны в US-3.7, по заявке на вывод в US-10.4 (R2).

## US-2.5. Повторная заявка после отказа

| Поле | Содержание |
| --- | --- |
| ID | US-2.5 |
| Релиз | R1 |
| Требования | FT-2.4, FT-11.1 |
| Процесс или use case | BPMN-02 (исключения E4 и E5), SM-05/T2, T6, UC-02 |

### История

**Как** покупатель, которому отказали в статусе продавца, **я хочу** исправить анкету и подать заявку заново, **чтобы** получить статус продавца после устранения замечаний.

### Критерии приёмки

**Сценарий 1. Повторная заявка после паузы**
- **Дано** профиль в статусе «отклонён», с отказа прошло не менее 24 часов
- **Когда** заявитель исправляет анкету и отправляет заявку
- **Тогда** профиль последовательно проходит «черновик» и «на проверке», срок рассмотрения 3 суток отсчитывается с новой подачи

**Сценарий 2. Заявка раньше паузы**
- **Дано** с отказа прошло меньше 24 часов
- **Когда** заявитель пытается отправить заявку
- **Тогда** заявка не принимается, профиль остаётся «черновик»
- **И** заявитель видит дату и время, когда можно подать новую заявку

**Сценарий 3. Правки сразу после отказа**
- **Дано** профиль в статусе «отклонён», пауза не прошла
- **Когда** заявитель начинает исправлять анкету
- **Тогда** профиль возвращается в «черновик», причина отказа остаётся видна
- **И** отправка станет доступна, когда пауза закончится

### Примечания

- Пауза 24 часа это параметр платформы (FT-11.1). Для проверки используется значение, настроенное на стенде.
- Пауза проверяется при отправке, а не при исправлении: заявитель не теряет время на правки, очередь модератора защищена от повторов (SM-05, решение 1).

## US-2.6. Блокировка продавца и снятие блокировки

| Поле | Содержание |
| --- | --- |
| ID | US-2.6 |
| Релиз | R2 |
| Требования | FT-2.3, FT-9.3, FT-11.2 |
| Процесс или use case | SM-05/T8, T9, SM-04/T9, T10 |

### История

**Как** модератор, **я хочу** заблокировать недобросовестного продавца и снять блокировку, **чтобы** защитить покупателей, не ломая уже оформленные заказы.

### Критерии приёмки

**Сценарий 1. Блокировка продавца**
- **Дано** продавец одобрен, у него есть опубликованные товары, открытые заказы и деньги на балансе
- **Когда** модератор блокирует продавца
- **Тогда** его товары скрываются с витрины, новые заявки на вывод не принимаются
- **И** открытые заказы и споры дорабатываются, начисления и удержание продолжаются

**Сценарий 2. Снятие блокировки**
- **Дано** продавец заблокирован
- **Когда** модератор снимает блокировку
- **Тогда** товары возвращаются в прежние статусы, вывод снова возможен

### Примечания

- Товар, заблокированный самим модератором (US-3.5), при снятии блокировки продавца не возвращается: возвращаются только товары с причиной «блокировка продавца» (SM-04/T10).

## Решения и открытые вопросы

Открытых вопросов нет. Решения, принятые при написании историй:

1. **Заявитель это пользователь с ролью «Покупатель».** Отдельной роли «Заявитель» в разделе 3 нет, поэтому истории пишутся от покупателя. Роль «Продавец» назначается только в SM-05/T3.
2. **Письмо о решении по заявке описано отдельной историей.** FT-2.2 и часть FT-11.4 про подключение закрыты в US-2.4, чтобы решение модератора (US-2.2, US-2.3) и уведомление проверялись независимо.
3. **Одна заявка на пользователя.** Пока профиль «на проверке», вторая заявка не создаётся (US-2.1, сценарий 4).
