## Основной сценарий

1. **Система** («Остатки и ключи») получает событие «заказ оплачен». Резерв получает статус «использован» (SM-08/T2), ключи заказа получают статус «выдан» и остаются привязанными к заказу (SM-03/T4; BPMN-01, шаг 8; FT-7.1).
2. **Система** («Выдача») создаёт первичную выдачу «в очереди» (SM-06/T1), формирует письмо с ключами, расшифровывая их только на этом шаге, и запускает контроль 30 минут с момента оплаты (шаг 9; NFT-3.2, NFT-2.4).
3. **Система** передаёт письмо провайдеру. На это отводится не более 60 секунд для 95% заказов (шаг 9; NFT-2.0). Письмо уходит на адрес из снимка e-mail в заказе и содержит ровно столько ключей, сколько заказано. Это и есть сообщение «ключ выдан» покупателю (FT-11.0).
4. **E-mail-провайдер** принимает письмо. Выдача получает статус «отправлено» (SM-06/T2), заказ получает статус «выдан» (SM-01/T9). С этого момента открываются окно обращения в поддержку 72 часа, окно спора 72 часа и срок удержания средств 7 дней (шаг 10; FT-7.0).
5. **E-mail-провайдер** подтверждает доставку в почтовый ящик. Выдача получает статус «доставлено» (SM-06/T5), фиксируется время доставки для метрики BG-01. Не более 30 минут от оплаты для 95% заказов (шаг 11; NFT-2.1).

## Альтернативные сценарии

- **1a.** Событие «заказ оплачен» пришло повторно. **Система** находит первичную выдачу по заказу и игнорирует событие: вторая выдача и второе письмо не создаются, ключи не берутся заново (FT-6.2, NFT-2.3).
- **1b.** Заказ стал «оплачен» через позднюю оплату (UC-05, SM-01/T7). Сценарий начинается с шага 1, контроль 30 минут отсчитывается от повторного подтверждения оплаты.
- **5a.** Подтверждение доставки приходит позже 30 минут. К этому времени сработал контроль и создал обращение (5y). Выдача получает «доставлено», обращение переходит в «решено» без участия оператора (SM-07/T4). Заказ учитывается в метрике как не уложившийся в 30 минут.

## Исключения

- **4x.** Провайдер не принял письмо: сбой или отказ (BPMN-01, E9). **Система** повторяет отправку с нарастающей задержкой (FT-7.3), номер попытки растёт, статус выдачи остаётся «в очереди» (SM-06/T3), заказ остаётся «оплачен». Когда попытки исчерпаны, выдача получает «ошибка» (SM-06/T4), создаётся обращение «создано» с источником «система» (SM-07/T1), администратор получает оповещение, сообщение уходит в очередь недоставленных сообщений. Заказ остаётся «оплачен».
- **5x.** Провайдер сообщил о недоставке: отказ или неверный адрес (E10). Выдача получает «ошибка» (SM-06/T6), заказ остаётся «выдан», создаётся обращение «создано» (SM-07/T1). Дальше работает UC-04.
- **5y.** Подтверждения доставки нет 30 минут (E11). Заказ попадает в очередь поддержки (обращение «создано»), администратор получает оповещение. Статус выдачи не меняется, автоматического возврата нет. Если по заказу уже есть открытое обращение, второе не создаётся.
- **5z.** Провайдер повторно присылает тот же статус письма. Уведомление игнорируется (NFT-2.3).

## Нефункциональные ограничения

| Ограничение | Значение | Требование |
| --- | --- | --- |
| Передача письма провайдеру | Не более 60 секунд для 95% заказов | NFT-2.0 |
| Доставка письма | Не более 30 минут после оплаты для 95% заказов | NFT-2.1, FT-7.0 |
| Дубль ключа | 0 случаев, ключ привязан не более чем к одному заказу | FT-7.1, NFT-2.2 |
| Повторная обработка событий | Оплата, выдача, письмо не создают дублей | NFT-2.3 |
| Заказ без обработки | Через 30 минут без доставки заказ в очереди поддержки, не дольше 1 часа без обработки | NFT-2.4 |
| Хранение ключа | Зашифрован, значение не попадает в логи и ответы API | NFT-3.2 |
| Сбой почты | Повторы, очередь недоставленных сообщений, передача в поддержку | NFT-4.3 |
| Метрики | Время выдачи и число заказов в очереди поддержки | NFT-6.1 |
