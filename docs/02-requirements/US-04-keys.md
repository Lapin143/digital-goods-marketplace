## US-4.1. Способ выдачи товара

| Поле | Содержание |
| --- | --- |
| ID | US-4.1 |
| Релиз | R1 (пул), R2 (API) |
| Требования | FT-4.0 |
| Процесс или use case | BPMN-03 (шаг 1), SM-03 |

### История

**Как** продавец, **я хочу** выбрать способ выдачи товара, **чтобы** платформа знала, откуда брать ключ для покупателя.

### Критерии приёмки

**Сценарий 1. Выдача из пула ключей**
- **Дано** продавец создаёт или правит товар
- **Когда** он выбирает способ «из загруженного пула ключей»
- **Тогда** в карточке товара в кабинете доступна загрузка ключей, остаток товара считается по пулу (US-4.5)

**Сценарий 2. Способ по запросу к API в R1 недоступен**
- **Дано** действует релиз R1
- **Когда** продавец открывает форму товара или отправляет запрос со способом «по запросу к API»
- **Тогда** в форме предлагается только способ «из пула ключей», запрос с другим способом отклоняется

**Сценарий 3. Выдача по запросу к API (R2)**
- **Дано** действует релиз R2, у продавца выпущен API-ключ
- **Когда** он выбирает для товара способ «по запросу к API»
- **Тогда** пул ключей у такого товара не ведётся, остаток задаёт продавец (US-4.7), ключ платформа запрашивает у системы продавца при каждом заказе

### Примечания

- Способ выдачи входит в поля товара (FT-3.0). Смена способа у опубликованного товара не требует модерации (US-3.6).
- Правила смены способа при уже существующих ключах и резервах относятся к R2 и уточняются при проработке выдачи по API (граница детализации R2 в Ф1).

## US-4.2. Загрузка пула ключей вручную

| Поле | Содержание |
| --- | --- |
| ID | US-4.2 |
| Релиз | R1 |
| Требования | FT-4.1, NFT-3.2 |
| Процесс или use case | BPMN-03 (шаг 2, исключение E4), SM-03/T1 |

### История

**Как** продавец, **я хочу** добавить ключи в пул товара вручную, **чтобы** товар можно было продавать.

### Критерии приёмки

**Сценарий 1. Ключи добавлены**
- **Дано** у продавца есть товар в статусе «черновик», «на модерации», «опубликован» или «отклонён» со способом выдачи «пул»
- **Когда** он вводит ключи по одному в строке и сохраняет
- **Тогда** каждый новый ключ сохраняется в статусе «свободен», остаток товара растёт на число принятых ключей
- **И** продавец видит итог: принято столько-то ключей

**Сценарий 2. Дубликаты внутри товара**
- **Дано** в пуле товара уже есть ключ, либо в списке одинаковые ключи
- **Когда** продавец сохраняет список
- **Тогда** повторяющиеся значения отклоняются, остальные сохраняются
- **И** остаток растёт только на принятые ключи, продавец видит число отклонённых

**Сценарий 3. Одинаковое значение в другом товаре**
- **Дано** такое же значение ключа есть в пуле другого товара
- **Когда** продавец добавляет его в этот товар
- **Тогда** ключ принимается, дубликатами считаются только значения внутри одного товара

**Сценарий 4. Чужой или недоступный товар**
- **Дано** товар принадлежит другому продавцу или находится в статусе «архив» или «заблокирован»
- **Когда** продавец пытается добавить ключи
- **Тогда** операция отклоняется, ключи не сохраняются

### Примечания

- Дубликаты определяются по HMAC значения с секретом сервера, а не по обычному хешу: короткие ключи нельзя подобрать перебором (FT-4.1). Уникальность гарантирует индекс по паре «товар, HMAC».
- Удалять свободные ключи продавец не может: это граница MVP (SM-03, решение 3).

## US-4.3. Загрузка пула ключей файлом CSV

| Поле | Содержание |
| --- | --- |
| ID | US-4.3 |
| Релиз | R1 |
| Требования | FT-4.1 |
| Процесс или use case | BPMN-03 (шаг 2, исключение E4), SM-03/T1 |

### История

**Как** продавец, **я хочу** загрузить большой пул ключей файлом CSV, **чтобы** не вводить тысячи значений вручную.

### Критерии приёмки

**Сценарий 1. Файл принят**
- **Дано** у продавца есть доступный товар со способом выдачи «пул» и файл CSV с ключами, по одному в строке
- **Когда** он загружает файл
- **Тогда** все уникальные ключи сохраняются в статусе «свободен», остаток растёт на их число
- **И** продавец видит отчёт: принято и отклонено столько-то строк

**Сценарий 2. В файле дубликаты**
- **Дано** в файле есть значения, которые повторяются внутри файла или уже есть в пуле товара
- **Когда** файл загружен
- **Тогда** дубликаты отклоняются, остальные ключи сохраняются
- **И** повторная загрузка того же файла не меняет остаток: все его значения уже в пуле

**Сценарий 3. Некорректные строки**
- **Дано** в файле есть пустые строки или значения длиннее 1 КБ
- **Когда** файл загружен
- **Тогда** такие строки отклоняются с указанием номера строки, остальные ключи сохраняются

**Сценарий 4. Пул переполняется**
- **Дано** в пуле товара 99 990 ключей, в файле 20 новых уникальных значений
- **Когда** продавец загружает файл
- **Тогда** файл отклоняется целиком, остаток не меняется, продавец видит предел 100 000 ключей на товар

### Примечания

- Пределы взяты из допущений раздела 2.2 требований: ключ до 1 КБ, пул одного товара до 100 000. Их контроль при загрузке принят как уточнение FT-4.1.
- Файлы с пулами хранятся в S3-совместимом хранилище в РФ (раздел 6.2 требований).

## US-4.4. Ключи зашифрованы и не показываются после загрузки

| Поле | Содержание |
| --- | --- |
| ID | US-4.4 |
| Релиз | R1 |
| Требования | FT-4.2, NFT-3.2 |
| Процесс или use case | BPMN-03 (шаг 2), SM-03, [UC-03](UC-03-key-issuance.md) |

### История

**Как** продавец, **я хочу** загружать ключи, которые хранятся зашифрованными и нигде не показываются, **чтобы** утечка базы, логов или экрана не раскрыла мой товар.

### Критерии приёмки

**Сценарий 1. После загрузки ключи не видны**
- **Дано** ключи загружены в пул товара
- **Когда** продавец, модератор или администратор открывают товар и список ключей
- **Тогда** они видят число ключей по статусам, значений ключей нет ни на одном экране

**Сценарий 2. Значение хранится зашифрованным**
- **Дано** ключ сохранён в базе
- **Когда** проверяется запись ключа в таблице
- **Тогда** значение зашифровано (AES-256), открытого значения в базе нет
- **И** мастер-ключ шифрования и секрет HMAC для проверки дублей хранятся вне базы данных

**Сценарий 3. Значения нет в логах и ответах API**
- **Дано** выполнены загрузка пула и выдача ключа покупателю
- **Когда** проверяются логи всех сервисов и ответы API
- **Тогда** значений ключей в них нет

**Сценарий 4. Запрос значения через кабинет**
- **Дано** ключ загружен
- **Когда** пользователь любой роли пытается получить его значение через кабинет или запрос к API кабинета
- **Тогда** такой операции нет, запрос отклоняется

### Примечания

- Единственное место, где значение ключа расшифровывается, это формирование письма с ключом сервисом выдачи (US-6.1). Ключ оператору поддержки не показывается (US-7.3).
- Проверка NFT-3.2 описана в `docs/08-testing/nfr-methodology.md` (Ф1, шаг 7).

## US-4.5. Остаток товара с пулом ключей

| Поле | Содержание |
| --- | --- |
| ID | US-4.5 |
| Релиз | R1 |
| Требования | FT-4.3 |
| Процесс или use case | SM-03, SM-08, BPMN-01 |

### История

**Как** продавец, **я хочу** видеть остаток товара, равный числу свободных ключей, **чтобы** вовремя пополнять пул.

### Критерии приёмки

**Сценарий 1. Остаток равен числу свободных ключей**
- **Дано** в пуле 100 ключей: 87 «свободен», 3 «зарезервирован», 10 «выдан»
- **Когда** продавец открывает товар
- **Тогда** остаток равен 87

**Сценарий 2. Резерв уменьшает остаток, снятие резерва возвращает его**
- **Дано** остаток товара 87, покупатель оформил заказ на 2 штуки
- **Когда** ключи зарезервированы
- **Тогда** остаток равен 85
- **И** после снятия резерва (срок истёк или отказ в оплате) остаток снова равен 87

**Сценарий 3. Выданный ключ в остаток не возвращается**
- **Дано** ключи заказа выданы покупателю
- **Когда** заказ позже возвращается
- **Тогда** выданные ключи остаются «выдан», остаток не растёт

**Сценарий 4. Дубликаты остаток не меняют**
- **Дано** остаток 87
- **Когда** продавец загружает ключи, все из которых уже есть в пуле
- **Тогда** остаток остаётся 87

### Примечания

- Остаток вычисляется, отдельного статуса товара «нет в наличии» нет (SM-04).

## US-4.6. Товар с нулевым остатком недоступен для заказа

| Поле | Содержание |
| --- | --- |
| ID | US-4.6 |
| Релиз | R1 |
| Требования | FT-4.4, FT-5.2 |
| Процесс или use case | BPMN-03 (исключение E6), BPMN-01 (исключение E2), SM-01/T3, [UC-01](UC-01-purchase.md) |

### История

**Как** покупатель, **я хочу** сразу видеть, что товара нет в наличии, **чтобы** не тратить время на оформление, которое закончится отменой.

### Критерии приёмки

**Сценарий 1. Остаток равен нулю**
- **Дано** товар опубликован, остаток равен нулю
- **Когда** покупатель открывает карточку товара
- **Тогда** действие «Купить» недоступно, показано, что товара нет в наличии

**Сценарий 2. Остаток исчерпан после открытия карточки**
- **Дано** покупатель открыл карточку, пока остаток был 1, другой покупатель успел зарезервировать последний ключ
- **Когда** первый покупатель оформляет заказ
- **Тогда** резерв не создаётся, заказ получает статус «отменён», платёж не создаётся
- **И** покупатель видит сообщение о том, сколько штук осталось

**Сценарий 3. Заказано больше, чем осталось**
- **Дано** остаток товара 3
- **Когда** покупатель оформляет заказ на 5 штук
- **Тогда** частичного резерва нет: заказ получает статус «отменён», покупатель видит остаток 3 и может оформить новый заказ на 3 штуки

### Примечания

- Товар с нулевым остатком остаётся «опубликован» и виден на витрине (SM-04).
- Проверку остатка при оформлении выполняет сервис заказов (BPMN-03, E6).

## US-4.7. Остаток товара с выдачей по API

| Поле | Содержание |
| --- | --- |
| ID | US-4.7 |
| Релиз | R2 |
| Требования | FT-4.3, FT-4.0 |
| Процесс или use case | SM-03 (раздел «Остаток товара»), SM-08/T5 |

### История

**Как** продавец с выдачей ключей по API, **я хочу** сам задавать остаток товара, **чтобы** платформа продавала не больше, чем я могу выдать.

### Критерии приёмки

**Сценарий 1. Остаток меняется с заказами**
- **Дано** продавец задал остаток 50
- **Когда** покупатель оформляет заказ на 2 штуки, затем заказ отменяется или резерв истекает
- **Тогда** остаток уменьшается до 48, при отмене или истечении резерва восстанавливается до 50

**Сценарий 2. Ручная правка не затирает новые заказы**
- **Дано** продавец открыл форму остатка при значении 50, за это время оформлен заказ на 2 штуки
- **Когда** он сохраняет новое значение
- **Тогда** система обнаруживает, что запись изменилась, сохранение отклоняется, продавец видит актуальный остаток 48 и повторяет правку

### Примечания

- Контроль версии записи при ручной правке закреплён в разделе 8.2 требований.

## Решения и открытые вопросы

Открытых вопросов нет. Решения, принятые при написании историй:

1. **Защита ключей выделена в историю US-4.4.** FT-4.2 касается нескольких ролей и проверяется отдельными сценариями: экраны, хранение, логи и API.
2. **Пределы размеров контролируются при загрузке.** Ключ до 1 КБ и пул до 100 000 взяты из допущений раздела 2.2 и приняты как правила загрузки (US-4.3).
3. **Продавец не удаляет ключи.** Свободный ключ можно только добавить, отзыв ключей вне MVP (SM-03, решение 3).
4. **Правила смены способа выдачи у существующего товара относятся к R2.** Фаза Ф1 прорабатывает R1 полностью, R2 укрупнённо. Эти правила уточняются при проработке выдачи по API.
