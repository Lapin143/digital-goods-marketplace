# UC-02. Подача заявки продавца и модерация

| Поле | Содержание |
| --- | --- |
| ID | UC-02 |
| Актор | Заявитель (покупатель, подающий заявку), модератор. Внешний участник: e-mail-провайдер |
| Цель | Получить статус продавца после проверки анкеты и документов |
| Предусловия | Пользователь зарегистрирован с ролью «Покупатель». Профиль продавца отсутствует, либо в статусе «черновик», «отклонён» или «на доработке» (SM-05) |
| Постусловия | Успех: профиль «одобрен», у пользователя роль «Продавец», второй фактор настроен. Иначе: профиль «отклонён» с причиной или «на доработке» с комментарием |
| Триггер | Пользователь решает стать продавцом и заполняет анкету |
| Требования | FT-1.3, FT-2.0, FT-2.1, FT-2.2, FT-2.4, FT-11.1, FT-11.2, FT-11.4, NFT-3.0, NFT-4.3, NFT-5.0, NFT-5.3, NFT-6.1 |
| Процесс | [BPMN-02](../03-processes/BPMN-02-seller-onboarding.md), шаги 1 – 9, исключения E1 – E5 |
| Статусные модели | [SM-05](../03-processes/SM-05-seller-profile.md) |
| User stories | [US-1.5](US-01-accounts.md), [US-2.1](US-02-sellers.md), [US-2.2](US-02-sellers.md), [US-2.3](US-02-sellers.md), [US-2.4](US-02-sellers.md), [US-2.5](US-02-sellers.md), [US-8.8](US-08-admin-audit.md) |

## Основной сценарий

1. **Заявитель** заполняет анкету: тип (ИП, самозанятый, юрлицо), наименование, реквизиты, описание ассортимента, документы (BPMN-02, шаг 1; FT-2.0). Профиль хранится в статусе «черновик» (SM-05/T1).
2. **Заявитель** отправляет заявку. **Система** сохраняет документы в S3-совместимом хранилище в РФ и переводит профиль в «на проверке» (шаг 2; SM-05/T2).
3. **Система** ставит заявку в очередь модератора и запускает срок рассмотрения не более 3 суток (шаг 3; FT-2.1).
4. **Модератор** проверяет анкету и документы и выбирает решение «Одобрить» (шаг 4; FT-2.1).
5. **Система** записывает решение в журнал аудита без персональных данных в открытом виде (шаг 5; FT-11.2, NFT-5.3).
6. **Система** переводит профиль в «одобрен» (SM-05/T3), назначает роль «Продавец» и требует настроить второй фактор (шаг 6).
7. **Система** отправляет заявителю письмо с решением, то же решение видно в кабинете (шаг 7; FT-2.2, FT-11.4).
8. **Заявитель** входит в систему и при первом входе настраивает второй фактор. **Система** проверяет код из приложения-аутентификатора и включает 2FA (шаг 8; FT-1.3).
9. **Система** открывает кабинет продавца (шаг 9). Дальше продавец создаёт товары по BPMN-03.

## Альтернативные сценарии

- **4a.** Модератор отклоняет заявку и указывает причину (BPMN-02, E1). Профиль «отклонён», причина и дата отказа записываются (SM-05/T4), роль не выдаётся, заявителю уходит письмо с причиной. Заявитель может начать исправлять анкету: профиль возвращается в «черновик» (SM-05/T6, E4), а отправить заявку можно не раньше чем через 24 часа после отказа (FT-2.4). Сценарий продолжается с шага 1.
- **4b.** Модератор возвращает заявку на доработку и указывает комментарий (E2). Профиль «на доработке» (SM-05/T5), заявка выходит из очереди модератора, заявителю уходит письмо с комментарием. Срока на доработку нет. После доработки заявитель отправляет заявку повторно (SM-05/T7), срок 3 суток отсчитывается заново, сценарий продолжается с шага 3.

## Исключения

- **2x.** Анкета заполнена не полностью. Заявка не отправляется, профиль остаётся «черновик», незаполненные поля выделены.
- **2y.** Профиль был отклонён, с отказа прошло меньше 24 часов (E5). Заявка не принимается, профиль остаётся «черновик», заявитель видит, когда можно подать новую.
- **4x.** За 3 суток решения нет (E3). Администратор получает оповещение, в метрику сроков модерации записывается просрочка. Статус заявки не меняется, автоматического решения нет.
- **4y.** Заявку уже решил другой модератор. Решение не применяется, модератор видит актуальный статус.
- **7x.** Провайдер не принял письмо. Сервис уведомлений повторяет отправку, решение по заявке не откатывается, заявитель видит его в кабинете.
- **8x.** Код второго фактора неверный. Кабинет не открывается, пока не введён верный код.

## Нефункциональные ограничения

| Ограничение | Значение | Требование |
| --- | --- | --- |
| Срок рассмотрения заявки | Не более 3 суток с каждой подачи | FT-2.1 |
| Пауза перед новой заявкой после отказа | 24 часа, параметр платформы | FT-2.4, FT-11.1 |
| Второй фактор | Обязателен для продавца, модератора, оператора поддержки и администратора | FT-1.3, NFT-3.0 |
| Журнал аудита | Решение записывается без персональных данных в открытом виде | NFT-5.3 |
| Документы продавцов | Хранятся на серверах в РФ | NFT-5.0 |
| Метрика сроков модерации | Просрочка попадает в метрику | NFT-6.1 |
| Сбой почты | Письмо повторяется, решение не теряется | NFT-4.3 |
