## User stories

Один файл на эпик. В каждом файле вверху таблица историй, ниже сами истории: поля (ID, релиз, требования, процесс), история «Как..., я хочу..., чтобы...», критерии приёмки, примечания. Истории релиза R1 написаны подробно, у каждой есть основной сценарий и сценарий исключения. Истории R2 и R3 даны укрупнённо.

Правила, по которым написаны истории:

- Все идентификаторы FT и NFT взяты из требований v1.5, новых нет. Каждое требование релиза R1 покрыто хотя бы одной историей релиза R1.
- Роли берутся из раздела 3 требований, для автоматических действий используется роль «Система». Заявитель на статус продавца это покупатель, подавший заявку.
- Числа в критериях взяты из требований: резерв 15 минут, платёжная сессия 12 минут, окна 72 часа, срок модерации 3 суток, одноразовый код 5 минут и 5 попыток.
- Эксплуатационные качества без пользовательского сценария (восстановление, масштабирование, язык интерфейса) оформлены историями US-8.10, US-8.11 и US-8.12, чтобы у каждого NFT релиза R1 был проверяемый критерий.
- Решения, принятые при написании историй, перечислены в конце каждого файла в разделе «Решения и открытые вопросы».

## Use cases

Пять сценариев описывают сквозные пути, которые проходят через несколько историй. У каждого есть основной сценарий, альтернативы, исключения и таблица нефункциональных ограничений. Исключения нумеруются по шагу основного сценария (3x, 5y), альтернативы буквой a, b.

| Use case | Файл | Процесс | Актор | Истории |
| --- | --- | --- | --- | --- |
| UC-01. Покупка цифрового товара | [UC-01-purchase.md](UC-01-purchase.md) | BPMN-01, шаги 1 – 7 | Покупатель | 10 |
| UC-02. Подача заявки продавца и модерация | [UC-02-seller-application.md](UC-02-seller-application.md) | BPMN-02 | Заявитель, модератор | 7 |
| UC-03. Выдача ключа и гарантированная доставка | [UC-03-key-issuance.md](UC-03-key-issuance.md) | BPMN-01, шаги 8 – 11 | Система | 8 |
| UC-04. Обращение в поддержку, повторная отправка, смена e-mail | [UC-04-support-request.md](UC-04-support-request.md) | BPMN-04 | Покупатель, оператор | 7 |

Связь между историями и use cases двусторонняя: use case перечисляет свои истории, а каждая такая история называет use case в поле «Процесс или use case». Проверка симметрии входит в проверки шага.

Дальше от историй идёт трассировка: процесс, use case, статусная модель, API, тест-кейс. Матрица трассировки находится в `docs/08-testing/traceability.md`.
