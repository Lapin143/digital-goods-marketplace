# Эпик 7. Поддержка

| Поле | Содержание |
| --- | --- |
| Эпик | 7. Поддержка |
| Релиз | R1 |
| Роли | Покупатель, Оператор поддержки, Система |
| Требования | FT-1.5, FT-7.2, FT-7.3, FT-7.5, FT-11.0, FT-11.2, NFT-3.2, NFT-3.5, NFT-3.7, NFT-5.3, NFT-6.1 |
| Процессы | [BPMN-04](../03-processes/BPMN-04-support-request.md), [BPMN-01](../03-processes/BPMN-01-purchase.md), статусные модели [SM-07](../03-processes/SM-07-support-ticket.md), [SM-06](../03-processes/SM-06-delivery.md) |

Эпик описывает, что происходит, когда автоматическая доставка не сработала: покупатель создаёт обращение, оператор берёт его в работу, повторно отправляет ключ или меняет e-mail после двух подтверждений, обращение закрывается фактом доставки. Обращения от системы (недоставка, контроль 30 минут) создаются в [эпике 6](US-06-delivery.md) и обрабатываются здесь так же, как обращения покупателей. Вход покупателя по коду из SMS описан в [US-1.7](US-01-accounts.md).

## US-7.1. Обращение «Не получил ключ»

| Поле | Содержание |
| --- | --- |
| ID | US-7.1 |
| Релиз | R1 |
| Требования | FT-7.2, NFT-3.5 |
| Процесс или use case | BPMN-04 (шаги 2, 3 и 4, исключение E1), SM-07/T1, [UC-04](UC-04-support-request.md) |

### История

**Как** покупатель, **я хочу** нажать «Не получил ключ» в карточке заказа, **чтобы** поддержка помогла мне получить оплаченный товар.

### Критерии приёмки

**Сценарий 1. Обращение создано**
- **Дано** заказ покупателя «выдан», с первичной выдачи прошло не более 72 часов, открытого обращения по заказу нет
- **Когда** покупатель нажимает «Не получил ключ»
- **Тогда** создаётся обращение в статусе «создано» с источником «покупатель», оно встаёт в очередь поддержки
- **И** покупатель видит, что обращение принято

**Сценарий 2. Окно обращения закрыто**
- **Дано** с первичного перехода заказа в «выдан» прошло больше 72 часов
- **Когда** покупатель пытается создать обращение
- **Тогда** обращение не создаётся, покупатель видит, что срок обращения истёк

**Сценарий 3. Повторная отправка не продлевает окно**
- **Дано** оператор повторно отправил ключ на 70-м часу после первичной выдачи
- **Когда** покупатель на 80-м часу нажимает «Не получил ключ»
- **Тогда** обращение не создаётся: окно считается от первичной выдачи

**Сценарий 4. Обращение по заказу уже открыто**
- **Дано** по заказу есть обращение в статусе «создано» или «в работе»
- **Когда** покупатель нажимает кнопку ещё раз
- **Тогда** второе обращение не создаётся, покупатель видит, что обращение уже принято

**Сценарий 5. Заказ не «выдан» или чужой**
- **Дано** заказ в статусе «оплачен», «отменён» или «возвращён», либо заказ принадлежит другому покупателю
- **Когда** покупатель пытается создать обращение
- **Тогда** действие недоступно, запрос отклоняется

**Сценарий 6. Превышен лимит частоты**
- **Дано** число запросов на создание обращений достигло лимита
- **Когда** покупатель отправляет ещё один запрос
- **Тогда** запрос отклоняется, обращение не создаётся

### Примечания

- Окно 72 часа настраивается (FT-7.2, FT-11.1). Автоматическая передача заказа системой этим окном не ограничена.
- Покупатель, потерявший доступ к e-mail, входит в кабинет по коду из SMS (US-1.7) и создаёт обращение из той же карточки заказа.
- Лимит частоты обращений задаётся параметром платформы (NFT-3.5, FT-11.1).

## US-7.2. Очередь обращений и взятие в работу

| Поле | Содержание |
| --- | --- |
| ID | US-7.2 |
| Релиз | R1 |
| Требования | FT-7.5, FT-7.3, NFT-6.1 |
| Процесс или use case | BPMN-04 (шаг 5), SM-07/T2, T3, [UC-04](UC-04-support-request.md) |

### История

**Как** оператор поддержки, **я хочу** видеть общую очередь обращений и брать их в работу, **чтобы** помогать покупателям, не дублируя работу коллег.

### Критерии приёмки

**Сценарий 1. Очередь двух источников**
- **Дано** в очереди есть обращения покупателей и обращения, созданные системой
- **Когда** оператор открывает очередь
- **Тогда** он видит обращения в статусе «создано» с источником, заказом, статусом выдачи и временем создания, старые выше новых
- **И** значений ключей в очереди и в карточке обращения нет

**Сценарий 2. Обращение взято в работу**
- **Дано** обращение «создано»
- **Когда** оператор берёт его в работу
- **Тогда** обращение получает статус «в работе», в нём записывается оператор, другие операторы видят его занятым

**Сценарий 3. Два оператора берут одно обращение**
- **Дано** обращение «создано»
- **Когда** два оператора берут его одновременно
- **Тогда** обращение получает первый, второй оператор видит, что обращение уже в работе

**Сценарий 4. Возврат в очередь**
- **Дано** обращение «в работе» у оператора, смена закончилась
- **Когда** оператор возвращает обращение в очередь
- **Тогда** обращение получает статус «создано», оператор в нём сбрасывается, дата создания не меняется, обращение доступно всем операторам

**Сценарий 5. Метрика очереди**
- **Дано** в очереди есть обращения
- **Когда** администратор смотрит метрики
- **Тогда** число заказов в очереди поддержки совпадает с числом обращений в статусах «создано» и «в работе»

### Примечания

- Срока обработки обращения оператором в требованиях нет. Состояние очереди контролируется метрикой (NFT-6.1, US-8.9).
- Обращение «в работе» не закрывается оператором вручную (US-7.5).

## US-7.3. Повторная отправка ключа по обращению

| Поле | Содержание |
| --- | --- |
| ID | US-7.3 |
| Релиз | R1 |
| Требования | FT-7.5, FT-11.2, NFT-3.2, NFT-3.6, NFT-5.3 |
| Процесс или use case | BPMN-04 (шаги 6 и 7, исключение E6), SM-06/T1, SM-07, [UC-04](UC-04-support-request.md) |

### История

**Как** оператор поддержки, **я хочу** повторно отправить ключ покупателю, не видя сам ключ, **чтобы** решить проблему с доставкой, не получая доступа к товару.

### Критерии приёмки

**Сценарий 1. Повторная отправка**
- **Дано** обращение «в работе», заказ «выдан», у заказа нет выдачи «в очереди»
- **Когда** оператор выбирает «Повторно отправить ключ»
- **Тогда** снимок адреса доставки в заказе обновляется текущим e-mail учётной записи, создаётся выдача типа «повторная» в статусе «в очереди», письмо передаётся провайдеру
- **И** оператор видит статус выдачи, но не значение ключа
- **И** окна обращения 72 часа, спора 72 часа и удержание 7 дней не сдвигаются

**Сценарий 2. Действие записано в журнал аудита**
- **Дано** оператор выполнил повторную отправку
- **Когда** смотрим журнал аудита
- **Тогда** есть запись: оператор, роль, действие, обращение, заказ, время, без e-mail в открытом виде

**Сценарий 3. Повторное письмо не доставлено**
- **Дано** повторная выдача создана
- **Когда** провайдер сообщает отказ или неверный адрес
- **Тогда** выдача получает статус «ошибка», обращение остаётся «в работе», оператор может повторить отправку или сменить e-mail (US-7.4)

**Сценарий 4. Уже есть выдача «в очереди»**
- **Дано** у заказа есть выдача в статусе «в очереди»
- **Когда** оператор пытается отправить ключ повторно
- **Тогда** вторая выдача не создаётся, оператору предлагается дождаться результата

**Сценарий 5. Обращения нет**
- **Дано** обращение не «в работе» у этого оператора
- **Когда** оператор пытается отправить ключ повторно
- **Тогда** действие недоступно: действия выполняются только по обращению

### Примечания

- Если выдача уже «отправлено», но доставки нет, оператор может отправить ключ повторно (SM-06).
- Ключ формирует и отправляет сервис «Выдача», оператору он не передаётся ни в каком виде (US-4.4).

## US-7.4. Смена e-mail покупателя после двух подтверждений

| Поле | Содержание |
| --- | --- |
| ID | US-7.4 |
| Релиз | R1 |
| Требования | FT-7.5, FT-1.5, FT-11.0, FT-11.2, NFT-3.5, NFT-3.7, NFT-5.3 |
| Процесс или use case | BPMN-04 (смена e-mail, исключения E4, E5 и E7), SM-07, [UC-04](UC-04-support-request.md) |

### История

**Как** оператор поддержки, **я хочу** сменить e-mail покупателя, потерявшего доступ к почте, только после подтверждения кодом из SMS и кодом на новый адрес, **чтобы** ключ дошёл до владельца, а чужой человек не перехватил учётную запись.

### Критерии приёмки

**Сценарий 1. E-mail изменён**
- **Дано** обращение «в работе», покупатель вошёл по коду из SMS и открыл форму обращения
- **Когда** оператор вводит новый e-mail, покупатель вводит в форме верный код из SMS, отправленный на его подтверждённый номер, и верный код из письма на новый адрес
- **Тогда** e-mail учётной записи меняется, затем ключ отправляется повторно на новый адрес (US-7.3)
- **И** покупатель получает письмо о смене на новый и на прежний адрес
- **И** в журнал аудита пишутся имя поля и HMAC-хеши значений до и после, e-mail в открытом виде туда не попадает

**Сценарий 2. Оператор не видит коды**
- **Дано** покупатель вводит коды в форме обращения
- **Когда** проверка завершена
- **Тогда** оператор видит только результат каждой проверки: «пройдена» или «не пройдена», кода не видит и от покупателя его не принимает

**Сценарий 3. Код из SMS не подтверждён**
- **Дано** покупатель вводит код из SMS
- **Когда** код неверный, или введён позже чем через 5 минут, или сделано 5 неверных попыток
- **Тогда** e-mail не меняется, оператор видит «проверка не пройдена», обращение остаётся «в работе»
- **И** новый код можно запросить в пределах лимита: не более 3 за 10 минут и 10 за сутки

**Сценарий 4. Новый адрес не подтверждён**
- **Дано** код из SMS подтверждён, на новый адрес отправлен код
- **Когда** код из письма неверный, истёк или исчерпаны 5 попыток
- **Тогда** e-mail в учётной записи не меняется, обращение остаётся «в работе»

**Сценарий 5. Новый адрес уже занят**
- **Дано** новый e-mail привязан к другой учётной записи
- **Когда** оператор вводит этот адрес
- **Тогда** код на него не отправляется, e-mail не меняется
- **И** покупатель и оператор видят нейтральное сообщение «Адрес использовать нельзя» без указания причины

**Сценарий 6. Нет обращения в работе**
- **Дано** обращение не «в работе» или его нет
- **Когда** оператор пытается сменить e-mail
- **Тогда** действие недоступно

### Примечания

- Решение при моделировании: если новый e-mail уже принадлежит другой учётной записи, действует то же правило нейтрального сообщения, что и для номера телефона (FT-1.5). Это уточнение FT-7.5, требования не меняются.
- Решение при моделировании: письмо о смене e-mail (FT-11.0) уходит и на новый, и на прежний адрес, чтобы владелец, сохранивший доступ к прежней почте, узнал о смене.
- Смена e-mail выполняется только оператором по обращению. Самостоятельной смены e-mail в личном кабинете в требованиях нет.

## US-7.5. Закрытие обращения по факту доставки

| Поле | Содержание |
| --- | --- |
| ID | US-7.5 |
| Релиз | R1 |
| Требования | FT-7.3, FT-7.5 |
| Процесс или use case | BPMN-04 (шаг 8), SM-06/T5, SM-07/T4, [UC-03](UC-03-key-issuance.md), [UC-04](UC-04-support-request.md) |

### История

**Как** система, **я хочу** закрывать обращение, когда ключ доставлен, **чтобы** очередь поддержки содержала только нерешённые проблемы.

### Критерии приёмки

**Сценарий 1. Доставка закрывает обращение**
- **Дано** обращение «создано» или «в работе»
- **Когда** по заказу провайдер подтверждает доставку письма: повторной отправки либо первоначального письма, которое всё же дошло
- **Тогда** выдача получает статус «доставлено», обращение получает статус «решено», уходит из очереди
- **И** покупатель получает письмо с ключом, если отправка была повторной

**Сценарий 2. Вручную закрыть нельзя**
- **Дано** обращение «в работе», доставки нет
- **Когда** оператор пытается закрыть обращение без доставки
- **Тогда** такого действия нет: обращение закрывается только фактом доставки

**Сценарий 3. Решённое обращение не открывается**
- **Дано** обращение «решено»
- **Когда** ключ снова не получен
- **Тогда** старое обращение не открывается, покупатель создаёт новое, если окно 72 часа ещё открыто (US-7.1)

### Примечания

- Закрытие без доставки оставило бы покупателя без ключа и без следа в очереди (SM-07, решение 2).
- Граница MVP: если ключ невозможно доставить даже после поддержки, обращение остаётся открытым, и оператор не имеет действия возврата (SM-07, решение 4). Такое обращение видно администратору в очереди и в метрике.

## Решения и открытые вопросы

Открытых вопросов нет. Решения, принятые при написании историй:

1. **Адрес, уже занятый другой учётной записью, не принимается при смене e-mail.** Нейтральное сообщение «Адрес использовать нельзя» повторяет правило для телефона. Этот путь добавлен в BPMN-04 как исключение E7 и в SM-07.
2. **Письмо о смене e-mail уходит на оба адреса.** Так владелец узнаёт о смене, даже если злоумышленник получил доступ к SMS.
3. **Недоставляемый заказ остаётся границей MVP.** Если у покупателя нет доступа ни к почте, ни к телефону, платформа не вернёт деньги по обращению: автовозврат есть только при поздней оплате (FT-6.4), а возврат по спору только для выданного заказа (FT-8.0). Ограничение указано в итоговом отчёте Ф1.
