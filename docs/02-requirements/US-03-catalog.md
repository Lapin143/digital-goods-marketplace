Пул ключей и остаток описаны в [эпике 4](US-04-keys.md). Оповещение администратора о просрочке проверки товара описано в [эпике 8](US-08-admin-audit.md) (US-8.8).

## US-3.1. Создание товара

| Поле | Содержание |
| --- | --- |
| ID | US-3.1 |
| Релиз | R1 |
| Требования | FT-3.0, FT-3.1 |
| Процесс или use case | BPMN-03 (шаг 1), SM-04/T1 |

### История

**Как** продавец, **я хочу** создать товар с описанием, ценой и способом выдачи, **чтобы** подготовить его к проверке и продаже.

### Критерии приёмки

**Сценарий 1. Товар создан**
- **Дано** пользователь имеет роль «Продавец», профиль в статусе «одобрен»
- **Когда** он заполняет название, описание, тип (ключ игры, лицензия ПО, подарочная карта или пополнение, подписка), платформу, регион активации, цену, способ выдачи и сохраняет
- **Тогда** товар создаётся в статусе «черновик» и не виден на витрине

**Сценарий 2. Не заполнено обязательное поле**
- **Дано** продавец открыл форму товара
- **Когда** он сохраняет товар без названия, описания, типа, платформы, региона активации, цены или способа выдачи, либо с ценой не больше нуля
- **Тогда** товар не создаётся, незаполненное или неверное поле выделено

**Сценарий 3. Пользователь не продавец**
- **Дано** у пользователя нет роли «Продавец», например заявка ещё на проверке
- **Когда** он пытается создать товар
- **Тогда** действие отклоняется, управления товарами в его кабинете нет

### Примечания

- Цена задаётся в рублях, валюта одна (раздел 2.1 требований).
- В релизе R1 способ выдачи один: пул ключей. Выдача по запросу к API доступна с R2 (US-4.1).

## US-3.2. Отправка товара на модерацию

| Поле | Содержание |
| --- | --- |
| ID | US-3.2 |
| Релиз | R1 |
| Требования | FT-3.1, FT-3.2 |
| Процесс или use case | BPMN-03 (шаги 3 и 4), SM-04/T2 |

### История

**Как** продавец, **я хочу** отправить товар на проверку, **чтобы** он появился на витрине после решения модератора.

### Критерии приёмки

**Сценарий 1. Товар отправлен на модерацию**
- **Дано** товар в статусе «черновик», обязательные поля заполнены
- **Когда** продавец отправляет товар на модерацию
- **Тогда** товар получает статус «на модерации» и встаёт в очередь модератора, начинается срок проверки 3 суток
- **И** изменить поля товара, пока он на модерации, нельзя

**Сценарий 2. Товар без ключей**
- **Дано** пул ключей товара пуст
- **Когда** продавец отправляет товар на модерацию
- **Тогда** товар уходит на модерацию: ключи для отправки не обязательны
- **И** после публикации заказ такого товара оформить нельзя, пока остаток равен нулю (US-4.6)

**Сценарий 3. Товар уже на модерации**
- **Дано** товар в статусе «на модерации»
- **Когда** продавец отправляет его ещё раз
- **Тогда** второй записи в очереди модератора нет, срок проверки не сбрасывается

**Сценарий 4. Публикация без модератора**
- **Дано** товар в статусе «черновик», «отклонён» или «архив»
- **Когда** продавец пытается сам сделать его опубликованным
- **Тогда** действие отклоняется, на витрине остаются только товары, одобренные модератором (BG-05)

### Примечания

- Правка товара в статусе «на модерации» запрещена, чтобы модератор одобрял именно то, что проверял. Для правки продавец отзывает товар в архив и восстанавливает его (US-3.8) или дожидается решения (SM-04, решение 4).

## US-3.3. Одобрение товара модератором

| Поле | Содержание |
| --- | --- |
| ID | US-3.3 |
| Релиз | R1 |
| Требования | FT-3.1, FT-3.2, FT-11.2, NFT-3.2, NFT-5.3 |
| Процесс или use case | BPMN-03 (шаги 5, 6 и 7), SM-04/T3 |

### История

**Как** модератор, **я хочу** одобрить проверенный товар, **чтобы** он появился на витрине.

### Критерии приёмки

**Сценарий 1. Товар одобрен**
- **Дано** товар в статусе «на модерации» находится в очереди модератора
- **Когда** модератор нажимает «Одобрить»
- **Тогда** товар получает статус «опубликован» и появляется на витрине
- **И** решение записывается в журнал аудита: кто, в какой роли, действие, объект, время
- **И** продавец получает письмо и запись в кабинете (US-3.7)

**Сценарий 2. Товар уже решён другим модератором**
- **Дано** товар получил решение другого модератора, он не в статусе «на модерации»
- **Когда** второй модератор нажимает «Одобрить»
- **Тогда** решение не применяется, модератор видит актуальный статус товара

**Сценарий 3. Ключи модератору не показываются**
- **Дано** в пуле товара есть ключи
- **Когда** модератор открывает товар на проверке
- **Тогда** он видит описание, цену и остаток, но не значения ключей

### Примечания

- Автоматического одобрения нет: проверку выполняет человек (BG-05).
- Для продавца, который заблокирован (R2), одобрение невозможно (SM-04/T3).

## US-3.4. Отклонение товара с причиной

| Поле | Содержание |
| --- | --- |
| ID | US-3.4 |
| Релиз | R1 |
| Требования | FT-3.2, FT-11.2, NFT-5.3 |
| Процесс или use case | BPMN-03 (исключение E1), SM-04/T4, T5 |

### История

**Как** модератор, **я хочу** отклонить товар с указанием причины, **чтобы** продавец понял, что исправить, а запрещённый контент не попал на витрину.

### Критерии приёмки

**Сценарий 1. Товар отклонён**
- **Дано** товар в статусе «на модерации»
- **Когда** модератор отклоняет товар и указывает причину
- **Тогда** товар получает статус «отклонён», причина сохраняется в товаре, на витрине товара нет
- **И** решение записывается в журнал аудита

**Сценарий 2. Причина не указана**
- **Дано** модератор выбрал «Отклонить»
- **Когда** он отправляет решение без причины
- **Тогда** решение не сохраняется, товар остаётся «на модерации», модератор видит, что причина обязательна

**Сценарий 3. Продавец исправил товар и отправил заново**
- **Дано** товар в статусе «отклонён», причина видна продавцу
- **Когда** продавец исправляет товар и отправляет его на модерацию
- **Тогда** товар получает статус «на модерации», срок проверки 3 суток отсчитывается заново

**Сценарий 4. Отклонить можно только товар на модерации**
- **Дано** товар в статусе «опубликован»
- **Когда** модератор пытается его «отклонить»
- **Тогда** действие недоступно, для опубликованного товара существует блокировка (US-3.5)

### Примечания

- После правки отклонённый товар сам на модерацию не уходит: продавец отправляет его явно (SM-04/T5).

## US-3.5. Блокировка опубликованного товара модератором

| Поле | Содержание |
| --- | --- |
| ID | US-3.5 |
| Релиз | R1 |
| Требования | FT-3.1, FT-11.2, FT-11.4, NFT-5.3 |
| Процесс или use case | SM-04/T8, T11 |

### История

**Как** модератор, **я хочу** заблокировать опубликованный товар, **чтобы** быстро убрать с витрины запрещённый контент, обнаруженный после публикации.

### Критерии приёмки

**Сценарий 1. Товар заблокирован**
- **Дано** товар в статусе «опубликован»
- **Когда** модератор блокирует товар и указывает причину
- **Тогда** товар получает статус «заблокирован» и пропадает с витрины
- **И** продавец получает письмо с причиной, решение записывается в журнал аудита
- **И** заказы, оформленные раньше, доводятся до выдачи

**Сценарий 2. Причина не указана**
- **Дано** модератор выбрал «Заблокировать»
- **Когда** он отправляет решение без причины
- **Тогда** блокировка не применяется, товар остаётся «опубликован»

**Сценарий 3. Блокировать можно только опубликованный товар**
- **Дано** товар в статусе «черновик», «на модерации», «отклонён» или «архив»
- **Когда** модератор пытается его заблокировать
- **Тогда** действие недоступно

**Сценарий 4. Продавец исправил заблокированный товар**
- **Дано** товар в статусе «заблокирован» по решению модератора
- **Когда** продавец исправляет товар и отправляет его заново
- **Тогда** товар получает статус «на модерации», модератор принимает новое решение, срок проверки 3 суток

### Примечания

- Раздел 3 требований даёт модератору блокировку товаров, но не снятие. Блокировку по решению модератора не снимают кнопкой: путь назад идёт через правку и новую модерацию (SM-04, решение 3).
- Заблокированный товар нельзя убрать в архив: он должен оставаться виден модератору (SM-04).

## US-3.6. Правка опубликованного товара

| Поле | Содержание |
| --- | --- |
| ID | US-3.6 |
| Релиз | R1 |
| Требования | FT-3.2 |
| Процесс или use case | BPMN-03 (исключения E2 и E3), SM-04/T6, T7 |

### История

**Как** продавец, **я хочу** менять данные опубликованного товара, **чтобы** обновлять цену и описание без остановки продаж там, где это безопасно.

### Критерии приёмки

**Сценарий 1. Правка названия, описания или типа**
- **Дано** товар в статусе «опубликован»
- **Когда** продавец меняет название, описание или тип
- **Тогда** товар сразу снимается с витрины и получает статус «на модерации», срок проверки 3 суток отсчитывается заново
- **И** заказы, оформленные раньше, доводятся до выдачи

**Сценарий 2. Правка цены, платформы, региона или способа выдачи**
- **Дано** товар в статусе «опубликован»
- **Когда** продавец меняет цену, платформу, регион активации или способ выдачи
- **Тогда** правка сохраняется, товар остаётся «опубликован», модерация не запускается
- **И** заказы, созданные до правки, сохраняют прежнюю цену

**Сценарий 3. Правка товара на модерации**
- **Дано** товар в статусе «на модерации»
- **Когда** продавец пытается изменить любое поле
- **Тогда** изменения отклоняются, продавец видит, что товар проверяется

### Примечания

- Правило защищает цель BG-05: после публикации нельзя подменить название, описание или тип и обойти модерацию.
- Цена заказа фиксируется при его создании (раздел 6.1: у заказа есть цена и сумма).

## US-3.7. Уведомление продавца о решениях по товару

| Поле | Содержание |
| --- | --- |
| ID | US-3.7 |
| Релиз | R1 |
| Требования | FT-11.4, FT-3.2, NFT-4.3 |
| Процесс или use case | BPMN-03 (шаги 8 и 9), SM-04/T3, T4, T8 |

### История

**Как** продавец, **я хочу** получать письмо о решении по товару и видеть причину в кабинете, **чтобы** вовремя исправить товар или узнать, что он опубликован.

### Критерии приёмки

**Сценарий 1. Товар одобрен**
- **Дано** модератор одобрил товар
- **Когда** решение записано
- **Тогда** продавцу уходит письмо «товар опубликован», в кабинете у товара статус «опубликован»

**Сценарий 2. Товар отклонён или заблокирован**
- **Дано** модератор отклонил или заблокировал товар и указал причину
- **Когда** решение записано
- **Тогда** продавцу уходит письмо с причиной, та же причина видна в карточке товара в кабинете

**Сценарий 3. Письмо не принято провайдером**
- **Дано** решение записано, провайдер не принял письмо
- **Когда** сервис уведомлений получает отказ
- **Тогда** отправка повторяется с нарастающей задержкой, статус и причина в кабинете остаются доступными

### Примечания

- Письма продавцу о решении по заявке на подключение описаны в US-2.4, по заявке на вывод в US-10.4 (R2).

## US-3.8. Архив и восстановление товара

| Поле | Содержание |
| --- | --- |
| ID | US-3.8 |
| Релиз | R1 |
| Требования | FT-3.1 |
| Процесс или use case | SM-04/T12, T13 |

### История

**Как** продавец, **я хочу** снять товар с продажи и при необходимости вернуть его, **чтобы** не удалять историю и не терять пул ключей.

### Критерии приёмки

**Сценарий 1. Товар отправлен в архив**
- **Дано** товар в статусе «черновик», «на модерации», «опубликован» или «отклонён»
- **Когда** продавец снимает товар с продажи
- **Тогда** товар получает статус «архив», не виден на витрине и выходит из очереди модератора
- **И** открытые заказы по товару доводятся до выдачи, резервы снимаются по сроку

**Сценарий 2. Товар восстановлен**
- **Дано** товар в статусе «архив»
- **Когда** продавец восстанавливает товар
- **Тогда** товар получает статус «черновик», пул ключей сохраняется, дальше обычный путь с модерацией

**Сценарий 3. Заблокированный товар в архив не уходит**
- **Дано** товар в статусе «заблокирован»
- **Когда** продавец пытается отправить его в архив
- **Тогда** действие отклоняется

**Сценарий 4. Публикация из архива**
- **Дано** товар в статусе «архив»
- **Когда** продавец пытается сделать его опубликованным без восстановления
- **Тогда** действие отклоняется: сначала восстановление в «черновик», затем модерация

### Примечания

- FT-3.1 называет статус «архив» и не описывает переходы. Приняты правила SM-04 (решение 5): архивировать можно из четырёх статусов, восстанавливать только в «черновик».

## US-3.9. Витрина и карточка товара

| Поле | Содержание |
| --- | --- |
| ID | US-3.9 |
| Релиз | R1 |
| Требования | FT-3.1, FT-4.4, NFT-1.0 |
| Процесс или use case | BPMN-03 (шаг 7, исключение E6) |

### История

**Как** гость или покупатель, **я хочу** видеть на витрине только опубликованные товары и открывать их карточки, **чтобы** выбрать товар, который можно купить.

### Критерии приёмки

**Сценарий 1. Карточка опубликованного товара**
- **Дано** товар в статусе «опубликован»
- **Когда** гость открывает его карточку
- **Тогда** он видит название, описание, тип, платформу, регион активации, цену и наличие
- **И** карточка отвечает не дольше 300 мс (95-й перцентиль) при нагрузке 50 запросов в секунду

**Сценарий 2. Неопубликованный товар**
- **Дано** товар в статусе «черновик», «на модерации», «отклонён», «заблокирован» или «архив»
- **Когда** гость или покупатель ищет его в каталоге или открывает прямую ссылку
- **Тогда** товара нет в выдаче, по прямой ссылке показывается «Товар не найден»

**Сценарий 3. Нулевой остаток**
- **Дано** товар опубликован, остаток равен нулю
- **Когда** гость открывает карточку
- **Тогда** карточка показывается, действие «Купить» недоступно, показано, что товара нет в наличии

### Примечания

- Нагрузочный профиль NFT-1.0 проверяется по методике из `docs/08-testing/nfr-methodology.md` (Ф1, шаг 7).
- Оформление заказа из карточки описано в US-5.1.

| Поле | Содержание |

| Релиз | R1 |
| Требования | FT-3.3, NFT-1.1 |
| Процесс или use case | Отдельного процесса нет |

### История

**Как** гость или покупатель, **я хочу** искать товары по части названия, **чтобы** быстро найти нужную игру, лицензию или карту.

### Критерии приёмки

**Сценарий 1. Поиск находит товары**
- **Дано** в каталоге есть опубликованные товары
- **Когда** пользователь вводит часть названия
- **Тогда** в выдаче только опубликованные товары, в названии которых есть введённый текст, регистр букв не влияет на результат
- **И** результат возвращается не дольше чем за 500 мс (95-й перцентиль)

**Сценарий 2. Ничего не найдено**
- **Дано** ни одно название не содержит введённый текст
- **Когда** пользователь запускает поиск
- **Тогда** показывается пустой результат с сообщением «Ничего не найдено»

**Сценарий 3. Неопубликованные товары**
- **Дано** товар в статусе «на модерации», «заблокирован» или «архив» с подходящим названием
- **Когда** пользователь ищет по этому названию
- **Тогда** такой товар в выдаче не показывается

### Примечания

- Поиск выполняется средствами PostgreSQL: часть названия без учёта регистра ищется по триграммному индексу (физическая модель, шаг 12 Ф2). Переход на OpenSearch запланирован в R3 (раздел 8.2 требований).

## US-3.11. Фильтры каталога

| Поле | Содержание |
| --- | --- |
| ID | US-3.11 |
| Релиз | R1 |
| Требования | FT-3.4, NFT-1.1 |
| Процесс или use case | Отдельного процесса нет |

### История

**Как** гость или покупатель, **я хочу** фильтровать товары по типу, платформе, региону активации и цене, **чтобы** увидеть только то, что подходит мне.

### Критерии приёмки

**Сценарий 1. Несколько фильтров вместе**
- **Дано** в каталоге есть опубликованные товары разных типов, платформ, регионов и цен
- **Когда** пользователь задаёт тип, платформу, регион и диапазон цены
- **Тогда** в выдаче только товары, которые подходят под все условия сразу
- **И** результат возвращается не дольше чем за 500 мс (95-й перцентиль)

**Сценарий 2. Фильтры вместе с поиском**
- **Дано** пользователь ввёл часть названия
- **Когда** он добавляет фильтр по платформе
- **Тогда** в выдаче товары, подходящие и под название, и под фильтр

**Сценарий 3. Под фильтры ничего не подходит**
- **Дано** ни один товар не соответствует выбранной комбинации
- **Когда** фильтры применены
- **Тогда** показывается пустой результат и действие «Сбросить фильтры»

**Сценарий 4. Нижняя граница цены больше верхней**
- **Дано** пользователь указал диапазон цены
- **Когда** нижняя граница больше верхней
- **Тогда** фильтр по цене не применяется, показано сообщение о неверном диапазоне

### Примечания

- В выдаче участвуют только опубликованные товары.

## Решения и открытые вопросы

Открытых вопросов нет. Решения, принятые при написании историй:

1. **Все семь полей товара обязательны при создании.** SM-04/T1 перечисляет их в условии. Ключи для создания и отправки на модерацию не нужны (SM-04/T2).
2. **Блокировка товара модератором выделена в историю US-3.5.** Раздел 3 требований даёт модератору блокировку товаров, FT-3.1 содержит статус «заблокирован». Снятия блокировки нет: товар исправляют и проверяют заново.
3. **Продавец видит решения по товару через US-3.7.** Это закрывает часть FT-11.4 про товар. Часть про подключение закрыта в US-2.4, про вывод в US-10.4.
4. **Регистр букв в поиске не влияет на результат.** Это уточнение FT-3.3, на цель и срок не влияет.
