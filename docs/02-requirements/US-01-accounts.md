## US-1.1. Регистрация по e-mail и паролю

| Поле | Содержание |
| --- | --- |
| ID | US-1.1 |
| Релиз | R1 |
| Требования | FT-1.0, NFT-3.1, NFT-3.5 |
| Процесс или use case | Отдельного процесса нет. Шаг предшествует BPMN-01 |

### История

**Как** гость, **я хочу** зарегистрироваться по e-mail и паролю с подтверждением почты, **чтобы** покупать товары и получать ключи на свой адрес.

### Критерии приёмки

**Сценарий 1. Успешная регистрация**
- **Дано** гость открыл форму регистрации, e-mail в системе не зарегистрирован
- **Когда** он вводит e-mail и пароль и отправляет форму
- **Тогда** создаётся учётная запись с ролью «Покупатель», на указанный адрес уходит письмо со ссылкой подтверждения
- **И** пароль хранится только в виде хеша с солью (bcrypt или Argon2) и не попадает в логи
- **И** после перехода по ссылке адрес считается подтверждённым и гость может войти

**Сценарий 2. E-mail уже зарегистрирован**
- **Дано** в системе есть учётная запись с этим e-mail
- **Когда** гость отправляет форму регистрации с этим адресом
- **Тогда** вторая учётная запись не создаётся
- **И** ответ формы такой же, как в сценарии 1: «Проверьте почту». По ответу нельзя узнать, занят ли адрес
- **И** на этот адрес уходит письмо со ссылками на вход и восстановление пароля

**Сценарий 3. Вход до подтверждения почты**
- **Дано** гость зарегистрировался, но ссылку из письма не открыл
- **Когда** он пытается войти по e-mail и паролю
- **Тогда** вход не выполняется, гость видит, что почта не подтверждена, и может запросить письмо повторно в пределах лимита запросов (NFT-3.5)

### Примечания

- Роль «Покупатель» присваивается при регистрации. Роль «Продавец» появляется только после одобрения заявки (US-2.2).
- Срок жизни ссылки подтверждения и сам текст письма настраиваются в Keycloak и в критерии приёмки не входят.

## US-1.2. Регистрация и вход через VK ID

| Поле | Содержание |
| --- | --- |
| ID | US-1.2 |
| Релиз | R1 |
| Требования | FT-1.1 |
| Процесс или use case | Отдельного процесса нет. Провайдер в проекте эмулируется |

### История

**Как** гость, **я хочу** зарегистрироваться и входить через VK ID, **чтобы** не придумывать отдельный пароль.

### Критерии приёмки

**Сценарий 1. Первый вход через VK ID**
- **Дано** гость ещё не связан с VK ID, провайдер подтверждает вход и передаёт e-mail
- **Когда** гость выбирает «Войти через VK ID» и разрешает доступ
- **Тогда** создаётся учётная запись с ролью «Покупатель», e-mail считается подтверждённым, гость входит в кабинет

**Сценарий 2. Повторный вход**
- **Дано** учётная запись, созданная через VK ID, уже существует
- **Когда** гость снова выбирает «Войти через VK ID»
- **Тогда** он входит в ту же учётную запись, дубль не создаётся

**Сценарий 3. Провайдер не подтвердил вход**
- **Дано** гость нажал «Войти через VK ID»
- **Когда** он отказывается дать доступ или провайдер возвращает ошибку
- **Тогда** вход не выполняется, учётная запись не создаётся, гость остаётся на странице входа с понятным сообщением

**Сценарий 4. Провайдер не передал e-mail**
- **Дано** провайдер подтвердил вход, но не передал e-mail
- **Когда** гость завершает вход
- **Тогда** гостю предлагают указать e-mail, на него уходит письмо подтверждения, как в US-1.1
- **И** до подтверждения оформить заказ нельзя, потому что ключ приходит на e-mail (FT-7.0)

### Примечания

- Решение при моделировании: e-mail, полученный от VK ID, считается подтверждённым. Если e-mail не передан, действует правило сценария 4. Это уточнение FT-1.1 по FT-1.0 и FT-7.0, требования не меняются.
- Если учётная запись, созданная через VK ID, позже потеряет доступ к e-mail, она восстанавливается так же, как любая другая: вход по коду из SMS (US-1.7).

## US-1.3. Вход по e-mail и паролю

| Поле | Содержание |
| --- | --- |
| ID | US-1.3 |
| Релиз | R1 |
| Требования | FT-1.0, NFT-3.1, NFT-3.5 |
| Процесс или use case | Отдельного процесса нет. Вход входит в функции гостя из раздела 3 требований |

### История

**Как** гость с учётной записью, **я хочу** войти по e-mail и паролю, **чтобы** увидеть свои заказы и оформлять новые.

### Критерии приёмки

**Сценарий 1. Успешный вход**
- **Дано** учётная запись активна, e-mail подтверждён
- **Когда** пользователь вводит верные e-mail и пароль
- **Тогда** он получает доступ в кабинет своей роли
- **И** для продавца, модератора, оператора поддержки и администратора вход продолжается вторым фактором (US-1.5)

**Сценарий 2. Неверный пароль**
- **Дано** учётная запись существует
- **Когда** пользователь вводит неверный пароль или несуществующий e-mail
- **Тогда** вход не выполняется, сообщение одинаковое для обоих случаев: «Неверный e-mail или пароль»

**Сценарий 3. Превышен лимит попыток входа**
- **Дано** с одного адреса или на одну учётную запись сделано число неудачных попыток входа, равное лимиту
- **Когда** пользователь пробует войти снова
- **Тогда** вход временно отклоняется, даже если пароль верный, пользователь видит, что попытку можно повторить позже

**Сценарий 4. Деактивированная учётная запись**
- **Дано** администратор деактивировал учётную запись (US-8.2)
- **Когда** владелец вводит верные e-mail и пароль
- **Тогда** вход не выполняется

### Примечания

- Лимит попыток входа и период задаются параметром платформы (NFT-3.5, FT-11.1). Для проверки используется значение, настроенное на стенде.
- Отдельного функционального требования на вход нет. История выведена из FT-1.0 и раздела 3.

## US-1.4. Восстановление пароля по e-mail

| Поле | Содержание |
| --- | --- |
| ID | US-1.4 |
| Релиз | R1 |
| Требования | FT-1.2, NFT-3.5 |
| Процесс или use case | Отдельного процесса нет |

### История

**Как** покупатель, продавец, модератор, оператор поддержки или администратор, **я хочу** восстановить пароль по e-mail, **чтобы** вернуть доступ к кабинету, если пароль забыт.

### Критерии приёмки

**Сценарий 1. Успешное восстановление**
- **Дано** у пользователя есть учётная запись, он имеет доступ к её e-mail
- **Когда** он запрашивает восстановление и переходит по ссылке из письма, затем вводит новый пароль
- **Тогда** пароль заменён, в кабинет можно войти с новым паролем, старый пароль не подходит
- **И** новый пароль хранится в виде хеша с солью (NFT-3.1)

**Сценарий 2. Неизвестный e-mail**
- **Дано** в системе нет учётной записи с введённым адресом
- **Когда** запрашивается восстановление
- **Тогда** ответ формы такой же, как для существующего адреса: «Если адрес зарегистрирован, мы отправили письмо»
- **И** письмо не отправляется

**Сценарий 3. Превышен лимит запросов**
- **Дано** число запросов восстановления с одного адреса или на один e-mail достигло лимита (NFT-3.5)
- **Когда** запрашивается ещё одно восстановление
- **Тогда** запрос отклоняется, письмо не отправляется

### Примечания

- Для продавца, модератора, оператора поддержки и администратора после смены пароля вход по-прежнему требует второго фактора (US-1.5).
- Покупатель, потерявший доступ к e-mail, восстанавливает доступ входом по коду из SMS (US-1.7), а не восстановлением пароля.

## US-1.5. Второй фактор для продавца и сотрудников

| Поле | Содержание |
| --- | --- |
| ID | US-1.5 |
| Релиз | R1 |
| Требования | FT-1.3, NFT-3.0 |
| Процесс или use case | BPMN-02 (шаг 8 основного пути), [UC-02](UC-02-seller-application.md) |

### История

**Как** продавец, модератор, оператор поддержки или администратор, **я хочу** входить по паролю и коду из приложения-аутентификатора, **чтобы** чужой человек не получил доступ к ключам, деньгам и решениям платформы.

### Критерии приёмки

**Сценарий 1. Первая настройка второго фактора**
- **Дано** пользователю назначена роль «Продавец», «Модератор», «Оператор поддержки» или «Администратор», второй фактор ещё не настроен
- **Когда** он входит в систему
- **Тогда** вместо кабинета открывается настройка второго фактора
- **И** доступ в кабинет появляется только после того, как введён верный код из приложения-аутентификатора

**Сценарий 2. Вход с кодом**
- **Дано** второй фактор настроен
- **Когда** пользователь вводит верные e-mail и пароль, затем верный код
- **Тогда** он входит в кабинет своей роли

**Сценарий 3. Неверный код**
- **Дано** пользователь ввёл верные e-mail и пароль
- **Когда** он вводит неверный код или пропускает этот шаг
- **Тогда** доступ в кабинет не открывается, сообщение не раскрывает, что именно неверно

### Примечания

- Второй фактор настраивается в момент назначения роли: продавцу при первом входе после одобрения заявки (SM-05/T3), сотруднику при первом входе после назначения роли администратором (US-8.1).
- Покупатель второй фактор не использует: его защищает подтверждённый телефон (US-1.6).
- Признак 2FA хранится в учётной записи, а не в профиле продавца (SM-05, решение 5).

## US-1.6. Подтверждение телефона перед первой покупкой

| Поле | Содержание |
| --- | --- |
| ID | US-1.6 |
| Релиз | R1 |
| Требования | FT-1.5, NFT-3.5, NFT-3.7 |
| Процесс или use case | BPMN-01 (шаг 2, исключение E1), [UC-01](UC-01-purchase.md) |

### История

**Как** покупатель, **я хочу** подтвердить номер телефона кодом из SMS прямо при оформлении первого заказа, **чтобы** поддержка могла убедиться, что учётная запись принадлежит мне, а выбранный товар не потерялся.

### Критерии приёмки

**Сценарий 1. Успешное подтверждение**
- **Дано** у покупателя нет подтверждённого номера, он оформляет заказ, товар и количество выбраны
- **Когда** он вводит свободный номер и верный код из SMS в течение 5 минут
- **Тогда** номер привязывается к учётной записи и помечается подтверждённым
- **И** оформление заказа продолжается с тем же товаром и количеством
- **И** при следующих покупках шаг подтверждения не показывается

**Сценарий 2. Код неверный, истёк или попытки исчерпаны**
- **Дано** покупатель запросил код
- **Когда** он вводит неверный код, или вводит верный код позже чем через 5 минут, или делает 5 неверных попыток
- **Тогда** номер не подтверждается, заказ не создаётся
- **И** код одноразовый: после успешного ввода повторно использовать его нельзя
- **И** покупатель может запросить новый код в пределах лимита

**Сценарий 3. Номер уже привязан к другой учётной записи**
- **Дано** номер подтверждён в другой учётной записи
- **Когда** покупатель вводит этот номер
- **Тогда** SMS не отправляется, подтверждение не выполняется
- **И** покупатель видит нейтральное сообщение «Номер использовать нельзя» без указания причины

**Сценарий 4. Лимит запросов кода**
- **Дано** с этой учётной записи или на этот номер за 10 минут уже запрошено 3 кода, либо за сутки 10 кодов
- **Когда** покупатель запрашивает ещё один код
- **Тогда** запрос отклоняется, SMS не отправляется, покупатель видит, когда можно повторить

### Примечания

- Лимиты 3 за 10 минут и 10 за сутки действуют на учётную запись и на номер, значения настраиваются (NFT-3.5, FT-11.1).
- Номер уникален в пределах платформы: один номер привязан к одной учётной записи. Уникальность гарантирует и индекс в базе сервиса идентификации (раздел 8.2 требований).
- Выбор между собственным модулем Keycloak и отдельным модулем в сервисе уведомлений фиксируется в ADR (Ф2), на критерии приёмки не влияет.

## US-1.7. Вход по коду из SMS без доступа к e-mail

| Поле | Содержание |
| --- | --- |
| ID | US-1.7 |
| Релиз | R1 |
| Требования | FT-1.7, NFT-3.5, NFT-3.7 |
| Процесс или use case | BPMN-04 (шаг 1, исключение E2), [UC-04](UC-04-support-request.md) |

### История

**Как** покупатель, потерявший доступ к e-mail, **я хочу** войти по одноразовому коду из SMS на подтверждённый телефон, **чтобы** увидеть свои заказы и обратиться в поддержку, если ключ не пришёл.

### Критерии приёмки

**Сценарий 1. Успешный вход по коду**
- **Дано** у учётной записи подтверждён телефон, покупатель не может войти по e-mail и паролю
- **Когда** он вводит номер, получает SMS и вводит верный код в течение 5 минут
- **Тогда** открывается короткая сессия: покупатель видит свои заказы, создаёт обращения в поддержку и вводит коды смены e-mail

**Сценарий 2. Ограничения такой сессии**
- **Дано** покупатель вошёл по коду из SMS
- **Когда** он пытается оформить заказ, оплатить, сменить пароль, e-mail, номер или другие данные учётной записи
- **Тогда** действие отклоняется, покупатель видит, что для этого нужен обычный вход

**Сценарий 3. Код неверный, истёк или попытки исчерпаны**
- **Дано** покупатель запросил код
- **Когда** код неверный, или введён позже чем через 5 минут, или сделано 5 неверных попыток
- **Тогда** вход не выполняется, в кабинет покупатель не попадает
- **И** новый код можно запросить в пределах лимита: не более 3 за 10 минут и 10 за сутки

**Сценарий 4. Номер неизвестен платформе**
- **Дано** введённый номер не привязан ни к одной учётной записи
- **Когда** покупатель запрашивает код
- **Тогда** SMS не отправляется, ответ формы такой же, как для известного номера: «Если номер подтверждён, мы отправили код»

**Сценарий 5. Письмо о входе по SMS**
- **Дано** у учётной записи подтверждён телефон и указан e-mail
- **Когда** вход по коду из SMS выполнен успешно
- **Тогда** на e-mail учётной записи уходит письмо с временем входа и советом сменить пароль, если вход выполнял не владелец
- **И** при неудачной попытке (неверный код, исчерпанные попытки) письмо не отправляется

### Примечания

- Письмо о входе смягчает подмену SIM-карты (T-01 модели угроз): владелец, сохранивший доступ к почте, узнаёт о чужом входе. Введено в версии 1.6 (F9-1); событие и шаблон письма добавляются в контракты в срезе 1 Ф4.
- Смена e-mail выполняется только оператором поддержки по обращению (US-7.4). Покупатель, вошедший по SMS, меняет адрес не сам, а через обращение.
- Если утрачены и e-mail, и телефон, восстановление в MVP не поддерживается (раздел 1.3 требований).

## US-1.8. Смена номера телефона

| Поле | Содержание |
| --- | --- |
| ID | US-1.8 |
| Релиз | R2 |
| Требования | FT-1.6, FT-11.0, FT-11.2, NFT-3.5, NFT-3.7 |
| Процесс или use case | BPMN-07 |

### История

**Как** покупатель, потерявший доступ к телефону, но сохранивший доступ к e-mail, **я хочу** сменить номер в личном кабинете, **чтобы** снова получать коды и защитить учётную запись.

### Критерии приёмки

**Сценарий 1. Успешная смена номера**
- **Дано** покупатель вошёл в кабинет по e-mail и паролю
- **Когда** он вводит код из письма на e-mail учётной записи, затем свободный новый номер, затем код из SMS на новый номер
- **Тогда** номер в учётной записи заменён и подтверждён, покупатель получает письмо о смене
- **И** смена записана в журнал аудита: ID объекта, имя поля и HMAC-хеши значений до и после, сам номер в открытом виде не хранится

**Сценарий 2. Новый номер уже занят**
- **Дано** новый номер привязан к другой учётной записи, код из письма введён верно
- **Когда** покупатель вводит этот номер
- **Тогда** SMS не отправляется, номер не меняется, покупатель видит нейтральное сообщение «Номер использовать нельзя»

### Примечания

- Порядок шагов фиксирован: сначала код из письма, затем проверка уникальности, затем SMS на новый номер (BPMN-07).

## Решения и открытые вопросы

Открытых вопросов нет. Решения, принятые при написании историй:

1. **Ответ форм регистрации, восстановления пароля и входа по SMS не раскрывает, существует ли учётная запись.** Так по ответу нельзя перебрать адреса и номера. Это продолжение правила нейтрального сообщения из FT-1.5, требования не меняются.
2. **Вход по e-mail и паролю описан историей без отдельного FT.** Он следует из функций гостя в разделе 3 и из FT-1.0.
3. **E-mail из VK ID считается подтверждённым.** Если e-mail не передан, перед первым заказом его нужно указать и подтвердить (US-1.2).
4. **Статус учётной записи «заблокирован»** из раздела 6.1 требований в этом эпике не используется: в требованиях нет функции, которая переводит в него обычную учётную запись. Блокировка продавца выполняется статусом профиля (SM-05), учётную запись можно деактивировать (US-8.2). В версии 1.6 статус из раздела 6.1 убран.
