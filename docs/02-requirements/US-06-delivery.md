## US-6.1. Выдача ключа после оплаты

| Поле | Содержание |
| --- | --- |
| ID | US-6.1 |
| Релиз | R1 |
| Требования | FT-6.2, FT-7.0, FT-11.0, NFT-2.0, NFT-2.3, NFT-3.2 |
| Процесс или use case | BPMN-01 (шаги 8, 9 и 10), SM-01/T9, SM-06/T1, T2, SM-03/T4, [UC-03](UC-03-key-issuance.md) |

### История

**Как** система, **я хочу** после подтверждения оплаты привязать ключи к заказу и отправить их на e-mail покупателя, **чтобы** покупатель получил товар без участия человека.

### Критерии приёмки

**Сценарий 1. Ключи выданы и письмо принято**
- **Дано** заказ «оплачен», ключи привязаны к заказу и имеют статус «выдан», создана выдача «в очереди»
- **Когда** почтовый провайдер принимает письмо
- **Тогда** выдача получает статус «отправлено», заказ получает статус «выдан»
- **И** письмо содержит ровно столько ключей, сколько заказано, и отправлено на адрес из снимка e-mail в заказе
- **И** с этого момента открываются окно обращения в поддержку 72 часа, окно спора 72 часа и удержание средств продавца 7 дней

**Сценарий 2. Скорость передачи письма**
- **Дано** серия оплаченных заказов при исправном провайдере
- **Когда** замеряется время от подтверждения оплаты до передачи письма провайдеру
- **Тогда** для 95% заказов оно не больше 60 секунд

**Сценарий 3. Повторное событие «заказ оплачен»**
- **Дано** по заказу уже создана первичная выдача
- **Когда** событие «заказ оплачен» приходит повторно
- **Тогда** вторая первичная выдача не создаётся, второе письмо с ключом не уходит

**Сценарий 4. Письмо ещё не принято провайдером**
- **Дано** заказ «оплачен», провайдер письмо не принял
- **Когда** покупатель открывает заказ
- **Тогда** заказ остаётся «оплачен», повторы отправки выполняет система (US-6.4)

### Примечания

- Статус «выдан» у ключа наступает при подтверждении оплаты, у заказа позже, когда письмо принято (SM-03, решение 1). Первый переход заказа в «выдан» происходит один раз за жизнь заказа.
- Значение ключа расшифровывается только при формировании письма и в логи не попадает (US-4.4).

## US-6.2. Один ключ не выдаётся двум заказам

| Поле | Содержание |
| --- | --- |
| ID | US-6.2 |
| Релиз | R1 |
| Требования | FT-7.1, NFT-2.2, NFT-2.3 |
| Процесс или use case | BPMN-01 (шаг 4), SM-03/T2, T4, [UC-01](UC-01-purchase.md), [UC-03](UC-03-key-issuance.md) |

### История

**Как** покупатель, **я хочу** получить ключ, который не достанется другому покупателю, **чтобы** купленный товар не оказался уже активированным.

### Критерии приёмки

**Сценарий 1. Параллельные заказы на ограниченный пул**
- **Дано** в пуле товара 10 свободных ключей
- **Когда** 50 покупателей одновременно оформляют заказы по 1 штуке
- **Тогда** ровно 10 заказов получают резерв и ключи, остальные 40 получают статус «отменён» без платежа
- **И** ни один ключ не привязан к двум заказам

**Сценарий 2. Частичного резерва нет**
- **Дано** в пуле 5 свободных ключей
- **Когда** два покупателя одновременно оформляют заказы по 3 штуки
- **Тогда** один заказ получает 3 ключа, второй получает статус «отменён», остаток равен 2

**Сценарий 3. Повторные события**
- **Дано** ключи заказа уже «выданы»
- **Когда** событие оплаты приходит повторно
- **Тогда** новые ключи не берутся, статусы не меняются

**Сценарий 4. Возврат не возвращает ключ в продажу**
- **Дано** ключ получил статус «выдан»
- **Когда** заказ возвращается
- **Тогда** ключ остаётся «выдан» и в пул свободных не возвращается

**Сценарий 5. Защита на уровне базы**
- **Дано** ключ привязан к заказу
- **Когда** выполняется запись, привязывающая тот же ключ ко второму заказу
- **Тогда** база отклоняет запись ограничением, второй привязки не возникает

### Примечания

- Цель BG-06: 0 случаев выдачи одного ключа двум покупателям. Проверка NFT-2.2 выполняется нагрузочным тестом с одновременными заказами (Ф1, шаг 7: методика, Ф4: сценарии).
- Защита построена на блокировке строки с пропуском занятых, привязке ключа к одному заказу и запрете возврата «выдан» в «свободен» (SM-03).

## US-6.3. Письмо с ключом доходит в срок

| Поле | Содержание |
| --- | --- |
| ID | US-6.3 |
| Релиз | R1 |
| Требования | FT-7.0, NFT-2.1, NFT-6.1 |
| Процесс или use case | BPMN-01 (шаг 11), SM-06/T5, [UC-03](UC-03-key-issuance.md) |

### История

**Как** покупатель, **я хочу** получить письмо с ключом не позднее чем через 30 минут после оплаты, **чтобы** сразу начать пользоваться товаром.

### Критерии приёмки

**Сценарий 1. Доставка в срок**
- **Дано** оплаченный заказ, письмо принято провайдером
- **Когда** провайдер подтверждает доставку в почтовый ящик
- **Тогда** выдача получает статус «доставлено», фиксируется время доставки
- **И** для 95% заказов от подтверждения оплаты до статуса «доставлено» проходит не больше 30 минут (цель BG-01)

**Сценарий 2. Метрика считается по «доставлено»**
- **Дано** выдача в статусе «отправлено», доставка не подтверждена
- **Когда** считается доля заказов, доставленных за 30 минут
- **Тогда** такой заказ в числитель не входит: «отправлено» это не «доставлено»

**Сценарий 3. Доставка позже срока**
- **Дано** провайдер подтвердил доставку на 40-й минуте
- **Когда** выдача получает статус «доставлено»
- **Тогда** заказ учитывается в метрике как не уложившийся в срок, выдача всё равно считается доставленной

### Примечания

- Срок 30 минут и доля 95% входят в цель BG-01 и в NFT-2.1. Метрика «время выдачи» относится к NFT-6.1.

## US-6.4. Повтор отправки и передача в поддержку при недоставке

| Поле | Содержание |
| --- | --- |
| ID | US-6.4 |
| Релиз | R1 |
| Требования | FT-7.3, NFT-2.3, NFT-4.3 |
| Процесс или use case | BPMN-01 (исключения E9 и E10), SM-06/T3, T4, T6, SM-07/T1, [UC-03](UC-03-key-issuance.md) |

### История

**Как** система, **я хочу** повторять отправку при сбоях провайдера и передавать заказ в поддержку, если письмо не удаётся доставить, **чтобы** оплаченный заказ не остался без ключа.

### Критерии приёмки

**Сценарий 1. Повторы при сбое провайдера**
- **Дано** выдача «в очереди», провайдер не принял письмо
- **Когда** число попыток не исчерпано
- **Тогда** отправка повторяется с нарастающей задержкой, номер попытки растёт
- **И** при первой успешной попытке выдача получает статус «отправлено», заказ «выдан»

**Сценарий 2. Попытки исчерпаны**
- **Дано** все попытки отправки закончились отказом провайдера
- **Когда** последняя попытка не удалась
- **Тогда** выдача получает статус «ошибка», создаётся обращение в поддержку с источником «система», администратор получает оповещение
- **И** заказ остаётся «оплачен», сообщение уходит в очередь недоставленных сообщений

**Сценарий 3. Провайдер сообщил о недоставке**
- **Дано** выдача «отправлено», заказ «выдан»
- **Когда** провайдер сообщает, что письмо не доставлено: отказ или неверный адрес
- **Тогда** выдача получает статус «ошибка», заказ остаётся «выдан», создаётся обращение в поддержку

**Сценарий 4. Повторное уведомление провайдера**
- **Дано** выдача уже «отправлено» или «доставлено»
- **Когда** провайдер повторно присылает тот же статус
- **Тогда** уведомление игнорируется, письмо второй раз не отправляется

### Примечания

- Число попыток и задержки между ними это параметры платформы, их значения подбираются в Ф2 в бюджетах времени (SM-06).
- Окно обращения 72 часа к обращениям, созданным системой, не применяется (US-7.1).

## US-6.5. Контроль заказа без доставки 30 минут

| Поле | Содержание |
| --- | --- |
| ID | US-6.5 |
| Релиз | R1 |
| Требования | FT-7.3, NFT-2.4, NFT-6.1, BG-06 |
| Процесс или use case | BPMN-01 (исключение E11), SM-06 (раздел «Контроль 30 минут»), SM-07/T1, T4, [UC-03](UC-03-key-issuance.md) |

### История

**Как** система, **я хочу** автоматически передавать в поддержку заказ, не доставленный за 30 минут, **чтобы** ни один оплаченный заказ не остался без обработки дольше часа.

### Критерии приёмки

**Сценарий 1. Контроль сработал**
- **Дано** с подтверждения оплаты прошло 30 минут, выдача не «доставлено»
- **Когда** срабатывает контроль
- **Тогда** заказ попадает в очередь поддержки (обращение «создано», источник «система»), администратор получает оповещение
- **И** статус выдачи не меняется, автоматического возврата денег нет

**Сценарий 2. Письмо доставлено после срабатывания контроля**
- **Дано** обращение создано контролем, выдача «отправлено»
- **Когда** провайдер подтверждает доставку
- **Тогда** выдача получает статус «доставлено», обращение получает статус «решено», покупатель ничего не делает

**Сценарий 3. Ни один заказ не остаётся без обработки**
- **Дано** оплаченный заказ без выдачи и без возврата
- **Когда** с подтверждения оплаты проходит 60 минут
- **Тогда** по заказу есть обращение (в очереди или у оператора) либо заказ уже «возвращён»

**Сценарий 4. Обращение по заказу уже открыто**
- **Дано** по заказу уже есть обращение в статусе «создано» или «в работе»
- **Когда** срабатывает контроль или выдача получает «ошибка»
- **Тогда** второе обращение не создаётся, данные добавляются в имеющееся

**Сценарий 5. Контроль после поздней оплаты**
- **Дано** заказ стал «оплачен» через позднюю оплату
- **Когда** отсчитываются 30 минут
- **Тогда** отсчёт идёт от повторного подтверждения оплаты, а не от первой попытки

### Примечания

- Контроль это таймер, а не переход: статуса выдачи «просрочено» нет (SM-06).
- Цель BG-06: 0 оплаченных заказов, которые через 1 час остались без выдачи, без возврата и без передачи в поддержку.

## US-6.6. Покупатель видит статус выдачи

| Поле | Содержание |
| --- | --- |
| ID | US-6.6 |
| Релиз | R1 |
| Требования | FT-7.0, FT-5.3, FT-7.2 |
| Процесс или use case | BPMN-01, SM-01, SM-06, [UC-03](UC-03-key-issuance.md), [UC-04](UC-04-support-request.md) |

### История

**Как** покупатель, **я хочу** после оплаты видеть статус заказа, срок получения ключа и адрес отправки, **чтобы** понимать, что делать, если письма нет.

### Критерии приёмки

**Сценарий 1. Статус после оплаты**
- **Дано** заказ «оплачен» или «выдан»
- **Когда** покупатель открывает заказ
- **Тогда** он видит статус заказа, срок получения ключа «до 30 минут» и e-mail, на который отправлен ключ

**Сценарий 2. Письма нет, заказ «выдан»**
- **Дано** заказ «выдан», письмо не пришло
- **Когда** покупатель открывает заказ в течение 72 часов после первичной выдачи
- **Тогда** в карточке заказа есть кнопка «Не получил ключ» (US-7.1)

**Сценарий 3. Заказ «оплачен», выдача в очереди**
- **Дано** заказ «оплачен», выдача «в очереди» или «ошибка»
- **Когда** покупатель открывает заказ
- **Тогда** кнопки «Не получил ключ» нет, показано, что выдачу выполняет система и ключ придёт на e-mail

### Примечания

- Кнопка доступна только для заказов в статусе «выдан»: пока заказ «оплачен», выдачу ведёт и контролирует система (SM-07, недопустимые переходы).

## US-6.7. Выдача по запросу к API продавца

| Поле | Содержание |
| --- | --- |
| ID | US-6.7 |
| Релиз | R2 |
| Требования | FT-7.4, FT-4.3, FT-6.4 |
| Процесс или use case | SM-01/T10, SM-08/T5, SM-03 (раздел «Остаток товара») |

### История

**Как** система, **я хочу** запрашивать ключ у продавца по API после оплаты и ждать ответа не более 10 минут, **чтобы** продавать товары, ключи которых платформа не хранит.

### Критерии приёмки

**Сценарий 1. Продавец ответил вовремя**
- **Дано** заказ «оплачен» на товар с выдачей по API
- **Когда** продавец возвращает ключ в течение 10 минут
- **Тогда** ключ сохраняется в зашифрованном виде со статусом «выдан», дальше выдача идёт как для обычного заказа

**Сценарий 2. Нет ответа или ошибка**
- **Дано** заказ «оплачен» на товар с выдачей по API
- **Когда** продавец не отвечает 10 минут или возвращает ошибку
- **Тогда** заказ получает статус «отменён», остаток товара восстанавливается, запускается автовозврат с причиной «тайм-аут API продавца»

### Примечания

- Автовозврат использует тот же механизм, что в US-5.7, включая ручной возврат через очередь администратора.

## Решения и открытые вопросы

Открытых вопросов нет. Решения, принятые при написании историй:

1. **Метрика BG-01 считается по статусу «доставлено».** Заказ со статусом «отправлено» без подтверждения доставки в долю доставленных вовремя не входит (US-6.3, сценарий 2).
2. **Обращение по заказу одно.** Контроль 30 минут и ошибка выдачи не создают второе обращение, если открытое уже есть (US-6.5, сценарий 4, SM-07/T1).
3. **Кнопка «Не получил ключ» показывается только у заказа «выдан».** До этого выдачу контролирует система (US-6.6).
