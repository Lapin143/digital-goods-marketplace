## 1. Для чего нужен runbook

[developer-guide.md](developer-guide.md) отвечает на вопрос «как поставить и как работать»: он идёт по порядку, от установки до запуска сервиса из IDE. Runbook отвечает на вопрос «что делать, когда уже что-то случилось»: он устроен по признакам и по операциям, которые делают редко и в спешке (сбросить второй фактор, перевыпустить сертификаты). Читают его по необходимости, поэтому каждая запись самостоятельна: признак, проверка, действие, как убедиться.

Три команды, с которых начинается любой разбор:

```bash
make ps                    # какой контейнер не healthy или завершён, код выхода
make logs S=<контейнер>    # последние 100 строк его журнала
make stand-check           # состав, готовность, порты, сети, секреты, память (SET= и DEBUG= те же, что при запуске)
```

Стенд ноутбука не хранит ценных данных: если разбор затянулся, `make reset` и `make up` создают его заново (раздел 4, строка про том).

## 2. Учётные записи

### 2.1. Аварийная учётная запись Keycloak

Администратор служебного realm `master`: пользователь `dgm-admin`, пароль в `secrets/keycloak_admin`. Она нужна для консоли Keycloak: пользователи, роли, второй фактор, сеансы.

| Среда | Как открыть консоль |
| --- | --- |
| Ноутбук, CI | Стенд с `DEBUG=1`, один раз `make keycloak-console`, затем адрес `https://localhost:18445/auth/admin/` в браузере, который доверяет `secrets/tls_ca.crt` ([developer-guide.md](developer-guide.md), раздел 6) |
| Сервер (Ф6) | Консоль наружу не публикуется, шлюз отвечает на `/auth/admin` кодом 404. Доступ только через туннель SSH к контейнеру Keycloak. Пароль запечатан и хранится вне сервера, использование даёт оповещение ([threat-model.md](../05-architecture/threat-model.md), T-40). Порядок и оповещение закрываются в Ф6 |

Через эту учётную запись ничего не делают, пока есть обычный администратор платформы: это аварийный путь.

### 2.2. Первый администратор платформы

По [roles-permissions.md](../05-architecture/roles-permissions.md) (раздел 11, пункт 6) первый администратор создаётся при развёртывании, а второй фактор он настраивает при первом входе. Администратор нужен раньше любого входа через платформу, потому что остальных сотрудников назначает он (OP-80, инвариант INV-38: хотя бы один активный администратор). Запись в базе платформы для него отдельно не заводится: она создаётся при первом обращении с его токеном (ADR-025, решение Р-6), роль берётся из токена, а сверка раз в минуту подтягивает состояние Keycloak.

| Среда | Как создать |
| --- | --- |
| Ноутбук, CI | `make keycloak-users` создаёт `admin-1` (с секретом TOTP) и `admin-2` (без него), пароли и секреты в `secrets/test_users.json`; код TOTP даёт `make otp WHO=admin-1` |
| Сервер (Ф6) | Скрипт развёртывания (в Ф3 и Ф4 его нет). До него вручную в консоли Keycloak, порядок ниже |

Порядок вручную в консоли:

1. Войти в консоль под `dgm-admin` (раздел 2.1), выбрать realm `dgm` вверху слева.
2. Users, Add user: имя пользователя и адрес электронной почты, «Email verified» включить, «Required user actions» оставить пустым, создать.
3. Credentials, Set password: пароль, «Temporary» выключить для первого входа администратора.
4. Role mapping, Assign role: роль `admin`. Роль одна на пользователя: если Keycloak выдал `buyer` по умолчанию, снять её.
5. Details, «Required user actions»: Configure OTP, сохранить.
6. Первый вход (страница входа клиента `dgm-web`): пароль, затем настройка приложения-аутентификатора (QR-код или ключ) и код из приложения.
7. **Повторный вход обязателен.** После первой настройки TOTP токен несёт `amr = [pwd]` без `otp` (находка F4-2, решение Р-45), шлюз отвечает на него 403 `second-factor-required`. Выйти и войти заново: пароль, код, в токене `amr = [otp, pwd]`. Интерфейс делает это сам (`prompt=login`), при ручной проверке достаточно нового входа.
8. Проверить, что запись появилась: вызов `GET /api/v1/staff/users?role=admin` (OP `listStaffUsers`) с новым токеном возвращает администратора в списке (запись создаётся при первом обращении).

Что проверено на стенде. Путь «пользователь с обязательным действием Configure OTP, настройка, отказ без `otp`, повторный вход с `otp`, доступ к административным операциям» выполняет `make accounts-check` (TC-112, TC-118, TC-120) на одноразовом пользователе, которого администратор переводит в роль `admin`. Шаги 1 – 5 в консоли Keycloak этой проверкой не повторяются: их выполняет скрипт `make keycloak-users` через административный API, а в графической консоли вручную они сверены с документацией Keycloak и на стенде не гонялись. Скрипт развёртывания, который заменит шаги 1 – 5 для сервера, остаётся задачей Ф6.

Остальных сотрудников (`moderator`, `support-operator`, новых `admin`) назначает уже администратор платформы: `POST /api/v1/staff/users/{userId}/change-role` (OP-80, `changeUserRole`). Платформа ставит роль в Keycloak, добавляет обязательное действие Configure OTP и пишет событие аудита.

Нельзя оставить платформу без администратора: деактивация или перевод в другую роль последнего активного администратора отклоняется кодом 409 `last-admin-required` (TC-114). Пока второго администратора нет, сначала назначьте его, потом выводите первого.

### 2.3. Потерян второй фактор у сотрудника

Признак: сотрудник вводит верный пароль и не может пройти запрос кода (телефон потерян, приложение переустановлено без переноса).

Действие (делает администратор после подтверждения личности по другому каналу, T-40):

1. Консоль Keycloak (раздел 2.1), realm `dgm`, Users, найти пользователя.
2. Credentials: удалить запись типа OTP.
3. Details, «Required user actions»: добавить Configure OTP, сохранить.
4. Sessions: завершить все сеансы пользователя.
5. Сообщить сотруднику: при следующем входе после пароля запросится настройка приложения-аутентификатора, а после настройки нужен ещё один вход (раздел 2.2, шаг 7).
6. **Записать действие в журнал аудита вручную.** Операции платформы пишут аудит сами (OP-80, деактивация, анонимизация), а сброс в консоли Keycloak платформа не видит: события о нём нет, INV-42 нарушается, пока запись не внесена. До среза 3 Ф4, где появляется модуль аудита и операция сброса фактора, запись делает администратор в файле `secrets/audit-manual.log` на ноутбуке (на сервере в журнале изменений, который ведёт владелец стенда): время в UTC, кто выполнил, чей фактор сброшен (идентификатор пользователя), как подтверждена личность, номер обращения. Файл в репозиторий не коммитится (каталог `secrets/` в `.gitignore`).

Пример строки: `2026-10-12T09:41Z; admin-1; user 6f0c…; личность подтверждена звонком по номеру из профиля; обращение SUP-123`.

Проверка: сотрудник входит, видит настройку TOTP, после неё получает токен, входит повторно и получает `amr = [otp, pwd]`. Всё это воспроизводит `make accounts-check` (TC-118, TC-120) на одноразовом пользователе, а удаление записи OTP и добавление действия в консоли проверено на ноутбуке 8 октября на `seller-1` (страница «Настройка мобильного аутентификатора» с QR-кодом). Сам сброс в графической консоли после шага 9 Ф4 вручную не повторялся. Перед работой в консоли выполните `make keycloak-console` (раздел 2.1).

### 2.4. Потерян второй фактор у единственного администратора

Признак: администратор один, второй фактор утерян, сбросить его некому (T-40).

Действие: войти в консоль Keycloak аварийной учётной записью `dgm-admin` (раздел 2.1) и сбросить второй фактор администратору платформы по порядку раздела 2.3. После входа администратора платформы проверить, что у него и у второго администратора (если есть) настроены фактор и сеанс. Использование `dgm-admin` на сервере должно дать оповещение (Ф6) и быть записано.

Предупреждение: это единственная точка обхода второго фактора. Пароль `secrets/keycloak_admin` на сервере не хранят вместе с ключами на ноутбуке.

На ноутбуке вместо этого проще пересоздать тестовых пользователей: `make keycloak-users`.

## 3. Сертификаты и секреты

Сертификаты контейнеров действуют 90 дней, центр сертификации 5 лет ([infra/pki/README.md](../../infra/pki/README.md)). Команды `make certs` и `make secrets` безопасно повторять: действующее не перевыпускается.

### 3.1. Проверка срока

```bash
make pki-status        # сколько дней осталось у каждого сертификата
make pki-verify        # цепочка, алгоритм, срок, имена, ключи, уникальность секретов; при сроке меньше 14 дней падает
```

Признаки просрочки: контейнер не готов с ошибкой `certificate has expired` в журнале (`make logs S=<контейнер>`), браузер и `curl` отклоняют шлюз, `make pki-verify` красный.

### 3.2. Перевыпуск сертификатов контейнеров

```bash
make certs             # перевыпускает сертификаты, у которых осталось меньше 30 дней
make pki-verify        # убедиться, что все в порядке
make down              # остановить контейнеры, данные сохраняются
make up SET=<тот же набор> [DEBUG=1]
```

Сервисы Java перечитывают сертификат сервера сами (`reload-on-update`), а PostgreSQL, Redis, Kafka, nginx, Keycloak и клиентские соединения читают файлы при старте. Поэтому надёжный путь это остановка и запуск всего набора, как выше. Шлюз перечитывает сертификат клиента (для mTLS к сервисам) только при старте: перезапуск обязателен.

Как убедиться: `make stand-check` и `make pki-status`. Для показа цели вехи: `make demo`.

### 3.3. Смена секретов (пароли, ключи)

Только если секрет скомпрометирован. На ноутбуке данные тестовые, поэтому самый короткий путь:

```bash
make down
python3 infra/pki/dgm_pki.py secrets --force   # новые пароли и ключи
make reset                                     # тома удалены: базы создаются с новыми паролями
make up SET=<набор> [DEBUG=1]
```

Если базу сохранять не нужно, этого достаточно. Если нужно сохранить данные (на сервере), после `--force` вызывается `make db-roles` (пароли ролей в PostgreSQL заменяются на новые), а ключи шифрования (`inventory_kek`) меняются перешифровкой по [ADR-009](../05-architecture/adr/ADR-009-key-encryption-hmac.md), не простой заменой. Подробности и таблица ситуаций в [infra/pki/README.md](../../infra/pki/README.md). Проверено на ноутбуке 8 октября: после `--force` и `make reset` набор `dev-min` поднялся с нуля, `make stand-check` 14 из 14.

### 3.4. Новый центр сертификации

Нужен, если ключ центра скомпрометирован или потерян (`.pki/ca.key`):

```bash
make down
rm -rf .pki
python3 infra/pki/dgm_pki.py certs --force
make up SET=<набор> [DEBUG=1]
```

Затем в Windows удалить старый корневой сертификат из хранилища и добавить новый `secrets/tls_ca.crt` ([developer-guide.md](developer-guide.md), раздел 6).

## 4. Типовые сбои

Формат: признак, что проверить, что сделать. Таблица идёт от самых частых при первом запуске.

| Признак | Что проверить | Что сделать |
| --- | --- | --- |
| `permission denied` на `/var/run/docker.sock` | `docker version` в Ubuntu | Запустить Docker Desktop, включить интеграцию с Ubuntu (Settings, Resources, WSL integration). Для Alloy (набор `obs`) при необходимости `DOCKER_GID=0 make up ...` |
| `port is already allocated`, `address already in use` (8443, 15432, 18445) | `ss -ltnp \| grep :8443` в Ubuntu, `netstat -ano \| findstr :8443` в Windows | Остановить процесс-владельца порта. Если это прежний стенд, `make down`. Порты стенда в [developer-guide.md](developer-guide.md), раздел 5 |
| `make up` завершается по времени ожидания, контейнер `unhealthy` | `make ps`, затем `make logs S=<контейнер>` | Причину показывает журнал. Типичные: нет памяти (следующая строка), просроченный сертификат (раздел 3.1), прежний том Kafka (строка про том). Значение `WAIT_TIMEOUT=900 make up ...` помогает на медленном диске при первом запуске |
| Контейнер завершён с кодом 137 или `OOMKilled: true` | `docker inspect -f '{{.State.OOMKilled}} {{.State.ExitCode}}' $(docker compose ps -a -q <сервис>)`; метрика `container_oom_events_total` в Prometheus на `full-obs` | Не хватило памяти контейнеру или WSL. Сначала `wsl --shutdown` и меньший набор (`SET=dev-min`). Лимиты контейнеров поднимают только по замеру ([memory-measurements.md](memory-measurements.md), раздел 5), а не «на всякий случай» |
| Весь WSL тормозит, Windows подвисает | Диспетчер задач: процесс `Vmmem` | Лимит WSL ниже, чем сумма наборов ([developer-guide.md](developer-guide.md), раздел 4): `.wslconfig` `memory=3GB`, меньший набор, закрыть лишнее |
| Токены отклоняются с кодом 401 сразу после выхода компьютера из сна | `date` в Ubuntu и время Windows, у токена сроки `iat` и `exp` | Часы WSL ушли вперёд или назад. Допуск шлюза 30 секунд. `wsl --shutdown` в PowerShell, затем `make up` |
| Браузер: `NET::ERR_CERT_AUTHORITY_INVALID` на `https://localhost:8443` | Установлен ли `secrets/tls_ca.crt` в доверенные корневые центры | [developer-guide.md](developer-guide.md), раздел 6. Для `curl` ключ `--cacert secrets/tls_ca.crt` |
| `make pki-verify` красный, `x509: certificate has expired` | `make pki-status` | Раздел 3.2 |
| Kafka не стартует после смены секретов или версии, в журнале несовпадение идентификатора кластера | `make logs S=kafka` | Том хранит прежние метаданные. Данные стенда не ценные: `make reset`, затем `make up` |
| Изменён `gen_realm.py`, а Keycloak прежний | `make realm` пересоздаёт файл, но Keycloak применяет его только на пустой базе | `make keycloak-reimport` (realm `dgm` удаляется и создаётся заново, пользователи пропадают, затем `make keycloak-users`). На сервере realm не удаляют |
| Вход в Keycloak не проходит: неверный пароль у тестового пользователя | `secrets/test_users.json` | Пароли одноразовые и пересоздаются `make keycloak-users`. После `make keycloak-reimport` пользователей нужно создать заново |
| Роль или обязательное действие не появились в Keycloak после операции администратора (OP-80), в журнале платформы «Keycloak не выполнил назначение роли ... повторит сверка» | `make logs S=platform-service`, в сообщении код ответа Keycloak; консоль Keycloak (раздел 2.1), Users, Role mapping | Сверка платформы повторяет назначение раз в минуту. Код 403 означает нехватку прав служебной записи `platform-service` (должны быть `manage-users`, `view-users`, `query-users`; чтение роли по имени требует `view-realm`, поэтому платформа берёт роль из списка доступных пользователю, шаг 9 Ф4), 5xx или обрыв означает недоступный Keycloak. Права служебной записи не расширять без решения: нужно исправить вызов |
| Заявка одобрена, а у заявителя нет роли продавца: после входа он по-прежнему покупатель или Keycloak не предлагает настроить TOTP | `make logs S=platform-service`: «Keycloak не принял роль продавца ... повторит сверка» (Keycloak был недоступен в момент одобрения) или «Учётной записи ... в платформе ещё нет» (событие пришло раньше записи пользователя); `GET /api/v1/staff/users?email=...` администратором: роль `seller` в платформе есть или нет; тема `catalog.events.dlq` (`make logs S=kafka`, сообщение с `seller.approved`) | Роль `seller` есть в платформе: сверка выставит атрибут, роль и TOTP в Keycloak в ближайшую минуту после возвращения Keycloak, вручную ничего не назначать (INV-36). Роли в платформе нет: запись пользователя появилась позже события, и сообщение лежит в DLQ (хранится 14 суток). Сверка создаёт записи всех пользователей Keycloak раз в минуту, поэтому на практике это бывает только при остановленной платформе. Процедура повторной обработки DLQ в срезе 1 не автоматизирована и запланирована в разделе 6 этого документа; пока её нет, надёжный путь на стенде это новая заявка. Заявитель должен выйти и войти заново: в выданном ранее токене роли нет |
| Шлюз отвечает 401 | Токен есть, не просрочен (5 минут), выдан этим Keycloak (`iss` совпадает с `https://localhost:8443/auth/realms/dgm`) | Получить новый токен: `make demo`, `make -s token` |
| Шлюз отвечает 403 | Область и роль токена не подходят маршруту, у сотрудника нет второго фактора (`amr` без `otp`) | Токен другого пользователя (`make -s token WHO=...`) |

### 4.1. Событие в `.dlq`

**Что случилось.** Потребитель сервиса повторил обработку события три раза с паузами 1, 5 и 25 секунд (всего 31 секунда), обработчик так и не справился, и запись ушла в тему `<тема>.dlq` ([ADR-006](../05-architecture/adr/ADR-006-idempotency.md), `EventProcessor` в `service-kit`). Событие, которое не разобрать (нет конверта, неверная схема, лишнее поле), и отказ без смысла повторять (`FatalEventException`) уходят туда сразу, с одной попыткой. Следующие события раздела обрабатываются как обычно, партиция не стоит. Запись хранится 14 суток: вернуть событие нужно раньше. Заголовки записи: `dlq-consumer` (обработчик), `dlq-error-class` и `dlq-error-message` (текст со скрытыми адресами и ключами), `dlq-attempts`, `dlq-failed-at`, `dlq-original-topic`, `dlq-original-partition`, `dlq-original-offset`.

**Как заметить.** Оповещение `EventSentToDlq` (critical: темы `payment.events`, `order.events`, `inventory.events`, `delivery.events`) или `EventSentToDlqMinor` (warning: остальные темы, [dgm.yml](../../infra/obs/prometheus/rules/dgm.yml), счётчик `events_dlq_total{service, topic, consumer}`) на наборах с наблюдением, строка в журнале сервиса `Запись <тема>[<раздел>]@<смещение> отправлена в <тема>.dlq` (`make logs S=platform-service`) и просмотр очередей:

```bash
python3 tools/ops/dlq_replay.py list delivery.events          # что лежит: место, время, обработчик, тип, идентификатор, попытки, причина
python3 tools/ops/dlq_replay.py show delivery.events --event-id <id>     # заголовки, поля конверта и имена полей data
```

Скрипт читает очередь контейнером Kafka в сети стенда с сертификатом оператора (на стенде `kafka-init`, суперпользователь Kafka; на сервере заведите отдельного принципала с правом чтения `*.dlq` и записи в темы событий и укажите его `--principal`). Значения событий (`data`) не показываются: в них бывают адреса и суммы. Сервисы свои `.dlq` читать не могут и чужие тоже (проверяет `infra_security.sh`).

**Что решить по причине.**

| Что показывает `show` | Что это значит | Что делать |
| --- | --- | --- |
| `RetryableEventException`, обработчик `support-event-handler`, тема `delivery.events` | `delivery.failed` или `delivery.overdue` пришли раньше `order.paid` или `order.issued` того же заказа, модели чтения заказа в поддержке ещё нет (F3-21). Поток потребителя один, поэтому за 31 секунду `order.paid` из соседней темы прочитан не был | Убедиться, что строка заказа появилась: `select order_number, buyer_id, order_status from support.order_view where order_id = '<заказ>'` в `platform_db`. Если появилась, вернуть событие |
| `RetryableEventException` или ошибка базы, Keycloak, почтового провайдера: зависимость была недоступна дольше 31 секунды | Временный сбой, сообщение само по себе исправно | Восстановить зависимость (раздел 4, `make ps`, `make logs S=<сервис>`), затем вернуть событие |
| `FatalEventException` или `InvalidEventException` (нет обязательного поля, неверная схема, номер заказа занят другим заказом) | Событие повреждено или противоречит данным: повтор даст тот же отказ и вернёт его в `.dlq` через 31 секунду | Не возвращать. Найти издателя по `source` в конверте (`show`) и исправить его, при необходимости издатель опубликует исправленное событие. Запись остаётся как след и истекает через 14 суток |
| Ошибка в коде обработчика (`NullPointerException`, `IllegalStateException`) | Событие исправно, ошибка в сервисе | Исправить и развернуть сервис, затем вернуть событие |

**Как вернуть.** Сначала без `--yes`: скрипт покажет, что и куда он вернёт, и напомнит проверить причину.

```bash
python3 tools/ops/dlq_replay.py replay delivery.events --event-id <id>          # показать, ничего не отправлять
python3 tools/ops/dlq_replay.py replay delivery.events --event-id <id> --yes    # вернуть в delivery.events
python3 tools/ops/dlq_replay.py replay delivery.events --partition 0 --offset 5 --yes   # то же по месту в очереди
```

Скрипт записывает то же значение под тем же ключом и с теми же заголовками `ce_type` и `traceparent`, без заголовков `dlq-*` (добавляет `dlq-replayed-from`). Событие получают все обработчики темы. Те, что уже применили его, получают дубль и ничего не делают: ключ дедупликации `(обработчик, идентификатор события)` в `processed_event` ([ADR-006](../05-architecture/adr/ADR-006-idempotency.md)), поэтому повторное возвращение безопасно, а письмо администратору по тому же событию второй раз не уйдёт. Если событие одного идентификатора лежит в очереди дважды (отказали два обработчика), его возвращают один раз: повтор доставит его обоим. Проверка результата: у `delivery.failed` в `support.ticket` появилось одно открытое обращение по заказу, в `support.events` одно `ticket.created`; журнал сервиса не содержит нового «отправлена в ....dlq».

**Как проверить весь путь.** `make dlq-check` на наборе `full` (`DEBUG=1`): ядовитая запись, событие раньше модели заказа, просмотр, возврат и второй возврат скриптом из этого раздела; тот же сценарий идёт в CI (TC-012, [TC-e2e.md](../08-testing/TC-e2e.md)).

**Чего не делать.** Не возвращать событие, пока причина не снята: оно вернётся в очередь через 31 секунду и снова сработает оповещение. Не переписывать значение вручную и не публиковать событие в исходную тему от имени сервиса: идентификатор события должен остаться тем же, иначе дедупликация не узнает его. Не очищать `.dlq` и `processed_event`, чтобы «заново прогнать» поток: так повторно применятся события, которые уже сработали.

### 4.2. Обращение без оператора

**Что случилось.** Обращение (от покупателя «Не получил ключ» или от системы, если выдача не удалась или просрочена) в статусе `created` ждёт оператора больше часа ([SM-07](../03-processes/SM-07-support-ticket.md), NFT-2.4). Платформа считает возраст самого старого такого обращения запросом по индексу раз в 15 секунд и отдаёт его метрикой `support_queue_oldest_age_seconds` (рядом `support_queue_tickets{status}`: сколько обращений в очереди и в работе). Значение 0 означает пустую очередь.

**Как заметить.** Оповещение `SupportTicketUnattended` (warning, [dgm.yml](../../infra/obs/prometheus/rules/dgm.yml)) на наборах с наблюдением; без него оператор видит самые старые обращения первыми в очереди (`GET /api/v1/staff/support-tickets`, старые выше).

**Что сделать.**

1. Открыть очередь и взять самое старое обращение в работу (`POST /api/v1/staff/support-tickets/{ticketId}/take`). Два оператора одновременно: обращение получает первый, второй видит 409, это не сбой.
2. Если нужен перерыв, вернуть обращение в очередь (`.../release`): время создания не меняется, оно остаётся на своём месте и счётчик возраста не обнуляется.
3. Если обращений в очереди нет, а оповещение горит: метрику считает платформа раз в 15 секунд, подождать минуту; затем сверить с базой (`select count(*), min(created_at) from support.ticket where status = 'created'` под ролью `app_support`) и посмотреть `make logs S=platform-service` на строку «Метрики очереди поддержки не обновлены» (база была недоступна, значения остаются прежними до следующего прохода).

**Чего не делать.** Не править статус обращения в базе руками: статус меняют только операции платформы, триггер `trg_ticket_status_transition` допускает только переходы SM-07, а взятие и возврат пишут запись в журнал аудита (`support.ticket_taken`, `support.ticket_released`).

## 5. Что собирать при обращении за помощью
