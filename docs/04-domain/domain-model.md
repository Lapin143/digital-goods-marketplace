## 1. Как читать документ

Модель описывает, какие данные есть в системе, кто ими владеет и какие правила должны быть верны всегда. Это логический уровень: без типов данных, индексов и таблиц, они появятся в Ф2 в `docs/07-data/`.

Основные понятия:

- **Сущность** это то, о чём система хранит данные и что имеет собственный жизненный цикл: заказ, ключ, платёж.
- **Владелец данных** это ровно один bounded context (он же сервис и отдельная база данных). Только владелец меняет сущность. Остальные контексты просят об изменении командой или событием.
- **Связь между контекстами** это только идентификатор. Контекст не обращается к таблицам другого контекста и не хранит чужие данные как свои. Исключения оформлены явными копиями («снимками») и перечислены в решении 5.
- **Статус** берётся из статусной модели SM. В карточке сущности указана ссылка, подробные переходы лежат в модели.
- **Инвариант** это условие, которое верно в любой момент времени, в том числе при сбоях, повторах и одновременных запросах. Инварианты собраны в разделе 6 и имеют номера INV-NN, на них будут ссылаться тест-кейсы.

## 3. Агрегаты и границы транзакций

Агрегат это группа записей, которые меняются вместе в одной транзакции базы данных. Всё, что лежит за границей агрегата, согласуется событиями и в конечном счёте.

| Агрегат | Состав | Что меняется одной транзакцией |
| --- | --- | --- |
| Заказ | Заказ | Смена статуса заказа и запись исходящего события |
| Платёж | Платёж с данными о попытках возврата | Смена статуса платежа, признаки возврата и исходящее событие |
| Пул ключей товара | Ключи и резервы одного товара, остаток по API | Резервирование: блокировка свободных ключей с пропуском занятых, создание резерва и перевод ключей в «зарезервирован». Снятие резерва и перевод в «использован» |
| Баланс продавца | Операции по балансу и записи журнала баланса одного продавца | Начисление и комиссия по заказу создаются парой. Создание заявки на вывод проверяет доступный остаток под блокировкой баланса продавца |
| Заявка на вывод | Заявка и парная операция «вывод» | Создание заявки и резерв суммы, выплата или отказ и сторнирование |
| Журнал аудита | Запись аудита | Только добавление |

Заказ, платёж, выдача и ключи принадлежат разным агрегатам и контекстам. Поэтому сценарий покупки построен как сага (раздел 8.2 требований): резерв, оплата и выдача согласуются событиями, а сбой отменяется компенсацией.

## 4. Сущности

В таблицах атрибутов указаны ключевые атрибуты из раздела 6.1 требований и атрибуты, добавленные при проработке процессов. Добавленные помечены словом «добавлен» с указанием источника. Ссылка на сущность другого контекста всегда идёт по идентификатору.

### 4.1. Пользователь

| Поле | Содержание |
| --- | --- |
| Владелец | Идентификация (Keycloak и расширение платформы) |
| Назначение | Учётная запись человека: покупатель, продавец или сотрудник платформы. Единственное место, где персональные данные хранятся как основные (кроме снимков адреса доставки, решение 5) |
| Статусы | активен, деактивирован. «Заблокирован» в разделе 6.1 есть, но в процессах не используется |
| Связи | На пользователя по ID ссылаются профиль продавца, заказ (BuyerID), обращение, спор, журнал аудита (ActorID) |
| Требования | FT-1.0 … FT-1.7, FT-11.2 |

| Атрибут | Описание и правила |
| --- | --- |
| ID (UUID) | Идентификатор, единственная ссылка на пользователя для других контекстов |
| E-mail | Уникален среди учётных записей. При входе через VK ID берётся у провайдера и считается подтверждённым (US-1.2) |
| Номер телефона | Уникален: один номер привязан только к одной учётной записи (FT-1.5). Пуст, пока не подтверждён |
| Признак подтверждения телефона | Без него первый заказ не оформляется (FT-1.5) |
| Имя | Отображаемое имя |
| Роль | Покупатель, Продавец, Модератор, Оператор поддержки, Администратор. «Гость» не хранится. Роль «Продавец» появляется только при одобрении профиля, роли сотрудников назначает администратор (US-8.1) |
| Признак 2FA | Обязателен для продавца, модератора, оператора поддержки и администратора (FT-1.3). Хранится в учётной записи, а не в профиле продавца (SM-05, решение 5) |
| Этап смены номера | Какой этап уже пройден: код на e-mail, проверка уникальности, код SMS. Без него можно было бы пропустить проверку (BPMN-07). R2, добавлен |
| Дата регистрации | Дата создания учётной записи |
| Дата деактивации, признак анонимизации | Деактивация сохраняет историю, персональные данные анонимизируются по запросу (раздел 6.2, FT-1.4). Добавлены при моделировании |

| Атрибут | Описание и правила |

### 4.4. Товар

| Поле | Содержание |
| --- | --- |
| Владелец | Каталог |
| Назначение | Предложение продавца: что продаётся, за сколько и как выдаётся |
| Статусы | черновик, на модерации, опубликован, отклонён, заблокирован, архив ([SM-04](../03-processes/SM-04-product.md)) |
| Связи | SellerID. На ID товара ссылаются ключ, резерв, остаток по API, заказ |
| Требования | FT-3.0 … FT-3.4, FT-4.4, FT-2.3 |

| Атрибут | Описание и правила |
| --- | --- |
| ID | Идентификатор товара |
| SellerID | Продавец, ID профиля |
| Название, описание | Правка названия, описания или типа опубликованного товара возвращает его на модерацию (SM-04/T6) |
| Тип | Ключ игры, лицензия ПО, подарочная карта или пополнение, подписка |
| Платформа, регион активации | Правка не требует новой модерации (SM-04/T7) |
| Цена | В рублях. Заказ хранит цену снимком на момент оформления |
| Способ выдачи | Пул ключей (R1) или API продавца (R2) |
| Причина отклонения | Заполняется решением модератора, видна продавцу (FT-11.4) |
| Статус до блокировки | Что было с товаром перед блокировкой. Нужен, чтобы после снятия блокировки продавца вернуть товар в прежнее состояние. Добавлен (SM-04, решение 1) |

Остаток товара из раздела 6.1 не хранится в Каталоге: для способа «пул» это число свободных ключей, для способа «API» отдельная сущность «Остаток по API» (решение 1). Каталог показывает значение из своей копии для витрины, которую обновляет событием «остаток изменился» (NFT-1.0).

### 4.6. Резерв

| Поле | Содержание |
| --- | --- |
| Владелец | Остатки и ключи |
| Назначение | Временное закрепление ключей (или остатка по API) за заказом на время оплаты |
| Статусы | активен, использован, снят ([SM-08](../03-processes/SM-08-reservation.md)) |
| Связи | OrderID, ProductID. Ключи резерва это ключи заказа в статусе «зарезервирован» |
| Требования | FT-5.2, FT-6.3, FT-6.5, NFT-2.2 |

| Атрибут | Описание и правила |
| --- | --- |
| ID | Идентификатор резерва |
| OrderID | Заказ. За время жизни у заказа может быть несколько резервов: поздняя оплата создаёт новый |
| ProductID | Товар |

Правила: значение изменяется только в допустимых границах (ноль, отрицательные и нечисловые значения отклоняются). Уже созданные заказы сохраняют сроки, с которыми были созданы. В R2 окно спора плюс срок решения должны быть короче срока удержания (INV-26). Каждое изменение пишется в журнал аудита со значениями до и после, потому что параметры не содержат персональных данных (NFT-5.3).

## 7. Решения при моделировании

1. **Остаток для выдачи по API принадлежит «Остаткам и ключам».** В разделе 6.1 остаток записан атрибутом товара, но его уменьшает сервис «Остатки и ключи» при каждом заказе, а правит продавец. Если оставить атрибут в «Каталоге», сущность меняют два контекста. Поэтому введена сущность «Остаток по API», а «Каталог» получает значение событием для витрины.
2. **Роль «Продавец» назначает «Идентификация» по событию.** «Подключение продавцов» публикует «профиль одобрен», «Идентификация» выдаёт роль и включает требование настроить 2FA при входе. Так сущность «Пользователь» меняет только её владелец.
3. **Статус пользователя «заблокирован» не используется.** В требованиях нет функции, которая переводит в него обычную учётную запись. Блокировка продавца выполняется статусом профиля, учётную запись можно деактивировать. Замечание вынесено на версию 1.6 требований.
4. **SellerID это ID профиля продавца, BuyerID это ID пользователя.** Профиль и пользователь связаны по UserID. Отдельный идентификатор отделяет данные продаж (товары, заказы, деньги) от учётной записи с персональными данными: контексты продаж и финансов ссылаются на профиль и не знают, какой пользователь за ним стоит.
5. **Копии данных (снимки) разрешены в шести местах и больше нигде.** Цена и комиссия в заказе, название товара в заказе, адрес доставки в заказе и выдаче, реквизиты в заявке на вывод, срок резерва в заказе. Снимок фиксирует факт на момент события и не обновляется автоматически. Единственный способ изменить снимок адреса это повторная отправка по обращению: «Поддержка» командой просит «Заказы» обновить адрес, «Заказы» публикуют событие, «Выдача» создаёт повторную выдачу.
6. **API-ключ продавца принадлежит «Подключению продавцов».** Ключ выпускается только одобренному продавцу и связан с его статусом. API Gateway проверяет ключ запросом к этому сервису с кэшем в Redis.
7. **Резерв это отдельная сущность с несколькими экземплярами на заказ.** Резерв кончается раньше заказа, а поздняя оплата создаёт новый резерв для того же заказа.
8. **Комиссия фиксируется в заказе при создании.** Ставка по умолчанию 2% берётся из параметров, в R3 она зависит от месячного оборота продавца (US-12.1). Смена параметра не меняет созданные заказы.
9. **Движения по деньгам продавца только добавляются.** Комиссия отдельная операция со знаком минус, статус меняется записью журнала, возврат сторнирует начисление и комиссию целиком.
10. **Атрибуты, добавленные по итогам процессов.** Товар: статус до блокировки и причина блокировки (SM-04). Обращение: источник (SM-07). Заказ: причина отмены (SM-01). Платёж: данные о попытках возврата (SM-02). Заявка на вывод: срок обработки (SM-10). Спор: признак исполнения (SM-09). Операция по балансу: причина заморозки и ID заявки (SM-11).
11. **Письма с ключами формирует «Выдача», а не «Уведомления».** Открытое значение ключа существует только в памяти двух контекстов: расшифровывают «Остатки и ключи», получает по защищённому вызову и вкладывает в письмо «Выдача» (ADR-009). Остальные контексты значения не видят, поэтому письмо с ключом уходит провайдеру напрямую и не проходит через Kafka (NFT-3.2). Остальные письма отправляют «Уведомления».
