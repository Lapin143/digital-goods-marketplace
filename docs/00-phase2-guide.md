# Ф2. Архитектура и контракты: пошаговый план

**Для кого:** системный аналитик, который ведёт проект. Фаза Ф1 закончена, веха M1 закрыта, итоги в [отчёте о Ф1](00-phase1-report.md).
**Время:** 20–30 часов, недели 3–4 [плана проекта](00-project-plan.md).
**Результат:** веха M2 «можно писать код без догадок». Архитектура в нотации C4, записи решений (ADR), контракты API и событий, физические модели баз данных, стратегия тестирования и матрица трассировки v2.

Фаза Ф2 заканчивается до первой строки кода сервисов. Из этих документов в Ф3 собирается каркас (Compose, Kafka, Keycloak, шлюз, CI), а в Ф4 пишутся сервисы. Порядок шагов важен: каждый следующий артефакт опирается на предыдущие. Если на шаге обнаружилось расхождение с требованиями или с документами Ф1, действуйте по разделу «Если нашли расхождение».

**Что делаем детально, а что укрупнённо.** Релиз R1 прорабатывается полностью: контракты, таблицы, диаграммы. Для R2 и R3 на этой фазе проектируются границы сервисов, события и ключевые решения, но подробные контракты и схемы таблиц появятся перед Ф5 и Ф6.

## Общие правила

### Рабочий цикл для каждого шага

1. Подготовьте артефакты шага в рабочей копии репозитория.
2. Запустите проверки шага (они перечислены в блоке «Что проверить»): отрисовка диаграмм, разбор контрактов, прогон SQL на настоящем PostgreSQL, перекрёстные проверки идентификаторов, валидатор документов.
3. Исправьте найденное. Расхождения, которые меняют смысл, записываются в раздел «Решения» документа.
4. Один артефакт или одна связанная группа артефактов дают один commit с подписью из шага.
5. Отправьте изменения на GitHub и в папку `C:\dev\digital-goods-marketplace`, и только потом переходите к следующему шагу.

### Как рисуем архитектуру: C4

Архитектурные схемы рисуются в нотации C4 в виде кода Mermaid (`C4Context`, `C4Container`, `C4Component`, `C4Dynamic`, `C4Deployment`). Так диаграммы лежат в репозитории рядом с текстом, GitHub рисует их без плагинов, а изменения видны в обычном diff. Подробные правила закрепляются в `c4-notation.md` на шаге 1. Главные из них:

1. На диаграмме один уровень абстракции. Контекст показывает системы и людей, контейнеры показывают приложения и хранилища, компоненты показывают устройство одного контейнера. Уровень кода (L4) не рисуем.
2. Не больше 12–15 элементов на диаграмме. Если больше, диаграмму делим по областям, как сделано с картой контекстов в Ф1.
3. У каждого элемента название по-русски, технология латиницей и одно предложение о назначении. У каждой связи глагол и протокол: «передаёт заказ, REST/HTTPS», «публикует событие, Kafka».
4. Алиасы элементов совпадают с кодами сервисов (`order-service`, `inventory-service`) и используются так же в OpenAPI, AsyncAPI и SQL.
5. Под диаграммой стоит таблица элементов: ответственность, технология, владелец данных, релиз. Диаграмма даёт картину, таблица даёт точные значения.
6. R1 и R2 не смешиваются на одной диаграмме: расширения R2 рисуются отдельной диаграммой.
7. Динамику со временем, ветвлением и повторами (альт, цикл) показывают sequence-диаграммы Mermaid, потому что C4 Dynamic не умеет ветвлений. Для главного пути покупки есть и динамическая диаграмма C4 с нумерованными связями.

### Чем проверяем

Часть привычных инструментов недоступна в среде, где ведётся проектирование (нет доступа к реестрам пакетов), поэтому проверки сделаны своими скриптами, а промышленные линтеры подключаются в CI на фазе Ф3.

| Что проверяем | Чем сейчас | Что добавится в Ф3 |
| --- | --- | --- |
| Диаграммы Mermaid, включая C4 | Отрисовка `mmdc` (Mermaid 11.16), та же библиотека, что на GitHub | Проверка в CI |
| Контракты OpenAPI | Скрипт: структура, `$ref`, уникальность `operationId`, схемы ошибок, примеры против схем (`jsonschema`) | Spectral в CI |
| Контракты AsyncAPI | Скрипт: структура 3.0, ссылки на сообщения и схемы, примеры против схем | AsyncAPI CLI в CI |
| SQL | Прогон DDL на настоящем PostgreSQL 16, проверочные запросы и тест конкуренции | Миграции Flyway и Testcontainers |
| Идентификаторы и ссылки | Скрипты перекрёстных проверок, валидатор документов Ф1 | Проверка документов в CI |

### Если нашли расхождение

1. Запишите вопрос в документе, над которым работаете, в раздел «Решения».
2. Решите, меняет ли ответ требования. Не меняет: зафиксируйте решение и идите дальше. Меняет: запишите замечание для требований v1.6 в итоговый отчёт Ф2, версию v1.5 на месте не правьте.
3. Если расхождение с документом Ф1 (процесс, статусная модель, домен), исправьте документ Ф1 отдельным commit с понятной подписью и перечислите правку в отчёте Ф2.

## Шаг 1. Нотация C4 и диаграмма контекста

**Папка:** `docs/05-architecture/`. **Файлы:** `c4-notation.md`, `c4-context.md`, обновлённый `README.md`.

**1.1. Нотация** (`c4-notation.md`). Правила из раздела «Как рисуем архитектуру», цветовая и текстовая конвенция, ограничения Mermaid (нет автоматической раскладки: порядок элементов и параметры `UpdateLayoutConfig` управляют видом), пример корректной подписи элемента и связи. Рассмотренные альтернативы: Structurizr DSL и PlantUML с библиотекой C4. Они дают лучшую раскладку, но требуют отдельного исполняемого инструмента, а Mermaid рисуется на GitHub без него.

**1.2. Диаграмма контекста** (`c4-context.md`, уровень 1). Система «Маркетплейс цифровых товаров» в центре. Люди: гость, покупатель, продавец, модератор, оператор поддержки, администратор (раздел 3 требований). Внешние системы: платёжный шлюз, почтовый провайдер, SMS-провайдер, VK ID, банк для ручных выплат (R2), системы продавцов по API (R2). Для каждой связи указано, что передаётся и по какому каналу. Отдельная диаграмма для R2 показывает связи, появляющиеся позже.

*Что проверить:*

- Все роли из раздела 3 требований и все внешние системы из раздела 2.2 («Эмуляция») есть на диаграмме. Нет «лишних» систем, которых нет в требованиях.
- Каждая связь направлена от инициатора и подписана глаголом и каналом.
- Диаграмма отрисована без ошибок и читается без увеличения.
- Заглушки (платёж, почта, SMS, VK ID, банк) названы внешними системами, но в таблице под диаграммой отмечено, что в проекте их роль играет один контейнер-заглушка.

**Commit:** `docs: нотация C4 и диаграмма контекста`.

*Что уметь объяснить:*

- Что такое C4 и чем уровни отличаются друг от друга: для кого каждый уровень и какой вопрос на него отвечает.
- Почему на уровне контекста нет технологий и сервисов.
- Чем модель C4 лучше «картинки со стрелками»: у каждого элемента и связи есть смысл, который можно проверить.

## Шаг 2. Декомпозиция на сервисы и диаграмма контейнеров

**Папка:** `docs/05-architecture/`. **Файлы:** `decomposition.md`, `c4-containers.md`, `adr/ADR-002-microservices-consolidation.md`.

**2.1. Декомпозиция** (`decomposition.md`). 12 контекстов из Ф1 раскладываются по сервисам. Требования к результату:

- На R1 получается 5–6 прикладных сервисов (плюс Keycloak, шлюз и интерфейс). Границы контекстов сохраняются внутри кода и отдельными схемами данных.
- Для каждого объединения записана причина по критериям: общий жизненный цикл данных, скорость изменений, нагрузка и масштабирование, требования безопасности (ключи в отдельном сервисе), команда.
- Для каждого сервиса: код, контексты внутри, схема и база данных, синхронные вызовы, публикуемые и принимаемые события, нагрузка, релиз появления.
- Правила, чтобы потом можно было разделить: модули внутри сервиса не обращаются к таблицам друг друга, обмениваются через интерфейсы и события.
- Расширения R2 и R3: какие сервисы добавляются и какие объединённые сервисы придётся разделить.

**2.2. Диаграмма контейнеров** (`c4-containers.md`, уровень 2). Контейнеры R1: интерфейс (React), шлюз, прикладные сервисы, Keycloak, PostgreSQL, Kafka, Redis, MinIO, заглушка внешних систем. Связи с протоколами. Вторая диаграмма показывает добавления R2.

**2.3. ADR-002.** Контекст, варианты (монолит, 12 отдельных сервисов, выбранное укрупнение), решение, последствия, условие пересмотра.

*Что проверить:*

- Каждый из 12 контекстов попадает ровно в один сервис.
- События и вызовы из bounded-contexts.md есть на диаграмме как связи, и нет связей, которых нет в bounded-contexts.md.
- Нет общей базы данных у разных сервисов: у каждого своя схема и база.
- Ни один контейнер не владеет сущностью, которой владеет другой (сверка с таблицей владельцев ER).
- Объединение не нарушает принцип «ключи видит только один сервис» (решение 11 доменной модели).

**Commit:** `docs: декомпозиция на сервисы, диаграмма контейнеров, ADR-002`.

*Что уметь объяснить:*

- Почему микросервисы здесь оправданы, а не «потому что модно», и когда монолит был бы лучше.
- Как выбираются границы сервиса и что такое «распределённый монолит».
- Что значит «объединили сервисы, но сохранили границы» и чем это помогает разделить их потом.

## Шаг 3. ADR о взаимодействии сервисов

**Папка:** `docs/05-architecture/adr/`. **Решения:** ADR-003 Kafka, ADR-004 Saga, ADR-005 Transactional Outbox, ADR-006 идемпотентность, ADR-011 гарантированная доставка, ADR-015 интеграция с платёжным шлюзом.

Каждая запись по шаблону: контекст, минимум две альтернативы с плюсами и минусами, решение, последствия, условие пересмотра, связанные требования. Отклонённые альтернативы из плана записываются честно: RabbitMQ, Camunda и Temporal, прямые вызовы, SOAP, распределённая транзакция.

Что должно войти в содержание:

- **ADR-004 (Saga).** Оркестрация в сервисе заказов, шаги и компенсации из BPMN-01 и SM-01, таймеры, поведение при сбое каждого шага.
- **ADR-005 (Outbox).** Таблица, публикатор, гарантии (минимум один раз), порядок, очистка.
- **ADR-006 (идемпотентность).** Три уровня: ключ идемпотентности запроса, таблица обработанных событий, уникальные ограничения. Что считается ключом для каждого типа события.
- **ADR-011 (доставка).** Повторы с нарастающей задержкой, лимит попыток, DLQ, передача в поддержку по 30 минутам (NFT-2.4).
- **ADR-015 (шлюз).** Webhook плюс REST, проверка подписи, дедупликация уведомлений, поведение заглушки.

*Что проверить:*

- В каждой записи есть все разделы шаблона и не меньше двух рассмотренных вариантов.
- Решения не противоречат разделу 8.2 требований и BPMN/SM Ф1 (числа таймеров и повторов берутся оттуда).
- Индекс в `adr/README.md` обновлён.

**Commit:** `docs: ADR взаимодействия сервисов (003–006, 011, 015)`.

*Что уметь объяснить:*

- Чем оркестрация саги отличается от хореографии и почему здесь выбран оркестратор.
- Какую проблему решает Outbox и почему нельзя просто опубликовать событие после commit.
- Что такое доставка «минимум один раз» и как идемпотентность превращает её в «эффективно один раз».

## Шаг 4. ADR о целостности и данных

**Решения:** ADR-007 защита от двойной выдачи ключа, ADR-008 остаток API-товаров, ADR-009 шифрование ключей и HMAC для дублей, ADR-012 резерв (PostgreSQL как источник истины, Redis как таймер), ADR-013 поздняя оплата, ADR-014 журнал аудита без персональных данных.

Что должно войти в содержание:

- **ADR-007.** Блокировка строки `FOR UPDATE SKIP LOCKED`, уникальные ограничения, почему не распределённая блокировка в Redis. Связь с инвариантами INV-01 и INV-02.
- **ADR-008.** Оптимистичная блокировка остатка (версия записи), сценарий «продавец правит, пока идёт заказ».
- **ADR-009.** AES-256, где хранится мастер-ключ, ротация, HMAC для проверки дублей, что попадает в логи (ничего).
- **ADR-012.** Таймер в Redis, сверяющая задача, что происходит при потере Redis.
- **ADR-013.** Окна 12 и 15 минут, перерезервирование, автовозврат, решение о заказе при нехватке ключей.
- **ADR-014.** Что хранится в журнале (ID, имя поля, HMAC до и после), где лежат персональные данные, как выполняется анонимизация.

*Что проверить:* то же, что на шаге 3, плюс: числа и правила совпадают с SM-03, SM-08, SM-01, доменной моделью (INV-NN названы в записи).

**Commit:** `docs: ADR о целостности и данных (007–009, 012–014)`.

*Что уметь объяснить:*

## Шаг 5. ADR об идентификации и безопасности

**Решения:** ADR-010 Keycloak и подтверждение телефона по SMS, ADR-021 API Gateway, ADR-022 шифрование внутреннего трафика.

- **ADR-010.** Свой SPI в Keycloak или модуль в сервисе уведомлений. Кто владеет одноразовыми кодами, где они хранятся (Redis или база), вход по коду из SMS с ограниченной сессией (FT-1.7), смена номера (BPMN-07), ограничение частоты (NFT-3.5, NFT-3.7). Решение нужно принять до начала Ф3.
- **ADR-021.** Выбор шлюза: Spring Cloud Gateway, Kong, Traefik или NGINX. Критерии: проверка JWT, ограничение частоты с Redis, ключи API продавца (R2), потребление памяти на ноутбуке с 8 ГБ, привычный стек.
- **ADR-022.** Шифрование трафика между контейнерами стенда (находка 12 отчёта Ф1): TLS внутри сети против доверия к сети Compose и сети k3s.

*Что проверить:* то же, что на шаге 3. ADR-010 отвечает на вопросы из BPMN-01 (решение 3), BPMN-04 (решение 4) и закрывает остаточный риск из BPMN-04 на уровне модели угроз (шаг 9).

**Commit:** `docs: ADR об идентификации и безопасности (010, 021, 022)`.

*Что уметь объяснить:*

- Что такое OAuth2 и JWT, чем access-токен отличается от refresh-токена и где проверяется токен.
- Зачем нужен API Gateway и что плохого, если он станет «умным».

| Диаграмма C4 не рисуется | Проверьте тип блока (`C4Context`, `C4Container`, `C4Component`, `C4Dynamic`, `C4Deployment`), уникальность алиасов, что в подписях нет двойных кавычек и круглых скобок внутри строк |
| Элементы C4 наложились друг на друга | Поменяйте порядок объявления элементов и значения `UpdateLayoutConfig($c4ShapeInRow, $c4BoundaryInRow)`. Если элементов больше 15, разделите диаграмму |
| Контейнеров получилось больше шести | Вернитесь к критериям объединения в `decomposition.md`. R1 с 10–12 сервисами не помещается ни в срок, ни в память ноутбука |
| В контракте нашлась операция без истории | Это находка: либо не хватает истории, либо операция лишняя. Запишите в отчёт |
| SQL не выполняется на PostgreSQL | Исправьте файл, не обходя ошибку. Модель считается готовой только после чистого прогона с нуля |
| ADR получился без альтернатив | Решение без рассмотренных вариантов не принятое, а объявленное. Найдите хотя бы две реальные альтернативы и честно опишите их минусы |
| Нашли ошибку в ранее отправленном документе | Исправьте файл и сделайте новый commit, например `docs: исправлен переход в SM-03`. Историю переписывать не нужно |
