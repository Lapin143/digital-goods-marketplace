# Ф3. Каркас: пошаговый план

**Для кого:** системный аналитик, который ведёт проект. Фаза Ф2 закончена, веха M2 закрыта, итоги в [отчёте о Ф2](00-phase2-report.md).
**Время:** 15–25 часов, неделя 5 [плана проекта](00-project-plan.md).
**Результат:** веха M3 «всё поднимается одной командой». Окружение запускается командой `make up`, тестовый запрос проходит через шлюз с токеном до сервиса и базы, CI зелёный.

Ф3 первая фаза, в которой появляется исполняемый код. Но это не прикладные сервисы: продуктовых функций (каталог, заказ, оплата, выдача) здесь нет, они появятся в Ф4. Задача Ф3 дать основу, на которую Ф4 ляжет без переделок: инфраструктуру с шифрованием, вход и роли, шлюз, общую библиотеку сервисов, шесть пустых сервисов, заглушки внешних систем, CI и измеренные лимиты памяти.

**Главная идея фазы: ходячий скелет.** Скелет это тончайшая сквозная нить через все слои, а не набор независимых заготовок. В Ф3 три реальные операции из контракта OpenAPI (`listStorefrontProducts`, `listOrders`, `getProductCard`) проходят весь путь: браузер или клиент, шлюз, проверка токена, сервис, база по TLS. Если нить работает, значит соединены маршрутизация, JWT и области, mTLS между сервисами, права доступа к базе и сквозной идентификатор запроса. Новых операций и полей сверх контракта Ф2 не придумываем.

## Ограничения среды и как проверяем код

Это главное отличие Ф3 от Ф2, поэтому оно описано до шагов.

| Среда | Что доступно | Что недоступно |
| --- | --- | --- |
| Облачное рабочее место, где пишется код | Git, GitHub (чтение и запись), Python, Node (без `npm install`), Mermaid, PostgreSQL 16 | Maven Central, Gradle, Docker Hub, GHCR, npm, PyPI: запросы блокирует политика исходящего трафика. Собрать Java-проект и скачать образ здесь нельзя |
| Папка на вашем компьютере | Файлы репозитория, git | Сеть из виртуальной машины |
| **GitHub Actions (раннер `ubuntu-24.04`, 4 ядра, 16 ГБ, Docker 28, Compose 2.38, Java 17, Node 22)** | Все реестры, Docker, права на запуск контейнеров | Ничего существенного |

Следствие: **любой Java- и Docker-код проверяется только запуском в GitHub Actions**. Это не обход ограничений, а штатный способ: CI всё равно обязан быть главным судьёй в проекте. Принципы, чтобы это работало без догадок:

1. **Обратная связь по аннотациям.** Журналы запусков без входа недоступны, а аннотации заданий и шагов читаются по публичному REST API GitHub. Каждый шаг CI, который может упасть, при ошибке печатает диагностику в виде `::error title=…::` (хвост журнала, перевод строки кодируется как `%0A`). Помощник `tools/ci/diag.sh` делает это одним вызовом (шаг 3).
2. **Песочная ветка.** Итерации «правка, запуск, чтение ошибки» делаются в ветке `ci/sandbox`, чтобы не засорять `main` красными запусками. Проверенное дерево переносится на `main` одним squash-коммитом с понятной подписью, поэтому `main` всегда зелёный и сворачивается вперёд (fast-forward).
3. **Маленькие шаги.** Один запуск CI занимает 2–10 минут. Поэтому код пишется малыми порциями, с самым дешёвым проверяющим запуском на каждой.
4. **Честная фиксация.** Что проверено запуском CI, а что только прочитано глазами, говорится в отчёте. Нет зелёного запуска, нет галочки.
5. **Измерения на раннере, а не на ноутбуке.** Память контейнеров замеряется на раннере (16 ГБ, без лимита WSL). Для ноутбука берётся лимит `mem_limit` и правило «пик не выше 85 % лимита», а потом вы проверяете `make up SET=dev-min` у себя, этот шаг в итоговом списке «что остаётся вам».

## Общие правила

### Рабочий цикл для каждого шага

1. Подготовьте артефакты шага в рабочей копии.
2. Прогоните то, что можно проверить локально: скрипты `tools/docs-checks`, разбор YAML и JSON, `shellcheck`-подобный просмотр, запуск Python и Node без зависимостей, проверку Compose-файла скриптом.
3. Всё, что требует Java или Docker, отправьте в `ci/sandbox` и дождитесь зелёного запуска. Ошибку читайте по аннотациям, исправляйте причину, а не симптом.
4. Один артефакт или одна связанная группа дают один commit.
5. Когда шаг зелёный, перенесите результат на `main`, отправьте на GitHub и в папку `C:\dev\digital-goods-marketplace`, и только потом переходите к следующему шагу.
6. Если код шага расходится с документом Ф2, сначала решите, что правильно. Правится либо код, либо документ, отдельным commit с понятной подписью, и правка попадает в отчёт Ф3.

## Шаг 3. Основа CI: проверки документов, диагностика, ST-14

**Файлы:** `.github/workflows/ci.yml`, `tools/ci/diag.sh`, `tools/ci/README.md`, `.gitleaks.toml`.

**3.1. Задание `docs`.** Запускает `tools/docs-checks/run_all.sh --db` на раннере с PostgreSQL 16 и Mermaid CLI: документы, контракты, физическая модель БД, отрисовка каждой диаграммы. В конце вывода `run_all.sh` печатает сводку ошибок.

**3.2. Помощник `tools/ci/diag.sh`.** Запускает команду, сохраняет вывод, при ошибке печатает аннотацию `::error title=…::` со строками, которые объясняют причину. Аннотации читаются по REST API (`tools/ci/ci_status.py`), поэтому дальнейшие шаги отлаживаются без доступа к журналам.

**3.3. Задание `security` (ST-14).** Gitleaks по истории и по файлам, Trivy по файлам (уязвимости, секреты, конфигурации). Бинарные файлы проверяются по контрольным суммам выпуска.

**3.4. Самопроверки контролей** (`tools/ci/selftest.sh`): битый документ должен быть отвергнут, подложенный при запуске фиктивный секрет должен быть найден, `diag.sh` должен печатать аннотацию. Контроль, который ни разу не сработал, ничего не гарантирует.

**3.5. Песочная ветка.** `ci/sandbox` запускает те же задания, что `main`, и может переписываться. Проверенный коммит переносится в `main` быстрой перемоткой. Правила описаны в `tools/ci/README.md`.

*Что проверить:*

- Оба задания зелёные на песочной ветке.
- Намеренно испорченный документ (битая ссылка) даёт красный запуск, а в аннотации задания видна строка с причиной (проверено, запуск 37186908896).
- Принудительная отправка в песочную ветку работает, отправка в `main` по правилам только вперёд.

**Commit:** `ci: проверки документов, диагностика через аннотации, сканирование секретов (ST-14)`.

*Что уметь объяснить:*

- Что должно проверяться в CI и в каком порядке (быстрое раньше медленного).
- Чем сканирование секретов отличается от сканирования зависимостей.
- Почему проверка контроля (намеренно сломать и убедиться, что красно) обязательна.

## Шаг 5. Центр сертификации и секреты

**Файлы:** `infra/pki/*.sh`, `infra/pki/README.md`, `infra/pki/profiles.yaml`, цели `make certs`, `make secrets`.

**5.1. Центр сертификации** по ADR-022: частный, ECDSA P-256, срок корневого сертификата 5 лет, сертификаты контейнеров 90 дней, формат PEM (ключ PKCS#8). Закрытый ключ центра лежит в `.pki/` (права 0400) вне контейнеров и вне Git.

**5.2. Выпуск.** Скрипт `infra/pki/dgm_pki.py` (Python и `openssl`, без внешних пакетов) читает перечень контейнеров из `infra/pki/inventory.json` и выпускает `tls_<контейнер>.key`, `tls_<контейнер>.crt`, `tls_ca.crt` с `CN` равным имени контейнера (так `caller-filter` узнаёт вызывающего), SAN с именем контейнера и `localhost`. `make certs` перевыпускает сертификаты, у которых осталось меньше 30 дней.

**5.3. Секреты.** `make secrets` создаёт файлы секретов из того же перечня: ключи шифрования и подписи, пароли ролей баз (миграции и рабочие роли модулей), пароли пользователей Redis, пароль администратора и секрет клиента Keycloak. Значения случайные, в Git ничего не попадает. Для каждого секрета в перечне указаны читатели, `check_compose.py` проверит, что Compose монтирует секрет только им. Для CI секреты создаются при каждом запуске (test-strategy §12). Права файлов 0444 в каталоге 0700: причина в `infra/pki/README.md`.

*Что проверить:*

- 13 тестов скрипта (`make pki-test`): цепочка для обоих назначений, срок 90 дней, P-256, `CN` и SAN, чужой центр отвергается, ключ от другого сертификата замечается, истекающий сертификат перевыпускается, действующий сохраняется, секреты уникальны и длинные, ключа центра среди секретов нет.
- Перечень секретов совпадает с таблицей c4-deployment §6 (таблица приведена к перечню в этом шаге).
- `tools/ci/check-no-secrets-in-git.sh` и Gitleaks подтверждают, что в Git нет ключей и значений секретов.

**Commit:** `infra: частный центр сертификации и генерация секретов (ADR-022)`.

*Что уметь объяснить:*

- Что такое mTLS и чем он отличается от обычного TLS.
- Почему сертификаты короткоживущие и как идёт перевыпуск.
- Почему секреты это файлы, а не переменные окружения.

## Если что-то пошло не так

| Проблема | Что делать |
| --- | --- |
| Запуск CI красный, причина неясна | Читайте аннотации задания и шага. Если диагностики нет, добавьте её через `diag.sh` и повторите запуск. Не угадывайте |
| Образ не скачивается в CI | Проверьте имя и версию в `versions.md`. Если образ удалён автором, это находка для ADR (как с MinIO), а не повод брать «похожий» |
| Контейнер завершается по OOM | Не повышайте лимит вслепую: снимите пик (`docker stats`), сравните с правилом 85 % и запишите причину в бюджет |
| Сервис не стартует из-за TLS | Проверьте SAN сертификата (имя контейнера в сети), срок, права файла секрета `0400`, совпадение центра сертификации |
| Токен не проходит на шлюзе | Сравните `iss` и `aud` с realm, часы контейнеров, доступность ключей Keycloak (кэш) |
| Проверка документов красная после правки кода | Код разошёлся с документом: решите, что правильно, правьте один из них отдельным commit |
| `main` не принимает push | Ветка ушла вперёд. Получите изменения, пересоберите bundle, не переписывайте историю |
| Запуск на ноутбуке падает по памяти | Используйте набор меньше (`dev-min`), проверьте лимит `.wslconfig`, закройте лишнее. Сумма лимитов набора должна помещаться в таблицу бюджета |
