# Ф3. Каркас: пошаговый план

**Для кого:** системный аналитик, который ведёт проект. Фаза Ф2 закончена, веха M2 закрыта, итоги в [отчёте о Ф2](00-phase2-report.md).
**Время:** 15–25 часов, неделя 5 [плана проекта](00-project-plan.md).
**Результат:** веха M3 «всё поднимается одной командой». Окружение запускается командой `make up`, тестовый запрос проходит через шлюз с токеном до сервиса и базы, CI зелёный.

Ф3 первая фаза, в которой появляется исполняемый код. Но это не прикладные сервисы: продуктовых функций (каталог, заказ, оплата, выдача) здесь нет, они появятся в Ф4. Задача Ф3 дать основу, на которую Ф4 ляжет без переделок: инфраструктуру с шифрованием, вход и роли, шлюз, общую библиотеку сервисов, шесть пустых сервисов, заглушки внешних систем, CI и измеренные лимиты памяти.

**Главная идея фазы: ходячий скелет.** Скелет это тончайшая сквозная нить через все слои, а не набор независимых заготовок. В Ф3 три реальные операции из контракта OpenAPI (`listStorefrontProducts`, `listOrders`, `getProductCard`) проходят весь путь: браузер или клиент, шлюз, проверка токена, сервис, база по TLS. Если нить работает, значит соединены маршрутизация, JWT и области, mTLS между сервисами, права доступа к базе и сквозной идентификатор запроса. Новых операций и полей сверх контракта Ф2 не придумываем.

## Ограничения среды и как проверяем код

Это главное отличие Ф3 от Ф2, поэтому оно описано до шагов.

| Среда | Что доступно | Что недоступно |
| --- | --- | --- |
| Облачное рабочее место, где пишется код | Git, GitHub (чтение и запись), Python, Node (без `npm install`), Mermaid, PostgreSQL 16 | Maven Central, Gradle, Docker Hub, GHCR, npm, PyPI: запросы блокирует политика исходящего трафика. Собрать Java-проект и скачать образ здесь нельзя |
| Папка на вашем компьютере | Файлы репозитория, git | Сеть из виртуальной машины |
| **GitHub Actions (раннер `ubuntu-24.04`, 4 ядра, 16 ГБ, Docker 28, Compose 2.38, Java 17, Node 22)** | Все реестры, Docker, права на запуск контейнеров | Ничего существенного |

Следствие: **любой Java- и Docker-код проверяется только запуском в GitHub Actions**. Это не обход ограничений, а штатный способ: CI всё равно обязан быть главным судьёй в проекте. Принципы, чтобы это работало без догадок:

1. **Обратная связь по аннотациям.** Журналы запусков без входа недоступны, а аннотации заданий и шагов читаются по публичному REST API GitHub. Каждый шаг CI, который может упасть, при ошибке печатает диагностику в виде `::error title=…::` (хвост журнала, перевод строки кодируется как `%0A`). Помощник `tools/ci/diag.sh` делает это одним вызовом (шаг 3).
2. **Песочная ветка.** Итерации «правка, запуск, чтение ошибки» делаются в ветке `ci/sandbox`, чтобы не засорять `main` красными запусками. Проверенное дерево переносится на `main` одним squash-коммитом с понятной подписью, поэтому `main` всегда зелёный и сворачивается вперёд (fast-forward).
3. **Маленькие шаги.** Один запуск CI занимает 2–10 минут. Поэтому код пишется малыми порциями, с самым дешёвым проверяющим запуском на каждой.
4. **Честная фиксация.** Что проверено запуском CI, а что только прочитано глазами, говорится в отчёте. Нет зелёного запуска, нет галочки.
5. **Измерения на раннере, а не на ноутбуке.** Память контейнеров замеряется на раннере (16 ГБ, без лимита WSL). Для ноутбука берётся лимит `mem_limit` и правило «пик не выше 85 % лимита», а потом вы проверяете `make up SET=dev-min` у себя, этот шаг в итоговом списке «что остаётся вам».

## Общие правила

### Рабочий цикл для каждого шага

1. Подготовьте артефакты шага в рабочей копии.
2. Прогоните то, что можно проверить локально: скрипты `tools/docs-checks`, разбор YAML и JSON, `shellcheck`-подобный просмотр, запуск Python и Node без зависимостей, проверку Compose-файла скриптом.
3. Всё, что требует Java или Docker, отправьте в `ci/sandbox` и дождитесь зелёного запуска. Ошибку читайте по аннотациям, исправляйте причину, а не симптом.
4. Один артефакт или одна связанная группа дают один commit.
5. Когда шаг зелёный, перенесите результат на `main`, отправьте на GitHub и в папку `C:\dev\digital-goods-marketplace`, и только потом переходите к следующему шагу.
6. Если код шага расходится с документом Ф2, сначала решите, что правильно. Правится либо код, либо документ, отдельным commit с понятной подписью, и правка попадает в отчёт Ф3.

## Шаг 3. Основа CI: проверки документов, диагностика, ST-14

**Файлы:** `.github/workflows/ci.yml`, `tools/ci/diag.sh`, `tools/ci/README.md`, `.gitleaks.toml`.

**3.1. Задание `docs`.** Запускает `tools/docs-checks/run_all.sh --db` на раннере с PostgreSQL 16 и Mermaid CLI: документы, контракты, физическая модель БД, отрисовка каждой диаграммы. В конце вывода `run_all.sh` печатает сводку ошибок.

**3.2. Помощник `tools/ci/diag.sh`.** Запускает команду, сохраняет вывод, при ошибке печатает аннотацию `::error title=…::` со строками, которые объясняют причину. Аннотации читаются по REST API (`tools/ci/ci_status.py`), поэтому дальнейшие шаги отлаживаются без доступа к журналам.

**3.3. Задание `security` (ST-14).** Gitleaks по истории и по файлам, Trivy по файлам (уязвимости, секреты, конфигурации). Бинарные файлы проверяются по контрольным суммам выпуска.

**3.4. Самопроверки контролей** (`tools/ci/selftest.sh`): битый документ должен быть отвергнут, подложенный при запуске фиктивный секрет должен быть найден, `diag.sh` должен печатать аннотацию. Контроль, который ни разу не сработал, ничего не гарантирует.

**3.5. Песочная ветка.** `ci/sandbox` запускает те же задания, что `main`, и может переписываться. Проверенный коммит переносится в `main` быстрой перемоткой. Правила описаны в `tools/ci/README.md`.

*Что проверить:*

- Оба задания зелёные на песочной ветке.
- Намеренно испорченный документ (битая ссылка) даёт красный запуск, а в аннотации задания видна строка с причиной (проверено, запуск 37186908896).
- Принудительная отправка в песочную ветку работает, отправка в `main` по правилам только вперёд.

**Commit:** `ci: проверки документов, диагностика через аннотации, сканирование секретов (ST-14)`.

*Что уметь объяснить:*

- Что должно проверяться в CI и в каком порядке (быстрое раньше медленного).
- Чем сканирование секретов отличается от сканирования зависимостей.
- Почему проверка контроля (намеренно сломать и убедиться, что красно) обязательна.

## Шаг 7. Миграции Flyway, базы и роли

**Файлы:** `tools/docs-checks/db/gen_migrations.py`, `services/<сервис>/src/main/resources/db/migration/<модуль>/V<n>__<модуль>.sql`, `infra/postgres/{roles.json,init/10-databases-and-roles.sql}`, `tools/docs-checks/check_db_roles.py`, `tools/stand-checks/{lib.sh,db_migrations.sh}`.

**7.1. Миграции из тех же частей, что и DDL.** `gen_migrations.py` делит части `tools/docs-checks/db/parts/*.sql` по заголовкам разделов: `common/V1` служебные таблицы и функция контроля статусов, затем по миграции на схему модуля (правило модульности 7: у модуля своя папка), последней `access/V<n>` роли и права. Номера сквозные внутри сервиса, Flyway читает все подпапки. Содержимое разделов не меняется ни на символ: склейка миграций (без шапок) равна `docs/07-data/ddl/<сервис>.sql` по SHA-256, а тот равен сборке `build.py` из частей. Ключ `--check` в `run_all.sh` находит любое расхождение, лишний файл или правку руками.

**7.2. Базы и роли.** `infra/postgres/roles.json` единственный перечень: 7 баз, 6 ролей-мигратор `migrator_<сервис>` (владельцы баз), 11 рабочих ролей `app_<модуль>`, роль `keycloak`. `init/10-databases-and-roles.sql` читает его, берёт пароли из секретов (`pg_read_file` на стороне сервера, ни в окружение, ни в журнал они не попадают), выставляет атрибуты (`nosuperuser nocreatedb nocreaterole`), пределы соединений (равны пулам из memory-budget: сервис 8, Keycloak 10, мигратор 2), отзывает `CONNECT` у `PUBLIC` и выдаёт его только владельцу и своим рабочим ролям, в конце проверяет итог. Каталог `init` смонтирован в `/docker-entrypoint-initdb.d`, скрипт выполняется при первом запуске пустого тома и безопасно повторяется командой `make db-roles`. `check_db_roles.py` связывает перечень с DDL (роли из разделов «Роли и права»), `inventory.json` (секреты и читатели), memory-budget (арифметика соединений) и compose.

**7.3. Применение.** Сервис при старте подключается ролью-мигратором и применяет миграции (c4-deployment §7), затем работает под рабочими ролями. Таблицы журнала аудита: рабочей роли записи выдано только `SELECT` и `INSERT`, а `UPDATE`, `DELETE` и `TRUNCATE` запрещены ещё и триггером, который не пускает даже владельца (INV-42).

*Что проверить:*

- Документные проверки (`docs`): `gen_migrations.py --check`, `check_db_roles.py`, а `db/apply.sh` теперь строит базы из миграций, поэтому 39 тестов базы, сверка модели и 113 запросов `EXPLAIN` проверяют именно их. Самопроверка (`selftest.sh docs`) ловит правку миграции, предел соединений сверх пула и чужой секрет у роли.
- Стенд (`infra`, `db_migrations.sh`): образ Flyway применяет миграции всех шести сервисов с нуля под ролью-мигратором по TLS (`verify-full`), повторный запуск ничего не меняет, подмена уже применённой миграции отвергается проверкой контрольных сумм. Таблиц 44 (по числу `create table` в DDL, без месячных секций аудита и таблицы истории Flyway). Права: мигратор не суперпользователь, не читает файлы сервера и не подключается к чужой базе; рабочая роль не видит чужую схему, не создаёт объекты, не читает историю миграций; журнал аудита не изменить и не очистить; второе соединение сверх предела отвергается; `make db-roles` повторяется без ошибок.

*Решения* (c4-deployment §9, 14 и 15): образ Flyway (13.6.0) нужен только проверке стенда, сами сервисы применяют миграции библиотекой из Spring Boot (совпадение версий проверяется запуском сервисов на шаге 12); пока выпуск R1 не вышел, базовые миграции пересобираются целиком, затем изменения идут только новыми номерами.

**Commit:** `db: миграции Flyway из DDL Ф2, базы и роли по сервисам`.

*Что уметь объяснить:*

- Что такое миграции и почему нельзя править уже применённую (контрольная сумма, история в `flyway_schema_history`).
- Почему у сервиса своя роль и своя база, а не одна на всех, и зачем отдельная роль миграций с правом создавать таблицы, когда работает роль без этого права.
- Почему пределы соединений ролей считаются из пулов, а не «с запасом».

## Шаг 8. Объектное хранилище вместо MinIO

**Файлы:** `docs/05-architecture/adr/ADR-024-object-storage.md`, `infra/storage/{entrypoint.sh,init.sh,policy-seller-documents.json,root_user}`, `compose.yaml` (`object-storage`, `storage-init`), `tools/stand-checks/storage_checks.sh`, `tools/ci/storage-spike.sh`, задание `storage` в CI, правки документов Ф2.

**8.1. Спайк в CI.** MinIO архивирован (апрель 2026), поэтому каждый кандидат (SeaweedFS 4.48, RustFS 1.0.1, Garage 2.4.1) прошёл одинаковые проверки на раннере `ubuntu-24.04` с ограничениями стенда: не root, файловая система только для чтения, без привилегий, 192 МБ без свопа. Проверялись TLS с цепочкой нашего центра, отказ обычному HTTP, загрузка потоком 12 МБ с контрольной суммой, подписанная ссылка (рабочая, просроченная, с испорченной подписью), учётная запись на один бакет, сохранность данных после перезапуска, память. Спайк нашёл три факта, которых нет в обзорах: у SeaweedFS остаются слушающие порты на всех адресах, у Garage нет TLS на S3, а клиенты на rustls отвергают самоподписанный сертификат с признаком центра сертификации (`CaUsedAsEndEntity`), поэтому проверка идёт с настоящей цепочкой, как у нашего центра.

**8.2. ADR-024.** Выбран RustFS 1.0.1: единственный выполняет требования TLS, учётной записи на один бакет и одного открытого порта без дополнительных контейнеров, пик памяти около 100 МБ, Apache-2.0. Минус: проект молодой (1.0 от 16 сентября 2026). Смягчение: запасной вариант SeaweedFS проверен тем же спайком, поведение хранилища проверяет `storage_checks.sh` в каждом запуске CI. Алиас `object-storage` и контракт S3 API сохраняются.

**8.3. Контейнеры.** `object-storage` (192 МБ, порт 9000 по TLS, консоль отключена, том `objectdata`): `entrypoint.sh` копирует сертификат в память под именами, которых ждёт сервер, и готовит файлы корневой записи (имя в `root_user`, пароль из секрета `storage_admin`). `storage-init` (32 МБ, образ клиента `rustfs/rc:v0.1.36`, разовое задание по образцу `kafka-init`): создаёт бакет `seller-documents`, политику `seller-documents-rw` и учётную запись `catalog-service` с паролем из `storage_catalog`. Скрипт повторяем: политика и пароль каждый раз приводятся к файлу и секрету, поэтому правка политики и смена пароля выполняются командой `make storage-init`. Разовое задание входит по паролю и не имеет своего сертификата (исключение в `check_compose.py`).

**8.4. Правка документов.** Упоминания MinIO заменены в c4-containers, c4-deployment (строки 2.2, том `objectdata`, секреты `storage_admin` и `storage_catalog`, отладочный порт 19000 вместо консоли, решение 16), decomposition, ADR-022, project-plan, test-strategy, catalog-service-schema и DDL (комментарий к `object_key`). Название продукта стоит в versions.md, compose.yaml, `infra/storage`, ADR-024, уровне развёртывания и README, в логических документах «объектное хранилище». Память: группа `storage` 224 МБ, суммы наборов пересчитаны.

*Что проверить:*

- Документные проверки (`check_compose.py`, `check_budgets.py`, `check_security.py`, `check_refs.py`): состав, образ, лимит, секреты и порты `object-storage` и `storage-init` сходятся с документами, суммы памяти пересчитаны.
- Задание `images`: теги `rustfs/rustfs:1.0.1` и `rustfs/rc:v0.1.36` существуют.
- Задание `storage`: `storage_checks.sh` проходит целиком. Хорошие случаи: загрузка и скачивание 12 МБ, подписанная ссылка, работа в своём бакете. Плохие: обычный HTTP, чужой центр, чужой бакет (запись, чтение, перечисление, ссылка), создание и удаление бакетов, неверный пароль, анонимный доступ, просроченная и подделанная ссылка.
- Устойчивость: повторный init, подмена политики узкой и её возврат, смена пароля (начинается со знака «-»), перезапуск без потери данных, пик памяти не выше 85% лимита.
- Поиск по документам: упоминаний MinIO нет, кроме ADR-024, отчётов и руководств Ф2, Ф3 (история).

**Commit:** `docs: объектное хранилище вместо архивного MinIO (ADR-024)`, `infra: профиль storage`.

*Что уметь объяснить:*

## Шаг 10. Keycloak, realm как код

**Файлы:** `infra/keycloak/{gen_realm.py,realm/dgm-realm.json,entrypoint.sh,provision_test_users.py,reimport_realm.py,sms-otp/,README.md}`, `docker/Dockerfile.keycloak`, `compose.yaml` и `compose.debug.yaml` (`keycloak`), `tools/docs-checks/check_realm.py`, `tools/stand-checks/{kc_client.py,test_kc_client.py,keycloak_checks.py,keycloak_checks.sh}`, задание `keycloak` в CI, правки документов Ф2 (c4-deployment, versions).

**10.1. Realm как код.** Файл `dgm-realm.json` не правится руками: его создаёт `gen_realm.py` из таблиц в начале скрипта (роли, области, клиенты, сроки, потоки входа), идентификаторы потоков детерминированы. Роли «Покупатель», «Продавец», «Модератор», «Поддержка», «Администратор» (roles-permissions §2), одна роль на пользователя: роль по умолчанию даёт только `buyer`. Клиенты `dgm-web`, `dgm-staff`, `dgm-sms`, `platform-service`; `fullScopeAllowed=false`, поэтому роли попадают в токен только через области клиента, а область с привязкой к роли выдаётся только пользователям этой роли. Аудитория `dgm-api`, утверждения `phone_verified` (из атрибута, который меняет только администратор) и `amr` (`pwd`, `otp`, `vk`, `sms`); сроки по §2.1 (access 5 минут, refresh одноразовый, простой и максимум сессии по группам); защита от перебора (5 неудач, блокировка на 15 минут); Argon2 и длина пароля от 12; вход через VK ID на заглушке; исходящая почта на SMTP заглушки.

**10.2. Второй фактор.** У продавца, модератора, поддержки и администратора обязательна форма OTP: в потоке входа четыре условных подпотока по роли (`CONDITIONAL` с условием по роли и обязательной формой OTP внутри). Условия «OTP, если настроен» нет: оно позволило бы войти без второго фактора тому, кто его не настроил. Вход через VK ID и по SMS для этих ролей закрыт отдельными потоками. Проверено на настоящем Keycloak 26.8: у продавца без TOTP токен не выдаётся, с TOTP `amr` содержит `pwd` и `otp`.

**10.3. Расширение SMS.** По ADR-010 тонкий SPI с провайдером `sms-otp`. В Ф3 оно собирается (`javac --release 21` по библиотекам того же образа Keycloak) и подключено к потоку `sms-login`, но отказывает с кодом 501: логика кодов в `platform-service` появится в Ф4.

**10.4. Контейнер.** `dgm/keycloak` собирается Compose из `docker/Dockerfile.keycloak`: официальный образ, расширение, `kc.sh build`, curl (из ubi9 для проверки готовности по TLS). Файловая система только для чтения, запись в `tmpfs`; секреты из файлов (`entrypoint.sh`), в окружении их нет; база по TLS с проверкой имени; 640 МБ, куча 384 МБ. Адрес для браузера `https://localhost:8443/auth` (шлюз проксирует `/auth` и `/vkid` на шаге 13), он же издатель `iss`.

**10.5. Проверки.** `check_realm.py` сверяет JSON с roles-permissions.md (набор ролей, областей, кому выдаются, сроки, второй фактор, Argon2, структура потоков, отсутствие секретов и людей в файле, равенство результату генератора). `keycloak_checks.py` входит настоящим кодом авторизации с PKCE за каждую роль (около 100 проверок), `keycloak_checks.sh` добавляет ограничения контейнера, TLS, таблицу `credential` (Argon2, своя соль, паролей в открытом виде нет) и память. Пользователи для тестов создаются скриптом из случайных паролей, в репозитории их нет.

**10.6. Правка документов.** c4-deployment (том, сеть `data`, отладочный порт 18445, секрет `keycloak_vkid_client`, решение 18 с известными ограничениями), versions.md (строки `keycloak-spi` и `keycloak-curl`: базы этапов сборки), `check_compose.py` (несколько баз сборки у одного контейнера).

*Что проверить:*

- `check_realm.py` проходит и ловит намеренные ошибки (срок токена, перебор, TLS, политика паролей, второй фактор не у той роли, область не той роли, секрет значением, `amr` без срока, ручная правка файла).
- В CI Keycloak собирается и поднимается, realm импортируется, токен тестового пользователя содержит `aud`, `scope`, `phone_verified`, `amr`; повторный запуск пропускает импорт.
- Токен продавца без второго фактора не выдаётся (ST-13 готовится, полная проверка в Ф4).
- Модульные тесты клиента входа (`make keycloak-test`): TOTP по векторам RFC 4226 и RFC 6238, PKCE, разбор страниц.

**Commit:** `infra: Keycloak, realm как код, проверка realm`.

*Что уметь объяснить:*

- Чем отличаются OAuth2, OpenID Connect и JWT.
- Что такое область (scope), аудитория (aud) и `amr`.
- Почему realm хранится как код и как избегается дрейф настроек (генератор, проверка против документа, импорт только на пустой базе, удаление realm для повторного импорта).
- Почему условия «OTP, если настроен» нет в потоке входа.

## Шаг 11. Библиотека `service-kit`

**Файлы:** `libs/service-kit/**`, тесты.

**11.1. Компоненты** (c4-components, раздел «Общая библиотека»):

- `jwt-filter`: проверка подписи, `iss`, `aud`, срока и областей.
- `caller-filter`: сопоставление CN сертификата вызывающего сервиса с разрешённым списком операций (mTLS).
- `trace-filter`: сквозной идентификатор запроса, ответы по RFC 9457 (`application/problem+json`).
- `outbox-relay`: публикация событий из таблицы Outbox в Kafka с идемпотентным производителем ([ADR-005](05-architecture/adr/ADR-005-transactional-outbox.md)).
- `event-consumer`: обработка с таблицей обработанных событий, повторами через 1, 5 и 25 секунд и очередью DLQ ([ADR-011](05-architecture/adr/ADR-011-guaranteed-delivery.md)).
- `SecretValue` (не попадает в журнал), `Clock` (подменяется в тестах), настройки TLS для Postgres, Kafka и Redis из секретов.

**11.2. Правила ArchUnit.** Сервис не обращается к таблицам другого модуля, не пишет секреты в журнал, не использует системные часы напрямую (decomposition, conventions).

**11.3. Тесты.** Модульные (`test`, задание `build`) и интеграционные (`integrationTest`, задание `kit`). Интеграционные идут на настоящих PostgreSQL и Kafka поднятого стенда по TLS, с клиентским сертификатом сервиса и правами по CN (решение 11 стратегии тестирования: Testcontainers повторил бы настройку стенда второй раз): отправка из Outbox в Kafka по порядку, перехват блокировки лидера, повторы с задержкой и «парковка» после десяти неудач, чтение события потребителем, повторная доставка, повторы 1, 5, 25 секунд и DLQ. Модульные тесты: отказ при неверной подписи, чужом издателе, чужой аудитории, истёкшем сроке, неверных областях и ролях, вызывающем сервисе не из списка, запрещённых символах в пути, а также каждое правило ArchUnit на заведомо плохом классе.

*Что проверить:*

- Тесты в CI зелёные. Количество и перечень тестов указаны в отчёте.
- Намеренное нарушение правила ArchUnit в песочной ветке даёт красный запуск.
- Нет `System.currentTimeMillis` и `Instant.now()` вне `Clock`.

**Commit:** `lib: service-kit (jwt, caller, trace, outbox, consumer, SecretValue, Clock, ArchUnit)`.

*Что уметь объяснить:*

- Как работает Transactional Outbox и от какой ошибки защищает.
- Что такое идемпотентный потребитель и зачем DLQ.
- Чем общая библиотека полезна и в чём её риск (связанность версий).

Чего в таблице нет, то получает 404; `/internal/**` и `/actuator/**` наружу не открываются никогда.

**13.2. Один фильтр.** `EntryFilter` выполняет по порядку: сквозной идентификатор, проверку пути (строгую для `/api`, `/internal`, `/auth`, `/actuator`), маршрут, размер тела по `Content-Length`, токен (`iss`, `aud=dgm-api`, срок, подпись по ключам Keycloak, ленивая загрузка и кэш; алгоритм `none`, чужие ключи и изменённые токены отклоняются тем же декодером, что в сервисах), области, второй фактор и запрет сессии по SMS, лимит частоты, очистку внешних заголовков. Подробная таблица в ADR-021, раздел «Реализация».

**13.3. Ограничение частоты.** `RedisRateLimiter` Spring Cloud Gateway, 11 групп лимитов (ключ пользователь из токена или IP), перевод «запросов в минуту» в корзину токенов в секунду (запрос стоит `60 / НОД(лимит, 60)` токенов). Ответ 429 с `Retry-After`. Redis не отвечает за 200 мс или вернул ошибку: запрос проходит, счётчик `dgm_gateway_ratelimit_failopen_total` растёт (fail-open).

**13.4. Порты и заголовки.** 8443 снаружи (TLS 1.3 и 1.2, клиентский сертификат не нужен), к сервисам mTLS с проверкой имени, 8444 метрики и здоровье (mTLS, отладочный 127.0.0.1:18446), проба готовности `/ready` на 127.0.0.1:8081. HSTS, `nosniff`, `DENY` и `no-referrer` в каждом ответе, `traceparent` и `X-Correlation-Id` в каждом ответе и в запросе к сервису. Ошибки любого рода выходят как `Problem` (RFC 9457): сервис не отвечает 503, не успел 504.

**13.5. Тесты.**

- Задание `build`, модульные: `RouteTableTest` (таблица), `EntryFilterTest` (фильтр целиком без сети: ST-03 подделки, области, 2FA, SMS, лимиты, отказ открытым, заголовки), `RedisRequestLimiterTest` (перевод лимитов), `GatewayProxyTest` (Spring Boot, настоящие Spring Cloud Gateway и Netty, заглушки сервисов на локальных портах), `GatewayArchitectureTest` (правила каркаса и правило тонкого шлюза). Образ проверяется статически (`check-image.sh ... static`): без секретов шлюз, как и сервисы, не стартует.
- Задание `gateway`, стенд: `make up SET=dev-auth DEBUG=1` (Keycloak, Redis, шлюз), `make up SET=dev-purchase DEBUG=1` (сервисы), `make keycloak-users`, `make gateway-check`. Настоящий вход Keycloak выдаёт токены покупателя и продавца: через шлюз проходят витрина без токена и защищённый маршрут с токеном (сервис проверяет токен второй раз), подделки (подменённый `sub`, дописанная область, подправленный срок, `alg=none`, испорченная подпись) получают 401, чужая роль и область 403, большое тело 413 до чтения, `/internal/**`, `/actuator/**`, консоль Keycloak и realm `master` 404 (также при записи символов через `%6d`, `;`, `//`). Вход по коду авторизации проходит через сам шлюз. Лимиты: `POST /orders` 10 в минуту на пользователя и независимость пользователей и групп, вход Keycloak 30 в минуту с IP, возврат к 200 после `Retry-After`. Порт управления без клиентского сертификата не отвечает, метрики отказов и задержек читаются. Затем Redis останавливается: запросы идут (отказ открытым), метрика растёт, готовность остаётся UP; Redis запускается, и лимиты возвращаются без перезапуска шлюза. Контейнер: пользователь 10001, чтение только, 320 МБ, порты, сети, пароль Redis не в окружении и журналах, токены не в журнале, JSON, TLS 1.1 отклоняется.

*Что проверить:*

- Тесты шлюза зелёные: запрос без токена 401, с чужим издателем 401, без области 403, превышение лимита 429.
- ST-03 в виде тестов JUnit и проверок на стенде: алгоритм `none`, чужой издатель, просроченный токен, изменённая область.
- Задание `gateway` зелёное, заметка с памятью шлюза после проверок.

**Commit:** `gateway: Spring Cloud Gateway, проверка JWT и ограничение частоты (ADR-021)`.

*Что уметь объяснить:*

- Зачем шлюз и чем он отличается от «толстого» шлюза с бизнес-логикой.
- Что означает fail-open и в каких случаях выбирается fail-closed (шлюз: лимит по IP открытый, коды подтверждения SMS в `platform-service` закрытый).

## Шаг 17. Дымовой тест и финализация CI

**Файлы:** `tools/stand-checks/smoke.py`, `tools/stand-checks/stateless_check.py`, `tools/ci/smoke-sabotage.sh`, `docs/08-testing/nft-phase3.md`, `tools/docs-checks/check_workflows.py`, `tools/docs-checks/check_nft.py`, `.github/workflows/ci.yml`, `.github/dependabot.yml`; в Java журнал обращений (`AccessLogFilter` каркаса и `EntryFilter` шлюза).

**17.1. Журнал обращений.** Чтобы сквозной идентификатор можно было найти в журналах, каждый сервис и шлюз пишут по строке INFO `dgm.access` на ответ: метод, путь без строки запроса, статус, время в мс; идентификатор в поле MDC `correlationId` (у шлюза в тексте строки). Фильтр каркаса стоит сразу после `TraceFilter` и до проверки токена, поэтому в журнале есть и отказы безопасности.

**17.2. Дымовой тест (`make smoke`).** Один проход через каждый слой за минуту:

1. токен покупателя от Keycloak по коду авторизации с PKCE, запросы идут через шлюз;
2. три операции: страница `/`, витрина (ETag и 304), история заказов с токеном (в `order_db` лежит служебный заказ, его видит владелец и не видит другой покупатель, U1), плюс отказы: без токена 401, `/internal/**` закрыт;
3. ST-03: токен без подписи, HS256, чужой ключ RSA с верным издателем, чужой издатель, изменённая область и `sub`, настоящий токен Keycloak после истечения срока (срок клиента сокращается на время одного входа через Admin API и возвращается);
4. mTLS внутреннего вызова из контейнера в сети `app`: `order-service` проходит фильтр вызывающего, другой сервис с сертификатом нашего центра получает 403, без сертификата рукопожатие не проходит;
5. Outbox → Kafka: служебная строка в `outbox` базы `order_db` публикуется `order-service`, маркер читается из темы `order.events` потребителем `delivery-service` (по ACL), конверт CloudEvents сверяется со строкой;
6. один `X-Correlation-Id` виден в журналах шлюза и сервиса, `trace id` из заголовка ответа совпадает со строкой сервиса, при поднятом стеке наблюдения тот же идентификатор находится в Loki по меткам обоих сервисов.

Проверка проверки: `make smoke-sabotage` запускает тест в режимах `SMOKE_SABOTAGE=token|scope|cert` (испорченная подпись токена, токен продавца без области `orders.read`, внутренний вызов с сертификатом чужого сервиса), каждый обязан дать красный результат.

**17.3. Проверки NFT этапа** описаны в [nft-phase3.md](08-testing/nft-phase3.md): метод, порог и задание CI для NFT-1.3, 3.0, 3.1, 3.3, 3.5 и ST-03, ST-14; `check_nft.py` проверяет, что названные проверки существуют. Остальные требования закрываются проверками шагов 8–15, которые теперь собраны в одной таблице. Номера запусков CI записываются в отчёт на шаге 20.

## Если что-то пошло не так

| Проблема | Что делать |
| --- | --- |
| Запуск CI красный, причина неясна | Читайте аннотации задания и шага. Если диагностики нет, добавьте её через `diag.sh` и повторите запуск. Не угадывайте |
| Образ не скачивается в CI | Проверьте имя и версию в `versions.md`. Если образ удалён автором, это находка для ADR (как с MinIO), а не повод брать «похожий» |
| Контейнер завершается по OOM | Не повышайте лимит вслепую: снимите пик (`docker stats`), сравните с правилом 85 % и запишите причину в бюджет |
| Сервис не стартует из-за TLS | Проверьте SAN сертификата (имя контейнера в сети), срок, права файла секрета `0400`, совпадение центра сертификации |
| Токен не проходит на шлюзе | Сравните `iss` и `aud` с realm, часы контейнеров, доступность ключей Keycloak (кэш) |
| Проверка документов красная после правки кода | Код разошёлся с документом: решите, что правильно, правьте один из них отдельным commit |
| `main` не принимает push | Ветка ушла вперёд. Получите изменения, пересоберите bundle, не переписывайте историю |
| Запуск на ноутбуке падает по памяти | Используйте набор меньше (`dev-min`), проверьте лимит `.wslconfig`, закройте лишнее. Сумма лимитов набора должна помещаться в таблицу бюджета |
