# Глоссарий

Единые термины проекта. Определения согласованы с [требованиями v1.4](../02-requirements/requirements_v1.4.md): если определение здесь расходится с требованиями, правится глоссарий или выпускается новая версия требований. Точные условия переходов между статусами описываются в статусных моделях (`docs/03-processes/`).

Термины сгруппированы по темам, внутри групп идут по алфавиту. Последний столбец показывает, где термин определяется или используется в требованиях.

## 1. Роли

| Термин | Определение | Источник |
| --- | --- | --- |
| Администратор | Сотрудник платформы: управляет ролями, параметрами (комиссия, сроки, лимиты), обрабатывает заявки на вывод, следит за зависшими заказами, смотрит журнал аудита | Раздел 3 |
| Гость | Посетитель без учётной записи: может искать товары, смотреть карточки, регистрироваться и входить | Раздел 3 |
| Модератор | Сотрудник платформы: проверяет заявки продавцов и товары, решает споры, блокирует продавцов и товары | Раздел 3 |
| Оператор поддержки | Сотрудник платформы: обрабатывает обращения по заказам, повторно отправляет ключ, меняет e-mail покупателя после подтверждения кодом | Раздел 3, FT-7.5 |
| Покупатель | Зарегистрированный пользователь, оформляющий заказы. Для всех действий покупателя нужна регистрация | Раздел 3 |
| Продавец | Пользователь с одобренным профилем: размещает товары, загружает ключи, видит заказы и баланс, подаёт заявки на вывод | Раздел 3 |
| Система | Служебный актор: автоматические задачи (резерв и его снятие, выдача, письма, расчёт комиссии, разблокировка средств, повторы, оповещения) | Раздел 3 |

## 2. Каталог и ключи

| Термин | Определение | Источник |
| --- | --- | --- |
| Витрина | Публичная часть каталога: на ней показываются только опубликованные товары | FT-3.1 |
| Ключ | Единица цифрового товара: код активации, лицензия, код подарочной карты. Хранится в зашифрованном виде и после загрузки не отображается в интерфейсе. Статусы: свободен, зарезервирован, выдан, аннулирован | FT-4.2, раздел 6.1 |
| Модерация | Ручная проверка заявок продавцов и товаров модератором до появления на витрине. Срок проверки не более 3 суток | FT-2.1, FT-3.2 |
| Остаток | Для товара с пулом: число свободных ключей. Для товара с выдачей по API: число, которое задаёт продавец, оно уменьшается при оформлении заказа и восстанавливается при отмене или истечении резерва | FT-4.3 |
| Профиль продавца | Анкета подключения: тип (ИП, самозанятый, юрлицо), наименование, реквизиты, документы, описание ассортимента. Статусы: черновик, на проверке, на доработке, одобрен, отклонён, заблокирован | FT-2.0, раздел 6.1 |
| Пул ключей | Набор ключей одного товара, загруженный продавцом вручную или файлом CSV. Размер до 100 000 ключей. Дубликаты в пределах товара отклоняются | FT-4.1, раздел 2.2 |
| Способ выдачи | Как товар попадает к покупателю: из загруженного пула ключей или по запросу к API продавца (R2). Задаётся для каждого товара | FT-4.0 |
| Товар | Предложение продавца: название, описание, тип (ключ игры, лицензия ПО, подарочная карта или пополнение, подписка), платформа, регион активации, цена, способ выдачи. Статусы: черновик, на модерации, опубликован, отклонён, заблокирован, архив | FT-3.0, FT-3.1 |

## 3. Заказ и оплата

| Термин | Определение | Источник |
| --- | --- | --- |
| Автовозврат | Возврат денег покупателю по решению самой системы, без участия оператора или модератора. В R1 применяется при поздней оплате, если выдать товар невозможно. Возврат идемпотентен, при сбое шлюза повторяется, при исчерпании попыток попадает в очередь администратора | FT-6.4 |
| Заказ | Покупка одного товара одного продавца в количестве от 1 до 10 штук, оплачиваемая одним платежом. Корзины нет (ADR-001) | FT-5.0, FT-5.1 |
| Платёжная сессия | Период, в течение которого покупатель может оплатить заказ через шлюз. По умолчанию 12 минут, настраивается и всегда короче резерва, чтобы запас в 3 минуты покрывал задержку уведомления шлюза | FT-5.2 |
| Платёжный шлюз | Внешняя система приёма платежей и возвратов. Хранит данные карт, мы их не храним | FT-6.0, NFT-5.1 |
| Поздняя оплата | Подтверждение платежа от шлюза пришло после того, как резерв был снят и заказ отменён. Система пытается заново зарезервировать ключи: при успехе заказ продолжается как обычный оплаченный, при неудаче выполняется автовозврат | Раздел 4, FT-6.5 |
| Резерв | Временное закрепление ключей за заказом на время оплаты, чтобы их не получил другой покупатель. По умолчанию 15 минут, настраивается. Неоплаченный заказ отменяется, резерв снимается | FT-5.2, FT-6.3 |
| Снимок адреса доставки | E-mail покупателя, зафиксированный в заказе при оформлении. При повторной отправке по обращению снимок обновляется | Раздел 4, FT-7.5 |

**Статусы заказа.** Точные условия переходов описываются в статусной модели SM-01.

| Статус | Значение |
| --- | --- |
| Создан | Заказ оформлен, ключи зарезервированы |
| Ожидает оплаты | Платёжная сессия открыта, подтверждение оплаты ещё не получено |
| Оплачен | Шлюз подтвердил платёж, выдача ещё не завершена |
| Выдан | Ключ привязан к заказу, и письмо с ключом принято почтовым провайдером (статус выдачи «отправлено»). Первичный переход в этот статус открывает окно обращения в поддержку (72 часа), окно спора (72 часа) и срок удержания средств (7 дней). Повторная отправка эти сроки не сдвигает |
| Отменён | Заказ закрыт без выдачи товара: оплата не поступила в срок, оплата отклонена или снят резерв. Если подтверждение оплаты придёт позже, действует правило поздней оплаты |
| Возвращён | Деньги покупателю возвращены через шлюз |

## 4. Выдача и поддержка

| Термин | Определение | Источник |
| --- | --- | --- |
| Выдача | Передача ключа покупателю: привязка ключа к заказу и отправка письма. В модели данных это сущность «Выдача», которая фиксирует каждую попытку (первичную или повторную по обращению), канал, адрес и статус | FT-7.0, раздел 6.1 |
| Доставка | Подтверждение почтовым провайдером того, что письмо попало в почтовый ящик покупателя. Статус выдачи «доставлено». По нему измеряется цель BG-01. Не путать со статусом заказа «выдан» | Раздел 4, NFT-2.1 |
| Обращение в поддержку | Запрос покупателя по заказу, если ключ не получен. Покупатель создаёт его из личного кабинета в течение 72 часов после выдачи (срок настраивается). Заказ с недоставленным письмом попадает в очередь поддержки автоматически | FT-7.2, FT-7.3 |
| Одноразовый код | Код подтверждения (SMS или e-mail): действует не более 5 минут, число попыток ввода ограничено (по умолчанию 5) | NFT-3.7 |
| Очередь поддержки | Список обращений и заказов с проблемной доставкой, который разбирают операторы | FT-7.3 |
| Подтверждение телефона | Проверка номера кодом из SMS. Выполняется до оформления первой покупки, номер привязывается к учётной записи | FT-1.5 |
| Повторная отправка | Действие оператора по обращению: тот же ключ отправляется ещё раз. Ключ оператору не показывается | FT-7.5 |

**Статусы выдачи:** в очереди, отправлено, доставлено, ошибка.

## 5. Споры (R2)

| Термин | Определение | Источник |
| --- | --- | --- |
| Спор | Претензия покупателя по выданному заказу. Открывается в течение 72 часов после выдачи с указанием причины. Продавец может ответить, модератор принимает решение за 24 часа: возврат, отказ в возврате или замена ключа. Пока спор открыт, деньги по заказу недоступны к выводу | FT-8.0…FT-8.4 |

## 6. Финансы продавца

| Термин | Определение | Источник |
| --- | --- | --- |
| Баланс продавца | Начисления за выданные заказы за вычетом комиссии. Все движения фиксируются в неизменяемом журнале | FT-9.2, FT-9.4 |
| Вывод средств | Заявка продавца на выплату от 1 000 ₽. Статусы: создана, на проверке, выплачена, отклонена. Администратор обрабатывает заявки вручную | FT-9.3 |
| Комиссия | Доля с каждого заказа, которую получает платформа. По умолчанию 2%, настраивается администратором | FT-9.0 |
| Удержание | Срок, в течение которого деньги по выданному заказу недоступны к выводу: 7 дней с первичного перехода заказа в статус «выдан» | FT-9.2 |
| Шкала комиссии | Ставки по месячному обороту продавца: до 300 тыс. ₽ — 2%, от 300 тыс. до 1 млн ₽ — 1,5%, свыше 1 млн ₽ — 1%. Пороги и ставки настраиваются (R3) | FT-9.1 |

## 7. Интеграция и администрирование

| Термин | Определение | Источник |
| --- | --- | --- |
| API-ключ продавца | Секрет для доступа продавца к API платформы. Хранится в виде хеша и показывается один раз при выпуске. Продавец может выпустить и отозвать ключ | FT-10.0, NFT-3.4 |
| Webhook | Уведомление, которое платформа отправляет на адрес продавца о заказах и спорах | FT-10.3 |
| Журнал аудита | Неизменяемый журнал действий администраторов, модераторов и операторов поддержки. Не содержит персональных данных в открытом виде: для персональных полей хранятся ID объекта, имя поля и HMAC-хеш | FT-11.2, NFT-5.3 |
| Параметры платформы | Настройки, которые меняет администратор: комиссия, время резерва, срок платёжной сессии, лимиты, сроки | FT-11.1 |
| Заглушка | Эмуляция внешней системы (платёжный шлюз, e-mail, SMS, VK ID, банк), которая заменяет её в проекте | Раздел 2.2 |
| 2FA | Двухфакторная аутентификация: обязательна для продавца, модератора, оператора поддержки и администратора | FT-1.3 |

## 8. Технические термины

| Термин | Определение |
| --- | --- |
| ADR | Запись архитектурного решения: контекст, рассмотренные варианты, решение, последствия, условие пересмотра |
| BPMN | Нотация для моделирования бизнес-процессов |
| CQRS | Разделение моделей записи и чтения. У нас упрощённый вариант: отдельная модель чтения для истории заказов и очереди поддержки, обновляется по событиям |
| Correlation-id | Сквозной идентификатор, по которому один заказ прослеживается через логи и трассировку всех сервисов (NFT-6.0) |
| DLQ (очередь недоставленных сообщений) | Очередь, куда попадают сообщения, которые не удалось обработать после всех повторов. Их разбирают отдельно |
| HMAC | Код на основе хеша и секретного ключа сервера. Используется вместо обычного хеша для проверки дублей ключей: без секрета короткие значения нельзя подобрать перебором |
| Idempotency (идемпотентность) | Свойство операции: повторная обработка того же события или запроса даёт тот же результат и не создаёт дублей (FT-6.2, NFT-2.3) |
| Оптимистичная блокировка | Запись содержит номер версии. При обновлении проверяется, что версия не изменилась, иначе конфликт. Применяется для остатка товаров с выдачей по API |
| Пессимистичная блокировка (`FOR UPDATE SKIP LOCKED`) | Строка блокируется на время операции, строки, уже занятые другими транзакциями, пропускаются. Позволяет параллельно резервировать разные ключи и не выдать один дважды |
| Перцентиль (p95) | Значение, которое не превышают 95% измерений. Например, p95 = 300 мс означает, что 95% запросов быстрее 300 мс |
| RPO / RTO | Допустимая потеря данных при сбое и допустимое время восстановления. У нас не более 15 минут и не более 1 часа (NFT-4.1) |
| Retry (повторы) | Повторные попытки операции с нарастающей задержкой между ними |
| Saga | Способ довести до конца сценарий, затрагивающий несколько сервисов, цепочкой локальных транзакций с компенсирующими действиями при сбое. У нас: резерв → оплата → выдача, с откатом резерва и возвратом денег |
| Transactional Outbox | Событие записывается в ту же транзакцию базы, что и изменение данных, и затем отдельным процессом публикуется в Kafka. Событие не теряется, если сервис упал после записи |
