# Ф4, срез 3 «Поддержка, аудит, администрирование»: пошаговый план

**Для кого:** системный аналитик, который ведёт проект. Срезы 1 «Продавцы, товары, ключи» и 2 «Заказ, оплата, выдача» закрыты, итоги в [отчёте среза 1](00-phase4-slice1-report.md) и [отчёте среза 2](00-phase4-slice2-report.md).
**Время:** около 37 часов (разброс 33 – 41) по факту срезов 1 и 2; по таблице шагов 82 часа. Расчёт и его последствия для вехи M4 в разделе «Время по шагам».
**Результат:** срез 3, последний срез Ф4. Работающие сценарии «покупатель не получил ключ → обращение → оператор берёт в работу → повторная отправка или смена e-mail по двум подтверждениям → ключ доставлен, обращение решено» и «администратор меняет параметр → сервисы подхватывают его без перезапуска → действие видно в журнале аудита без персональных данных». Письма покупателю и продавцу по решениям платформы, три экрана (покупатель, оператор, администратор), тесты, зелёный CI, документы, совпадающие с кодом, и закрытие Ф4: демо R1, отчёты, прогноз.

Этот документ описывает только срез 3. Фазу закрывает шаг 24: демо «от каталога до ключа на почте, плюс поздняя оплата и сбой доставки», итоговый отчёт Ф4 и решение по серверу.

**О порядке работы.** [Отчёт среза 2](00-phase4-slice2-report.md) (раздел 11) обещал писать это руководство отдельно. Вы сказали «продолжим» 25 октября, поэтому оно написано сразу, а ответ на вопрос «что резать» (решение D-14) остаётся вашим и не блокирует старт: таблица сокращений в разделе «Время по шагам» работает при любом ответе. Ручной проход демо срезов 1 и 2 остаётся открытым пунктом: если он покажет расхождения с живым стендом, они записываются в раздел 6 [demo-slice1.md](09-operations/demo-slice1.md) и разбираются на шаге 2 или перед ним.

**Главная идея среза: платформа должна уметь доказать, что произошло, и безопасно позволить человеку вмешаться.** В срезах 1 и 2 всё делали автоматы. В срезе 3 появляются люди с правом изменить чужой заказ, чужой адрес и параметры платформы, а значит, три вещи, которые надо уметь объяснить на собеседовании. Первая: **журнал аудита как поток событий** (Transactional Outbox → тема `audit.events` → потребитель → таблица, в которую можно только добавлять, [ADR-014](05-architecture/adr/ADR-014-audit-log-no-pii.md)): действия без записи не бывает, а записи без персональных данных нельзя испортить задним числом. Вторая: **смена e-mail как доказательство владения двумя независимыми каналами** (код в SMS на подтверждённый телефон и код на новый адрес, [ADR-010](05-architecture/adr/ADR-010-keycloak-sms-codes.md)): оператор запускает смену, но не видит кодов и не может провести её сам. Третья: **конфигурация как событие** (сжатая тема `platform.config`, слушатели в сервисах, версия вместо метки времени): параметр меняется без выпуска версии, а инвариант «платёжная сессия короче резерва» (INV-07) охраняется и при сохранении, и при применении. Отдельная линия среза это **упрощённый CQRS** ([ADR-017](05-architecture/adr/README.md), пишется на шаге 2): очередь поддержки читается из проекции, которую ведут события, а не из таблиц чужих сервисов.

**Правило среза: чтение чувствительного тоже действие.** Журнал аудита и документы продавца сами записывают, кто их открыл (F9-4, F9-5, угроза T-35). Если запись не удалась, данные не отдаются: безопаснее отказать, чем показать без следа.

## Ограничения среды

Те же, что в срезах 1 и 2 ([руководство среза 1](00-phase4-guide.md), раздел «Ограничения среды», [руководство среза 2](00-phase4-slice2-guide.md)): **Java, Docker и npm проверяются только в GitHub Actions**, итерации идут в ветке `ci/sandbox`, диагностика читается по аннотациям, один полный запуск около 12 минут. Что меняется в срезе 3:

| Что | Следствие |
| --- | --- |
| Новых контейнеров нет | Все шаги идут на существующем наборе `full` (по лимитам 4832 МБ). Память не растёт, но `platform-service` получает три новых нагрузки (потребитель журнала, читатель очереди, слушатель конфигурации), поэтому его пик в замерах шагов 8, 17 и 21 смотрится отдельно (на К5 он был 262 из 352 МБ, 74 %) |
| Коды подтверждения нельзя прочитать из Redis | В Redis лежит только HMAC кода (`otp_pepper`). Проверки стенда берут код из журнала заглушек SMS и почты (команды чтения порта 8444 `stubs_admin.py`), как проверка телефона среза 1. Срок кода 5 минут проверяют модульные тесты на управляемых часах (NFT-3.7), на стенде ждать нечего |
| Лимиты кодов общие с адреса (F4-10) | Покупателей и сотрудников для проверок готовим без запроса кодов, через Keycloak Admin API с атрибутом `phone_verified`; сам путь «код в SMS» проходит один покупатель на сценарий, между сценариями пауза `UI_AUTH_GAP` (F4-22) |
| Сессия по SMS ограничена | Покупатель, вошедший по коду из SMS, может создавать обращение и вводить коды, но не оформляет заказ и не видит историю (`x-sms-session` в контрактах). Проверка идёт на стенде и в Newman |
| Тема `platform.config` сжатая | Читать её надо с начала, а на общем стенде CI в ней лежат значения соседних проверок. Слушатель применяет только версию выше сохранённой, а проверки стенда возвращают параметры к значениям по умолчанию в конце сценария (как заглушки в срезе 2) |
| Сроки в минутах | Окно обращения 72 часа и удержание записываются параметрами и проверяются сдвигом `Clock` в модульных тестах и записью параметра `support.window-seconds` меньше обычного на стенде; реальные сроки на стенде не ждём |

## Шаг 12. `delivery-service`: повторная выдача по `order.address-updated`

**Файлы:** `services/delivery-service/src/main/java/dgm/delivery/delivery/{handler,service,domain,repository}/**`, `LATER_CONSUMERS` (убрать пару), тесты, `TC-delivery.md`.

**12.3. Конкуренция.** Два одинаковых события `order.address-updated` подряд (повтор Kafka и повторный щелчок оператора с другим ключом): одна выдача `queued`, второе событие пропущено; серия из 50 повторов.

**TC этого шага.** Следующие номера `TC-delivery.md`: повторная выдача создаётся по событию, дубль события не создаёт второй выдачи, письмо с ключом уходит на новый адрес, значений ключей нет нигде кроме письма (канарейка ST-01 охватывает повторное письмо).

*Что проверить:*

- Запасной контроль без индекса `uq_delivery_order_id_queued`: тест двух событий красный.
- Повторная выдача не создаёт запись контроля 30 минут и не двигает `delivery.overdue`.
- Пара `delivery-domain` и `order.address-updated` ушла из `LATER_CONSUMERS`, `check_code_docs.py` проходит.

**Commit:** `feat(delivery): повторная выдача по order.address-updated (Р-170)`.

*Что уметь объяснить:*

## Шаг 13. `resendKeyForTicket`: повторная отправка ключа по обращению

**Файлы:** `dgm.platform.support.service.ResendService`, клиент вызова соседа (`OrderClient`), `controller`, тесты, `TC-support.md`.

**13.1. Проверки (быстрые, по проекции).** Обращение `in_progress` и взято этим оператором, иначе 409 `ticket-not-in-progress` (US-7.3, сценарий 5: действия только по обращению); заказ `issued`, иначе 409 `state-conflict`; выдачи в очереди нет, иначе 409 `delivery-in-progress` («дождаться результата», сценарий 4).

**13.2. Решение до вызова (Р-165, правило 16).** Короткой транзакцией пишется `audit.recorded` с кодом `support.resend-requested` (оператор, роль, обращение, заказ, время, IP оператора как есть, e-mail нет) и `ticket.action = resend`; транзакция закрывается **до** вызова соседа.

**13.3. Ключ идемпотентности выводится из номера обращения и `order_view.delivery_updated_at` (Р-170). Ответ платформе 202: исход виден в статусе выдачи обращения. Недоступность `order-service` даёт 503 и повтор оператором с тем же ключом без дублей.

**13.4. Окна не сдвигаются.** Окно 72 часа, окно спора и удержание 7 дней считаются от первичной выдачи (US-7.1, сценарий 3).

## Если что-то пошло не так

| Что случилось | Что делать |
| --- | --- |
| Сервис не применяет изменённый параметр | Смотрите `config_version{key}` и `config_rejected_total{key,reason}` сервиса, закреплён ли ключ (`dgm.config.pinned-keys`, только в профиле `fast-time`), нет ли ответа `stale-config`; тема `platform.config` читается с начала, переиздание значений делает платформа при старте |
| Администратор не может сохранить срок резерва или сессии | Это INV-07: сессия строго короче резерва. Сначала поднимите резерв, затем сессию (и наоборот при уменьшении); 422 называет границы |
| Журнал аудита пуст, хотя действия были | Смотрите `audit_records_total`, тему `audit.events` и `audit.events.dlq`, права `app_audit_writer`, секции (`audit_default_rows`); запись с открытым персональным значением уходит в DLQ |
| `UPDATE` или `DELETE` по журналу «прошли» | Этого быть не должно: проверьте триггеры `trg_audit_log_no_*` на таблице и секциях, ST-09 должен быть красным без них |
| Два оператора взяли одно обращение | Проверьте условие `status = 'created'` в `UPDATE` и тест гонки; запасной контроль без условия должен краснеть |
| Повторная отправка создала две выдачи | Проверьте индекс `uq_delivery_order_id_queued` и обработчик `order.address-updated` (`already-queued`); ключ идемпотентности вызова выводится из состояния проекции |
| Смена e-mail «зависла» после падения | Состояние «подтверждён, не завершён»: повторите завершение, коды заново не нужны; `IdentityReconciler` завершит этап старше 60 секунд |

| Память набора `full` не помещается | Не режьте лимиты задним числом. Запишите замер в `memory-measurements.md` и решите по Р-145: WSL 5 ГБ или сервер |
| CI дольше 12 минут | Не запускайте полную сборку на каждый commit: документы проверяйте локально, код пачками по связанным изменениям |
| Срез не помещается в часы | Не режьте тесты и документы молча. Таблица сокращений в разделе «Время по шагам», решение принимаете вы после К9 |
| Нашли расхождение документа и кода | Раздел «Если нашли расхождение» среза 1: решение отдельным commit и строка в отчёте |
