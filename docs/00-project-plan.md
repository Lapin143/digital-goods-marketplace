# План проекта: маркетплейс цифровых товаров

| | |
| --- | --- |
| **Основание** | Требования к системе v1.5 (`docs/02-requirements/requirements_v1.5.md`) |
| **Репозиторий** | `digital-goods-marketplace` |

План отвечает на три вопроса: что мы делаем, в каком порядке и как понимаем, что очередной этап закончен.

---

## 1. Цель проекта и критерии готовности

**Цель.** Построить маркетплейс цифровых товаров на микросервисной архитектуре с полным комплектом аналитической и архитектурной документации и рабочим демо-стендом. Проект показывает путь от бизнес-целей до работающей системы и объясняет, зачем выбрана каждая технология.

**Проект завершён, когда выполнено всё из списка:**

- Релизы R1, R2 и R3 из требований v1.5 работают на демо-стенде, доступном по публичной ссылке.
- Комплект документации из раздела 10 полный и лежит в репозитории.
- Матрица трассировки заполнена без пустых клеток: каждое требование R1–R3 связано с user story, процессом, API или событием и тест-кейсом.
- Автотесты зелёные в CI: unit и интеграционные (Testcontainers). Отдельно есть набор API-тестов (Postman/Newman) и нагрузочные сценарии (k6), включая проверку «ни одного ключа дважды».
- Есть видео-демо на 5 минут, README с быстрым запуском и «история проекта» с ответами на вопрос «зачем здесь эта технология?».

## 2. Принципы

1. **Документация в репозитории.** Markdown, диаграммы как код (Mermaid), контракты в YAML, BPMN в файлах `.bpmn`. Документ обновляется в той же итерации, что и код.
2. **Сначала аналитика, потом код.** Фазы Ф1 и Ф2 завершаются до первой строки кода. Код проверяется на соответствие документам, а не наоборот.
3. **Сквозная трассировка.** Цель (BG) → требование (FT/NFT) → user story → процесс → API или событие → тест-кейс. Веха закрывается только при заполненной матрице.
4. **После каждой вехи есть то, что можно показать.**
5. **Технология попадает в проект, только если у неё есть задача в нашем домене.** Остальное остаётся в ADR как рассмотренная альтернатива.
6. **Готовое важнее большого.** Если время поджимает, сокращаем объём по правилу из Ф6, а не растягиваем срок.

## 4. Технологическая карта

Каждая технология привязана к задаче домена и к фазе, где она появляется.

### Уровень 1. Ядро

| Технология | Задача в проекте | Фаза |
| --- | --- | --- |
| REST + OpenAPI | Публичное API и API продавца. Контракты пишем первыми | Ф2, Ф4 |
| PostgreSQL + Flyway | База на каждый сервис (один сервер, отдельные базы), миграции. Блокировка `FOR UPDATE SKIP LOCKED` на пуле ключей | Ф3, Ф4 |
| Kafka | События между сервисами: заказ оплачен, ключ выдан, письмо отправлено и другие | Ф3, Ф4 |
| Saga | Резерв → оплата → выдача с компенсациями (снятие резерва, автовозврат) | Ф4 |
| Transactional Outbox | Событие не теряется, если сервис упал после записи в базу | Ф4 |
| Идемпотентность | Повторное уведомление шлюза или повторное событие не создаёт дублей | Ф4 |
| Retry + DLQ | Повторы отправки письма с нарастающей задержкой, недоставленное уходит в поддержку | Ф4 |
| Пессимистичная и оптимистичная блокировки | Пул ключей (блокировка строки) и остаток API-товаров (версия записи) | Ф4, Ф5 |
| Redis | Таймеры резервов (источник истины в PostgreSQL), кэш каталога, ограничение частоты запросов | Ф4 |
| Keycloak (OAuth2, JWT) | Пять ролей, 2FA, вход через VK ID (эмуляция), подтверждение телефона | Ф3, Ф4 |
| API Gateway | Единая точка входа, проверка токенов, ограничение частоты | Ф3 |
| Docker + Compose | Запуск одной командой, профили | Ф3 |
| GitHub Actions | Сборка, тесты, публикация образов | Ф3 |

### Уровень 2. Усиление

| Технология | Задача в проекте | Фаза |
| --- | --- | --- |
| MinIO (S3) | Документы продавцов. Нужен уже в R1 (FT-2.0). Файлы CSV с пулами ключей не хранятся, загрузка потоком (ADR-009) | Ф3 |
| CQRS (упрощённо) | Отдельная модель чтения для истории заказов и очереди поддержки | Ф4 (срез 3), Ф5 |
| gRPC | Вызов резерва «Заказы → Остатки и ключи». Сначала REST, затем замер k6 и сравнение с gRPC, итог в ADR | Ф5 |
| Версионирование API | Пример v1 → v2 на одном эндпоинте | Ф5 |
| Prometheus, Grafana, Loki, OpenTelemetry | Метрики, логи, сквозная трассировка заказа. Сквозной correlation-id закладываем в каркасе | Ф3 (id), Ф6 |
| Kubernetes (k3s) + Helm | Деплой на арендованный сервер | Ф6 |
| OpenSearch | Поиск по каталогу вместо PostgreSQL FTS | Ф6 |
| Тесты | Testcontainers (в CI), Postman/Newman, k6 (на сервере) | Ф4–Ф6 |

### Уровень 3. Только в ADR

SOAP-мок, RabbitMQ, Camunda и Temporal в реализацию не входят: для них нет естественной задачи в нашем домене. Они описаны в ADR как рассмотренные и отклонённые альтернативы (Camunda и Temporal в ADR про Saga, RabbitMQ в ADR про гарантированную доставку, SOAP в ADR про интеграцию с платёжным шлюзом).

## 6. Фазы и шаги

Часы в заголовках фаз приблизительные.

### Ф0. Подготовка (6–10 ч)

Пошаговая инструкция: `docs/00-phase0-guide.md`.

- Аккаунт GitHub с двухфакторной защитой, GitHub Desktop
- Репозиторий `digital-goods-marketplace` (публичный, с README и лицензией MIT), клон в локальную папку, тестовый commit и push
- Проверка виртуализации и свободного места на диске (не менее 40 ГБ)
- WSL2 с Ubuntu и ограничением памяти через `.wslconfig`
- Docker Desktop, проверка `docker run hello-world`
- VS Code с расширениями для Markdown, Mermaid, YAML и Docker
- Проверка редактора BPMN (bpmn.io)
- Скелет репозитория: папки `docs/`, README-навигатор, шаблоны (ADR, user story, use case, тест-кейс), требования v1.5, этот план
- Commit и push скелета

**Веха M0:** репозиторий готов, окружение работает.

### Ф1. Аналитика (25–35 ч)

Пошаговая инструкция: `docs/00-phase1-guide.md`.

Порядок важен: каждый следующий артефакт опирается на предыдущие.

**1. Видение, стейкхолдеры, глоссарий** (`01-vision/`)
- Документ «Видение и границы» (по разделу 1 требований)
- Стейкхолдеры и их интересы
- Глоссарий: заказ, резерв, платёжная сессия, выдача, доставка, поздняя оплата, автовозврат, пул ключей, снимок адреса

**2. Бизнес-процессы BPMN** (`03-processes/`)
- BPMN-01 Покупка: резерв → оплата → выдача, поздняя оплата, автовозврат
- BPMN-02 Подключение продавца
- BPMN-03 Модерация товара
- BPMN-04 Обращение в поддержку: повторная отправка и смена e-mail. Здесь закрыты три открытых вопроса из приложения C требований v1.4, решения вошли в v1.5 (FT-1.7, FT-7.5)
- BPMN-05 Спор (R2)
- BPMN-06 Вывод средств (R2)
- BPMN-07 Смена номера телефона (R2)

**3. Статусные модели с матрицами переходов** (`03-processes/`)
- SM-01 Заказ (включая переход «отменён → оплачен» при успешном перерезервировании и статус «возвращён»)
- SM-02 Платёж, SM-03 Ключ, SM-04 Товар, SM-05 Профиль продавца
- SM-06 Выдача, SM-07 Обращение в поддержку, SM-08 Резерв
- SM-09 Спор, SM-10 Заявка на вывод, SM-11 Операция по балансу (R2)

**4. User stories с критериями приёмки** (`02-requirements/`)
- R1 детально, критерии в формате «Дано / Когда / Тогда»
- R2 и R3 укрупнённо, детализируем перед соответствующей фазой
- Эпики: учётные записи, продавцы, каталог, ключи, заказ и оплата, выдача и доставка, поддержка, администрирование и аудит; R2: споры и возвраты, финансы, API продавца; R3: комиссия и отчёты

**5. Use cases** (`02-requirements/`)
- UC-01 Покупка цифрового товара
- UC-02 Подача заявки продавца и модерация
- UC-03 Выдача ключа и гарантированная доставка
- UC-04 Обращение в поддержку, повторная отправка, смена e-mail
- UC-05 Поздняя оплата и автовозврат

**6. Домен и данные** (`04-domain/`)
- Доменная модель и bounded contexts
- Логическая ER-диаграмма

**7. Контроль качества требований**
- Методика проверки NFR: как и на чём измеряем каждое NFT (например, NFT-2.0 и NFT-2.2)
- Матрица трассировки v1 (`08-testing/traceability.md`)

**Веха M1:** аналитическая база R1 готова. Итоги: `docs/00-phase1-report.md`.

### Ф2. Архитектура и контракты (20–30 ч)

Пошаговая инструкция: `docs/00-phase2-guide.md`. Архитектурные схемы рисуются в нотации C4 (Mermaid). Каждый шаг заканчивается проверкой, commit и отправкой на GitHub.

**1. Нотация C4 и диаграмма контекста** (`05-architecture/`)
- Правила рисования, диаграмма уровня 1 для R1 и расширения R2

**2. Декомпозиция на сервисы и диаграмма контейнеров**
- Укрупнение для R1: предварительно 5–6 прикладных контейнеров, границы контекстов сохраняются в коде и схемах данных (ADR-002)

**3–5. ADR по списку из раздела 8 (фаза Ф2)**
- Взаимодействие сервисов: 003, 004, 005, 006, 011, 015
- Целостность и данные: 007, 008, 009, 012, 013, 014
- Идентификация и безопасность: 010, 021, 022. Решение по SMS-подтверждению телефона (свой SPI в Keycloak или модуль в сервисе уведомлений) фиксируем в ADR-010 до начала Ф3

**6. Диаграммы компонентов C4** ключевых сервисов (заказы, остатки и ключи, выдача, платежи)

**7. Sequence-диаграммы SEQ-01…SEQ-06:** покупка (успешный путь), поздняя оплата, повторы доставки и DLQ, смена e-mail через поддержку, подтверждение телефона и вход по SMS, одобрение продавца

**8. Диаграмма развёртывания C4, бюджеты времени и памяти**
- Платёжная сессия 12 мин, резерв 15 мин, 60 с до передачи письма, 30 мин до доставки, повторы и задержки
- Профили Compose под лимит памяти среды разработки

**9. Матрица ролей и прав, модель угроз**

**10. Сквозные соглашения и AsyncAPI** (события R1 и схемы)

**11. OpenAPI для R1** (каталог, заказы, продавец, модерация, поддержка, администрирование)

**12. Физические модели БД по сервисам:** индексы, уникальные ограничения (в том числе «товар + HMAC ключа»), таблицы outbox и обработанных событий

**13. Стратегия тестирования**

**14. Матрица трассировки v2** (добавлены API и события), итоговый отчёт

**Веха M2:** можно писать код без догадок. Итоги: `docs/00-phase2-report.md`.

### Ф3. Каркас (15–25 ч)

- Docker Compose с профилями: `infra`, `core`, `ui`, `stubs`, `obs`
- PostgreSQL: один сервер, отдельная база на сервис, миграции Flyway
- Kafka (один брокер), Redis, MinIO
- Keycloak: realm с ролями, 2FA для сотрудников и продавцов, эмуляция VK ID, подтверждение телефона по решению ADR-010
- API Gateway: проверка JWT, ограничение частоты запросов
- Шаблон сервиса: health, метрики, миграции, outbox, сквозной correlation-id в логах
- Контейнер заглушек внешних систем (платёж, e-mail, SMS, VK ID, банк)
- CI в GitHub Actions: сборка, unit-тесты, интеграционные тесты, публикация образов
- Замер потребления памяти каждым контейнером и таблица лимитов (`09-operations/memory-budget.md`)
- Фиксация версий Java, Spring Boot, Docker и остальных компонентов после проверки актуальных релизов

**Веха M3:** всё поднимается одной командой, тестовый запрос проходит через gateway с токеном, CI зелёный.

### Ф4. Реализация R1 (50–70 ч)

Три вертикальных среза. Каждый заканчивается работающим сценарием и тестами.

**Срез 1. Продавцы, товары, ключи**
- Регистрация, вход, подтверждение телефона (FT-1.0–FT-1.5), вход по коду из SMS при потере доступа к e-mail (FT-1.7)
- Заявка продавца и модерация (FT-2.0–FT-2.2), повторная подача заявки после отказа (FT-2.4)
- Товары, статусы, модерация (FT-3.0–FT-3.2)
- Пул ключей: ручная загрузка и CSV, шифрование, HMAC против дублей (FT-4.0–FT-4.4)
- Каталог: поиск и фильтры на PostgreSQL FTS (FT-3.3, FT-3.4)
- Экраны: каталог, продавец, модератор

**Срез 2. Заказ, оплата, выдача**
- Оформление заказа, резерв ключей с `SKIP LOCKED`, Redis-таймер и сверяющая задача (FT-5.0–FT-5.3)
- Оплата через заглушку шлюза, идемпотентная обработка уведомлений (FT-6.0–FT-6.3)
- Saga и Transactional Outbox
- Выдача ключа, письмо через заглушку, отслеживание статуса доставки (FT-7.0, FT-7.1, FT-7.3)
- Повторы с нарастающей задержкой, DLQ, передача в поддержку, оповещение администратора (NFT-2.4)
- Поздняя оплата: перерезервирование или автовозврат (FT-6.4, FT-6.5)
- Экраны: оформление заказа, статус заказа, история заказов (FT-5.4)

**Срез 3. Поддержка, аудит, администрирование**
- Определить состав интерфейса администратора: в R1 экран «Параметры и журнал аудита», экран выводов в R2, остальное через Swagger и консоль Keycloak
- Обращение из кабинета, кнопка «Не получил ключ» (FT-7.2)
- Повторная отправка, смена e-mail с кодом, который вводит покупатель (FT-7.5)
- Очередь поддержки на отдельной модели чтения (упрощённый CQRS)
- Журнал аудита без персональных данных (FT-11.2, NFT-5.3)
- Уведомления покупателю (FT-11.0) и продавцу о решениях платформы по заявке и товару (FT-11.4, часть R1), параметры администратора (FT-11.1), базовая комиссия (FT-9.0)
- Экраны: оператор поддержки, параметры и журнал аудита

**Тесты и документы фазы**
- Unit и интеграционные тесты (Testcontainers) в CI
- Набор API-тестов в Postman, прогон через Newman
- k6: двойная выдача (параллельная покупка последнего ключа), NFT-1.0–NFT-1.2
- Тест-кейсы по user stories R1 (`08-testing/`)
- Отчёт по трассировке, сверка «документы = код»
- Решение об аренде сервера для полных прогонов и нагрузочных тестов (провайдер, конфигурация, бюджет) по результатам замеров памяти из Ф3
- Сценарий демо: от каталога до ключа на почте, плюс поздняя оплата и сбой доставки

**Веха M4:** демо R1.

### Ф5. Релиз R2 (40–60 ч)

Для каждого блока повторяем цикл: уточнить аналитику, обновить контракты, написать код, написать тесты.

- API продавца: выпуск и отзыв API-ключа, загрузка пулов, список заказов, webhook (FT-10.0–FT-10.3)
- Выдача по запросу к API продавца, тайм-аут 10 минут, отмена и возврат (FT-7.4)
- Остаток API-товаров с оптимистичной блокировкой (FT-4.3)

## 9. Критерии готовности артефактов

| Артефакт | Считается готовым, когда |
| --- | --- |
| BPMN | Есть основной и исключительные пути, указаны требования, которые процесс реализует |
| Статусная модель | Есть матрица переходов «из → в → условие → кто или что инициирует», недопустимые переходы перечислены |
| User story | Есть роль, цель, ценность и критерии «Дано / Когда / Тогда», ссылка на FT |
| ADR | Есть контекст, минимум две альтернативы, решение, последствия, условие пересмотра |
| Диаграмма C4 | Один уровень абстракции, у элементов технология и назначение, у связей глагол и протокол, диаграмма отрисована без ошибок, под ней таблица элементов |
| Sequence-диаграмма | Участники совпадают с контейнерами C4, исключения процессов отмечены, переходы статусов совпадают с SM |
| OpenAPI и AsyncAPI | Проходят проверку линтером, у каждой операции есть примеры и описание ошибок |
| Тест-кейс | Привязан к user story и требованию, есть шаги и ожидаемый результат |
| Веха | Шаги фазы выполнены, матрица трассировки без пустых клеток, демо воспроизводится с нуля |
