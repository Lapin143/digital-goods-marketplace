## 3. Принятые решения

### 3.1. Три вопроса из приложения C требований v1.4

Все три закрыты в [BPMN-04](03-processes/BPMN-04-support-request.md), приложение C в v1.5 пустое.

| Вопрос | Решение | Влияние на требования |
| --- | --- | --- |
| Как покупателю попасть в кабинет без доступа к e-mail | Вход по одноразовому коду из SMS на подтверждённый телефон. Сессия даёт доступ только к заказам и обращениям, пароль и данные учётной записи менять нельзя. Остаточный риск подмены SIM-карты принят и войдёт в модель угроз Ф2 | Новое FT-1.7 (R1) |
| Подтверждать ли новый e-mail при смене через поддержку | Да, кодом на новый адрес, код вводит покупатель. Это защита и от опечатки, и от ключа, ушедшего постороннему | FT-7.5 дополнено вторым подтверждением |
| Утрачены и e-mail, и телефон | В MVP не поддерживается: третьего подтверждённого канала нет | Ограничение уже стояло в разделе 1.3 |

### 3.2. Правки требований в v1.5

Версия 1.5 выпущена один раз, после неё требования не менялись. Изменения относительно v1.4:

- **Новые требования:** FT-1.7, FT-2.4, FT-8.5, FT-8.6, FT-9.5, FT-11.4.
- **Изменённые требования:** FT-1.5, FT-1.6, FT-2.1, FT-2.3, FT-3.2, FT-6.4, FT-6.5, FT-7.5, FT-8.1, FT-8.2, FT-8.4, FT-9.2, FT-9.3, FT-11.1, FT-11.2, NFT-3.5.
- **Раздел 6.1:** добавлена сущность «Резерв» (активен, использован, снят) и статусная модель операции по балансу SM-11.
- **Содержательные решения:** номер телефона уникален; после отказа можно подать заявку заново через 24 часа; «на доработке» не закрывается автоматически; частичной выдачи при поздней оплате нет; при возврате комиссия не взимается; срок ответа продавца по спору не ограничен, на заказ один спор; просрочка модерации ведёт к оповещению, а не к автоматическому решению.

### 3.3. Правила, которые действуют сразу в нескольких процессах и моделях

| Правило | Где действует | Почему так |
| --- | --- | --- |
| Просрочка срока (заявка продавца, товар, спор, заявка на вывод) даёт оповещение администратору и метрику, но не автоматическое решение | BPMN-02, 03, 05, 06, NFT-6.1 | Цель BG-05 требует проверки человеком. Автоматическое решение по спору отдало бы деньги одной стороне без проверки |
| Частичной выдачи и частичного возврата нет: заказ выдаётся или возвращается целиком | SM-01, SM-02, SM-03, FT-6.5, FT-8.4 | Иначе усложняются возврат, комиссия и статусы заказа |
| Комиссия при возврате не взимается, начисление и комиссия сторнируются целиком | SM-11, FT-9.5 | Платформа не зарабатывает на возврате. Комиссия это отдельная операция со знаком минус, поэтому сторнирование простое |
| Ключ после возврата остаётся «выдан» и в оборот не возвращается | SM-03, FT-7.1, NFT-2.2 | Ключ мог дойти до покупателя |
| Заказ «выдан», когда письмо принято провайдером. «Доставлено» это отдельный статус выдачи, по нему считается цель BG-01 | SM-01, SM-06 | Измеримая цель привязана к факту доставки, а не отправки |
| Сбой шлюза при открытии платёжной сессии откатывает заказ: резерв снимается, заказ «отменён» | SM-01/T12, SM-08/T6, BPMN-01 | Пробел нашёлся при написании историй, это сага с компенсацией |
| Одно открытое обращение на заказ. Закрывает его подтверждённая доставка, а не оператор | SM-07, SM-06, BPMN-04 | Нет дублей в очереди, нельзя «закрыть без отправки» и оставить покупателя без ключа |
| Каждая ручная повторная отправка это новая выдача типа «повторная» | SM-06 | История доставки по заказу сохраняется целиком |
| Реквизиты вывода сохраняются снимком, сумма резервируется при создании заявки | BPMN-06, SM-10, SM-11 | Защита от подмены получателя и от двух заявок на одни деньги |
| Деньги заморожены по трём причинам: удержание, спор, резерв под вывод. Причина хранится атрибутом | SM-11, BPMN-05 | После решения спора нужно знать, куда вернуть деньги |
| Один спор на заказ навсегда. Срок 24 часа считается с открытия и начинается заново, если спор вернулся модератору | BPMN-05, SM-09, FT-8.5 | Простое измерение срока, защита от повторных споров |
| Заблокированный продавец: входит и отвечает на споры, заказы доводятся, создание товаров и вывод закрыты, деньги копятся | SM-05, SM-04, SM-10, FT-2.3 | Открытые обязательства перед покупателями выполняются |
| Ответы регистрации, восстановления и входа по SMS не раскрывают, существует ли учётная запись. То же для занятого телефона и e-mail | US-1, US-7, BPMN-07 | Нельзя перебрать адреса и номера |
| Журнал аудита пишется до действия и наполняется через Outbox в одной транзакции с действием | BPMN-04, US-8.6 | Действия без записи в журнале не бывает |

### 3.4. Решения по историям и use cases

- Роль «Заявитель» не вводилась: заявитель на статус продавца это покупатель. Для автоматических действий используется роль «Система».
- Роль «Продавец» вручную не назначается, только по одобрению профиля. Иначе администратор обошёл бы модерацию.
- Последнего активного администратора нельзя лишить роли или деактивировать.
- Продавец ключи не удаляет, только добавляет. Размеры загрузки: ключ до 1 КБ, пул до 100 000.
- Письмо о смене e-mail по обращению уходит на оба адреса.
- Требования без пользовательского сценария (восстановление, масштабирование, язык интерфейса) оформлены историями US-8.10, US-8.11, US-8.12 со своими сценариями.
- Новых идентификаторов FT и NFT не вводилось, все истории ссылаются на ID из v1.5.
- Use cases разрезают BPMN-01 на три сценария: UC-01 (шаги 1–7), UC-03 (шаги 8–11), UC-05 (исключения поздней оплаты). UC-02 покрывает BPMN-02, UC-04 покрывает BPMN-04.

### 3.5. Решения по домену

Полный список с обоснованиями в разделе 7 [доменной модели](04-domain/domain-model.md), особые случаи границ в разделе 6 [bounded contexts](04-domain/bounded-contexts.md).

| Решение | Суть |
| --- | --- |
| Один владелец у каждой сущности | Если сущность меняют два контекста, границы проведены неверно: изменение идёт командой или событием владельцу |
| Остаток для выдачи по API принадлежит «Остаткам и ключам» | Введена сущность «Остаток по API». В «Каталог» значение приходит событием для витрины |
| Роль «Продавец» назначает «Идентификация» по событию «профиль одобрен» | Сущность «Пользователь» меняет только её владелец |
| SellerID это ID профиля продавца, BuyerID это ID пользователя | Данные продаж и денег отделены от учётной записи с персональными данными |
| API-ключ продавца принадлежит «Подключению продавцов» | Ключ связан со статусом продавца. Шлюз проверяет его запросом с кэшем в Redis |
| Снимки данных разрешены в пяти местах | Цена и комиссия в заказе, адрес в заказе и выдаче, реквизиты вывода, срок резерва. Адрес меняется только повторной отправкой: «Поддержка» командует «Заказам», «Заказы» публикуют событие, «Выдача» создаёт повторную выдачу |
| Письма с ключами отправляет «Выдача» напрямую провайдеру | Открытое значение ключа видит только она, через Kafka и «Уведомления» ключ не идёт (NFT-3.2) |
| Одноразовые коды принадлежат «Уведомлениям» | Окончательный выбор между собственным модулем и расширением Keycloak это ADR-010 в Ф2 |
| Резерв это отдельная сущность, на заказ их может быть несколько | Резерв кончается раньше заказа, поздняя оплата создаёт новый |
| Комиссия фиксируется в заказе при создании | Смена параметра не меняет созданные заказы. В R3 ставка зависит от месячного оборота |
| Движения по деньгам продавца только добавляются | Статус операции меняется записью журнала |
| 44 инварианта INV-01…INV-44 | Основа для тест-кейсов Ф4. Для них добавлен новый вид идентификатора INV-NN, он записан в таблице идентификаторов плана |

### 3.6. Решения по проверке NFR и трассировке

- **Окружения проверки:** локально, CI (Testcontainers, Newman) и арендованный сервер. Нагрузочные тесты k6 идут на сервере, потому что на компьютере с 8 ГБ памяти полные прогоны нельзя.
- **Четыре требования нельзя доказать на учебном стенде в полном виде:** доступность 99,5% в месяц (NFT-4.0), RPO и RTO (NFT-4.1), хранение в РФ (NFT-5.0), доставка за 30 минут у реального провайдера (NFT-2.1). Для каждого в методике записаны честная замена и то, что в портфолио можно утверждать.
- **Матрица трассировки** показывает идентификаторы без ссылок, чтобы её было удобно искать и сравнивать по версиям. Прочерк «–» всегда сопровождается причиной. Строки R2 и R3 включены, но проверка «нет пустых клеток» относится только к R1.
- **NFT-3.4 (API-ключи продавцов)** по историям относится к R2 и вынесен в раздел R2. Остальные 28 NFT входят в раздел R1.
