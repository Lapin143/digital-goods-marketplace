# 07. Физические модели данных

Схема базы данных каждого сервиса R1: таблицы, типы, ограничения, индексы с обоснованием запросом, триггеры, права ролей. SQL проверен прогоном с нуля на PostgreSQL 16, поведение проверено тестами на данных (в том числе с параллельными транзакциями), каждый запрос из ответственных историй проверен через `EXPLAIN`.

Логическая модель, из которой выведены таблицы, лежит в [04-domain](../04-domain/README.md), правила именования и типов в [conventions.md](../05-architecture/conventions.md), границы сервисов в [decomposition.md](../05-architecture/decomposition.md).

В R1 шесть баз по числу сервисов (правило «одна база на сервис», [ADR-002](../05-architecture/adr/ADR-002-microservices-consolidation.md)). Внутри `platform_db` четыре схемы по модулям (`identity`, `support`, `notification`, `audit_admin`), в `catalog_db` две (`seller_onboarding`, `catalog`). Один модуль владеет одной схемой и работает под своей ролью базы, чужая схема для этой роли недоступна. Всего таблиц предметной области 25, служебных (`outbox`, `processed_event`, `idempotency_key`) по три в каждой базе.

## 2. Как запустить и проверить

Нужен PostgreSQL 16. SQL запускается с остановкой на первой ошибке:

```bash
createdb catalog_db
psql -v ON_ERROR_STOP=1 -q -d catalog_db -f docs/07-data/ddl/catalog-service.sql
```

Миграции в рабочем проекте ведёт Flyway, по одной папке на модуль в `services/<сервис>/src/main/resources/db/migration/`. Их создаёт `tools/docs-checks/db/gen_migrations.py` из тех же частей, из которых `build.py` собирает DDL: служебные таблицы и функция контроля статусов одинаковы во всех шести базах и лежат в одной части (`V1`), затем по миграции на схему модуля, последней идут роли и права. Склейка миграций равна файлу `ddl/<сервис>.sql` по SHA-256, расхождение находит `gen_migrations.py --check`. Подробности: [services/README.md](../../services/README.md), базы и роли PostgreSQL: [infra/postgres/README.md](../../infra/postgres/README.md).

Скрипты проверки лежат в `tools/docs-checks/`:

| Скрипт | Что проверяет |
| --- | --- |
| `db/apply.sh` | Создаёт базы с нуля и применяет миграции Flyway по возрастанию версии (ключ `DB_SOURCE=ddl` берёт DDL одним файлом), любая ошибка останавливает прогон |
| `db/test_db.py` | 39 тестов на данных: гонки, уникальность, переходы статусов, неизменяемость, права ролей |
| `db/check_datamodel.py` | Сверка с документами: атрибуты ER и столбцы, соглашения по именам и типам, переходы SM, комментарии, таблица инвариантов |
| `db/check_explain.py` | `EXPLAIN` запросов историй на реалистичных объёмах: нужный индекс и нет полного просмотра больших таблиц |
| `db/gen_schema_docs.py` | Собирает `<service>-schema.md` из живого каталога базы |

## 3. Решения по физической модели

1. **Типы и имена по conventions.** Идентификаторы `uuid` (UUIDv7 создаёт приложение, идентификатор пользователя это `sub` из Keycloak), деньги `bigint` в копейках плюс `currency char(3)` с проверкой «RUB», время `timestamptz`, таблицы в единственном числе в `snake_case` (исключение `orders`, потому что `order` зарезервированное слово). Префиксы ограничений: `pk_`, `uq_`, `fk_`, `ck_`, индексов `ix_`.
2. **Статусы это коды, а допустимые переходы проверяет база.** Столбец `status` ограничен списком из conventions 7.2, а триггер `public.enforce_status_transition()` разрешает только переходы R1 из диаграмм SM. Переходы R2 (блокировка продавца, возврат после выдачи, замена ключа) добавят миграции R2. Так нарушение недопустимого перехода не зависит от аккуратности кода и видно сразу: ошибка `23514` с именем `ck_<таблица>_status_transition`.
3. **Между сервисами и между модулями внешних ключей нет.** Связи между границами это идентификаторы без ограничений (раздел 6). Внутри схемы внешние ключи есть. Скрипт проверки падает, если внешний ключ ведёт в чужую схему.
4. **Что можно проверить арифметикой, проверяется в базе.** Сумма заказа равна цене на количество, комиссия равна `(сумма × ставка + 5000) / 10000` с округлением половины вверх (`ck_orders_commission`, расчёт в `numeric` через `div()`, чтобы не получить переполнение `bigint`). Поэтому в заказе хранится ставка в базисных пунктах, а не только сумма комиссии.
5. **Данные, которые нельзя менять, защищены триггерами.** Снимки заказа, привязка ключа, журнал аудита. Роль приложения для ключей не имеет права `DELETE`, роль записи аудита не имеет `UPDATE`, `DELETE`, `TRUNCATE`.
6. **Ключи не хранятся открытым текстом.** В таблице `inventory.key` лежат шифртекст AES-256-GCM (`ciphertext`, `nonce`), ссылка на версию ключа данных (`dek_id`) и HMAC для поиска дублей. Ключ данных хранится в `inventory.data_key` в зашифрованном виде, мастер-ключ в базе отсутствует ([ADR-009](../05-architecture/adr/ADR-009-key-encryption-hmac.md)).
7. **Очереди строятся на частичных индексах.** Выборка работы (неотправленные события, выдачи к отправке, возвраты к исполнению, просроченные заказы) идёт по индексу `where` только по строкам в нужном состоянии. Индекс не растёт вместе с историей. Исполнители берут строки через `FOR UPDATE SKIP LOCKED` короткой транзакцией, сетевые вызовы вне транзакции ([ADR-007](../05-architecture/adr/ADR-007-double-issue-protection.md), [ADR-011](../05-architecture/adr/ADR-011-guaranteed-delivery.md), [ADR-013](../05-architecture/adr/ADR-013-late-payment.md), [ADR-015](../05-architecture/adr/ADR-015-payment-gateway-integration.md)).
8. **Журнал аудита разбит по месяцам.** Таблица `audit_admin.audit_log` секционирована по `occurred_at`, секции создаёт функция `create_audit_log_partition(date)` миграцией и ежемесячным заданием на три месяца вперёд, строки не попадают «в никуда» благодаря секции по умолчанию. Записи не удаляются автоматически, срок хранения не менее 3 лет, политика настраивается ([ADR-014](../05-architecture/adr/ADR-014-audit-log-no-pii.md), раздел «Хранение и удаление» в [требованиях](../02-requirements/requirements_v1.5.md)): по истечении срока секцию отключают и переносят в архивное хранилище целиком, строки не удаляются.
9. **Одноразовые коды входа в базе не хранятся.** Коды подтверждения телефона, счётчики запросов и блокировки по числу попыток живут в Redis с временем жизни ([ADR-010](../05-architecture/adr/ADR-010-keycloak-sms-codes.md)). В базе остаётся только признак подтверждения телефона и признак «передан в Keycloak».

## 4. Служебные таблицы в каждой базе

| Таблица | Назначение | Хранение |
| --- | --- | --- |
| `public.outbox` | Исходящие события пишутся в одной транзакции с изменением данных, публикатор читает пачку по возрастанию `id`, неудачные строки паркуются в `failed_at` ([ADR-005](../05-architecture/adr/ADR-005-transactional-outbox.md)) | Отправленные 3 суток |
| `public.processed_event` | Пары «потребитель, `event_id`», защита от повторной доставки (уровень 2 идемпотентности, [ADR-006](../05-architecture/adr/ADR-006-idempotency.md)) | 14 суток |
| `public.idempotency_key` | Ключи идемпотентности HTTP-запросов, хеш тела запроса и сохранённый ответ (уровень 1) | 24 часа |

Третий уровень идемпотентности это естественные ключи предметных таблиц: `uq_payment_order_id`, `pk_payment_event`, `uq_delivery_order_id_primary` и аналоги, они перечислены в таблице инвариантов.

## 5. Таблица инвариантов

Колонка «Способ» принимает значения из списка: «ограничение в базе», «транзакция», «проверка в коде», «событие». В колонке «Как обеспечено» имена в обратных кавычках это реальные ограничения, индексы и триггеры, скрипт проверки находит каждое имя в базах и падает, если его нет. Инварианты R2 (споры, баланс продавцов, API-ключи) помечены «R2.»: таблиц для них в R1 нет, способ записан как проектное решение для миграций R2.

Тесты инвариантов на данных названы в [test_db.py](../../tools/docs-checks/db/test_db.py) полем «инвариант» у каждого теста.

### 5.1. Ключи, остатки и резерв

| ID | Инвариант | Способ | Как обеспечено |
| --- | --- | --- | --- |
| INV-01 | Один ключ принадлежит не более чем одному заказу, в том числе при одновременных заказах | транзакция, ограничение в базе | Резерв выбирает свободные ключи запросом `FOR UPDATE SKIP LOCKED` по индексу `ix_key_product_id_free`, одновременные заказы берут разные строки. Привязка ключа к заказу и резерву идёт в той же транзакции. Перепривязка занятого ключа запрещена триггером `trg_key_immutable` (ошибка `ck_key_rebind`), условное обновление `where status = 'free'` второй рубеж на случай ошибки кода. Тест: 10 заказов на последний ключ дают одну выдачу |
| INV-02 | Ключ в статусах «зарезервирован» и «выдан» всегда привязан к заказу, свободный ключ не привязан ни к какому | ограничение в базе | `ck_key_binding`: у свободного ключа `order_id` и `reservation_id` пусты, у зарезервированного и выданного оба заполнены. `ck_key_issued_at` связывает «выдан» с датой выдачи |
| INV-03 | Значения ключей уникальны в пределах товара | ограничение в базе | `uq_key_product_id_hmac`: уникальность пары «товар, HMAC значения», открытое значение для сравнения не нужно. Пакетная загрузка использует `ON CONFLICT DO NOTHING` и считает дубли по результату |
| INV-04 | Выданный ключ не возвращается в «свободен», ключ «аннулирован» не используется снова | ограничение в базе | `trg_key_status_transition` разрешает только `free>reserved`, `reserved>free`, `reserved>issued`. «Аннулирован» появляется в R2 вместе с переходом `issued>voided` |
| INV-05 | Резерв охватывает всё заказанное количество, частичного резерва нет. Заказ получает все ключи или отменяется | транзакция, проверка в коде | Резерв и привязка всех ключей создаются одной транзакцией: либо `quantity` ключей, либо откат и ответ «нет остатка». `ck_reservation_quantity` ограничивает число 1…10 |
| INV-06 | У заказа в любой момент не больше одного резерва в статусе «активен» | ограничение в базе | Частичный уникальный индекс `uq_reservation_order_id_active` по `order_id` где `status = 'active'`. Поздняя оплата создаёт новый резерв только после снятия прежнего. Порядок в транзакции: сначала вставка резерва, затем привязка ключей |
| INV-07 | Срок платёжной сессии строго короче срока резерва | ограничение в базе, проверка в коде | В заказе `ck_orders_deadlines` (оба срока задаются вместе, сессия раньше резерва). В параметрах платформы `trg_platform_parameter_session_vs_reserve` с консультативной блокировкой не даёт правкой двух параметров одновременно нарушить соотношение. Заказ при создании берёт срок сессии из параметров |
| INV-08 | Остаток по API не отрицателен, уменьшение при резерве атомарно, правка продавца применяется только при совпадении версии | транзакция | R2. Остаток по API ведёт условное обновление `quantity = quantity - n where quantity >= n` и проверка версии записи. Таблица появится миграцией R2 |
| INV-09 | Товар с нулевым остатком недоступен для оформления заказа | ограничение в базе, транзакция, событие | Источник истины число свободных ключей в `inventory`, резерв при нехватке даёт отказ. Витрина читает копию `catalog.stock_view`, в которой `in_stock` вычисляется столбцом, а `ck_stock_view_available` запрещает отрицательное значение. Копию обновляет событие `stock.changed` |

### 5.2. Заказ, платёж и выдача

| ID | Инвариант | Способ | Как обеспечено |
| --- | --- | --- | --- |
| INV-10 | Количество в заказе от 1 до 10 | ограничение в базе | `ck_orders_quantity`, те же границы в копиях `ck_delivery_quantity` и `ck_reservation_quantity`. Заказ с другим числом отклоняется и в API с кодом 422 |

| INV-12 | Сумма заказа равна цене, умноженной на количество. Цена это снимок на момент оформления | ограничение в базе | `ck_orders_amount` (сумма равна цене на количество), `ck_orders_unit_price`, снимок защищён триггером `trg_orders_immutable` (ошибка `ck_orders_snapshot_immutable`) |

Тест: 149,99 ₽ при 2% даёт 300 копеек |
| INV-14 | Платёж меняет статус только по ответу или уведомлению шлюза, либо по отметке администратора о ручном возврате. Повторное уведомление ничего не меняет | ограничение в базе, транзакция | `pk_payment_event` по паре «внешний платёж, тип события»: повторная вставка нарушает ключ, поэтому второй раз статус не меняется. Переходы стережёт `trg_payment_status_transition`, подтверждённый платёж обязан иметь внешний идентификатор (`ck_payment_confirmed`). Неопознанные уведомления лежат в `uq_unmatched_notification_payment_event` без дублей |
| INV-15 | Возврат полный и единственный на платёж, повторный запрос возврата не создаёт второй возврат | ограничение в базе | `uq_payment_gateway_refund_id` (один внешний идентификатор возврата), `uq_refund_attempt_payment_id_succeeded` (одна принятая шлюзом попытка), `uq_refund_attempt_payment_id_open` (одна открытая попытка), `ck_payment_refunded` (статус «возвращён» и дата согласованы, причина обязательна), `trg_refund_attempt_guard` не меняет завершённую попытку |
| INV-16 | Заказ «оплачен» только при платеже «подтверждён», «возвращён» только при платеже «возвращён» | событие, проверка в коде | Данные о платеже в базе заказов нет, внешнего ключа между базами нет. Заказ переходит по событиям `payment.confirmed` и `payment.refunded`, потребитель применяет переход через `trg_orders_status_transition` (в том числе `cancelled>paid` для поздней оплаты) и дедуплицирует событие в `pk_processed_event` |
| INV-17 | Заказ «выдан» только когда ключи привязаны и провайдер принял письмо. Первый переход в «выдан» один раз за жизнь заказа, от него считаются окна и удержание, повторная отправка их не сдвигает | событие, ограничение в базе | Заказ переходит в «выдан» по событию `delivery.accepted` (`paid>issued` в `trg_orders_status_transition`). `ck_orders_issued_at` требует дату выдачи, триггер `trg_orders_immutable` не даёт её изменить (ошибка `ck_orders_issued_at_once`) |
| INV-18 | Первичная выдача по заказу одна, повторное событие «заказ оплачен» второй не создаёт | ограничение в базе | `uq_delivery_order_id_primary` по заказу для первичной выдачи, `uq_delivery_order_id_queued` не допускает две выдачи в очереди на заказ, `pk_processed_event` отсекает повторную доставку события |
| INV-19 | В письме ровно столько ключей, сколько в заказе, и они отправляются на адрес из снимка заказа | проверка в коде, ограничение в базе | Выдача хранит копию количества и адреса (`ck_delivery_quantity`, `ck_delivery_address_len`), письмо формируется по копии. Число ключей в ответе «Остатков и ключей» код сверяет с количеством до отправки |
| INV-20 | Значения ключей не попадают в логи, события Kafka и базу «Выдачи» | ограничение в базе, проверка в коде | В базе «Выдачи» нет столбцов под значение, код ошибки отправки допускает только `^[a-z0-9_.-]{1,64}$` (`ck_delivery_last_error_code`, `ck_delivery_attempt_error_code`): произвольный текст со значением ключа записать нельзя. ## 6. Почему между сервисами нет внешних ключей

Внешний ключ возможен только внутри одной базы. Между сервисами он невозможен физически, а между модулями одной базы запрещён осознанно: правило модульности 2 в [decomposition.md](../05-architecture/decomposition.md), раздел 7.2. Иначе схемы сцепляются, модуль нельзя вынести в отдельный сервис без переписывания схемы, а миграция одного модуля блокирует другой.

Вместо ключа на чужую сущность хранится идентификатор без ограничения (`order_id` в платеже, `product_id` в заказе). Целостность поддерживают три механизма:

1. **События и копии для чтения.** Владелец публикует событие, потребитель держит копию нужных полей (`stock_view`, `product_copy`, `order_view`, копии в выдаче). Копия подчиняется владельцу и не правится независимо.
2. **Проверка при записи.** Сервис проверяет существование чужой сущности вызовом API или по копии до вставки (заказ запрашивает карточку товара у каталога, платёж создаётся по команде заказа).
3. **Сверка по расписанию.** Задания находят расхождения: резерв без заказа, платёж без заказа, заказ в ожидании без платёжной сессии. Они описаны в [time-budgets.md](../05-architecture/time-budgets.md) и [ADR-011](../05-architecture/adr/ADR-011-guaranteed-delivery.md).

Цена решения: висячие ссылки теоретически возможны и обнаруживаются сверкой, а не отказом базы. Выигрыш: независимое развёртывание, миграции и масштабирование каждого сервиса.

## 7. Уровни изоляции и когда хватает блокировки строки

Во всех сервисах уровень по умолчанию `READ COMMITTED`. Каждый оператор видит данные, зафиксированные к моменту его начала, а не к началу транзакции. Этого достаточно, если конкурирующие транзакции не должны читать «соседний» результат, а согласованность обеспечивается явными механизмами:

| Задача | Механизм | Почему не выше уровень |
| --- | --- | --- |
| Не выдать один ключ двум заказам | `SELECT ... FOR UPDATE SKIP LOCKED` по строкам ключей | Конкурент не ждёт и не падает, а берёт другие строки. На `SERIALIZABLE` вторая транзакция получала бы ошибку сериализации и повторяла запрос, пропускная способность резерва падала бы |
| Не создать второй резерв, платёж, выдачу, обращение | Уникальный (в том числе частичный) индекс | Индекс проверяет базу при каждой вставке независимо от уровня, гонка заканчивается нарушением ключа у проигравшего, код обрабатывает его как «уже есть» |
| Не допустить отрицательный остаток или баланс | `UPDATE ... WHERE quantity >= n` или блокировка строки и проверка внутри транзакции | Условие проверяется блокирующим чтением, а не снимком, поэтому «потерянное обновление» невозможно |
| Сохранить инвариант, который затрагивает несколько строк (последний администратор, срок сессии против срока резерва) | Консультативная блокировка транзакции `pg_advisory_xact_lock` внутри триггера | Проверка читает другие строки, при `READ COMMITTED` две транзакции увидели бы старое состояние друг друга. Блокировка сериализует только эти проверки, остальные операции не страдают |
| Исполнитель очереди (возвраты, выдачи, события) | Короткая транзакция «занять» с арендой в столбце срока, затем сетевой вызов вне транзакции, затем короткая транзакция «записать результат» | Долгая транзакция держала бы блокировку на время обращения к внешнему шлюзу |

`REPEATABLE READ` и `SERIALIZABLE` в R1 не нужны: все конкурентные места закрыты блокировкой строки, уникальным индексом или консультативной блокировкой, а повторные попытки при ошибке сериализации усложнили бы код. Если появится инвариант, который нельзя выразить этими механизмами (например, сумма по нескольким строкам не выше лимита), там `SERIALIZABLE` с обязательным повтором транзакции станет следующим шагом.

## 8. Индексы: зачем и как проверить

Индекс нужен запросам, которые читают малую часть большой таблицы, и ограничениям уникальности. Лишний индекс замедляет каждую вставку и обновление и занимает память. Поэтому у каждого индекса в базе есть комментарий с запросом истории, ради которого он создан (`comment on index`), а таблицы без запроса индекс не получают: в описаниях схем (`<service>-schema.md`) комментарии выводятся рядом с определением индекса. Индекс по внешнему ключу создаётся, только если по нему есть запрос или удаляются строки родителя.

Как убедиться, что запрос использует индекс: `EXPLAIN (ANALYZE, BUFFERS)` на данных реалистичного объёма. На пустой таблице планировщик выберет полный просмотр, поэтому проверка работает на загруженных данных (60 тысяч товаров, 200 тысяч ключей, 100 тысяч заказов и так далее) после `ANALYZE`. Скрипт `check_explain.py` выполняет 113 запросов историй и проверяет по плану в формате JSON: узел чтения содержит ожидаемый индекс, на таблицах больше 5000 строк нет `Seq Scan`, сортировка больше 2000 строк не нужна там, где порядок задаёт индекс. Обратная проверка: каждый индекс базы должен встретиться хотя бы в одном плане, иначе он лишний и удаляется. Вывод плана по каждому запросу приведён в [explain-report.md](explain-report.md).

Признаки проблемы в плане: `Seq Scan` по большой таблице, `Rows Removed by Filter` в тысячи строк, сортировка (`Sort`) там, где ожидался порядок из индекса, оценка числа строк далеко от фактической (нужен `ANALYZE` или расширенная статистика).
